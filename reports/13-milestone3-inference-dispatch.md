## §2. 🔴 `runner.py` 를 고치지 않고 `infer.py` 를 새로 만든 이유

토폴로지가 2026-08-11 에 바뀌었다(워커는 추론만, 통합자가 유일한 쓰기 주체). 기존 `runner.py`
는 워커가 커밋·push 하는 전제로 짜여 있어서 **고치면 구 경로가 사라진다.** 그런데
`docs/8-git-authority.md` §8.4 ⚠️ 가 이미 정해 뒀다 — *"N-writer 기계장치는 측정으로 뒤집힐
여지가 있는 동안 되돌릴 수 있게 둔다."*

그래서 **나란히** 뒀다:

| | 구 토폴로지 | 현 토폴로지 |
|---|---|---|
| 마스터 | `work/runner.py` | `work/infer.py` |
| 워커 스킬 | `ax-work` | **`ax-infer`** |
| 판정 마커 | `ATTEMPT`/`HEAD`/`RESULT` 세 줄 | `RESPONSE`/`RESULT` 두 줄 |
| 산출물 | attempt 브랜치 + 커밋 | **`response.txt` 텍스트** |

워커에는 스킬이 **둘** 배달되고(`SKILLS_BY_ROLE["worker"]`), **파견 지시가 이름으로 고른다** —
지시 첫 줄이 `Follow the ax-infer skill (INFERENCE ONLY, not ax-work)` 다.

⚠️ 판정 규약은 **재사용하되 요구는 안 물려받았다.** `runner.parse_result` 를 그대로 쓰면
`ATTEMPT`/`HEAD` 가 없다고 *"제출할 근거가 없다"* 를 사유로 적는데, 추론 파견에는 브랜치도
커밋도 **없는 것이 정상**이라 그 사유는 거짓말이 된다. 사람이 읽는 실패 사유가 틀리면 엉뚱한
곳을 조사한다 — `parse_markers` 를 따로 두고 **비대칭 관대함**(BLOCKED 쪽에만 관대)만 물려받았다.

## §3. 🔴 응답 채널은 stdout 이 아니라 **파일**이다

마스터→워커는 이미 *"지시는 ASCII, 내용은 파일로"* 다(한글이 콘솔에서 깨지고 18KB stdin 이 안
닫혀 멈췄던 두 건). **워커→마스터도 같은 이유로 같아야 한다:**

- `.2` 의 콘솔은 **CP949** 다. 리포트 12 §6.3 에서 층3 이 UBT 의 한국어 출력에서 **디코딩부터
  죽었다** — 판정 문자열은 ASCII 라 살아 있었는데 거기 도달하지 못했다. 응답 본문에는 한국어
  주석이 섞이므로 stdout 으로 받으면 **같은 자리에서 깨진다**
- `scp` 는 바이트를 그대로 옮긴다. 그리고 `_remote_read` 는 판정을 **rc 가 아니라 결과물의
  존재**로 하므로 *"모르는 것을 없음으로 접는"* 실패가 없다(그 함수가 값을 치르고 배운 것)

**실측**: 응답 1,728자 중 한국어 52자가 온전히 왕복했다. `// [DOC] 미션 태스크 — 카메라를 …`
가 글자 그대로 돌아왔다.

🔴 **판정은 두 근거를 다 본다.** 마커만 보면 *"DONE 이라 말하고 파일을 안 쓴 것"* 을, 파일만
보면 *"반쯤 쓰이다 죽은 것"* 을 통과시킨다.

## §4. 🔴 실전이 잡은 계약 구멍 — 단위 78건이 통과하는 동안

*"샌드박스는 거짓 자신감을 준다"* 가 이 저장소의 규칙이고(소 3.1.4 의 존재 이유), 골조 게이트도
**실제로 돌려서야** 층3 의 디코딩 버그가 나왔다. 이번에도 같았다.

### 4.1 마커를 **어디에** 내라는 말이 애매했다

지시문에 *"The last two non-empty lines of **your output** must be …"* 라고 썼다. 워커는
**응답 파일의** 마지막 두 줄로 읽었다 — 그리고 옳게 일한 뒤 stdout 에는 이렇게 냈다:

    Final two lines of the output file:
    ```
    RESPONSE: 2
    RESULT: DONE
    ```
    No source files were edited, and no git operations (branch/commit/push) were performed.

마지막 줄이 `RESULT:` 가 아니라 **BLOCKED**. 판정은 옳았지만 **일은 제대로 해 놓고 떨어졌다**
(그 45초와 $0.35 를 버렸다). 그리고 더 나쁜 것이 있었다 — 응답 **파일 끝에도** 그 두 줄이
들어가 있었다:

    void UMissionTask_SetCamera::Clear()
    {
        Super::Clear();
    }
    RESPONSE: 2
    RESULT: DONE

🔴 **마커 검사가 통과했다면 `parse_files` 가 그 두 줄을 마지막 파일 본문에 그대로 넣었을
것이다.** `.cpp` 끝에 `RESULT: DONE` 이 박힌다. 조치 둘 — **하나로는 부족하다**:

1. **지시와 스킬을 못박았다**: `PRINT to stdout, as the last two non-empty lines you print and
   nothing after them` + `That file must contain ONLY those blocks: do NOT write RESPONSE: or
   RESULT: into it`. 스킬 §7 에는 실측 사례를 그대로 적었다(*"마커를 인용하지 말고 마커로만
   끝낸다"*)
2. **파서가 막는다**: `strip_trailing_markers()` 가 **맨 끝의 연속된 마커 줄만** 떼고 **⚠️ 로
   보고**한다. 🔴 조용히 지우지 않는다(지시를 안 지킨 사실이 사라진다). 🔴 통째로 버리지도
   않는다(옳게 만든 본문까지 버리면 같은 추론을 다시 산다)

**고친 뒤 재구동: ✅ 45초 · $0.27 · 마커 정상.**

### 4.2 ⚠️ EOF 개행이 사라졌다 — 손대는 파일마다 잡음 diff

응답을 원본과 diff 해서야 나왔다. `.h` 의 마지막 빈 줄이 없어졌다:

    @@ -2,0 +3 @@
    +// [DOC] 미션 태스크 — 카메라를 지정 타일로 옮긴다. …    ← 요청한 변경
    @@ -24 +24,0 @@
    -                                                        ← 🔴 요청하지 않은 변경

`parse_files` 가 블록마다 `strip()` 을 하기 때문이다(펜스·마커 잔재를 떼려면 필요하다). 통합자가
이걸 적용하면 **손대는 파일마다 EOF 가 바뀌고** 리뷰와 blame 이 더러워진다.

**관례를 재서 골랐다** — `Source/ModularStage` 의 `.h`/`.cpp` 160개:

    개행 하나로 끝   110  (69%)   ← 지배적이고 git 관례이기도 하다
    개행 없이 끝      36
    끝에 빈 줄 있음   14

→ **개행 하나로 정규화**한다. ⚠️ **완전 보존은 불가능하다**(strip 이 정보를 이미 지웠다).
나머지 50개는 EOF 가 한 줄 바뀌지만, 이쪽이 잡음이 가장 적다. 재구동 diff 로 확인: `.h` 는
빈 줄 하나(14개 부류), `.cpp` 는 개행 추가(36개 부류) — **예측한 그대로**다.

## §5. 🔴 파견은 큐에 제출하지 않는다 — 그 대가를 스풀로 갚는다

`submit(branch, head_commit)` 은 **커밋이 있어야** 부를 수 있고, 그 커밋은 통합자가 빌드를
통과시킨 뒤에 생긴다(소 1.4.3). 그래서 추론이 끝나도 태스크는 `claimed` 로 남는다.

⚠️ **중 1.4 가 없는 동안 리스(1200초)는 만료되고 태스크는 재확보된다.** 숨기지 않고
`Handoff.summary()` 가 그렇게 말한다. 🔴 **다만 같은 추론을 두 번 사지는 않는다:**

    스풀에 같은 기준 커밋의 통과분이 있으면  →  파견하지 않고 재사용 (♻️)
    기준 커밋이 다르면                      →  🔴 재사용하지 않는다

두 번째 줄이 중요하다. 트윈이 움직였으면 근거가 달라진 것이고, **낡은 응답을 적용하면 통합자의
빌드가 남의 실패로 깨진다.** 그래서 스풀 레코드에 `base_commit` 을 박아 둔다.

🔴 **스풀이 곧 "어디까지 진행됐나" 다**(소 1.3.3). 그래서 `ProjectPaths.responses` 에 적어 뒀다 —
**파생물이 아니다.** 매니페스트는 지우면 재수집되지만 이것은 **돈을 낸 LLM 출력**이고, 통합자가
적용할 때까지 유일한 사본이다. 청소 대상에 넣으면 안 된다.

### 5.1 🔴 큐가 `failed` 를 의존 해소로 센다

`logic_claim.py` 를 읽다 발견했다:

    completed = {tid for tid, t in idx.tasks.items()
                 if t.get("status") in ("verified", "cancelled", "failed")}
    # failed 도 dependents 차단 X — 영원 block 방지

큐 입장에서는 맞다(실패 하나가 뒤를 영영 막으면 안 된다). 그런데 **뎁스 분할**에서는 다르다 —
`X.d1` 이 실패했는데 `X.d2` 를 추론하면 **헛일이 확실하다**(앞 단계 본문이 없다). 큐의 정책을
바꾸지 않고 **마스터가 이번 실행의 실패를 기억해** 후속을 파견하지 않고 반납한다.

## §6. 포팅 모드 — 🔴 문서의 "동명 9쌍" 을 재보고 넘어섰다

마일스톤 문서가 *"실측: `Project_Alpha` ↔ `ModularStage` 동명 9쌍"* 이라 적어 뒀다. 재보니
**맞았고**(파일 1,654개 중 9쌍), 동시에 **그것만으로는 절반도 못 잡는다**는 것이 드러났다:

    stem 그대로 같은 것                                          9쌍
    🔴 접두사 정규화(Alpha · Alpha_ · MS · ModularStage) 후      21쌍   ← 2.3배

포팅이 **개명을 거쳤기** 때문이다. 추가된 12쌍은 전부 진짜 대응이었다:

    AlphaTableEnum        ↔  TableEnum
    AlphaManager_Mission  ↔  Manager_Mission
    AlphaCharacter        ↔  ModularStageCharacter   ← 접두사가 양쪽에 다르게 붙는다
    Alpha_HexagonTileItem ↔  Alpha_HexagonTileItem   ← 그대로 옮긴 것은 접두사가 남아 있다

🔴 **퍼지 매칭은 넣지 않았다.** 접두사 정규화까지가 결정적으로 방어되는 선이고, 편집 거리 같은
것을 넣으면 **틀린 원본을 붙인다.** 그건 원본이 없는 것보다 나쁘다 — 관계없는 코드에서 의도를
읽으면 모델은 자신 있게 엉뚱한 것을 만든다. 대신 **매칭 규칙을 결과에 실어**(`exact` / `prefix`)
사람이 가늠하게 하고, 못 찾으면 **못 찾았다고 둔다**(`MSMissionTask` 는 아무것도 안 붙었다).

### 6.1 🔴 경로만 싣는다 — 골조 생성과 **반대**인 이유

리포트 12 §6.3 ③ 이 남긴 교훈은 *"이름만 대고 내용을 안 줬더니 모델이 열거값을 지어냈다"* 였다.
여기서는 반대로 경로만 댄다. 모순이 아니라 **읽는 주체가 다르다:**

    골조 생성   마스터의 LLM — 파일 접근이 **없다**        → 🔴 내용을 실어야 한다
    추론 파견   워커의 Claude — 자기 체크아웃을 **읽는다**  → 경로를 대면 충분하다

실측이 이걸 뒷받침한다 — 워커가 stdout 에 *"`MissionTask_SetCamera.h`/`.cpp` 를 기준 커밋
`b1ba6af` 에서 그대로 읽었다"* 고 적었다. 그리고 매니페스트에 **금지 셋**을 못박았다: 원본을
Edit/Write 하지 않는다 · 복사해 붙이지 않는다 · **대상 파일 목록에 넣지 않는다.**

⚠️ **회귀 테스트로 지키는 것**: 포팅 원본 경로가 **대상 파일 목록으로 새지 않는다.** 두 목록이
한 문서에 있으니 실재하는 위험이고, 새면 워커가 **읽기 전용 모듈을 고친다.**

## §7. `/distribute` — 🔴 계획을 **파일로** 내야 자를 수 있다

    ① plan      분해 계획 → 🔴 **사람이 JSON 을 편집해 자른다**
    ② register  골조 생성 + 골조 빌드 게이트 → 통과해야 등재
    ③ dispatch  추론 파견 (직렬 기본)
    ④ 통합자    🕓 중 1.4 — 아직 없다

분해는 결정적이므로 계획 파일을 두는 이유는 **재현이 아니라 편집**이다. `preview()` 를 눈으로
보는 것만으로는 자를 수 없다 — 사람이 그 파일에서 조각을 지우고, `register` 가 **그 편집 결과**를
읽는다. 편집된 계획도 **불변식을 다시 검사한다**(같은 물결에 같은 파일이면 거부).

각 단계 출력이 *"다음은 사람이 한다"* 로 끝난다. 🔴 에이전트가 알아서 다음 단계로 넘어가지 않게
스킬에도 못박았다.

## §9.5 🔴 워커 2대 동시 파견 — 실전 통과, 그리고 **병렬 비용의 정체** (세션 후반)

세션 중에 사용자가 BC-250 을 재부팅해 `.43` 이 돌아왔다(§11.1). 유일하게 비어 있던 실전 검증을
메웠다 — 큐만 대역이고 파견·SSH·응답 채널은 전부 실물이다.

    36초 · 통과 2/2 · 합계 $0.4725
    [1] lp-setcamera  → .2  (윈도우)  $0.2273 · 캐시생성 23,628 · 캐시읽기 186,140 · 출력 1,925
    [2] lp-playdialog → .43 (BC-250)  $0.2452 · 캐시생성 25,588 · 캐시읽기 198,110 · 출력 2,010

- ✅ 두 기계가 **동시에** 일했고, 스풀에 **적용 순서가 보존**됐다
- ✅ `.43`(리눅스)의 응답은 **완벽했다** — 요청한 한 줄만, EOF 잡음도 0(그 두 파일이 이미 개행
  하나로 끝나는 부류였다). 🔴 즉 채널은 윈도우/리눅스 양쪽에서 같게 동작한다

### 🔴 "캐시 생성이 워커별 고정비" 가 숫자로 확인됐다

문서가 실측 2026-08-09 로 *"워커 2대는 12% 빠르고 90% 비쌌다 — 캐시 생성이 워커별 고정비"* 라
적어 뒀는데, **그 고정비가 얼마인지는 없었다.** 이번에 나왔다 — **워커당 캐시 생성 24~26K 토큰**
이고, 두 워커가 **각자 따로** 냈다. 기계마다 실려 가는 컨텍스트(그 머신의 `CLAUDE.md`·config)가
달라 캐시 프리픽스가 갈리기 때문이다. 워커를 N대 쓰면 그 비용을 N번 낸다.

⚠️ **그런데 시간 쪽은 문서와 다르게 나왔다.** 2건 병렬이 **36초**인데, 같은 종류의 단건 파견이
앞서 **45초**였다. 직렬이면 80초대일 것이므로 이번 조건에서는 병렬이 확실히 빨랐다.

🔴 **그래도 기본값을 바꾸지 않았다.** n=1 이고 조건이 다르다(옛 실측은 워커가 커밋·push 하던
구 토폴로지였다). 이 저장소의 규칙이 *"가중치를 눈으로 만지지 않는다 · 추측 대신 잰다"* 이고,
**기본값을 뒤집는 것은 A/B 로 재고 나서 할 일**이다. 지금 확실한 것은 둘뿐이다:
**⑴ 추가 워커 1대당 캐시 생성 24~26K 를 더 낸다 ⑵ 조각이 크면 시간 이득이 그것을 넘을 수 있다.**

## §10. 🔴 안 된 것 · 못 잰 것
- ⚠️ **병렬의 시간/비용 A/B 는 아직이다** — §9.5 가 방향을 뒤집을 수 있는 관측을 냈지만 n=1 이다.
  같은 조각으로 직렬 2건 vs 병렬 2건을 재야 기본값을 논할 수 있다
- ⚠️ **큐를 거친 e2e 는 아직 없다.** 실전 파견은 매니페스트를 직접 만들어 채널만 검증했다.
  `claim` → 파견 → 스풀 전체는 durable `task/<id>` 브랜치가 필요하고, 그건 **요청자(`.33`)가
  만든다** — §8.6 이 마일스톤 1부터 남겨 둔 그 한 칸이다
- 🔴 **적용하는 것이 아무도 없다.** 중 1.4(통합자)가 종점이다. 입력은 이미 정해져 있다 —
  `Handoff.ordered()` + `responses/<work_id>/<task>.json`(`files`·`base_commit`)

## §11.1 🔴 BC-250 은 크래시가 아니었다 — **정상 종료 뒤 44시간 미부팅**

세션 중 사용자가 *"BC250 돌고있는데?"* 라고 했는데 `.43` 이 안 잡혔다. 순서대로 좁혔다:

1. `.43` 은 **ARP 조차 INCOMPLETE** — 그 IP 에 아무것도 없다
2. /24 전체 ping 스윕 → `.36` 이 하나 잡혔지만 **모든 포트 닫힘 + 랜덤 MAC**(`ca:e4:e2`) =
   휴대폰류. 🔴 BC-250 이 아니다
3. 🔴 **ping 은 방화벽에 막힐 수 있으니 22번 포트로 전수 스윕** — 열린 것은 `.2`·`.33`·`.57`
   **셋뿐**. 즉 **IP 변경이 아니라 네트워크 부재**다

사용자가 재부팅하니 **같은 `.43` 으로** 돌아왔다. 이전 부팅의 로그가 답을 줬다:

    Aug 11 02:30:15 systemd[1]: Finished systemd-poweroff.service - System Power Off.
    Aug 11 02:30:15 systemd-shutdown[1]: Syncing filesystems and block devices.

🔴 **정상 종료다.** `last -x` 가 결정적이다 — 크래시는 종료 자리에 그렇게 찍힌다:

    Tue Aug 11 00:40 - 02:30  (01:49)    ← 이번 것: 정상 (crash 표시 없음)
    Sat Aug  8 12:21 - crash  (10:06)    ← 8월 8일 것은 **진짜 크래시였다**

08-11 02:30 은 지난 세션이 리포트 12 를 쓰고 마감한 직후다(종료 절차대로 내렸다). 그 뒤 44시간
OS 가 안 올라와 있었고, 사용자가 본 *"돌고 있다"* 는 전원/팬이었다 — **전원 복구 후 자동 부팅을
하지 않는 설정이면 정확히 이 모양**이 된다.

⚠️ 부팅 로그의 `amdgpu … Failed to clear hpd(rx) source=N on init` 다발은 **부팅 시점**에 찍힌
것이고 디스플레이 없는 헤드리스에서 핫플러그 감지가 없다는 뜻이다 — 종료와 무관한 알려진 잡음이다.

### ⚠️ 그리고 이 보드는 **추론 엔드포인트와 워커를 동시에 한다**

파견 전에 재 보니 35B 가 **영구 핀으로 13.2GB 상주**(`expires_at` 2318년)라 `MemAvailable` 이
**1.2GB** 였다. 이 보드는 **부하로 커널이 멈춘 전례**가 있어(소 3.2.1) 바로 던지지 않고 작게 쟀다:

    claude -p "Print exactly: OK"  →  최대 RSS **317MB** · 4.2초 · 🔴 **스왑 0**

들어간다. 🔴 **그리고 이 사소한 호출이 $0.106 였다** — 캐시 생성 17,209 토큰이 잡혀서다.
*"워커별 고정비"* 가 실체로 보인 첫 순간이고, §9.5 의 24~26K 와 같은 이야기다.
