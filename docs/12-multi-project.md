## 12.4 [중요] 이 문서가 정정하는 거짓 서술 — 같은 거짓말이 네 곳에 있었다

§5.5.2 는 마운트 정책을 정했지만 **강제하는 코드는 쓰이지 않았다.** 그런데 네 곳이 그것을
**이미 된 것처럼** 적었다:

| 자리 | 적힌 것 | 실제 |
|---|---|---|
| `docs/5_5-project-isolation.md` §5.5.2 | *"마운트되지 않은 프로젝트 요청은 ③ 에 따라 409 로 거부된다"* | 거부하는 코드가 없다 |
| `PLAN.md` 5.5 행 | *"mismatched requests get 409, fail-closed"* | 같다 (2026-08-22 정정) |
| `paths.py:167` 독스트링 | *"§5.5.2 의 단일 마운트 정책을 **강제한다**"* | 프로덕션 호출자 0 |
| `logic.set_active` 반환 | *"가리키는 프로젝트가 다른 동안에는 이 프로젝트의 문서 갱신이 **멈춰 있었다**"* | 안 멈췄다 |

[중요] **왜 이게 최악인가.** 그 문서들은 매 세션 읽힌다. 2026-08-21 세션이 그것을 믿고 그 위에
구현을 얹었고, 그 구현은 전량 되돌려졌다(리포트 28). **덜 된 것을 됐다고 적으면, 읽은 사람이
없는 것을 있다고 믿고 결정한다** — 코드가 덜 된 것보다 이것이 비싸다.

[주의] **부류가 다른 정정 하나가 곁에 있다 — 헷갈리지 말 것.** 같은 §5.5.2 의 *"**409** 로
거부된다"* 에서 **409 라는 형태**는 거짓 서술이 아니라 **결정이 바뀐 것**이다(§12.5-c: 200 +
ok:false + 사유). 위 표는 *"됐다고 적었는데 안 된 것"* 이고, 이것은 *"정하고 나서 다르게 정한
것"* 이다. 둘 다 고쳐야 하지만 **원인이 다르므로 대책도 다르다** — 앞은 「미룸을 기록하지
않은 것」, 뒤는 그냥 갱신이다.

[주의] **미룬 것 자체는 잘못이 아니다.** §5.5.5 의 미룸은 근거가 있었다. 잘못은 **미룬 사실을
적지 않은 것**이다. 미룸은 결정이고, 결정은 기록되어야 한다.

## 12.5-a [완료] 확정 — 설치는 여럿, 작업은 마운트된 하나 (사용자 2026-08-22)

> *"당연히 여러 프로젝트 레포를 설치할 수 있지. 근데 작업은 무조건 하나만 진행 되어야 한다는거야.
> 인프라 서버 기준으로 마운트된 것을 요청하고 분배 작업을 해야지 아니라면 인프라 서버에서
> 거절하라는거고"*

    설치   한 기계에 여러 프로젝트 체크아웃 — **허용**. 막을 이유가 없다
    작업   마스터의 마운트(`active`) **하나만** — 요청·분배의 대상은 그것뿐
    거절   마운트되지 않은 프로젝트의 요청·분배는 [중요] **인프라 서버가 거절한다**

[중요] **거절 주체가 정해진 것이 이 결정의 핵심이다.** 워커가 무엇을 들고 있는지로 판정하지
않는다 — 마스터가 자기 마운트를 기준으로 거절한다. 그래서 강제가 **한 곳**에 산다.

**귀결 다섯** (구현 범위가 줄어드는 것과, 늘어나는 것 하나):

1. **#229 는 「막는 일」이 아니다** — 설치를 허용하므로 체크아웃·`.ax` 를 여러 개 두는 것은
   정상이다. 남는 것은 잠금 단위 확인과 홈 스킬 덮어쓰기 처분뿐이다.
2. **#228 이 「거르기」에서 「단일화」로 단순해진다** — 큐가 프로젝트별로 필터링하는 것이 아니라
   **마운트된 것만 준다.** claimer 가 프로젝트를 신고하는 것은 여전히 필요하다 —
   *"신고 안 한 것을 훔치지 않는다"* 를 위해, 그리고 마운트와 어긋나면 **거절 사유를 말하기 위해**.
3. [중요] **전환은 큐 정리를 포함한다 — 「조용히 마르게 두는 것」은 틀렸다** (사용자 정정
   2026-08-22: *"당연히 마운트 변경되면 등록된 작업 태스크들 모두 정리해야지. 그냥 바라보는
   레포만 바꾸는건 잘못된거지"*).

   [주의] 처음에 이 자리에 *"큐가 안 주므로 다른 체크아웃의 claimer 는 자동으로 할 일이 없어진다
   — 별도 정지 장치가 필요 없다"* 고 적었다. **틀렸다.** 일을 안 주는 것과 정리된 것은 다르다.
   남는 것이 실측으로 다섯이다:

       큐          미종결 work·task 레코드      → #210 가드가 **돌아올 때 전환을 다시 막는다**
       워커        `.ax/work/<task_id>/` 부산물
       원격        `attempt/*` · `task/*` 브랜치
       마스터      `<프로젝트>/responses/` 스풀의 회수분
       durable     병합 안 된 브랜치            → 원전대로 보존이 맞지만 **셈은 남아야 한다**

   [중요] **지금 도구로는 미종결분을 못 치운다** — `work/cleanup.py:51` 이
   `DROP_STATUSES = ("verified", "cancelled")` 이고 *"`failed` 는 남긴다"* 가 의도다.
   `cleanup remote --apply`(#219)도 **병합 확인분만** 지운다. 그리고 `set_active` 는 정리를
   호출하지 않는다(실측: `logic.py` 에 cleanup 호출 0건) — **거절만 한다.**
4. **마운트가 바뀐 뒤 다른 체크아웃의 claimer 는 큐에서 일을 못 받는다** — 그것은 사실이지만
   **정리의 대체물이 아니다**(위 3).

5. **§5.5.2 의 「409 로 거부된다」가 비로소 참이 될 수 있다** — 그것을 실재하게 만드는 것이
   #243 이고, 이제 그 일감의 [미결]이 풀렸다.

[주의] **한 가지만 남았다 — 관리 도구는 예외다.** 프로젝트를 등록·클론·배달·최초 색인하는
일은 **마운트되기 전에** 도는 것이 필연이다(2026-08-21 온보딩이 전부 그 경로였다). 위 규칙의

가능해진다. **이 해석이 틀리면 말씀해 달라**(#229·#243 의 범위가 바뀐다).

## 12.5-b [완료] 확정 — 전환은 **되묻는다**, 임의로 종료하지 않는다 (사용자 2026-08-22)

> *"마운트 변경을 요청하면 서버에서는 지금 등록된 작업이 있는지 확인하고 없다면 변경하고,
> 있다면 다시 사용자에게 대화 방식으로 물어봐야지.. 정말 다 정리하고 바꿀꺼냐고
> **사람이 자리에 앉아있는데 니멋대로 종료하면 좋은 경험은 아닐꺼같은데**"*

계약:

    등록된 작업 없음   →  전환한다
    있음               →  **정리 대상을 이름으로 돌려주고 묻는다** — "정말 다 정리하고 바꿀까"
    사람이 승인        →  정리하고 전환한다 (이어서 한다)

[중요] **선례가 있다 — 새 패턴을 만들지 않는다.** `review.finalize_work(confirm=False)` 가
*"통합만 하고 멈추고 사람이 실행할 명령을 돌려준다"* 이고 `confirm=True` 가 *"머지·기재·정리를
이어서 한다"* 다. 전환도 같은 모양으로 둔다 — `confirm` 이 곧 트리거다.

[중요] **자동 정리도, 단순 거절도 아니다.** 셋을 구분해 둔다:

    자동 정리   사람 승인 없이 지운다            → **금지**. 사람이 자리에 앉아 있다
    단순 거절   "미종결 있음" 만 말하고 끝       → 지금 상태. 무엇을 치워야 하는지 안 알려 준다
    되묻기      대상을 이름으로 내고 승인을 받는다 → **확정**

그래서 지금 구현이 **틀린 것이 아니라 절반**이다 — `set_active` 는 거부는 하는데(#210 가드)
**무엇을 치우면 되는지 말하지 않는다.** 채울 것은 그 절반이다.

[주의] **`force=True` 는 의미가 달라진다.** 지금 force 는 *"미종결분을 두고 넘어간다"*(감수)인데,
확정된 계약의 승인은 *"정리하고 넘어간다"* 다. **둘은 다른 문이고, 전자는 찌꺼기를 확정적으로
만든다.** 유지·개명·폐기 판단이 #253 에 남아 있다.

### 이 결정은 전환에만 적용되는 규칙이 아니다

*"사람이 자리에 앉아 있는데 니 멋대로 종료하면 좋은 경험이 아니다"* — 이것은 §11.5(빌드·배포·
데몬 재기동은 묻고 승인 후)와 §11.1(애매하면 묻는다)과 **같은 뿌리**다. 파괴적이거나 사람의
작업을 끊는 동작은 **계획을 내고 승인을 받는다.** 이 저장소의 `plan` 기본값 관례
(`cleanup plan|apply` · `attempt plan|apply` · `batch plan`)가 이미 그 형태다.

## 12.5-c [완료] 확정 — 요청은 **태그를 담고**, 마스터는 **대조한다**. 빈 태그도 거절 (사용자 2026-08-22)

> *"검색 요청이나 작업 요청할 때 어떤 레포 작업을 요청하는건지 태그를 담아서 요청하고[워커,

§12.4 말미에 그 구분을 적어 뒀다.
[주의] HTTP 오류로 하면 `ax-client` 가 [미연결] 시 지난 스냅샷으로 폴백하도록 되어 있어서
**거절을 장애로 오인해 낡은 결과를 돌려준다.**

### [중요] 방향이 반대였다 — 지금 태그는 강제가 아니라 **우회**다

실측 2026-08-22. `context_search/paths.py:150 resolve(name)` 은 `name` 이 있으면 **`reg.active` 를

`layer3_verify` 를 마스터도 쓴다(`integrate.py:423,486` 의 `__import__`). 나머지 아홉은 **공용**이다 — `source_text.py` 는 마스터 8곳, `work/branch_names.py` 는 7곳이 쓴다.

[주의] **첫 스캔은 `utf8.py` 를 클라 전용으로, `claimer.py` 를 공용으로 냈다 — 둘 다 반대였다.**

### [주의] 이동의 함정 — 저장소 위치와 배달 위치가 **한 값을 겸한다**

`client/bundle.py:89 PAYLOAD_BY_ROLE` 의 항목 하나가 *저장소에서 읽을 위치*와 *클라에 놓일
위치*를 동시에 뜻한다. 그런데 배달 위치는 `.33` 의 `.mcp.json` args
(`.ax/lib/axmaster/clientside/client_mcp.py`)이고, `claimer.py` 의 경우 `.2` schtasks·`.43` cron 이
`axmaster.work.claimer` 로 부른다(그 파일 `:27-28`). [중요] **배달 위치를 바꾸면 두 기계의 상주가
죽는다.** 그래서 순서가 **#262(값을 가른다, 동작 불변) → #263·#264(이동) → #265(README)** 다.

[중요] **`PAYLOAD_BY_ROLE` 이 배달물의 정본 목록이라는 사실은 이동해도 안 바뀐다** — 디렉토리를
열어도 「어느 파일이 어느 역할에 가는가」는 그 목록에만 있다. 위화감의 절반은 그것이었다.

## 12.5 미결 — 사람이 정할 것

1. **`mcp.json` 을 마스터가 생성할지** — `.ax/config.json` 과 같은 방식(probe 실측 → 생성 →
   되읽어 대조)이면 프로젝트 귀속과 기계 귀속이 한 번에 풀린다. 사람이 손으로 넣은 항목
   보존 계약은 `merge_mcp_json` 이 이미 갖고 있다.
2. **원전 exe 6종** — 이식 / 로컬 유지 + **설치 절차** / 폐기. 「로컬 유지」로 정해도 새 기계에
   놓는 절차가 필요하다.
3. [완료] **claim 의 빈 `project` 값** — **fail-closed 로 확정**(사용자 2026-08-22, §12.5-c).
   활성 폴백은 채택하지 않았다. 이 항목은 기록으로만 남긴다.

## 12.5-g [완료] 확정 — 초기화는 **선언 표**로 적는다. 실행기는 그 표를 돈다 (사용자 2026-08-22)

> *"초기화 과정에서 사용할 **규격화된 내용**이 있어야 추후 클라측 작업할 때 추가 동작기능을

> + *"코드 작성에 대한 컨벤션 관리라던가."*

[중요] **`#259` 를 명령 하나로 구현하면 스크립트가 나오고 확장 자리는 다시 없다.** 그래서
「초기화된 프로젝트란 무엇인가」를 **선언**으로 먼저 적고 `#259`·`#254`·`#255`·`#238`·`#261` 이
그 선언의 **절**이 되게 한다. → `#266` (2단계 첫 자리, §12.3-a)

### 모양 — **파이썬 선언 표(저장소) + 트윈 `config.yaml` 의 `init:` 오버레이**

근거 셋. ① **원전이 그 모양이고 우리 `bundle.py` 가 이미 반쯤 그 모양이다**
(`SKILLS_BY_ROLE`·`PAYLOAD_BY_ROLE`·`MD_BEGIN/END`·`merge_claude_md`·`merge_mcp_json`) — 새 형식을
만들면 한 파일에 관례가 둘이 된다(리포트 29 §7-5 에서 이미 물린 자리). ② **긴 본문이 들어간다**
— CLAUDE.md 관리 구역·스킬 본문은 수백 줄이라 YAML 에서는 들여쓰기가 내용을 지배하고, 우리
`workshop/` 은 이미 실파일이다. ③ **두 곳으로 갈리지 않는다** — `ProjectConfig.to_yaml()` 이
`dict(self.raw)` 로 시작해 **모르는 키를 보존**하므로 `init:` 이 왕복으로 살아남는다.

[중요] **표에 본문을 박지 않는다 — 실파일 경로를 가리킨다** (`workshop_files()` 가 이미 그
관례다). [주의] **대상 집합은 디렉토리 전수로 잰다** — 목록을 대상 집합으로 쓰면 목록 밖
파일이 조용히 깨진다(`#263`).

## 12.6 여기서 배운 것 — 완료 조건을 쓰는 법

레드마인 소분류의 완료 조건을 **「무엇이 없으면 미완인가」**로 적는다.

    나쁨   "mcp.json 을 생성한다"
    좋음   "`plan` 출력에 `.mcp.json` 이 배달 항목으로 나타나고 `check` 가 해시로 잰다.
            `plan` 에 안 보이면 미완이다"

근거는 이 저장소의 실측이다 — 유닛 3,720건이 통과하는 동안 결함 10건이 살아 있었고
(*"Injection tests contracts, not reality"*), 「완료」 표시와 실물이 어긋난 사례가
원전 σ 감사가 만들어진 계기였다. **검증 가능한 사실 하나로 적으면 거짓 보고가 구조적으로
불가능해진다.**
