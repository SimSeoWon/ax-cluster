### ① 모델을 잘못 골랐다

기본값을 로컬 `qwen2.5-coder:14b` 로 뒀었다. **틀렸다.** 모토(*작성은 무료 로컬*)는 **본문
대량 생산** 이야기인데, 골조는 **작업당 1회**이면서 **모든 병렬 조각의 계약**이 된다 —
틀린 골조는 N개 조각을 전부 오염시킨다. 배칭 실측이 *"호출당 고정비가 지배한다"* 로 말한 것과
같은 논리로 **여기가 값을 쓸 자리**다. → `DEFAULT_MODEL = "claude:opus"`.

레인 문법을 `synth.generate` 에 확장했다 — `claude:opus` 처럼 **레인 뒤에 모델**을 붙인다.
`claude -p --model opus` 실측 통과. 🔴 층2 는 모델을 지정하지 않는다(소 2.2.1 이 정할 일을
코드에 박지 않는다).

### ② 관계 그래프를 안 쓰고 있었다

중 1.1(상속 + `#include`, LLM 0)에서 **이미 만들어 둔 그래프**를 골조 프롬프트가 안 읽었다.
규범과 선언부만 싣고 관계를 뺐다 — 부모를 모르면 `: public X` 를 지어내고, include 를 모르면
헤더를 잘못 문다. 실측:

    UMSViewBase   parents: UMSWidgetBase <- UCommonActivatableWidget · children (3)
                  includes: Source/ModularStage/UI/Base/MSWidgetBase.h
    UMissionTaskExecutor   parents: UObject <- FTickableGameObject

프롬프트 순서를 **규범 → 관계 → 선언부 → 지시**로 뒀다. 규범은 *무엇을 지킬지*, 관계는
*어디에 붙을지*, 선언부는 *정확한 철자*다 — 뒤로 갈수록 베껴야 하는 것이라 지시에 가깝게 둔다
(#26 실측: 베낄 텍스트가 지시에서 멀면 모델이 기억에서 꺼낸다).

## §4. 등록 배선 (소 1.1.4) — 🔴 과했던 것을 되돌렸다

처음엔 골조를 **필수**로 만들었다가 기존 테스트가 전부 깨졌다. 골조 없는 등록은 **원래부터
정상 경로**다(작업장이 골조를 쓰는 흐름). 되돌리고 조건을 하나로 좁혔다:

    instruction 있고 skeleton 없음  →  생성한다
    skeleton 이미 있음              →  🔴 손대지 않는다 (사람이 쓴 골조가 이긴다)
    둘 다 없음                      →  건너뛴다 (기존 동작 유지)

🔴 **골조 생성은 큐를 만지기 전에 끝낸다** — 등록 도중 실패하면 반쪽 work 가 남고 그건 사람이
치운다. 그리고 **생성한 골조가 골조가 아니면 등록하지 않는다**(`[PSEUDO]` 0개 = 완성 파일,
동결 0개 = 계약 불가). 원전이 값을 치르고 배운 실패다 — 글루 파일이 워커 태스크로 등재되던 버그.

테스트 `master/test_skeleton.py` **61건**, 전체 실패 0.

## §5. 🔴 토폴로지가 바뀌었다 — 쓰는 주체는 하나다 (사용자 확정 2026-08-11)

사용자가 원전 흐름을 기억해 짚었고, 이어서 이렇게 제안했다:

> *"워커들이 이 브랜치에 등록된 내용을 기준으로 추론을 하고 응답하면 메인 작업 컴퓨터가
> 빌드 되는지 적합한지 판단하고 원격 브랜치에 직접 커밋하는게 좋을꺼같아"*

    옛것   워커 N대가 각자 클론에서 수정 → 각자 커밋 → attempt push → 마커로 판정
    새것   워커는 **추론만** → 통합자가 **적용 → UE5 빌드 판정 → durable 커밋**

### 5.1 왜 이게 맞는가

옛 구조는 태스크를 **워커의 자기 신고**(`RESULT: DONE`)로 판정하고 *"컴파일되나"* 를 아무도
묻지 않았다. 🔴 **원전이 정확히 그 구조에서 사고를 냈다** — 빌드를 등재 *뒤*에 두었더니 깨진
골조가 `origin` 에 박히고 **워커 전원이 그 위에서 작업**했다. 빌드하는 주체를 커밋 주체로
만들면 그것이 **규율이 아니라 구조**가 된다.

내가 소 1.1.5(골조 빌드 게이트)와 소 2.3.5(통합 빌드)를 **따로 칸으로 만든 것 자체가** 옛
구조에서는 그것이 규율로만 지켜진다는 증거였다.

한 무리의 문제가 통째로 사라진다 — 워커 git 인증 · `attempt/` 찌꺼기 · *"워커는 브랜치를 못
지운다"* · 더티 트리 파견 차단 · CAS/펜싱의 절반. **전부 여러 대가 쓰기 때문에 있던 것**이다.
§5.2-D 가 이미 같은 방향으로 갔다(*"durable merge CAS·모델이 머지 권한은 1인 구도에선 불필요"*).

🔴 **포기하는 병렬은 이미 의심스러웠다**: 실측 2026-08-09 워커 2대는 **12% 빠르고 90% 비쌌다**
(캐시 생성이 워커별 고정비). 그리고 **층3 은 이미 `.2` 전용**이라 직렬이었다 — 직렬 병목은
**새로 생기는 게 아니라 위치가 옮겨진다.**

### 5.2 🔴 내가 다르게 본 한 가지 — 그 역할을 `.33` 이 아니라 `.2` 에

사용자의 첫 스케치는 적용·커밋을 **메인 작업 PC(`.33`)** 에 뒀다. 비교표를 만들어 제시했고
`.2` 안(B′)이 채택됐다.

| | `.33` 요청자 | `.2` 통합자 |
|---|---|---|
| UE5 | ✅ | ✅ 5.8 |
| 무인 구동 | ❌ 사람이 쓰는 기계 | ✅ **유일** |
| 가용성 | 🔴 낮다 — **이 세션 중에도 꺼져 있었다**(실측) | ✅ 전용·상시 |
| 게스트 규칙 | 🔴 읽기 전용 선호·worktree 강제·미커밋 `.uasset` 복구 불가 | 해당 없음 |

`.33` 은 원래 역할(등록·최종 리뷰·`[FEEDBACK]`)에 남는다 — **사람이 눈으로 볼 자리이지
파이프라인이 커밋을 밀어넣을 자리가 아니다.**

### 5.3 받아들이는 비용 두 개 (기록해 둔다)

1. **`.2` 가 적용+빌드의 단일 장애점이 된다.** 층3 이 이미 그랬으니 새 위험은 아니지만 더 많은
   일이 얹힌다.
2. **`.2` 의 추론 트리와 적용 트리가 겹치면 안 된다** → `git worktree` 로 가른다(소 1.4.1).
   ⚠️ **UE5 worktree 의 DDC/Binaries 재생성 비용은 여전히 미측정이다** — `.2` 에서 기존 체크아웃
   재사용을 택한 이유가 그 비용이었다(콜드 빌드 수십 분 예상). **강제 전에 잰다.**
