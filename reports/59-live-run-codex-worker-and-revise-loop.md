## 59.2 결함 ① — `.2` 의 codex 가 파일을 못 썼다 (rc=0 으로)

### 증상

1차 등재에서 `.2` 로 간 조각 2건이 **골조 대비 0줄**이었다. 층1 이 `[PSEUDO]` 잔재로 막았고,
마스터 기록에 남은 것은 그 한 줄뿐이었다 — **「codex 가 코드를 덜 썼다」로 보였다.**

### 원인 (프로브로 특정)

`.2` 에서 같은 플래그로 임시 폴더에 프로브를 돌렸다:

    exec_command failed: CreateProcess { message: "Rejected(\"Failed to create unified exec
        process: timed out after 15000ms connecting runner pipe-in\")" }
    Failed to write file ...\probe.txt
    agent_message: "Unable to create probe.txt because the file-writing tools failed."
    turn.completed                                    ← 🔴 정상 종료다

`.2` 의 `~/.codex/config.toml` 은 **데스크톱 앱이 관리**해서 `[windows] sandbox = "elevated"` 가
들어 있다. 그 러너는 세션 9(대화형 데스크톱)의 네이티브 파이프를 쓰는데 **SSH 는 세션 0** 이라
파이프가 안 닿는다. `win-worker-2.md` 의 세션 0 경계 그대로다.

🔴 **그런데 `codex exec` 는 rc=0 으로 끝난다.** 그래서 `wcommit._cycle` ②의 `rc != 0` 분기를
안 타고, 되읽기에 골조가 그대로 올라와 층1 이 막는다. **환경 실패가 코드 실패로 위장됐다.**

### 왜 `.43` 은 멀쩡했나

    .43  config.toml   16줄   windows/plugin/mcp_servers/notify → 0건
    .2   config.toml   60줄+  데스크톱 앱의 플러그인 · 네이티브 파이프 MCP · notify 훅

`.43` 은 헤드리스라 그런 게 없고, Linux 샌드박스는 별도 러너 파이프를 안 쓴다.

### 고침 — `f54b2fd`

`-c windows.sandbox="unelevated"` 를 **Windows 워커일 때만** 명령줄에 싣는다.

[중요] **앱이 관리하는 파일을 고치지 않는다** — 앱이 다시 쓴다. `network_access` 를 같은
이유로 같은 자리에서 주고 있다.
[주의] 값은 `elevated`/`unelevated` 둘뿐이고 다른 값이면 codex 가 **설정 로드 단계에서
거절**한다(실측). Linux 도 같은 스키마로 파싱하지만 쓰지 않으므로 안 싣는다.

[중요] **배선을 실물 probe 로 확인했다** — 수정이 `facts.windows` 조건부라 판정이 틀리면
조용히 안 먹는다:

    192.168.0.2   worker  os=windows  windows=True   → 플래그 실림: True
    192.168.0.43  worker  os=linux    windows=False  → 실림: False (의도대로)

### 🔴 [주의] 완전히 고쳐진 것이 아니다

2차 등재에서 `.2` 는 **attempt #1 에 또 0줄**이었고 **attempt #2 에 +33/-2 로 성공**했다.
왜 1차는 실패하고 2차는 됐는지 **모른다** — codex 자기 출력이 또 버려졌기 때문이다.

가설 둘, 둘 다 미검증:

    ⓐ 첫 실행에 러너 초기화가 늦어 15초 타임아웃에 걸린다 (2차는 웜)
    ⓑ 피드백이 실린 2차 프롬프트가 더 구체적이라 codex 가 다른 도구 경로를 골랐다

또한 프로브에서 **powershell 은 계속 죽는다**(`0xC0000142` STATUS_DLL_INIT_FAILED — 세션 0
특유). codex 가 `cmd.exe` 로 우회하는 것을 봤지만, 우회가 항상 되는지는 안 쟀다.

## 59.3 결함 ③ — `needs_revision` 이 파견 게이트에 안 보였다

`#388` 이 층1 차단에 재시도를 주면서 **`needs_revision`** 이라는 상태를 새로 만들었는데,
**후보 풀에만 알리고 파견 게이트에는 안 알렸다.**

    master/task_queue/logic_claim.py:162   pending + needs_revision   ← 후보 풀
    master/work/autodispatch.py:267        pending 만                 ← 파견 게이트

실측:

    23:20:34  [revise] c1e3d128 1/3 — 재시도로 보낸다        → needs_revision
    23:29:07  안 건다 — pending 태스크가 없다 (멱등)         → 아무도 안 집는다

work 이 terminal 3/4 에서 멈췄고 `_flip_if_all_terminal` 이 안 돌아 `merge_status` 가
`ready_for_review` 로 안 뒤집혔다 ⇒ **`.33` 은 끝났는지 실패했는지 영영 듣지 못한다**
(정본 ⑹ 이 통째로 죽는다).

🔴 [주의] **그 결함이 가려져 있던 이유가 중요하다.** 같은 날 `267f22a6` 의 2·3차 시도는
이어졌는데, 배관이 아니라 **우연**이었다 — 마침 `.33` 이 `[SKELETON-FIX]` 를 push 해 새 파견이
걸렸다. 재시도가 *도는 것처럼 보였기 때문에* 게이트를 의심하지 않았다.

### 고침 — `b786f1f`

판정 기준을 `DISPATCHABLE = ("pending", "needs_revision")` 하나로 모으고 세 자리(파견 게이트 ·
통합 판정 · 건수 계산)가 같은 것을 보게 했다. 사유 문구도 고쳤다 — `⑺ 사람 승인 대기` 는
거짓말이었다(사람이 아니라 파견을 기다리고 있었다).

회귀 못 셋을 박았다: 파견 게이트 통과 · 통합보다 파견 우선 · **후보 풀과 기준이 갈라지지
않는지**(`logic_claim` 소스를 직접 읽어 대조).

## 59.6 배운 것

🔴 **① 실패의 「받을 곳」이 종류마다 다른데, 우리는 갈래가 둘뿐이다.**

    코드가 틀렸다        → 워커 지휘자 (revise 루프)          있다
    미완성이라 사람이 채운다 → `.33` ([리뷰 요청 — 일부 미완성])   있다
    **환경이 막혔다**     → **마스터(사람)**                   🔴 없다

갈래가 없어서 환경 실패가 첫째로 흘렀고 **상한 3회를 태웠다.** 사유를 줘도 못 고치는
실패에 재시도를 붙이면 그냥 낭비다. 원전이 `_classify_verify_issues` 로 분류를 두는 이유가
이것이다.

🔴 **② 「돌아가는 것처럼 보이는 것」이 결함을 가린다.**
`needs_revision` 재시도는 실제로 돌았다 — 다만 우연이었다(`.33` 의 push 가 파견을 깨웠다).
동작을 봤다고 배관을 봤다고 생각하면 안 된다. **왜 돌았는지**를 봐야 한다.

🔴 **③ 회피와 수정을 내가 구분하지 못했다.**
`.2` 가 막히자 워커 모드를 `lane` 으로 내리자고 제안했다. 사용자 지적:
*"지금 버그가 발생하는건 고쳐야 하는거고 임시로 이전 방식으로 돌아가는건 그냥 회피하는거잖아"*.
맞다 — `lane` 은 생성이 마스터 한 대에 몰리는 구조이고(429 하나로 4조각 중 3이 죽은
2026-09-04 가 그 결과), `#385` 의 워커측 지휘자가 그 병목을 흩는 것이 **「분산」의 이름값**이다.
고치는 쪽으로 가니 **값 하나**였다.

**④ 조건부 수정은 조건을 실물로 재야 한다.** `facts.windows` 판정이 틀리면 수정이 조용히
안 먹는다. 배포 전에 probe 로 확인했고, 그 습관이 이번엔 값을 했다(맞았지만, 틀렸다면
「고쳤는데 안 고쳐진」 상태로 실증에 들어갔을 것이다).
