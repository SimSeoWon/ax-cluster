**읽는 법:**
- **마스터는 인프라다.** RAG·온톨로지로 **적합한 코드 뭉치를 조립해 윈도우에 건네는** 것까지가 역할이고,
  **파일 적용·컴파일·테스트·코드 등록은 윈도우가 한다.** 검증에 실패하면 **다시 요청**하는 루프다.
- **파일은 윈도우를 떠나지 않는다** — 마스터도 BC-250 도 파일을 소유하지 않는다.
  텍스트(컨텍스트/코드조각/diff)만 왕복한다.
- **BC-250 이 인계한 것은 "연산"이다.** AgentTest 에선 팀원 윈도우 PC 마다 로컬 LLM(Ollama)을
  각자 돌렸는데(`INSTALL.md`: "권장 사양 VRAM 5GB 이상"), 그 **추론 부하를 BC-250 이 넘겨받는다.**
  **파일을 다루던 역할이 옮겨온 게 아니다.**
- **오케스트레이션 지점은 세 곳**이다(2026-08-08 정정 — 이전엔 "두 곳"). 윈도우 PC **2대** 각각의
  Claude Code(사용자 접점)와, 마스터가 자기 모델 자원(Claude·agy·BC-250)으로 도는 것.
  단 **마스터의 오케스트레이션은 모델 호출·라우팅·컨텍스트 조립이지 파일 작업이 아니다**(§2.3).

> **[주의] 2026-08-07 정정** — 한때 "워커 풀을 마스터가 인계한다"로 적었으나 **틀렸다.**
> `worker/`(파일을 쓰는 작업자 하네스)는 **윈도우에 남는다.** 위 "BC-250 이 인계한 것은 연산"을 참조.

> [중요] **2026-08-08 정정 — 장비 구성이 계획과 달랐다.** 실제 보유는 **윈도우 UE5 PC 2대 + BC-250 2대
> (#1 추론 / **#2 는 Bazzite 게임 머신**) + 리눅스 마스터 1대**다. 파급이 두 방향으로 크다:
>
> **(가) 작업장이 2곳이다 — `task_queue` 의 claim/lease/fencing 은 필수다.**
> §5.2-D 에서 "1인 프로젝트니 팀 복잡도는 덜어내자"고 했지만, **동시에 파일을 만지는 작업장이
> 물리적으로 2대**이므로 claim/lease/fencing 은 **팀 복잡도가 아니라 실제 요구사항**이다.
> 걷어낼 후보에서 **완전히 제외한다.** (§5.4.5 의 "오케스트레이터가 둘이라 조율이 필수"가

### 2.2 설계 원칙 (AgentTest 2026-07-07 합의 계승)

1. **파일은 윈도우(작업장)를 떠나지 않는다** — [주의] **부분 폐기 2026-08-09, 아래 §2.2-a 참조.**
   지금 정확한 규칙: **Ollama 모델은 파일을 만지지 않는다**(텍스트 in/out). 그 모델을 호스팅하는
   *기계*는 워커 에이전트를 함께 돌릴 수 있고, 그 에이전트는 자기 체크아웃을 읽는다.
   ~~**마스터는 여전히 파일을 소유하지 않는다.**~~

   > [중요] **2차 정정 2026-08-14 — 마스터도 이제 쓴다. 다만 한 곳에만.** Flow Y(사용자 확정
   > 2026-08-14)가 *"마스터가 노드에서 받은 diff 를 task/attempt 브랜치에 **commit**"* 으로

   >
   >     마스터가 쓸 수 있는 것   attempt/<task>/<workshop>/<ts>  ·  task/<id>

   >                                유일한 변경이고 `.2` 로 위임한다)
   >

   > `.43` 이 쓰는 것과 같은 경로) · 정본 클론의 `pre-push` 훅. 정본 `origin` 의 push 봉인
   > (`DISABLED://…-PLAN.md-2.1`)은 **그대로 남는다** — 오발 push 를 시끄럽게 죽이는 가드다.
   > [중요] 서버측 브랜치 보호로는 대체할 수 없다: 네 대가 **같은 Gitea 계정 `Sim`** 으로 인증해서

   > 그리고 정본 트리는 계속 `main` 에 앉아 있다 — 작업 트리는 `<프로젝트>/ax-wt-<work_id>`
   > 로 **옆에** 선다(색인기의 `merge --ff-only` 전제를 깨지 않는다).
2. 검증은 LLM 판단보다 결정론적 게이트(테스트/타입체커/린터)를 우선한다. gajae-code 의 Ultragoal 단계가 이 역할.
3. 컨텍스트 전처리(요약/청크분류/임베딩)는 BC-250 로컬 LLM 에 맡겨 API 비용/레이턴시를 줄인다.
4. 마스터→노드 호출은 stateless — 컨텍스트 문자열을 매 요청마다 던지고, 응답 후 자동으로 상태가
   남지 않는다(Ollama `/api/generate` 의 `context` 필드를 재사용하지 않는 방식으로 이미 검증됨).
5. **오케스트레이터가 셋이므로 공유 자원(Gitea · task_queue · RAG) 조율이 필수다**
   (2026-08-08 정정 — 이전엔 "둘"). 윈도우 UE5 PC **2대**가 각각 파일을 소유·커밋하고,
   마스터가 세 번째다. 1인 프로젝트라고 claim/fencing 을 걷어내면 안 된다 —
   사람이 아니라 **오케스트레이터가 경쟁**하고, 이제 **작업장끼리도 경쟁**한다(§5.4.5).
6. **마스터는 인프라지 작업장이 아니다** (2026-08-07 확정). RAG·온톨로지로 매니페스트를 조립해
   **밀어 넣고**(pull 아님), 실제 수행(파일 적용·빌드·테스트·코드 등록)은 **윈도우가 한다.**
   Unreal MCP 같은 도구도 마스터가 직접 호출하지 않고 **서브에이전트가 몬다**(§2.3).

### 2.3 도구는 서브에이전트가 몬다 — 마스터는 컨텍스트를 댄다 (2026-08-07)

**마스터의 기여는 "무엇을 알고 시작하느냐"이지 "직접 손대는 것"이 아니다.**

```
마스터 ── RAG·온톨로지·클래스그래프로 컨텍스트 매니페스트 조립 ──▶ 밀어 넣기(push)
                                                                    │
                                          서브에이전트/워커가 수행 ◀─┘
                                          (도구 호출·코드 생성·에디터 조작)
```

- **Unreal MCP 가 대표 사례다.** 마스터가 붙을 수도 없고(loopback 전용, §3·리포트 05)
  붙을 이유도 없다 — **`ue-editor-operator` 서브에이전트가 윈도우에서 로컬로 몰고**,
  마스터는 그 에이전트가 쓸 온톨로지·RAG grounding 을 대준다.
  AgentTest 의 해당 에이전트 프롬프트가 이미 *"온톨로지·RAG 로 grounding 후 에디터 작업 수행"* 이다.
- 같은 원리가 코드 생성에도 적용된다 — 마스터는 **적합한 코드 뭉치를 조립해 건네고**,
  **윈도우가 적용·검증·등록**한다. 실패하면 마스터에 **다시 요청**한다.
- **"컨텍스트는 마스터가 미리 밀어 넣는다(pull 아님)"** 원칙(§2.2-3, README)의 확장이다.
  로컬 LLM 은 도구 호출을 못 하므로 애초에 pull 이 불가능했고, 도구를 쓸 수 있는
  에이전트에게도 **판단 근거는 마스터가 대준다**는 점은 같다.

> 이 구분이 흐려지면 마스터에 도구 호출 코드가 쌓이고, 결국 마스터가 UE5/윈도우에 묶인다
> — §5.2-C 가 빌드 러너를 인프라에 박지 않기로 한 것과 같은 이유다.

### 2.4 BC-250 은 워커가 아니라 추론 노드다 — 근거 (2026-08-07 결정)

"리눅스가 연산을 인계한다"면 BC-250 도 워커(파일 작업)여야 하지 않나? **아니다.**
BC-250 이 넘겨받은 것은 **추론 연산**뿐이고 **파일 작업은 윈도우에 그대로 남는다**(§2.1).

검증 문제는 걸림돌이 아니다 — **3층 게이트 중 UE5 가 필요한 건 층3뿐**이고(§4.3),
층3 은 §5.2-C 의 **CI 러너 패턴**(task_queue 잡으로 큐잉 → UE5 보유 기계가 claim)으로 이미 분리된다.
BC-250 에 UE5 가 없는 것은 문제가 아니다.

**진짜 이유는 셋이다:**

| 근거 | 내용 |
|---|---|
| **병렬성이 안 는다** | 워커는 **I/O 바운드**다 — 대부분을 LLM 응답 대기로 보낸다. 워커를 보드에 얹어도 같은 GPU 를 두고 경합할 뿐. **병목은 워커 호스팅이 아니라 추론 용량(보드 수)** 이다. §5.1 이 Go 대신 Python 을 고른 논리와 같다 |
| **메모리** | 14B 적재 시 `MemAvailable` 5.3GB. 거기에 git clone + 작업자 프로세스 + `claude`/`agy` CLI 를 얹으면 빠듯하고, 안정성 검증의 메모리 단조 감소(-620MB/30분)가 미해결이다 |
| **일회용성** | 노드에 CLI·자격증명·저장소 사본을 심으면 재구축이 어려워진다. 지금은 보드가 죽어도 전원만 다시 넣으면 복귀한다(§6.6) |

**따라서 병렬성은 보드를 늘려서 얻는다** — 마스터가 요청을 BC-250 #1/#2 로 분산하고,
보드가 늘면 병렬성이 자동으로 는다. 보드에 파일 작업을 얹어도 같은 GPU 를 두고 경합할 뿐이다.

> 반대로 갔다면 필요했을 것(참고): 노드에 저장소 클론 + `claude`/`agy` 설치 + 방화벽 확장 +
> "노드는 파일을 만지지 않는다" 원칙 폐기. 못 할 건 없으나 **얻는 게 병렬성이 아니다.**

### 2.2-a [주의] 그 기각이 2026-08-09 에 뒤집혔다 — **다른 이유로**

사용자 지시로 **BC-250 에 프로젝트 클론을 두었다**(`~/trunk/ModularStage`). 위 기각과 정면으로
부딪히므로, 무엇이 달라졌고 무엇이 그대로인지 적는다.

**[중요] 얻으려는 것이 다르다.** 위 기각은 *"병렬성을 얻으려고 보드에 파일 작업을 얹는가"* 에 대한
답이었고 그 판단은 **지금도 맞다** — 병렬성은 보드를 늘려서 얻는다. 오늘의 이유는 전혀 다르다:

> **판단의 원천은 소스코드다.** 로컬 모델은 파일을 못 읽어 규범만 주면 `CurrentStep`(실제
> `Step`) 같은 **한 글자 차이**를 지어낸다(실측 2026-08-09). 그 기계의 **Claude 가 소스를
> 읽어** 정확한 선언을 뽑아 모델에 넣어 주면 그 오류가 사라진다.

즉 **파일을 얹은 것은 모델이 아니라 에이전트**다. 모델은 여전히 텍스트만 받는다.

**그때 든 비용 중 이미 치른 것**: `claude` 는 BC-250 에 **이미 설치돼 있었다**(2.1.222).
방화벽 확장도 없었다 — 새 자격증명 없이 **기존 정방향 SSH 로 미러를 복제**했다.

**[중요] 그때 지적한 위험 중 아직 살아 있는 것 — 지우지 말 것:**

| 위험 | 지금 상태 |
|---|---|
| **메모리** | [중요] **미측정.** 35B 상주 시 `MemAvailable` 이 **513MB** 다(실측 2026-08-09). 그 위에서 Claude Code 를 돌리면 어떻게 되는지 **아직 안 재봤다.** 리포트 10 §8 이 이 보드를 정지시킨 것이 정확히 메모리 압박이었다 |
| **일회용성** | 보드가 죽으면 **클론도 다시 맞춰야 한다.** 지금은 마스터에서 rsync 로 복구되지만 **자동이 아니다** — "전원만 넣으면 복귀" 가 더 이상 완전하지 않다 |
| 디스크 | [완료] 문제없음 — 2.0GB / 여유 834GB |

**→ BC-250 에서 워커 에이전트를 실제로 돌리기 전에 메모리를 재라.** 35B 상주 + Claude Code 가
공존 가능한지가 미확인이고, 실패하면 조용히 느려지는 게 아니라 **보드가 멈춘다.**
