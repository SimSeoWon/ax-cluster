## 실마리 — 유휴가 아닌 연결

운영 8103 에 연결 하나가 남아 있었다. 마지막 요청 20:19:47 뒤 28분이 지났는데 uvicorn 은 유휴
연결을 5초면 닫는다. `ss -tni`: **마지막 수신 28분 전 · 마지막 송신 3.6초 전 · 데이터 세그먼트 115개**
— 서버가 약 15초마다 핑을 보내는, 끝나지 않은 응답이었다. 주인은 **이 세션의 Claude Code**(pid 182908)였고,
운영 로그엔 그 연결에 「POST 200」 만 두 번 있었다(202 도 GET 도 없음) — 내가 짐작한 순서와 달랐다.

요청 본문을 찍는 ASGI 래퍼로 실제 앱을 스크래치 포트에 띄우고 `claude -p --strict-mcp-config`
(haiku 1회)를 붙여 확보했다: Claude Code **2.1.295** 는 프로토콜 **2026-07-28** 로
`server/discover` → **`subscriptions/listen`** 을 같은 연결에 보내고, listen 을 세션 내내 SSE 로 연다.

## 재현과 원인

확보한 listen 본문을 그대로 재생한 뒤 SIGTERM — **실제 앱과 SDK 만 쓴 최소 서버(mcp 2.0.0 ·
uvicorn 0.52.1) 둘 다 100초가 지나도 안 꺼졌고**, 로그가 운영과 같았다.

원인: SDK 가 서버 종료 때 listen 스트림을 끝내지 않고, uvicorn 은 `timeout_graceful_shutdown=None`
이면 열린 응답을 무한히 기다린다 → systemd `TimeoutStopSec` 90초 → SIGKILL.
[주의] 첫 시도의 listen 재생은 400 이었다 — 파라미터를 짐작해 만들었기 때문. 실제 본문(`notifications`
구독 필드 포함)을 받아서야 재현됐다.

## 수정과 검증

사용자 선택 ①(② `TimeoutStopSec` 단축은 SIGKILL 을 앞당길 뿐 · ③ SDK 상류 보고는 별개).
분산 방식은 사용자 선택으로 로컬 서브 에이전트.

## 배운 것

- **통계로 안 갈리면 지금 살아 있는 사례를 본다** — 클라이언트 구성 비교는 아무것도 가르지 못했고,
  `ss -tni` 의 송수신 시각 하나가 「유휴가 아니다」를 말해 줬다.
- **클라이언트가 실제로 보내는 것을 잡는다** — 짐작한 요청(GET 스트림, list 류)으로는 전부 재현에
  실패했다. 요청을 기록하는 래퍼로 실물을 받은 뒤에야 재현됐다.
- **재기동의 정지는 옛 코드가 한다** — 수정 직후 재기동을 「실증」 이라 말했다가 정정했다. 실증은 그다음 재기동이다.
- 프로토콜이 클라이언트 쪽에서 바뀌면(2026-07-28) 서버 코드 변경 없이 운영 동작이 바뀐다 — 8/13 시작과의
  인과는 당시 클라이언트 버전 기록이 없어 확인하지 못했다.

## 남긴 것

- MCP SDK 상류 보고(종료 때 listen 스트림 미종료)는 하지 않았다.
- 빠르게 끝난 재기동 5회에 listen 스트림이 없었는지는 로그로 판정 불가.
- 다른 서비스(8101·8102)는 같은 기간 타임아웃 0 이라 같은 상한을 넣지 않았다 — listen 스트림을 받는지는 확인하지 않았다.
