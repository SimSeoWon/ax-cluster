## 5. 소 1.3.3 — 온톨로지 LLM 재합성 (중 1.3 의 마지막 LLM 조각)

`master/ontology/` 에 6모듈 신설. 결정적 부분(쓰기·검증·레이어·stale·수집)은 이미 있었고
**LLM 한 겹만** 비어 있었다.

    domain_md   도메인 MD 파싱        contexts  응집 조각화 + .h/.cpp 발췌
    prompt      actions/invariants    parse     응답 파서 + 결정적 필터
    synth       오케스트레이션         __main__  CLI (status·plan·verify·dry·refresh)

### 5.1 🔴 원본 파서를 그대로 옮기면 6/7 도메인이 조용히 빈다

원본 `_SECTION_PATTERNS` 는 6섹션 스키마만 안다. 실물은 **7개 중 1개만** 그 스키마다.
나머지 6개는 `시스템 개요` + `핵심 구현 패턴` + `확장 포인트` 라는 **제3의 사실상 표준**
(원본 `agent_defs.py:132` 가 에이전트에게 그 셋을 읽으라고 지시한다).

그대로 옮겼으면 6개 도메인이 `responsibilities=[]`·`boundary=[]`·`invariants=[]` 로 나오고
**파싱은 "성공" 으로 보고된다.** 실측 대조:

    GlobalEventSystem 서술량 — 원본 파서 322자  →  우리 1,225자 (3.8배)

**섹션을 전부 읽고 아는 것만 골라 쓰되 모르는 섹션은 남긴다.** 그리고 🔴 **없는 정규 섹션을
결과에 적는다**(`missing`) — 결손을 숨기면 다음 세션이 "원래 없나 보다" 로 읽는다.

### 5.2 🔴 프롬프트 예산을 실측으로 정했다

원본 상수(클래스 10 × `.h`3,000 + `.cpp`2,500 = **55KB**)는 **상용 API 전제**다. 우리 노드로
그대로 보내면 리포트 10 §8 의 사고를 반복한다. 그래서 `plan` 명령을 **LLM 0** 으로 먼저 만들고
`/api/generate` 의 `prompt_eval_count` 로 환산비를 쟀다:

| 프롬프트 17,315자 | 토큰 | 환산 | `num_ctx` 8192 여유 |
|---|---|---|---|
| 35B-A3B | 6,070 | 2.85자/tok | 2,122 tok |
| qwen2.5-coder:14b | 6,200 | 2.79자/tok | 1,992 tok |

**출력 여유가 2,000 토큰뿐이라 잘릴 자리였다.** JSON 5~15건에 2,500tok 을 확보하기로 하고
발췌 예산을 **11,000 → 7,000자**로 낮췄다. 전 조각이 **출력여유 3,459tok 이상**으로 들어간다.

### 5.3 🔴 페이로드를 조각내 두 노드에 나눠 던진다 (사용자 지시)

> *"컨텍스트 용량을 줄이진 않지만 페이로드를 분리해서 보내고 그걸 재합성할 수 있는 물리
> 성능이 있잖아."*

정확한 지적이었고 내 설계의 실제 결함을 짚었다. 단일 요청이면
`ProjectAlpha_UiViewManagement` 는 **67개 중 8개만 보이고 59개가 영영 안 보인다.**
**창을 못 늘리는 것과 데이터를 못 보는 것은 다른 문제**이고, 후자는 요청을 나누면 풀린다.

- **응집 순서로 자른다** — `#include` 그래프로 BFS. 이름순으로 자르면 한 액션의 참여자가
  서로 다른 조각으로 흩어져 **어느 조각에서도 안 보인다.** 실제로 `*_Renewal` 위젯 패밀리와
  `UWNDUIPage_*` 계열이 같은 조각에 모였다
- **`allowed` 는 도메인 전체 멤버**로 둔다 — 조각 단위로 좁히면 조각을 가로지르는 액션이
  통째로 버려진다. cross-domain 차단이라는 원래 목적은 그대로 지켜진다
- **레인당 in-flight 1** — 모델 이름이 곧 노드 선택이라, 모델당 스레드 하나면 노드당 1건이다

🔴 **다른 모델을 섞으면 핀이 깨진다.** 두 노드 다 `MAX_LOADED_MODELS=1` 이라 `.2` 에
`gemma3:12b` 를 요청하면 상주 14b 를 쫓아내고 브로커가 다시 올린다(~60초) — **왕복 스래싱**.
그래서 기본값은 **두 노드의 상주 모델**이다.

### 5.5 결정 3가지

- **objects 는 LLM 이 만들지 않는다** — 멤버·파일·레이어는 전부 결정적으로 나온다.
  물으면 있는 답을 지어내게 하는 것이고 틀릴 여지만 는다
- **actions 와 invariants 를 합쳐 부르지 않는다** — 프리필이 절반이 되지만 금지 규칙이
  서로 달라 지시 준수가 나빠진다. 우리의 실측된 실패 모드가 문장력이 아니라 형식 준수다
- **병합은 이름 기준이고, 그게 의미 종합이 아님을 명시한다** — 두 조각이 같은 흐름의
  앞뒤를 각각 보고 다른 이름을 붙이면 **둘 다 남는다.** 그 한계를 아는 채로 두는 것이
  조용히 하나를 버리는 것보다 낫다. 🔴 **대화형 에이전트가 나은 자리가 정확히 여기다**

| | 프롬프트 | 생성된 코드 |
|---|---|---|
| 규범 없음 | 1,251자 | `CurrentTaskIndex`(**헤더에 없다**) · `TaskList` |

그 `return` 이 **`ExecutorTickOnlyWhenRunning` invariant 그대로다**(*"틱은 CurrentState가
Running일 때만"*). 규범이 생성 결과를 바꿨다는 것이 실측으로 나왔다.

🔴 **그러나 환각이 사라지지는 않았다.** 소스와 대조하니:

    EMissionTaskExecutorState   → 실제 enum 은 `EMissionExecutorState`   (저장소 전체 0건)

**한 글자 차이의 근사 오류**다. 규범은 *무엇을 지킬지*를 주지만 **정확한 철자는 헤더에만
있다.** `docs/3-open-items.md` 의 *"추론 노드에 소스를 실어야 한다"* 가 이제 추측이 아니라

    <체크아웃>/CLAUDE.md            정본 본문 + 🔴 **머신별 AX 관리 블록**
    <홈>/.claude/skills/<이름>/     역할별 스킬

세 가지가 동시에 풀린다 — ⑴ 찾을 일이 없다(상대경로가 모든 머신에서 같다) ⑵ cwd 안이라
`--add-dir` 가 필요 없다(Claude 도구 범위가 cwd 기준, help 원문 *"the current directory"*)
⑶ **`.git/info/exclude`** 로 무시해 워킹트리를 안 더럽힌다. `.gitignore` 가 아닌 이유는
**마스터가 소스 저장소에 push 할 수 없기 때문**이다.

**CLAUDE.md 는 `/init` 으로 한 번 만들어 정본화**했다(226줄). 각 워커가 따로 `/init` 하면
서로 다른 문서가 생겨 지금 고치는 갈라짐이 재현된다. 🔴 그 본문에서 **머신 특정 서술을
걷어냈다** — `/init` 이 마스터 미러 기준으로 *"you cannot build here"* 를 써 놓아
`.2` 에서는 틀린 문장이었다. 머신 차이는 **관리 블록**에만 둔다.

### 14.4 역할 — `driven` 과 `role` 은 다른 축이다

사용자 정리: *"메인 작업 PC는 서버 마스터만 알면 되는 거고, 작업 요청하고 처리하는 것이나
온톨로지 등록 요청 등의 MCP들을 등록하는 것만 할 거고, 워커는 워커만의 내용이 있지 않을까?"*

    driven   닿을 수 있나   ssh | interactive
    role     시켜도 되나    worker | requester

🔴 **`.33` 은 SSH 가 열려 있어도 `requester` 라 `drivable_hosts` 에서 빠진다.** 사람이
편집 중인 트리에 일감을 파견하지 않는다. 스킬도 갈린다 — worker 는 `ax-work`,
requester 는 `ax-request`·`ax-ontology`.

### 14.5 🔴 능력 표의 축을 사용자가 바로잡았다

처음엔 UE5 유무를 앞세워 적었다. 사용자 지적: *"이 기능은 판단의 원천인 소스코드를 기반으로
클로드가 판단하라는 게 주안점인데 왜 .2 머신만 말한 거야?"* — 맞다. **소스 판단은 클론을
가진 모든 워커의 공통이자 본령**이고, UE5 는 그 다음 축(검증 가능 여부)이다.

이제 두 워커가 **같은 첫 문장**을 갖는다:

> 🔴 **소스를 근거로 판단한다** — 체크아웃 전체를 직접 읽고 선언부로 사실을 확인한다
> (**이것이 워커의 본령이고 모든 워커가 동등하다**)

BC-250 에는 *"컴파일·에디터·테스트만 안 된다. 소스 판단·코드 작성은 다른 워커와 똑같다 —
못 하는 것은 **옳음의 최종 판정**뿐"* 이 붙는다. 그리고 능력의 **결과**를 적는다:
`ue5 ❌` 가 아니라 *"층3 검증을 여기서 할 수 없다 → `ue5` 워커의 검증을 거쳐야 한다"*.

### 14.7 1인 + N워커 루프 확정 (`docs/8-git-authority.md` §8.4)

사용자가 대화로 확정한 것들:

1. **요청자가 durable `task/<id>` 를 원격에 만든다** — 마스터는 push 를 못 하므로(§2.1)
   push 권한이 있는 사람의 체크아웃이 그 자리다
2. **성공·실패 무관하게 attempt 를 push 한다** — *"안 그러면 실패 처리가 애매해져"*.
   버리면 무엇을 시도했는지 사라지고 피드백 근거도 없다
3. **피드백은 코드 위치에 `[FEEDBACK]` 블록으로 박는다** — 골조의 `[PSEUDO]` 와 같은 자리.
   큐의 텍스트만으로는 워커가 *어디를* 고칠지 모른다. 🔴 **재구현이 아니라 수정**(누적 모델)
4. **durable 은 오래 사는 작업 공간이고 머지는 끝에 사람이 한 번** — 이것이 AgentTest 를
   복잡하게 만들던 압력을 없앤다. `verify_worker.py`(314줄)의 CAS·머지 권한 이전은
   **재설계가 아니라 불필요**해진다
5. **층3 은 요청자가 가장 빠르다** — `.33` 에 UE5 가 있다. ⚠️ 단 **메인 워킹트리에서
   브랜치를 갈아타지 않는다**(`git worktree`). 사람의 미커밋 작업은 되살릴 수 없다
6. **언제든 멈출 수 있다** — 큐에 `cancel` 과 worker directive(화이트리스트·fire-once)가
   **이미 이식돼 있었다.** 🔴 즉시가 아니라 **다음 하트비트**에 멈춘다

**원본 대조**: 3번은 원본이 이미 검증한 형태다(`verifier.py:85` *"worker 브랜치에 feedback
주석을 target_file 상단에 박아 commit + push"* · `verify_worker.py:9~11` *"reject → durable 을
attempt 로 fast-forward(구현 누적) 후 [FEEDBACK] commit … 재구현 아님"*). 그리고 **게이트는
이미 이식돼 있다** — `layer2_verify.py:46` 이 `[PSEUDO]/[FEEDBACK]` 잔재를 검사한다.

## §17. 워커 찌꺼기 정리 (중 2.5.4, 레드마인 #27)

`python -m master.work.cleanup plan|apply`. 🔴 **워커는 스스로 못 지운다** — 스킬의 git 금지
목록에 브랜치 삭제가 있고 그건 의도다. 그래서 마스터가 치운다.

### 17.1 지우는 기준은 하나

    로컬 브랜치 삭제  ⇔  팁이 origin/<base> 에서 **도달 가능**하다
                        (= 정말 병합됐다 = 지워도 잃는 것이 없다)

도달 불가·확인 실패·fetch 실패는 **전부 보존**한다. 🔴 *fail-closed 의 방향이 여기서는
"보존"* 이다 — *"항상 attempt 를 push 한다"* 가 증거 보존이 목적이므로, 증거가 다른 곳에
살아 있음을 **확인하기 전에는** 없애지 않는다.

경계 셋을 더 뒀다: **원격은 건드리지 않는다**(`push --delete` 는 사람의 판단, 세어서 보고만) ·
부산물은 `verified`/`cancelled` 만 지우고 **`failed` 는 남긴다**(왜 실패했는지 볼 유일한 기록) ·
큐를 못 읽으면 부산물은 아예 손대지 않는다.

### 17.2 사용자 결정 — 작업 후 워커는 `main` 으로 복귀한다

*"작업 완료되면 브랜치도 다시 메인으로 돌아가는게 맞을꺼같아"*. 정리와 직결된다:
**체크아웃된 브랜치는 삭제 대상에서 빠지므로**, 워커가 `task/<id>` 에 앉아 있으면 그 브랜치는
영영 정리되지 않는다. 스킬의 종료 자세를 기준 브랜치 → `main` 으로 바꾸고, 정리기도 복귀를
수행한 뒤 **한 번 더 훑는다**(2회차를 사람이 기억해야 하는 건 설계가 아니다). ⚠️ 복귀는
`Source/` 가 깨끗할 때만 — 더러우면 체크아웃이 사람의 편집을 건드린다.

### 17.3 🔴 실측으로 잡은 셸 함정 둘 — 한쪽만 조용히 깨졌다

| 증상 | 원인 |
|---|---|
| 두 워커 다 브랜치 **0건** | `--format=%(refname:short) %(objectname)` 의 **공백을 원격 셸이 쪼개** git 이 뒷부분을 *패턴*으로 읽었다 → 구분자를 `:` 로(refname 에 못 쓰는 문자) |
| `.2` 는 되는데 `.43` 만 "브랜치 목록 실패" | 🔴 **`%(...)` 의 괄호가 POSIX 셸 문법**이다. cmd 는 그냥 넘겨서 **윈도우만 통과**했다 → 셸별로 따옴표를 다르게 감싼다(`'…'` / `"…"`) |

**두 번 다 "한쪽만 깨지는" 모양이었다** — 한 대에서만 확인했으면 통과로 착각했을 것이다.

## §18. 요청자(`.33`) 배선 완료 — ①~⑥ 이 실제로 한 바퀴 돌았다 (중 2.5.5)

### 18.1 `.33` git 인증 — SSH 키 (사용자 승인)

HTTP + GCM 이 비대화형에서 막혔다(실측): `wincredman` 저장소에 자격증명을 **저장할 수 없고**,

### 18.2 🔴 UE5 탐지가 `.33` 을 **잘못 재고 있었다**

    .2   C:\Program Files\UE_5.8\...              (직접 설치)
    .33  C:\Program Files\Epic Games\UE_5.8\...   (런처 설치)

**프로브 안에 경로를 박으면 같은 병**이다.

🔴 고치는 중에 회귀를 하나 만들고 잡았다: `if exist A (echo A) & if exist B (…)` 는 cmd 에서
**괄호를 써도** `&` 뒤가 첫 조건의 참 분기로 들어간다. 첫 후보가 있는 `.33` 은 통과하고 첫
후보가 없는 `.2` 는 **0줄**이 나왔다 — rc 는 양쪽 다 0이라 종료 코드로 구분되지도 않는다.
`for /d` 로 바꾸고 **rc 가 아니라 출력으로** 판정한다. 버전도 글롭에 박지 않는다(`UE_*`).

## §21. 생성 시점 선언부 주입 (레드마인 #26)

⚠️ **여전히 못 잡는 것**: *"디테일 패널은 함수맵으로 라우팅된다"* 같은 **설계 규칙 서술**은

현재 상태는 **의심 0**(방금 현재 커밋 기준으로 보호했으니 당연하다). 🔴 **깨끗한 보고는
아무것도 증명하지 않으므로** 좁히기 로직은 의존을 주입한 테스트로 못박았다 — 무관한 파일이
바뀌면 조용하고, 근거 파일이 바뀌면 잡고, 유령·사라진 클래스는 커밋과 무관하게 잡는다.

### 23.1 확장기 — 부분 문자열, 그리고 그 대가를 막는 두 가지

한국어엔 조사가 붙는다 — 「몬스터**를** 스폰한다」의 토큰은 「몬스터」가 아니다. 형태소

오탐이므로 둘로 막는다:

    🔴 MIN_TERM=2   한 글자 별칭은 어디에나 들어간다 (「적」이 「목적지」에)
    🔴 MAX_EXPAND=6 확장은 거들 뿐 — 질의를 대체하지 않는다

🔴 **원본을 지우지 않고 덧붙이기만** 한다(확장이 틀려도 0건으로 떨어지지 않게), 그리고

## §24. 질의 → 도메인 결정적 추론 (소 2.2.2)

`search_norms` 와 성격이 다르다:

    search_norms   BM25 + 벡터로 **닮은** 도메인      통계 · 순위 · 언제나 뭔가 나온다
    infer          질의에 나온 **클래스의 소속**      결정적 · 근거 있음 · 없으면 없다

후자가 맞으면 **근거를 댈 수 있다** — *"`UMissionTaskExecutor` 가 MissionRuntime 소속"*.

### 24.1 🔴 출처를 바꿨다 — `class_ontology` 표는 죽어 있다

마일스톤은 *"(`class_ontology` 읽기)"* 라고 적어 뒀는데, 실측하니 그 표는 **행이 0** 이다.
우리 파이프라인이 채우지 않는다. 실제 소속은 각 도메인의 `objects/*.yaml` 에 있고
`collect.classified_elsewhere` 도 거기서 읽는다. **죽은 표를 근거로 삼지 않았다** — 111개
클래스의 소속을 패키지에서 읽는다.

### 24.2 🔴 모르면 비운다 — 이게 존재 이유다

    「UMissionTaskExecutor 를 고쳐줘」  → MissionRuntime (질의에 직접)
    「미션 태스크 실행 흐름」            → MissionRuntime (별칭: 미션 태스크 / 태스크 실행)
    「다이얼로그 매니저 버그」           → MissionSystemTools (별칭: 다이얼로그 매니저)
    「UNknownClass 수정」              → 추론 불가 (미배정 후보 1: UNknownClass)
    「오늘 날씨」                      → 추론 불가

산문에서 도메인 이름을 닮은 말을 찾아 추측하지 않는다. 그 일은 `search_norms` 가 하고
그쪽은 노이즈 3중 차단을 갖고 있다 — 여기서 추측하면 *"결정적"* 이라는 유일한 값어치가 사라진다.
한글 질의는 식별자를 안 쓰므로 **시소러스 별칭이 실질 경로**다(소 2.2.1 과 짝이다).

### 24.3 소비처 — 규범 수집에 붙였다

`norms.attach` 가 추론을 먼저 보고 **순서를 바꾼다.** ⚠️ **대체하지 않는다** — 추론이 좁게
틀렸을 때 통계 히트를 잃으면 안 된다. 예산이 도메인 수를 자르므로(`MAX_DOMAINS=2`) 근거 있는
것이 먼저 실리는 것만으로 충분하다. 그리고 매니페스트 본문에 근거를 찍는다:

    _추론: UMissionTaskExecutor → MissionRuntime (질의에 직접)_

워커가 **이 도메인을 왜 믿어야 하는지** 알아야 하기 때문이다 — 통계로 닮은 것과 소속으로
짚은 것은 신뢰도가 다르다.

## §25. 도메인 뷰어 (소 2.4.2) — 그리고 그것이 잡아낸 것

### 25.1 🔴 서비스를 띄우지 않았다

마일스톤이 *"읽기 전용이면 yaml 파싱만으로 가능"* 이라 적어 뒀고 실제로 그렇다. **자립형
HTML 한 장**(외부 자원 0, CSS·JS 인라인)이다. 서비스를 늘리면 포트·베어러·ufw 가 따라붙는데
읽기 전용 뷰어에 그 공격면을 늘릴 이유가 없다.

⚠️ **내부망 공개는 보류했다** (사용자 결정 2026-08-10: *"파일로만 두고 공유는 나중에"*).
그 과정에서 두 가지가 드러났다 — 손대지 않고 보고만 한다:

    80/tcp    ALLOW Anywhere   ← apache2 가 물고 있다 (nginx 아님). LAN 한정이 아니다
    3000/tcp  ALLOW Anywhere   ← Gitea. REQUIRE_SIGNIN_VIEW 는 켜져 있다
    8101~8103 ALLOW 192.168.0.0/24  ← AX 3서비스는 규칙대로

### 25.2 🔴 manifest 를 믿지 않고 파일을 훑었더니 결함이 나왔다

    MissionEditor/L3/objects/UEditorView_MissionTaskEditor_Renewal.yaml

**파일은 있는데 `domain.yaml` 의 `objects` 목록에 없다.** 색인 페이로드와 `sync` 는 manifest
를 근거로 삼으므로 이 클래스는 **검색에도 동기화에도 빠져 있었다.** 전 도메인을 훑어 불일치는
이 1건뿐이고, **백업(받아온 스냅샷) 시점에도 동일**했다 — 내 refresh/복원이 만든 것이 아니다.

manifest 만 읽는 뷰어였다면 **영영 안 보였을 것**이다. 그래서 뷰어가 파일을 훑고, 불일치를
**첫 화면에** 적는다.

### 25.3 첫 화면에 무엇을 두었나 — 숫자가 아니라 판단 재료

    ⚠️ 도메인 경계 절이 없는 도메인 6개 — 합성이 다른 도메인의 클래스를 끌어올 수 있다
    🔴 manifest 에 없는 항목 파일 1개 — 검색에도 동기화에도 빠져 있다

항목마다 🔒 보호 표식과 **기준 커밋**을 함께 보여준다(드리프트를 볼 근거), 별칭·소스 경로·

## §26. MD 태그 전파 — 그리고 🔴 내 앞선 보고를 정정한다

### 26.1 정정: *"7개 중 6개 MD 에 `tags` 가 없다"* 는 **오독이었다**

awk 로 프론트매터를 잘라 세었는데 그게 틀렸다. **파서로 재보니 전부 있고 `domain.yaml` 과도
일치한다**(받아온 스냅샷이 양쪽을 맞춰 보냈다):

    도메인 MD 태그   8~15개 전부 존재 · 한글은 MissionSystemTools 4개뿐
    domain.yaml     MD 와 개수·한글 수 일치

이 오독은 리포트·스킬·마일스톤 세 곳에 퍼져 있었다. 세 곳 다 고쳤다.
🔴 **파서가 있는데 awk 로 센 것이 잘못이다** — 같은 파일을 두 가지 방법으로 읽으면 갈라진다.

### 26.2 🔴 그래도 전파 구멍은 실재했다 — 막았다

`synth.py` 는 `manifest_extra={"summary": …}` 만 넘겼다. 즉 **사람이 MD 에 한글 태그를 넣고
`refresh` 를 돌리면 그때 사라진다.** 지금까지 어긋나지 않은 것은 *아무도 MD 태그를 손대지
않았기 때문*이지 안전해서가 아니다.

`_manifest_extra()` 가 MD 태그를 싣되 🔴 **합치고 덮지 않는다** — `package.write` 는
`manifest_extra` 를 얕게 덮으므로(`man.update`) 미리 union 을 만든다. 순서는 **기존 것 먼저**
(사람이 정한 우선순위를 흔들지 않는다).

### 26.3 진짜 문제는 전파가 아니라 데이터였다

한글 태그가 전체 86개 중 **4개**다. 그래서 한글 검색의 실효 수단은 여전히 **별칭**이고,
소 1.4.4 에서 10개를 등록해 그 길을 냈다(§23). 전파는 *앞으로 넣을 것*을 지키는 장치다.

믿지 말고 파일을 훑는다) · 사람의 자리(`protected` ≠ `verified_by_user` · 보존만 있고 설정이
없으면 死코드다 · 레인이 결과를 가른다) · 분산(토큰을 안 준다 · 묶으면 싸고 워커를 늘리면
비싸다 · `main` 으로 복귀) · **조용히 틀리는 것들**(rc=0 인 scp 실패 · 원격 셸 문법 ·

### 30.2 함정 다섯 — 원전이 값을 치르고 배운 것

- 🔴 **reject 는 폐기·재구현이 아니라 전진·수정이다**(2026-06-21 정정, 사용자 확정). 옛
  구현은 reject 마다 durable 을 골조로 되돌려 **맞게 짠 코드까지 버렸다.** 동반 잠복 버그가
  더 무섭다 — *"모든 주석 보존"* 지시가 `[FEEDBACK]` 블록 삭제를 막아 **검증이 무한 실패**
  했고, **approve 경로만 본 셀프테스트가 그걸 못 봤다.**
- 🔴 **워커 1대면 데드락**이었다. 우리는 2대지만 **하나가 더티하면 1대**다.
- 🔴 **샌드박스는 거짓 자신감을 준다** — 실 e2e 만이 exe 미번들 · 빌드캐시 staleness ·
  `.claude/` 가 gitignore 라 매니페스트 커밋이 **rc=1 로 실패**하는 것을 드러냈다.
- ⚠️ **태그는 두 종류다** — `[PSEUDO]`/`[IMPL]` 은 지우고 `[DOC]`/`[STATE]`/`[BIND]`/
  `[REPLICATED]` 와 무태그 주석은 보존. getter/setter 엔 주석 금지.
- ⚠️ **Redmine 상태는 이름→id 동적 매핑**이다. 🔴 우리는 `status_id:4` 하드코딩 — **지금은
  맞지만 근거 없이 맞는 중**이다.

### 30.3 🔴 우리 코드의 버그 — `.h`/`.cpp` 가 아니라 **모듈** 문제였다

원전이 `.h`/`.cpp` 짝 찾기에서 겪은 사고를 읽고 우리 `batching.units()` 를 재 봤다.
**우리는 그 방향으로는 멀쩡했고, 반대 방향으로 틀려 있었다.**

    같은 모듈 · 다른 폴더(UE Public/ ↔ Private/)    50건   ✅ 우리 stem 방식이 이미 붙이고 있었다
    🔴 다른 모듈 · 같은 이름                          9건   ❌ 한 단위로 **잘못 묶고 있었다** (36파일)

⚠️ **헤더와 cpp 가 서로 덮어쓰던 문제가 아니다** — 짝짓기는 정상이었다. 열쇠가 basename
(`Alpha_HexagonTileItem`) 뿐이라 **경로가 다른 별개의 파일들**이 한 열쇠로 뭉친 것이다.
그리고 그 9건이 하필 전부 **포팅 원본↔대상**이었다:

    ModularStage/UI/HexGrid/Alpha_HexagonTileItem.{h,cpp}
    Project_Alpha/UI/Components/Hexagon/Alpha_HexagonTileItem.{h,cpp}   ← 원본, 읽기 전용

한 단위가 되면 워커에게 *"이 넷은 한 몸이니 같이 고쳐라"* 가 된다 — 원전이 **"원천 소스
Edit/Write 절대 금지"** 라고 못박은 바로 그것이다.

**고침**: 열쇠를 basename → **모듈 + 경로(`Public`/`Private`/`Classes` 제거) + stem**.

    실제 저장소 1,654 파일   850 → 859 단위
    .h/.cpp 짝이 붙은 단위    795          모듈을 넘어 묶인 단위  0
    묶음 215개 · 겹침 0        테스트 20/20 (신규 케이스 2종)

🔴 **독파가 없었으면 이 버그는 첫 분산 작업에서 원본을 고치고 나서야 드러났을 것이다.**
문서를 읽는 일이 "나중에 할 것" 으로 밀려 있던 값이 이만큼이다.
