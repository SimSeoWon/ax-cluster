## 2. `#276` — 유닛에 프로젝트 이름이 박혀 있었다

`ReadWritePaths=…/ModularStage/recipes` 형태였다. 결과 둘:

    ⓐ 표면을 늘릴 때마다 손으로 경로 추가 → `ontology/` 가 빠져 **시소러스 대행이 처음부터
      500**. 비마운트 방어가 아니라 **마운트된 프로젝트조차** 실패했다
    ⓑ 새 프로젝트(NS)는 애초에 불가능 — 유닛에 이름이 없으니까

[중요] **나는 그 500 을 「우리 코드가 막았다」고 잘못 읽었다** (전 세션). 막은 것은 systemd
샌드박스였고, 그것은 의도된 방어가 아니다. 트윈 루트를 열고 `#206` 의 의도(*"큐가 저장소 코드를
쓸 수 있게 되면 안 된다"*)는 `ReadOnlyPaths` 로 지켰다 — 경로를 좁히는 대신 코드를 되돌린다.

실측: 커널 마운트 테이블(`/proc/<pid>/mountinfo`)에서 루트 `rw`, 코드·문서·git 전부 `ro`.

[주의] **저장소 사본과 실물 유닛이 어긋나 있었다** — 실물에만 3줄(`AX_PROJECTS_ROOT` 포함).
손으로 고친 유닛은 다음 배포가 되돌린다. `test_sandbox.py` 가 그 드리프트를 잰다.

## 3. 태그 — 선언 표 하나, 사유 셋, 축 둘

엔드포인트마다 `if` 를 뿌리면 다음에 추가되는 엔드포인트는 태그가 없다. **실측이 그랬다**:
`#243` 이 시소러스 둘만 배선하고 `signals`·`history`·`claim` 을 남겼다. 그래서 표 하나
(`master/task_queue/tagging.py`)에 35라우트 4정책을 선언하고, **선언 없는 라우트가 생기면
테스트가 깨지게** 했다.

    no_project_tag     태그를 안 보냈다          → 고칠 곳: 발신자 배선
    not_mounted        다른 프로젝트다            → 고칠 곳: 마운트 전환
    project_mismatch   이 work 의 스탬프와 다르다  → 고칠 곳: 요청자의 착각

[중요] **`STAMP` 표면은 태그 필수에서 뺐다.** 거기엔 스탬프라는 판정 근거가 있어 「가정」이
아니다. 필수로 만들면 미종결 work 를 둔 채 마운트를 바꿨을 때 `#210` 이 지키려던 흐름이 깨진다.
같은 이유로 마스터 쪽 발신자는 **필수 표면에만** 태그를 붙인다.

사용자 결정이 규칙의 출처다: *"태그 없으면 동일하게 마운트 다름으로 처리해야지 그러다가 엉뚱한
데이터로 오염되는거잖아"*. 그 **사유**(오염)에서 선이 그대로 나온다 — 오염 경로는 태그가 없어
마운트로 가정하는 자리이고, 읽는 표면은 오염이 없다.

## 4. [중요] 실물 사고 — 문서가 예고한 순서를 내가 어겼다

`docs/12-multi-project.md` §12.5-c 에 이렇게 적혀 있었다:

> *"판단이 클라이언트보다 앞서면 태그 없는 요청이 전부 거절되고, 클라이언트가 서버보다 앞서면
> 서버가 모르는 인자를 받는다."*

나는 서버를 먼저 조였다(22:38). 배달은 22:55 였다. 그 20분 동안:

    .43 상주  22:40 시작 → 옛 코드(태그 안 보냄) → 서버가 200+ok:false 로 거절
              옛 코드는 `st == 200` 만 봐서 **거절을 태스크로 읽었다**
              → 빈 task_id 로 submit-fail 무한 반복. 로그 4.4MB · 큐 저널 44,343줄

피해 범위를 실측으로 갈랐다: **큐 상태·감사 파일 피해 없음**(works 25 전부 스탬프, 빈 task_id
0건, 큐 로그 최대 파일은 08-18 자 11K). 빈 `task_id` 요청은 상태에 닿기 전에 거부됐다.

[중요] **`.2` 는 우연히 살았다** — 그 상주가 배달 뒤(23:01)에 떠서 새 코드였다. 우연이 방어였다.
그래서 `#277`(배달이 상주를 갱신하지 않는다)을 신설했다. 확인 방법도 적어 뒀다: **파일 해시가
아니라 도는 프로세스를 본다** — 이번에 파일은 이미 맞았는데 사고가 났다.

정리: `.43` 상주를 죽였고 cron 감시자가 23:01:38 에 새 코드로 되살렸다(자기 치유가 이미 있다).
재기동 뒤 최근 120초 **거절 0건 · 정상 204 12건**, 두 워커 모두 태그를 실어 보낸다.

## 6. 스탬프 백필 21건 — 태그 계약의 숨은 선결

`work_id` 만 있는 요청은 스탬프가 없으면 마운트로 떨어진다. 태그를 필수로 해도 남는 오염
경로다. 21건 전부 `target_repo` 가 ModularStage 를 가리키고 최후 생성이 08-19(NS 는 08-22
신설)라 근거가 확실했다. **지금 25/25 전부 스탬프를 갖는다.**

[주의] 백필 도중 「디스크 7건 vs API 4건」 불일치를 「저장했는데 안 읽는 값」으로 의심했으나,
`project: null` 을 내 정규식이 스탬프로 센 것이었다. **불일치를 발견하면 내 계측기를 먼저
의심할 것** — 이번엔 디스크와 API 가 실제로 일치했다.

## 7. 여기서 배운 것

1. [중요] **테스트가 통과하는데 서버가 안 뜨는 상태를 만들었다.** 소스를 텍스트로만 읽는 테스트는
   `SyntaxError` 를 못 본다. `Restart=always` 때문에 `ActiveState=active` 도 나를 속였다.
   → `test_tagging` 이 AST 파싱을 한다. **「배선했다」의 판정은 파싱 + 라이브다.**
2. [중요] **경고를 문서에 적는 것과 순서를 지키는 것은 다른 일이다.** §12.5-c 가 이 사고를
   문장으로 예고했는데도 어겼다. 문서를 읽는 것으로는 안 되고, **순서를 실행 계획에 넣어야** 한다.
3. [중요] **선언이 한곳에 없으면 다음 것이 빠진다.** `#243`(엔드포인트 둘만) · 유닛(프로젝트
   이름 하드코딩) 둘이 같은 병이었다. 표 + 「선언 없으면 테스트 실패」가 그 병의 약이다.
4. [주의] **거절과 장애를 클라이언트가 가르는지 확인할 것.** 서버가 200+ok:false 로 옳게
   말해도, 받는 쪽이 상태 코드만 보면 거절을 성공으로 읽는다. 계약은 양쪽이 지켜야 성립한다.
5. [주의] **사용자가 든 「사유」에서 규칙을 도출하면 범위가 스스로 정해진다.** 「오염」이라는
   사유가 「쓰는 표면 필수 · 읽는 표면 선택」을 정했다 — 내가 임의로 좁힌 것이 아니다.
