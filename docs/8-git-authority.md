## 8. git 조작 권한 — 사람 세션과 파이프라인을 분리한다 (2026-08-07)

**AgentTest 는 "Claude 는 절대 커밋하지 않는다(사용자가 시켜도 금지)"는 절대 규칙을 갖고 있다.**
계기는 2026-07-12 사고 — 사용자의 **"중간 커밋하고 올게"**(본인이 하겠다는 **1인칭 서술**)를
지시로 **오독**해 임의로 `git commit` 을 실행했고, 사용자가 "다 지워진 줄 알고 깜짝 놀랐다"고 항의했다.
결론은 "의도를 더 잘 판별하자"가 **아니라 판별을 포기하고 금지를 절대화**하는 것이었다.
`build.bat`/배포/데몬 재기동도 같은 형태로 묶여 있다("빌드할까요?" 같은 질문 형태조차 금지).

**[주의] 그 규칙을 이 프로젝트에 그대로 복사하면 안 된다.** AgentTest 규칙이 막은 것은
**"개발 저장소에서 Claude 가 사람 대신 커밋하는 것"** 이지, **파이프라인이 설계대로 하는 git 조작**
(워커가 `task/<work>/<task>` 브랜치에 커밋, durable merge CAS)이 아니다. 후자는 plan v5.0 C.3 의 정상 동작이다.
**AX 클러스터는 마스터가 자율 오케스트레이션을 하므로 이 둘이 섞이기 쉽다** — 권한을 명시적으로 나눈다.

### 8.1 사람 세션 (Claude Code — 윈도우 오케스트레이터 ① / 마스터 작업 세션)

| 구분 | 규칙 |
|---|---|
| [완료] 요청 시 실행 | `add` · `commit` · `push`(일반) · `fetch`/`pull --ff-only` · 조회 계열 전부 |
| [실패] **실행 금지 — 되돌리기 어려움** | `push --force` · `reset --hard` · 브랜치/태그 **삭제** · `rebase` · 히스토리 재작성 · `clean -fdx` |
| 원칙 | 금지 항목은 **명령형 지시를 받아도 실행하지 않고**, 실행할 명령을 안내한다 |

- 이 저장소(`ax-cluster`)에 적용한다. **AgentTest 저장소는 참조용이라 애초에 커밋하지 않는다**
  — 그쪽 `CLAUDE.md` 의 절대 금지 규칙과도 일치한다.
- 1인칭 서술("~하고 올게", "~할게")을 지시로 읽지 말 것. 애매하면 되묻는다.

### 8.2 파이프라인 (윈도우 작업자 하네스 · 마스터 자동화 — 자율 실행)

**사람 세션 규칙의 적용 대상이 아니다.** 설계상 자율로 해야 하는 일이 있다.

| 구분 | 규칙 |
|---|---|
| [완료] 자율 허용 | `task/<work_id>/<task_id>` 및 attempt 브랜치 생성·커밋·push, `[FEEDBACK]` 커밋, durable merge(**CAS**), **`<remote>/main` 에서 도달 가능한 `attempt/`·`task/` 삭제** (#219 2026-08-18 · `finalize_work` 2026-08-21) |
| [실패] **금지** | `main` 직접 push · `push --force` · 히스토리 재작성 · 사람이 만든 브랜치 삭제 · [중요] **미병합(도달 불가) 브랜치 삭제** — 그 커밋이 거기에만 있을 수 있다 |
| 필수 | **CAS(compare-and-swap)로만 durable 전진** — 좀비 워커 방어(plan v5.0 C.2). 모든 조작은 로그로 추적 가능해야 한다 |

- 작업 브랜치는 워커의 것이고, `main` 은 사람의 것이다. **이 경계가 두 규칙을 가르는 기준이다.**
- 오케스트레이터가 둘이므로 **같은 브랜치에 동시 접근이 실재한다**(§2.2-5) — fencing 을 걷어내지 말 것.

### 8.3 [중요] 완료 신호를 믿지 말 것 — 산출물을 검증한다

**실측 사고 (2026-08-07, 마스터 리포트 04):** `agy` 에 "파일을 작성하라"고 지시했더니
`status:"SUCCESS"` + `response:"DONE"` 을 반환했는데 **파일이 어디에도 생성되지 않았다.**
원인은 print 모드가 기본적으로 편집 비활성이라 `--mode accept-edits` 가 필요했던 것 —
**작업은 무시되고 완료 신호만 온 것이다.**

AgentTest 가 이미 같은 계열 문제를 다루고 있다: `**TASK_COMPLETE**` 센티넬의 관대 인식,
`worker/validator.py` 의 제출 전 자기검증(`_frozen_decls`), `claude_spawn.syntax_check`.
**존재 이유가 이것이다 — 위임한 백엔드의 "완료" 주장을 그대로 믿으면 안 된다.**

**규칙: 위임 결과는 반드시 두 가지를 모두 확인한다.**
1. 반환된 상태(`status` / 종료코드 / 센티넬)
2. **산출물의 실제 존재와 내용** (파일 생성 여부, diff 적용 여부, 컴파일 통과 여부)

이 검증이 없으면 자동화에 **조용히 빈 결과가 흘러간다.** §4.3 의 3층 게이트가 층1 부터
결정론적 검사로 시작하는 것도 같은 이유다.

**[주의] 산출물이 존재해도 부족하다 (2026-08-07 2차 실증, 리포트 05).** `agy` 에 Unreal MCP 리서치를
위임했더니 파일도 생겼고 내용도 80% 정확했는데, **설계 결정을 좌우하는 절이 틀렸다** —
"Bind Address 를 `0.0.0.0` 으로 바꾸면 LAN 접속 가능"이라며 4단계 절차까지 서술했으나
실제로는 서버가 non-loopback `Origin` 을 거부하고, 함께 제시한 `Require Capability Token`
설정은 **존재하지 않는 기능이었다.** 그대로 믿었으면 아키텍처가 틀어졌다.
또 "실제 참조 URL"을 명시 요구했는데 **도메인 루트만 반환**했다(검색을 안 한 신호).
**→ 위임은 초안 생성용으로 쓰고, 사실 확정은 1차 출처로 한다. 출처를 요구하고 그 출처를 열어볼 것.**

## 8.4 작업 브랜치 수명주기 — 1인 + N워커 (사용자 확정 2026-08-09)

> 사용자: *"기존 AgentTest 는 여러 명이 하나의 프로젝트를 관리하다 보니 git 버전 관리가
> 고민이었는데, 이제 단일 1명의 작업자이고 여러 대 워커가 도와주는 것"* /
> *"실패 처리를 위해 메인 작업 PC에서 시작할 때 원격 브랜치를 만들어야 할 듯"* /
> *"성공하던 실패하던 작업용 원격 브랜치에 커밋하고, 검증 요청이나 메인 작업 컴퓨터가 검증"*

### 누가 무엇을 만드나 — [중요] **쓰는 주체는 하나다** (사용자 확정 2026-08-11, 아래 표를 대체)

> 사용자: *"워커들이 이 브랜치에 등록된 내용을 기준으로 추론을 하고 응답하면 메인 작업
> 컴퓨터가 빌드 되는지 적합한지 판단하고 원격 브랜치에 직접 커밋하는게 좋을꺼같아"*
> → 구조는 그대로 채택하고, **그 역할을 `.33` 이 아니라 `.2` 에 둔다**(아래 「왜 `.2` 냐」).

| 주체 | 하는 일 | 왜 그 주체인가 |
|---|---|---|
| **요청자** (`.33`, 사람의 PC) | ① `main` 최신화 ② [중요] **작업 브랜치 `task/<work_id>/base` 를 만들고 골조를 실물로 커밋해 push** (`#319` — 조각은 여기서 갈라진다) ③ 등록 ④ 최종 리뷰·`[FEEDBACK]` | [주의] 여기 있던 *"마스터는 소스 저장소에 push 할 수 없다(§2.1)"* 는 **2026-08-14 에 좁혀졌다** — 마스터는 `attempt/*`·`task/*` 에 쓴다. 남는 근거는 **`main` 은 사람이 보는 자리**라는 것이고, 그것은 그대로다 — 파이프라인이 `main` 에 커밋을 밀어넣지 않는다 |
| **마스터** | 큐·매니페스트·라우팅·**골조 생성** · [중요] **attempt/durable 커밋** (정정 2026-08-14) | [주의] *"파일을 소유하지 않는다"* 는 **Flow Y 로 좁혀졌다** — `attempt/*`·`task/*` 에만 쓰고 **`main` 과 빌드는 못 한다**(§2.2-1 2차 정정) |
| **작업장** (`.2`·`.43`) | durable/base 를 fetch → 작업 → [중요] **ephemeral `attempt/<work_id>/<task_id>/<workshop>/<ts>` 에 push** | [중요] **쓴다 — 다만 ephemeral 에만.** 공유 write 타깃이 없어 zombie push 충돌이 **구조적으로** 소멸한다 |
| **검증·머지 주체** | attempt 를 검증하고 [중요] **통과분만 durable 에 merge·push** | [중요] **durable 단일 writer.** epoch 게이트가 stale assignee(zombie)를 거부한다 |

> [중요] **정정 2026-08-14 (리포트 14 §2·§11.3).** 이 표에 있던 **「통합자(`.2`) = 유일한 쓰기 주체 /
> 워커는 커밋하지 않는다」는 틀렸다.** 원전 `cluster_coordinator.verify_and_merge` 의 주석이 이미
> *"durable 단일 writer 보존"* 이었고 **그 writer 는 서버**다 — 원전에서 **워커는 쓴다, ephemeral
> 에만.** 「단일 writer」는 우리가 발명한 것이 아니라 원전에 있던 것이고, 그것을 `.2` 로 옮기면서
> **attempt 계층 · epoch fencing · `cleanup_attempts` · fake 워커 주입을 같이 버렸다.**
> [주의] 그리고 프로젝트 `repo/CLAUDE.md` 의 커밋 규약이 `[verify-merge] <hash> <path> by
> <workshop-host>` 라 **작업장이 쓰는 그림을 이미 전제**하고 있었다.
> [중요] **아래 「왜 이렇게 바꿨나」 절은 그 잘못된 전제 위에 쓰였다** — 근거로 인용하지 말 것.
> 복구분 = `master/work/coordinator.py`(실 Gitea 실증 통과, reports/14 §15).

[중요] **왜 이렇게 바꿨나.** 옛 구조는 태스크를 **워커의 자기 신고**(`RESULT: DONE`)로 판정하고
*"컴파일되나"* 를 아무도 묻지 않았다. 원전이 정확히 그 구조에서 사고를 냈다 — 빌드를 등재
*뒤*에 두었더니 **깨진 골조가 `origin` 에 박히고 워커 전원이 그 위에서 작업**했다. 빌드하는
주체를 커밋 주체로 만들면 그것이 **규율이 아니라 구조**가 된다.

[주의] **정정 2026-08-14** — 여기 있던 *"덤으로 한 무리의 문제가 통째로 사라진다(워커 git 인증 ·
`attempt/` 찌꺼기 · CAS/펜싱의 절반)"* 는 **사라진 것이 아니라 원전이 이미 풀어 둔 장치를 버린
것**이었다: `cleanup_attempts` 가 찌꺼기를, **epoch 게이트**가 펜싱을 맡고 있었다(리포트 14 §2.1).
§5.2-D 가 이미 같은 방향으로 갔다(*"durable merge CAS·모델이 머지 권한은 1인 구도에선 불필요"*).

[중요] **포기하는 병렬은 이미 의심스러웠다** — 실측 2026-08-09, 워커 2대는 **12% 빠르고 90% 비쌌다**
(캐시 생성이 워커별 고정비). 그리고 층3 은 **이미 `.2` 전용**이라 직렬이었다. 즉 직렬 병목은
**새로 생기는 게 아니라 위치가 옮겨진다.**

#### 왜 `.33` 이 아니라 `.2` 냐

| | `.33` 요청자 | `.2` 통합자 |
|---|---|---|
| UE5 | [완료] | [완료] 5.8 |
| 무인 구동 | [실패] 사람이 쓰는 기계 | [완료] **유일** |
| 가용성 | [중요] 낮다 — 이 세션 중에도 꺼져 있었다(실측) | [완료] 전용·상시 |
| 게스트 규칙 | [중요] 읽기 전용 선호·worktree 강제·미커밋 `.uasset` 복구 불가 | 해당 없음 |

`.33` 은 원래 역할(등록·최종 리뷰·`[FEEDBACK]`)에 남는다 — **사람이 눈으로 볼 자리이지,
파이프라인이 커밋을 밀어넣을 자리가 아니다.**

#### [중요] 받아들이는 비용 두 가지

1. **`.2` 가 적용+빌드의 단일 장애점이 된다.** 층3 이 이미 그랬으니 새 위험은 아니지만, 더 많은
   일이 거기 얹힌다.
2. **`.2` 의 추론 트리와 적용 트리가 겹치면 안 된다** — 적용 중에 추론이 더러운 트리를 읽는다.
   → **`git worktree` 로 가른다**(요청자에게 처방한 것과 같은 방식). [주의] UE5 프로젝트의 worktree
   DDC/Binaries 재생성 비용은 **여전히 미측정**이다(아래 §층3 참조) — 통합자에 강제하기 전에 잰다.

[주의] **N-writer 기계장치는 지우지 않고 보류한다** — 워커 Gitea 키(§8.5) · `attempt/` 브랜치 ·
`work/cleanup.py`(328줄). 측정으로 뒤집힐 여지가 있는 동안은 **되돌릴 수 있게 둔다.**

### [중요] 실패의 증거를 버리지 않는다 — [주의] **다만 git 이 아니라 스풀에 남긴다**

**성공한 것만 남기면 실패가 조사 불가능해진다.** 무엇을 시도했고 어디서 막혔는지가
사라지고, 피드백을 줄 근거도 없어진다. 그 원칙은 그대로다. **바뀐 것은 어디에 남기느냐다.**

    지금   검증 → 통과분만 커밋 (통합자 단일 writer)
           실패 → 파일을 되돌린다 · 사유는 `[FEEDBACK]` 으로 큐에 · **증거는 스풀에**
                 (응답 원문·빌드 로그 꼬리 — `#323` 이후 **8103 화면에 나온다**)

[중요] **종전 서술(`성공/실패 → attempt push`)은 걷었다** (`#317` 미결 ⑦ · `#327`,
사용자 결정 2026-08-28). 그 형태는 `attempt.py` 의 마스터측 배선이 전제였는데 **측정 결과
한 번도 안 돌았다** — 프로덕션 호출자 0 · bare 에 attempt 브랜치 0.
`integrate.py` 머리말이 *"두 파일은 나란히 선다(측정으로 뒤집힐 여지가 있는 동안)"* 로 이
공존을 명시했고, **측정이 났으므로 닫혔다.**

[주의] **`attempt/*` 자체는 규약에 남는다** — 훅이 여전히 허용하고, 옛 브랜치를 읽는 경로
(`branch_names.parse_attempt`)도 남는다. 걷은 것은 **마스터가 그리로 커밋하던 배선**이다.

### 1인 체제라 덜어내는 것 / 그대로 두는 것

| | 팀 전제였던 이유 | 지금 |
|---|---|---|
| 작성자별 분리 (`reviews/<작성자>/`) | 팀원마다 리뷰가 섞임 | [중요] **덜어낸다** |
| durable merge CAS | 팀원 둘이 동시에 머지 | **단순화** — 사람이 최종 승인, 층3 이 게이트 |
| **attempt 브랜치 격리** | 팀원 PC 가 여럿 | [중요] **그대로** — 워커 머신이 2대라 충돌은 실재(리포트 06 §4.6) |
| **lease · epoch fencing** | 워커가 죽고 되살아남 | [중요] **그대로** — 기계도 죽는다 |

[주의] **`attempt` 를 "머지 후 폐기" 로만 보지 않는다.** 실패한 attempt 는 조사 자산이다.

[중요] **기준은 「자동이냐 사람이냐」가 아니라 「도달 가능하냐」다** (사용자 결정 2026-08-14 `#125`,
확장 2026-08-21). 이 문단은 *"자동화가 브랜치를 지우는 것은 금지"* 라고 적혀 있었으나 **#219
(2026-08-18)부터 사실이 아니었다** — 문서가 코드보다 늦었다. 지금 규칙:

    도달 가능 (= `<remote>/main` 에서 ancestor) → **자동 삭제**. 지워도 잃는 것이 없다.
        `cleanup remote --apply`(#219) · `finalize_work(confirm=True)`(원전 6단계 ③)
    도달 불가                                  → **사람 몫.** 그 커밋이 거기에만 있을 수 있다
    판정 불가 (tracking ref 없음·git 실패)      → **보존** (fail-closed 의 방향이 보존이다)

가드가 **둘**이라 자동 삭제가 성립한다 — `plan_branch_cleanup` 이 도달 가능분만 고르고, 그 위에서
`pre_push_hook.sh`(`#125`)가 **같은 판정을 한 번 더** 한다. 훅이 거부하면 우리 판정이 틀렸다는
뜻이므로 **`--no-verify` 로 밀지 않는다.**

[주의] 사람이 도달 불가 브랜치를 지우기로 결정했다면(실제로 2026-08-21에 있었다 — 2026-08-09
e2e 잔여 6개), **지우기 전에 팁을 보존한다**: `git bundle create <파일> <refs…> --not <base>`
(그날 실측 **4.9KB**). [중요] `--all` 로 뜨면 게임 저장소 전체 이력이 들어와 **1GB** 가 된다.

- 요청자 측 브랜치 생성·push (스킬 `ax-request` 에 절차는 적었으나 **자동 실행은 없다**)
- `register_work_tool(target_branch=…)` 이 값을 **저장만 하고 쓰지 않는다**
- durable ← attempt 승격 경로 (사람 승인 + 층3 통과 후)

### [중요] 워커는 끝나면 **`main` 으로 돌아온다** (사용자 확정 2026-08-09)

    시작:  fetch → checkout task/<work>/<task> → merge --ff-only → checkout -b attempt/…
    끝:    push attempt  →  checkout main  →  그 다음에야 판정 마커 세 줄

이유가 둘이고 **둘 다 실측에서 나왔다**:

⑴ **다음 작업의 출발점** — attempt 브랜치 위에 남으면 무관한 두 작업이 한 줄에 쌓인다
   (실측: 첫 시험 파견 뒤 `.43` 이 attempt 에 남아 있었다).
⑵ [중요] **정리가 가능해진다** — 체크아웃된 브랜치는 삭제 대상에서 빠지므로, `task/<work>/<task>` 에 앉아
   있으면 그 브랜치는 **영영 정리되지 않는다**(실측: 1회차 보존 → `main` 복귀 후 2회차 삭제).

**복귀는 마커보다 먼저** 한다 — 마커는 출력의 마지막 세 줄이어야 하고, push 로 커밋은 이미
안전하므로 순서를 바꿔 잃는 것이 없다. [주의] 복귀는 `Source/` 가 깨끗할 때만 한다.

### [중요] 브랜치를 지우는 권한 — **워커에겐 없다. 마스터가 치운다** (2026-08-09)

워커의 금지 목록에 브랜치 삭제가 있는 것은 의도다. 그래서 찌꺼기(로컬 `attempt/*`·`task/*`·
원격추적 ref·`.ax/work/<id>/`)는 **마스터가** 치운다 — `python -m master.work.cleanup plan|apply`.

    지운다  ⇔  팁이 origin/<base> 에서 **도달 가능**하다 (= 병합됐다 = 잃는 것이 없다)

도달 불가·확인 실패·fetch 실패는 **전부 보존**한다. [중요] *fail-closed 의 방향이 여기서는 보존*
이다 — *"실패해도 attempt 를 push 한다"* 가 증거 보존이 목적이므로, 증거가 다른 곳에 살아
있음을 확인하기 전에는 없애지 않는다. [중요] **원격은 건드리지 않는다**(`push --delete` 는 사람의
판단, 세어서 보고만). 부산물은 `verified`/`cancelled` 만 지우고 **`failed` 는 남긴다.**

### [중요] 피드백은 텍스트가 아니라 **코드 위치에 박는다** (사용자 확정 2026-08-09)

> 사용자: *"피드백을 골조처럼 코드 위치에 추가하고, 작업 워커를 할당해 해당 원격 브랜치
> 최신화 시도"*

골조가 `[PSEUDO]` 로 *"여기를 채워라"* 를 말하듯, 피드백은 `[FEEDBACK]` 으로 *"여기가
틀렸다"* 를 **같은 자리에** 말한다. 큐의 텍스트 필드만으로는 워커가 **어디를** 고칠지 모른다.

    ① 검증이 반려          → 대상 파일에 [FEEDBACK] 블록을 박아 commit + push
    ② 큐에 new_base_commit → 그 커밋을 다음 base 로 기록
    ③ 다음 claim           → 워커가 그 커밋에서 체크아웃 → 피드백이 **코드 안에 보인다**
    ④ 워커는 **수정**한다    → 재구현이 아니다

**원본이 검증한 형태 그대로다** — `mcp/master_orchestrator/verifier.py:85`
(*"worker 브랜치에 feedback 주석을 target_file 상단에 박아 commit + push"*),
`worker/verify_worker.py:9~11` (*"reject → durable 을 attempt 로 fast-forward(구현 누적)한 뒤
[FEEDBACK] 블록 commit … [FEEDBACK] 기준으로 **수정**(재구현 아님 — 누적 모델,
사용자 2026-06-21)"*).

[중요] **누적 모델이라는 점이 핵심이다.** 반려돼도 그때까지의 구현을 버리지 않고, 그 위에서
고친다. 그래서 실패한 attempt 도 push 되어야 한다 — 버리면 누적할 것이 없다.

**이식 상태:**

| | |
|---|---|
| [완료] **게이트** | `layer2_verify.py:46` 이 *"leftover `[PSEUDO]/[FEEDBACK]` placeholders"* 를 이미 검사한다 — 마커가 남은 코드는 통과하지 못한다 |
| [완료] **큐** | `submit(feedback=…, new_base_commit=…)` · `base_commit` 필드 |
| [실패] **박는 쪽** | `_embed_feedback_in_worker_branch` 상당이 없다 — 반려 시 `[FEEDBACK]` 을 파일에 써서 commit·push 하는 주체 |
| [실패] **durable ff** | 반려 시 durable 을 attempt 로 전진시켜 구현을 누적하는 경로 |

[주의] **누가 박나는 아직 미정이다.** 마스터는 push 를 못 하므로(§2.1) 후보는 둘 —
**요청자(사람의 PC)** 또는 **검증을 수행한 `ue5` 워커**. 층3 을 돌린 쪽이 결과를 아는
주체이므로 후자가 자연스럽지만, 사람의 승인 전에 워커가 durable 을 움직이게 할지는
별도 결정이다.

### [중요] durable 은 "빨리 머지할 것" 이 아니라 **오래 사는 작업 공간**이다 (사용자 확정 2026-08-09)

> 사용자: *"기존 AgentTest 와 달리 작업 요청자가 있으니 머지 단계가 나중이라 문제가 생길 일이
> 없이, 계속 작업용 원격 브랜치에서 모두 작업이 될 때까지 요청자와 대화식으로 피드백 요청이
> 가능할 듯"*

**이것이 AgentTest 를 복잡하게 만들던 압력을 없앤다.** 거기서는 팀원 여럿이 각자 결과를
`main` 쪽으로 밀어 넣으려 했기 때문에 **durable merge 를 빨리·안전하게** 하는 장치
(CAS·경합 방어·상용 모델 verdict 가 머지 권한을 가짐)가 필요했다.

우리는 다르다:

    task/<work>/base ──▶ 골조. 조각들이 여기서 갈라진다
    task/<work>/<task> ──▶ 워커들이 attempt 를 얹으며 **오래 산다**
                   요청자가 대화식으로 [FEEDBACK] 을 박고 재작업을 돌린다 (몇 번이든)
                   ▼
    main       ──▶ [중요] **다 됐을 때, 사람이, 한 번** 머지한다

| | AgentTest (팀) | 여기 (1인 + N워커) |
|---|---|---|
| 머지 시점 | 태스크마다 즉시 durable 로 | **끝에 한 번**, `main` 으로 |
| 머지 권한 | 상용 모델 verdict → CAS | **사람** (층3 이 게이트) |
| 경합 | 팀원 간 실재 | [중요] **없다** — 미는 주체가 하나다 |
| 피드백 | 워커↔검증자 자동 왕복 | **요청자와 대화식**, 횟수 제한 없음 |

**그래서 `verify_worker.py`(314줄)의 CAS·durable merge 권한 이전은 이식하지 않는다.**
리포트 08 §15.2 가 이미 *"이식 대상이 아니라 재설계 대상"* 으로 분류했는데, 재설계의 답이
여기서 나왔다 — **그 장치 자체가 필요 없어진다.**

#### [완료] 미정이던 것이 풀린다 — `[FEEDBACK]` 은 **요청자가 박는다**

앞 절에서 *"요청자냐 층3 을 돌린 워커냐"* 를 미정으로 남겼는데, 요청자가 루프 안에 상주하며
대화식으로 판단하므로 **요청자가 박는 것이 맞다.** 워커가 사람 승인 전에 브랜치를 움직이는
경로를 만들 이유가 없어진다.

    검증 결과 → 요청자에게 보고 → 사람이 판단 → 요청자가 [FEEDBACK] 을 박고 재작업 요청

[주의] **여전히 남는 경합 하나**: 워커 2대가 **같은 파일**을 만지는 태스크를 동시에 받으면
durable 로 얹을 때 충돌한다. 클래스 단위 분해가 파일을 가르므로 보통은 안 겹치지만,
**분해가 파일 경계를 지키는지는 분해기(§4.5)의 책임**이다 — 거기서 보장해야 한다.

### 8.5 워커 git 인증 — Gitea SSH 키 (2026-08-09 확보)

[중요] **이것이 §8.4 루프 전체의 선결이었다.** 워커가 durable 브랜치를 fetch 하고 attempt 를
push 해야 하는데, **두 대 모두 Gitea 에 접근하지 못했다**(실측):

    .2  (janus)  Git Credential Manager 가 대화형 프롬프트 → SSH 세션에서 실패
    .43 (BC-250) ksshaskpass 사망 — 자격증명 없음

Gitea 가 `REQUIRE_SIGNIN_VIEW = true` 라 **public 저장소인데도** 익명 클론이 안 된다.

**선택: HTTP 토큰이 아니라 Gitea SSH 키.** 셸을 주지 않고 **git 만** 주며, 워커에 새 비밀
파일을 심지 않는다(이미 있는 SSH 키를 쓴다). `docs/2-architecture.md` §2.2-a 가 걱정한
*"노드에 자격증명을 심으면 재구축이 어려워진다"* 도 덜하다.

    gitea@192.168.0.57:Sim/ModularStage.git

#### [중요] 함정 — Gitea 의 `HOME` 과 sshd 가 보는 홈이 다르다

키를 API 로 등록하면(`POST /api/v1/user/keys`, 201) Gitea 가 `authorized_keys` 를 쓰는데,
**systemd 유닛이 `HOME=/var/lib/gitea`** 라 거기에 쓴다. 반면 **sshd 는 `gitea` 계정의
passwd 홈인 `/home/gitea`** 를 본다. 두 경로가 어긋나 **키는 등록됐는데 인증은 계속 거부**된다.

    Environment=USER=gitea HOME=/var/lib/gitea     ← 유닛
    getent passwd gitea → /home/gitea              ← sshd 가 보는 곳

**조치(가장 덜 침습적):** 심볼릭 링크. `usermod` 도 `sshd` 재시작도 하지 않는다.

    ln -sfn /var/lib/gitea/.ssh /home/gitea/.ssh && chown -h gitea:gitea /home/gitea/.ssh

`StrictModes`(기본 yes)를 통과한다 — 경로상 디렉토리가 전부 `drwxr-x--- gitea:gitea` 이고
키 파일은 `-rw-------` 다. 되돌리기: `rm /home/gitea/.ssh`.

**검증(실측):**

| | |
|---|---|
| `ssh -T gitea@192.168.0.57` (양쪽) | *"successfully authenticated with the key named ax-worker-N, but Gitea does not provide shell access"* — 원하던 상태 그대로 |
| `git ls-remote origin HEAD` | `.2`·`.43` 둘 다 `bc4b38f` |
| `git push --dry-run origin HEAD:refs/heads/…` | `.2` **`[new branch]`** [완료] |

[주의] **Gitea API 토큰은 해시로만 저장되어 DB 에서 복구할 수 없다.** 새로 발급한다:
`gitea admin user generate-access-token --username Sim --scopes write:user,write:repository`.
발급본은 `~/.config/ax-cluster/gitea-token`(0600) — [중요] **저장소에 넣지 않는다.**

#### [중요] 마스터도 키를 갖는다 — `ax-master-write` (2026-08-14, Flow Y)

같은 절차로 **네 번째 키**를 등록했다(`POST /api/v1/user/keys`, id=4). 검증 실측:

    ssh -T gitea@192.168.0.57  →  "authenticated with the key named ax-master-write"
    push --dry-run gitea-write HEAD:refs/heads/attempt/…  →  [new branch] [완료]
    push --dry-run gitea-write HEAD:refs/heads/probe-…    →  [중요] pre-push 훅이 거부

[중요] **네 대가 전부 계정 `Sim` 이다** — 등록된 것은 저장소별 배포키가 아니라 계정 키다. Gitea 의
브랜치 보호 화이트리스트는 **사용자 단위**라 같은 계정을 쓰는 기계를 구분하지 못한다. 즉
*"마스터는 `main` 에 못 쓴다"* 를 **서버에 넣을 방법이 지금 구조에는 없고**, 그래서 가드가
클라이언트(`pre-push` 훅)에 있다. [주의] **기계별 신원 분리는 미결**이다 — 그것이 되면 서버측으로
옮길 수 있다. 그리고 실측 확인: `branch_protections` 는 지금 **`[]`**(main 보호 없음)이다.
→ `reports/16-master-write-surface.md` §5

#### 마스터가 bare 를 읽는 법 — `sg gitea` (2026-08-09 확인)

리포트 08 §7.4-2 가 *"`sim` 이 `gitea` 그룹에 파일상으론 있는데 세션 자격증명엔 없다 —
재로그인을 안 했다"* 로 남겨 둔 것의 답이다. **재로그인 없이 `sg` 로 우회된다:**

    sg gitea -c 'git -C <미러> ls-remote --heads origin'
    → bc4b38f…  refs/heads/main
      bc4b38f…  refs/heads/upgrade/ue5.8

서비스는 이미 갖고 있다(`ax-indexer.service` 의 `SupplementaryGroups=gitea`). **대화형
세션만** 그룹이 빠져 있고, 그래서 사람이 손으로 확인할 때만 걸린다.

→ **마스터는 인증 없이 bare 를 읽을 수 있다.** durable 브랜치가 실제로 만들어졌는지
**검증**하는 데 이걸 쓴다(읽기 전용이므로 §2.1 위반이 아니다).

#### ① `twin_commit` 과 ② durable 브랜치는 **같은 커밋을 쓴다**

`<프로젝트>/config.yaml` 의 `index.last_indexed_commit` 이 곧 **트윈이 지어진 커밋**이다
(지금 `bc4b38f`). 그러므로:

    조각 durable 의 기준 커밋  ==  작업 브랜치 task/<work>/base 의 tip   (#319 — 옛 값은 twin_commit)
                                          ==  index.last_indexed_commit

**따로 만들 필요가 없다.** 브랜치를 그 커밋에서 따면 워커가 받는 소스와 매니페스트의 근거가
**정의상 일치**한다 — 그게 ①이 풀려는 문제 전부다.

### 8.6 ⬜ 아직 안 한 것 (2026-08-09 시점)

| | 막힌 이유 |
|---|---|
| `register_work(target_branch=…)` 이 durable 브랜치를 **실제로 만들게** 하기 | [중요] 마스터는 push 를 못 한다 — **요청자가 만든다.** 그 `.33` 이 꺼져 있어 실행·검증 불가. 오늘은 `.2`/`.43` 이 대행해 e2e 를 냈다 |
| `.33` 의 git 인증 | 대화형이면 GCM 이 처리하므로 **지금은 불필요**. 자동화가 필요해지면 §8.5 와 같은 방식으로 키 등록 |

[완료] **선결이던 워커 git 인증은 끝났다**(§8.5) — `.2`·`.43` 둘 다 fetch·push 가 된다.

[완료] **매니페스트의 `twin_commit`·ff-only 따라잡기·정리는 끝났다** (2026-08-09).
매니페스트는 `## 기준 (커밋·브랜치)` 절을 싣고, [중요] 그 절은 **파견 시점에 다시 푼다** —
durable 브랜치는 설계상 *등록 이후* 요청자가 만들므로 **등록 시점 값은 정상 흐름에서 반드시
낡는다**(실측: 브랜치를 만든 뒤에도 매니페스트가 *"아직 없다"* 라고 말했다). ff-only 는 스킬이
못박고, 못 따라잡으면 `RESULT: BLOCKED` 다 — `reset --hard` 로 맞추지 않는다.
→ `master/work/runner.py` · `master/work/cleanup.py`

[중요] **남은 것은 요청자(`.33`) 한 칸이다.** ②마스터 할당 → ③워커 최신화 → ④추론 → ⑤통보 →
⑥`main` 복귀는 실측으로 끝까지 돌았다(71초). ①"사람이 작업을 등록하고 durable 을 만드는"
칸만 비어 있다.
