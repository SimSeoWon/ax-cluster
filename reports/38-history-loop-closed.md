# 38. 「기록이 없다」는 착각이었다 — 쓰기만 있던 루프를 닫았다

**날짜** 2026-08-24~25 · **일감** `#303` · `#304`(소 `#305`~`#310`)

## 1. 시작 — 사용자가 `.33` 에서 본 것

*"작업 완료했는데 히스토리가 없나본데"*. `.33` 세션도 같은 결론을 냈다 — 로컬에 파일이 없고,
마스터 RAG 검색이 0건, 8103 에 읽기 라우트가 없었으니 합리적인 판단이었다.

**틀렸다. 기록은 있었다** — `~/ax-cluster/NS/history/2026-08-24_0239_….md` 4,461바이트에
프론트매터·`affected_classes` 4개·`alternatives_considered` 3건·`user_quote` 까지 온전했다.
신호도 1건 적립돼 있었다.

[중요] **쓰기 배선은 처음부터 살아 있었다.** 없던 것은 **읽는 자리**다. 이 리포트는 그 한 문장을
확인하는 데 세 겹의 구멍을 지났다는 기록이다.

## 3. [중요] 「읽는 기계는 이미 있었다」 — 이 세션의 제일 큰 실측

`#306` 을 시작하며 파서를 새로 쓸 준비를 했는데, `walk_histories`·`parse_claude_history`·
`filter_for_classes` 가 **온톨로지 시드(`#158`)용으로 이미 이식돼 있었다.** 없던 것은 세션이
부를 표면뿐이었다.

원전을 먼저 읽는 규칙이 또 값을 냈다. 만약 새로 썼다면 같은 질문에 **두 개의 답**이 나왔을 것이다
— prefix 관용 매칭 규칙 하나만 어긋나도 `UManager_X` 와 `Manager_X` 가 갈린다.

[주의] 다만 `HistoryRecord` 가 **네 필드를 버리고 있었다**: `tags`·`supersedes`·`title` 이 아예
없고 `alternatives_considered` 는 `next_steps` 에 섞여 들어갔다(부정 지식과 후속 작업이 한 통에).
**뒤에 덧붙여** 살렸다 — 기존 소비자는 읽는 것만 읽으므로 안전하다.

`supersedes` 가 특히 중요하다. **뒤집힌 결정을 못 쫓으면 되돌린 것을 되돌린다.**

## 4. [중요] 문서의 예시 자체가 함정이었다 (`#305`)

배달 문서의 프론트매터 예시가 `affected_classes: []` **인라인**이었다. 소비자(원전 미니 파서)는
인라인 리스트를 스칼라 문자열로 읽어 `isinstance(list)` 검사에서 **통째로 버린다.**

즉 **문서의 예시를 그대로 따르면 필드가 조용히 사라진다.** 규약 문서를 고칠 때 「설명」만 보고
「예시」를 안 보면 이런 것이 남는다.

같은 절에서 `decision_type` 이 문서 7종 / 코드 8종이었다.

## 5. [중요] 한 세션 안에서 `#261` 이 재현됐다 (`#309`)

`#306` 에서 `find_history` 를 만들고, `PAYLOAD_BY_ROLE` 이 워커에 배달하고, 배달 문서에
*"작업 시작 직전에 부른다"* 고 적었다. 그리고 `#309` 감사에서 실측했다:

    worker    → POST /api/v1/history/search   403
    requester → POST /api/v1/history/search   200

**선언은 셋, 배선은 둘.** `WORKER_SCOPE` 에 경로가 없었다. `#261`(워커에 MCP 가 없어 컨벤션을
못 읽던 자리)과 **같은 부류가 같은 세션 안에서** 나왔다.

고치는 것은 한 줄이었지만, 그래서 **게이트를 세웠다**: 도구 목록에서 큐로 가는 읽기 도구를
실제로 dispatch 해 경로를 뽑아 스코프와 대조한다. 목록을 손으로 적으면 그 목록이 또 갈린다.
(처음엔 빈 인자로 dispatch 해서 `find_recipes` 를 놓쳤다 — 게이트가 2/3만 보고 통과할 뻔했다.)

## 6. 화면이 거짓말한 두 방향 (`#307`)

`#295` 는 **실패를 정상으로** 보여줬고, 이번은 **있는 것을 없다고** 보여줬다.
`api_history()` 가 `count:0` 을 하드코딩하고 *"트윈에는 history 기록이 아직 없다"* 를 붙였다.
`?limit=3` 도 시그니처에 인자가 없어 조용히 무시됐다.

곁에서 **완료 조건 4 를 실측으로 판정했다**: 8103 은 정말로 무인증 공개다(토큰 없이
`/api/v1/*` 200, 루프백·LAN 둘 다). 설계가 그렇다 — `webui/app.py:33 PREFIXES` 에 `/api/v1` 이
들어 있고 그것이 `public_prefixes` 로 넘어간다(웹 UI 가 자기 API 를 부르려면 필요하다).

그래서 이 라우트가 내보내는 것을 줄였다 — **`user_quote`(사람의 발화)·본문·절대경로는 안 나간다.**
전문 조회는 토큰이 걸린 8101 의 `find_history` 가 맡는다. 저장소가 레드마인 읽기에서 이미 한
판단과 같다. **화면은 돌고 사람의 말은 안 나간다.**

🔴 [주의] **`~/CLAUDE.md` 가 이 대목에서 틀렸다** — *"API paths on that port stay token-locked"*.
자동 로드 문서라 동의 없이 못 고쳐서 사용자에게 보고했다. **미결.**

## 7. 등재가 반쪽이었다 (`#303`)

일감 8건을 만들자마자 **전부 무버전**으로 떨어졌다. 대행 표면이 `fixed_version_id`·
`parent_issue_id` 를 못 썼다(읽기·필터엔 있었다). 이미 그렇게 쌓인 것이 13건.

[중요] **원전에도 없다** — 원전 `create_issue` 도 버전·부모를 안 받고 계층은 읽기만 썼다(사람이
UI 에서 붙인다). 그래서 이건 **이식 누락이 아니라 추가**이고, 근거는 우리 규약이다. 그 구분을
코드 주석에 적었다 — 섞어 적으면 다음 세션이 원전에 있었다고 읽는다.

[주의] **버전은 프로젝트에 속한다.** `update_issue` 에 `project` 를 안 주면 기본값(AX)에서 찾아
`ns` 이슈의 마일스톤을 영원히 못 찾는다. 역검증에서 그것이 그대로 나왔다 —
*"이 프로젝트(`ns`)에서 찾지 못해 생략"*. 프로젝트 축이 실제로 갈려 있다는 증거이기도 하다.

## 8. 사용자 지시가 축을 정했다 (`#309`)

> *"`.33` 스스로 동작할 수 있고 인프라 서버를 이용해 분산작업할 수도 있어. 이때 워커쪽에 기입되는
> 내용은 하나의 프로젝트에 디펜던시가 되지 않고, 신규 프로젝트를 등록한다고 할 때 셋업시 처리할
> 수 있도록 관리되어야 해."*

종전 관리 블록은 규약과 프로젝트 사실을 **한 블록에 섞어** 냈다. 읽는 쪽이 무엇이 프로젝트에
묶인 서술인지 알 수 없었다. 이제 블록이 자기 축을 말한다 — *"이 절의 규약은 역할 축이다.
프로젝트에 묶인 것은 아래 실측 절뿐이고 매 배달마다 마스터가 다시 만든다."*

완료 조건 2 의 판정은 **「워커는 기록을 쓰지 않는다」** 였고, 그것을 **문서에 적었다.**
빈칸으로 두면 다음 세션이 채운다 — 그러면 두 번째 writer 가 생긴다.

## 12. 여기서 배운 것

- **쓰기만 있는 기록은 없는 기록이다.** 적재를 이식하면 조회도 같이 이식됐는지 본다
- **문서는 설명과 예시가 따로 늙는다.** 예시가 소비자 계약을 깨는 경우가 실재했다
- **선언을 늘리면 배선 표를 같이 본다.** 한 세션 안에서 `#261` 이 재현됐다 —
  기억으로는 못 막는다. 게이트가 막는다
- **없는 것을 없다고 말하는 것과 있는 것을 없다고 말하는 것은 다르다.** 후자는 판단을 망친다
- **원전에 없는 것을 추가할 때는 「추가」라고 적는다.** 포팅과 섞이면 근거가 사라진다
