## 1. 총평: AX 도입에 어느 정도 도움이 되는가?

> **핵심 진단**: **"에이전트를 믿지 않는 아키텍처(Zero-Trust for AI Agents)"로는 상위 1% 수준의 실전 완성도**를 달성했으나, **"1인 개발자의 인지적 여유(ROI) 극대화"** 관점에서는 인프라 자체를 유지·보수하는 메타 작업(Meta-work) 비중이 본업(게임·제품 개발)을 압도하고 있는 상태다. 반면 **이 과정에서 실증으로 축적한 아키텍처 패턴과 실패 교훈은 회사(팀) 단위의 AX 인프라를 설계할 때 시행착오를 수개월 단축해 줄 가장 강력한 레퍼런스(테스트베드)**로 작동하고 있다.

- **엔지니어링 성숙도 (90 / 100)**:
  - 단일 IDE 내 코파일럿 활용을 넘어, 이기종 노드(`.57` 리눅스 마스터, `.2`·`.43` 윈도우/리눅스 워커, `.33` 윈도우 요청자)와 이기종 모델(Claude, Codex, Gemini, 로컬 Ollama)을 **결정론적 검증 게이트(층1 AST·pyflakes·mypy·UE5 빌드) + 교차 계열 리뷰(작성자 ≠ 검토자)**로 묶어낸 구조는 기업 R&D 조직에서도 보기 드문 실전형 엔지니어링이다.
- **개인 본업(게임 개발) ROI (현재 60 / 100 → 잠재력 95 / 100)**:
  - 170여 개의 작업 리포트와 930여 개의 Redmine 일감 중 상당수가 `AXCluster` 자기 자신의 규칙·배달·문서·예외를 고치는 데 쓰였다.
  - 다만 사용자가 이 홈 클러스터를 **사내 AX 인프라 도입을 위한 선행 R&D 샌드박스**로 겸용하고 있다는 점을 고려하면, 여기서 겪은 실패(상주 데몬 폭주, 프롬프트 무시, 세션 0 격리, 컨텍스트 오염)와 그 해결책은 현업 이식 시 값비싼 수업료를 대신 치른 고가치 자산이다.

## 2. 독보적으로 잘 설계된 점 (핵심 강점 4가지)

### 2.1 "프롬프트 지침은 어겨진다 — 필수 과정은 코드로 강제한다" (`docs/milestones/6-improvements.md:22-24`)
- 대다수 조직이 AI 도입 시 시스템 프롬프트에 `[중요] 절대 하지 마라`를 수백 줄 적고 끝낸다.
- AX 클러스터는 마일스톤 6을 거치며 **"문서와 기억으로 지킨 규칙은 몇 달째 반복해서 어겨졌고(Windows SSH 세션 0 11건, 옛 코드 배달 등), 파이썬 코드가 거절하게 만들자(`#831`, `#832`, `#931 step: requester` 서버 거절, `#921 issue_wrapup`) 그날 바로 라이브에서 막혔다"**는 사실을 실증으로 증명하고 시스템화했다.

### 2.2 교차 계열 검증(Cross-Model Verification)과 결정론적 게이트의 분리 (`docs/orchestrator-rules.md:73-74, 157-160`)
- 같은 모델 계열이 코드를 짜고 같은 모델이 리뷰하면 동일한 환각과 확증 편향을 공유한다.
- 작성 레인(`codex` / `claude`)과 검증·리뷰 레인(`agy` / `codex` 교차 배정)을 강제 분리하고, LLM 리뷰 앞단에 비용이 0에 수렴하는 결정론적 정적·통합 검사(`tests/integration/checks.json`)를 배치해 "기계가 잡을 수 있는 결함에 LLM 토큰을 쓰지 않는다"는 원칙을 관철했다.

### 2.3 워커 폴링 상주 데몬 철거 및 마스터 Push + 단일 타이머 일원화 (`docs/12-multi-project.md:9-16`)
- 초기 워커 상주 데몬(`claimer`, `buildjob`)이 유발하던 유령 프로세스, 구버전 코드 실행, 거절 응답 무한 재시도(20분간 로그 4.4MB 폭주, `#277`) 문제를 겪은 뒤, 미련 없이 모든 워커 상주를 걷어내고(`#320`, `#860`) 마스터의 SSH 제어와 `ax-followup.timer` 단일 수신자로 단순화한 결단은 운영 복잡도를 극적으로 낮췄다.

### 2.4 프로젝트 로컬 자산 배달과 해시·상태 대조 (`master.client update / check`, `#699`)
- 여러 워커 PC에 에이전트 스킬(`.agents/skills`)과 설정(`.codex/config.toml`, `.mcp.json`)이 흩어질 때 발생하는 설정 드리프트(Configuration Drift)를 막기 위해, 선언 표(`client/spec.py`) 한 곳에서 역할을 정의하고 `check` 명령으로 배포 출처 커밋과 실제 도착 파일을 기계적으로 대조하게 만든 점은 멀티 노드 AX 운영의 정석에 가깝다.

## 3. 잘못된 점 (비판적 진단: 현재 역효과가 나는 구조적 문제)

### 3.1 프롬프트·지침의 "판례법적 비대화" (Rule Bloat & Attention Dilution)
- **현상**: `AGENTS.md`, `CLAUDE.md`, `docs/orchestrator-rules.md`, 각 스킬 문서에 과거 에이전트가 실수했던 **개별 사건의 경위와 날짜(`사용자 결정 2026-XX-XX (#NNN)`)가 판례처럼 계속 누적**되고 있다. 심지어 `AGENTS.md`에는 *"세션 시작에 `~/ax-cluster/reports/`를 전문으로 읽는다"*처럼 리포트가 175개에 달한 현시점에는 물리적으로 불가능한 지시까지 남아 있다.
- **비판**: LLM의 컨텍스트 창과 어텐션(Attention)은 유한한 예산이다. 과거 사고의 역사적 배경과 변명까지 매 세션 시스템 지침으로 적재하면, 정작 **가장 중요한 핵심 불변식(Invariants)이 텍스트의 바다에 묻히는 'Lost-in-the-Middle' 현상**을 자초한다.
- **해결책**:
  1. **역사(Why/History)와 현행 규범(What/Rule)의 분리**: 역사적 경위는 `reports/`나 `docs/milestones/`에만 남기고, 자동 로드되는 `AGENTS.md`·`CLAUDE.md`·`orchestrator-rules.md`에는 압축된 현행 명령만 남긴다.
  2. **코드로 강제된 규칙의 프롬프트 퇴역**: 파이썬 코드(`#921`, `#931`, `#831` 등)가 이미 100% 차단하고 있는 항목은 프롬프트에서 길게 설명할 필요가 없다(에러 메시지 한 줄이면 충분하다).

### 3.2 작업 경중을 가리지 않는 획일적 중량 파이프라인 (One-Size-Fits-All Heavy Process)
- **현상**: `docs/orchestrator-rules.md:87`은 *"팀 인프라가 아니라 1인이 집의 여러 컴퓨터를 묶는 것"*이라고 선언하지만, 실제 절차는 사소한 UI/문서/단일 모듈 수정조차 **RAG 검색 → 플랜 등록 → 격리 워크트리 → 서브에이전트 위임 → 전체 통합 검사 194건(200초+) → 리포트 작성 → `issue_finish` → 신선도 판정 → 인수인계서 커밋·푸시 → 워커 3대 배달(`update`/`check`) → Redmine 노트**라는 대기업 릴리스 파이프라인을 매번 그대로 탄다.
- **비판**: 파이프라인 단계가 길수록 에이전트가 중간에 쿼터(5h 한도)나 네트워크 오류로 멈출 확률이 높아지고, 멈췄을 때 **걸쳐 있는 중간 상태(워크트리, 잠금 파일, T1/T2 상태, 미커밋 인수인계서)를 복구하는 인지적 부채가 고스란히 사람(지휘자)에게 전가**된다(`#919` 중단 사례가 정확히 이를 보여준다).
- **해결책**: 파급 반경(Blast Radius)에 따라 **경량 패스트트랙(Fast-track: 워커 배달이나 추론 체인에 영향이 없는 웹UI·리포트·문서 수정)**과 **정규 중량 트랙(워커 배포 자산·큐·브로커·C++ 빌드 변경)**의 검증·배달 범위를 차등화해야 한다.

### 3.3 런타임 세션 메모(`docs/orchestrator-handoff.md`)와 코드 배포 리비전(`HEAD`)의 강결합 모순
- **현상**: `docs/orchestrator-handoff.md`가 코드 저장소 `main` 브랜치 안에서 커밋 대상 파일로 관리되다 보니, *"인수인계서를 배달보다 먼저 커밋하지 않으면 워커가 1커밋 뒤처져 `check`가 실패한다(`#916`)"*, *"인수인계서가 미커밋 수정 상태면 `issue_finish`가 깨끗한 트리가 아니라며 거부한다"*는 모순이 발생한다.
- **비판**: **소프트웨어 릴리스 리비전(`HEAD`)**과 **에이전트 교대용 런타임 칠판(Blackboard/Handoff State)**은 생명주기가 전혀 다른 데이터다. 세션 메모 한 줄을 고쳤다고 워커 3대의 코드 정합성(`check`)이 깨지거나 재배달(`update`)을 요구하는 것은 데이터 계층 분리가 잘못된 것이다.
- **해결책**:
  - 단기: `master.client check`의 배달 출처 커밋 판정에서 `docs/`·`reports/` 등 비배달(Non-payload) 경로만 변경된 커밋은 동등(equivalent)으로 인정하거나,
  - 중기: 세션 인수인계 상태를 Git 추적 파일이 아닌 마스터 DB/런타임 상태(또는 Redmine 고정 위키/이슈)로 분리한다.

## 4. 부족한 점 (아직 비어 있는 아키텍처 고리)

### 4.1 "작업 착수 전(Pre-Plan)" 요구사항 수렴 프로토콜의 부재 (`#911`, `#939`, `#938` 연계)
- 지금까지 클러스터의 모든 정교한 장치는 **"코드를 짠 뒤(Post-Build) 어떻게 검증하고 마감할 것인가"**에 집중되어 있었다.
- 반면 **"코드를 짜기 전(Pre-Build) 사용자의 짧은 지시에서 숨은 전제·비범위(Out of scope)·성공 기준을 어떻게 오해 없이 뽑아낼 것인가"**는 추상적인 *"애매하면 묻는다"*(`docs/orchestrator-rules.md:28-29`) 한 줄에 의존해 왔다.
- 에이전트가 잘못된 전제로 1,000줄을 짜고 테스트까지 통과시킨 뒤에 사람이 발견하면, 결정론 게이트가 아무리 훌륭해도 전부 폐기해야 한다(인지적 부채 `#938`).

### 4.2 사후 비동기 리뷰 큐(`/reviews`, `/fixes`)의 피드백 루프 단절
- `docs/orchestrator-handoff.md:83`을 보면 `#929`, `#930`, `#931`, `#934`, `#829` 등 마감 후 비동기로 달린 리뷰 지적들이 미처리 상태로 쌓여 있다.
- **일감이 이미 닫히고(`closed`) 브랜치가 병합된 뒤에 도착하는 리뷰는 사람의 행동 동기를 유발하지 못해 결국 '읽지 않는 알림(Alert Fatigue)'으로 전락**한다.

### 4.3 실제 목적 프로젝트(`.33` 게임 개발) 기준의 가동률·성공률 지표 부재
- 클러스터의 본래 목적은 `.33` 작업장에서 언리얼/게임 프로젝트를 빠르게 개발하는 것이나, 여전히 *"`.33` 첫 실제 요청자 마감·연결 미확인"*(`docs/orchestrator-handoff.md:84`) 상태가 남아 있다. 인프라 자체의 헬스체크는 정교하지만, **"수요자(`.33`) 관점에서 주간 몇 건의 기능 조각을 무사고로 완주했는가"**를 보여주는 핵심 성과 지표(North Star Metric)가 전면에 나와 있지 않다.

## 5. 향후 강화해야 할 4대 전략 과제 (우선순위순)

| 순위 | 과제명 | 핵심 실행 내용 | 연관 일감 |
| :--- | :--- | :--- | :--- |
| **1순위** | **사전 인터뷰 & 스펙 고정 프로토콜 도입 (`ax-plan` 앞단 강화)** | `no_spec`/`plan_needed` 단계에서 ① RAG·코드 선조회(`Detect before ask`) → ② `HYPOTHESIS + CONFIDENCE %` 제시 → ③ `1 Question + GUESS(추정 답안)` 인터뷰 → ④ **`Out of scope`·파급 반경·증명 방법 포함 6줄 요약 승인** 후 구현 착수 | **#911**, **#939**, **#938** |
| **2순위** | **사후 리뷰를 '마감 전(Pre-finish) 편향 제거 검증'으로 전진 배치** | 마감 뒤에 쌓이는 비동기 리뷰 의존도를 줄이고, 커밋/마감 직전에 작성자 자기변호(`CLAIM`)를 제거한 **`ARTIFACT(diff) + CONTRACT(승인된 6줄 스펙)` 대조 검증(`doubt-driven`)** 및 **5대 에이전트 꼼수 감사(`Floor Guard`)**를 게이트로 실행 | **#908**, **#939** |
| **3순위** | **프롬프트 다이어트 및 `handoff` 결합 해소** | 코드로 이미 강제된 규칙과 역사적 경위를 자동 로드 지침(`AGENTS.md`, `CLAUDE.md`)에서 걷어내어 토큰 밀도를 2배 이상 높이고, `orchestrator-handoff.md` 변경이 워커 배달 해시를 깨뜨리지 않도록 분리 | **#841** |
| **4순위** | **인프라 Feature Freeze & 실전 도메인(`.33`) 집중 가동** | 위 1~3순위 반영 후 일정 기간 `AXCluster` 자체 기능 추가를 동결하고, 실제 게임 프로젝트(`ModularStage`, `NS`) 일감만 연속 투입하여 실전 처리량과 병목을 측정 | 마일스톤 7/8 본 목표 |

## 6. 부록: 회사(기업/팀) AX 인프라 구축 시 이식 가이드

홈 클러스터(`AXCluster`)에서 검증된 자산을 회사 팀 환경으로 가져갈 때, **그대로 가져가야 할 핵심 자산(Keep)**과 **팀 환경에 맞게 변형해야 할 요소(Adapt)**는 다음과 같다.

1. **그대로 이식할 핵심 아키텍처 (Keep)**
   - **선언형 클라이언트 자산 배포(`client/spec.py` + `deliver/check`)**: 사내 개발자 PC마다 에이전트 프롬프트·MCP 설정·스킬 버전이 달라지는 문제를 단번에 해결한다.
   - **결정론적 게이트 우선 원칙(Tiered Verification)**: LLM 리뷰어를 부르기 전에 AST·정적 분석·타입 체크·모듈 경계 검사를 먼저 돌려 실패 시 즉시 반려하는 구조는 사내 API 비용을 절반 이하로 줄여준다.
   - **작성 모델 ≠ 검증 모델 교차 배치**: 사내 코드 리뷰 자동화 시 작성 에이전트와 다른 모델(또는 작성자의 의도 설명을 제거한 클린 컨텍스트)로 리뷰하게 하는 규약.
   - **착수 전 인터뷰 + `Out of scope` 고정(#911·#939)**: 시니어/주니어 개발자가 에이전트에 작업을 시킬 때 가장 큰 품질 차이를 만드는 지점으로, 사내 표준 `/plan` 스킬로 배포하기 가장 좋다.
2. **기업 환경에 맞춰 바꿔야 할 요소 (Adapt)**
   - **단일 마운트(`active` 1개 강제) → 테넌트/프로젝트 태그 기반 멀티 라우팅**: 1인 홈 클러스터에서는 *"작업은 무조건 마운트된 하나만"*(`docs/12-multi-project.md:233`)이 맞지만, 회사에서는 여러 팀원이 동시에 서로 다른 저장소/브랜치 작업을 던지므로 큐와 색인기가 `project_id + branch` 단위로 동시 처리하도록 격리 단위를 넓혀야 한다.
   - **단일 파일 인수인계서(`orchestrator-handoff.md`) → 이슈 트래커(Jira/Redmine/GitHub Issues) 상태 머신 일원화**: 다수 인원이 협업할 때는 공유 마크다운 파일 하나를 수정하면 즉시 충돌(Merge Conflict)이 나므로, 모든 체크포인트와 잠금(Lock)은 이슈 번호(`#N`) 단위의 DB/API 상태로만 관리해야 한다.
   - **무인증 내부 포트(`8103` 등) → 역할 기반 토큰 스코프(`WORKER_SCOPE` / `REQUESTER_SCOPE`) 전면 적용**: 이미 큐 서버(`8101`)에서 검증한 스코프 분리(`#204`, `#931`)를 모든 내부 엔드포인트에 기본값으로 적용해야 한다.

`#911`(`pstack`), `#939`(`addyosmani/agent-skills`), `#938`(작업자 3단계 정의 및 인지적 부채·판단 포기 예방)은 별개의 아이디어가 아니라 **하나의 완결된 '인간-AI 협업 프로토콜'을 이루는 세 축**이다. 이 세 가지를 묶어 개발할 때 개인 클러스터와 회사 AX 인프라 양쪽에서 가장 큰 레버리지(효과)가 나온다.

### 7.2 통합 워크플로우 설계 (3-Phase Cognitive Debt Shield)

#### Phase 1. 착수 전 (Pre-Plan): '인지적 위임(#938 ①)' 상태를 만드는 3분 인터뷰
1. **선조회 및 가설 브리핑 (`#939` + `#911`)**:
   - 지휘자는 질문하기 전에 반드시 RAG(`search_context_tool`)와 대상 소스를 먼저 읽고 사전 맥락(`how`/`why`)을 확보한다.
   - 첫 응답에서 곧바로 계획을 세우지 않고 현재 파악한 가설과 확신도를 먼저 제시한다:
     ```markdown
     - **HYPOTHESIS**: <사용자가 달성하려는 1문장 목표>
     - **CONFIDENCE**: ~75% (누락: <확정이 필요한 설계 갈림길 1줄>)
     - **사전 맥락 (`how`/`why`)**: <확인한 정본 파일 경로 및 현재 동작>
     ```
2. **추정치·가역성 동반 단일 질문 (`#939` + `#911` + `#938`)**:
   - 확신도가 95% 미만이면 가장 중요한 갈림길 **단 1개**만 묻되, 작업자가 고민 비용을 아낄 수 있도록 **추정 답안(`GUESS`), 가역성(되돌리기 쉬운지), 판단 유보 시 기본값(`DEFAULT`)**을 함께 제시한다:
     ```markdown
     - **Q**: <핵심 결정 질문 1개>
     - **GUESS (추천)**: <안 A> — <근거 1줄> (가역성: 높음/낮음)
     - **DEFAULT (판단 유보 시)**: 지금 결정하기 어렵다면 <기본안>으로 진행하고 [판단 유보]로 기록합니다.
     ```
3. **6줄 스펙 카드(`Restate`) 확정 및 턴 종료 (`#911` + `#939`)**:
   - 답변이 수렴하면 `plan_set_tool`을 부르기 직전 아래 **6줄 스펙 카드**로 요약해 명시적 승인을 받는다:
     1. **Outcome (목표)**: 1문장 결과물
     2. **Blast Radius (변경 범위)**: 수정/생성할 허용 파일·모듈 경계
     3. **Out of Scope (비범위 — 필수)**: **이번 작업에서 절대 건드리지 않을 것**
     4. **Deferred (판단 유보 — `#938` ②)**: 이번에 결정을 미룬 항목 · 틀렸을 때 영향 · 재검토 시점
     5. **Proof Protocol (증명 계약 — `#911`)**: 완료를 증명할 구체적 실행 명령·관찰 가능한 출력
     6. **Execution Track (수행 방식)**: 단독(로컬 서브에이전트) vs AX 워커 분산 (또는 경량 패스트트랙)

#### Phase 2. 구현 및 인수인계 중 (In-Flight): '판단의 연기(#938 ②)'가 증발하지 않게 보존
- **판단 유보(`Deferred`)의 일급 객체화**:
  - 기존에는 작업 중 임시로 넘어간 가정이나 미검증 사항이 완료 요약에서 사라져 마치 확정·검증된 것처럼 보였다(이게 쌓이면 `#938` **③ 판단의 포기**가 발생한다).
  - 통합 설계에서는 `ax:plan` 블록과 작업 리포트, 인수인계서에 **`[판단 유보 / Open Assumptions]`** 섹션을 고정하여, *"무엇을 왜 미뤘고 언제 다시 봐야 하는지"*가 다음 세션이나 리뷰어에게 손실 없이 전달되게 한다.
- **코드-스펙 충돌 시 `CONFUSION` 즉시 노출 (`#939`)**:
  - 구현 중 실제 코드가 승인된 6줄 스펙과 충돌하면 조용히 우회하지 않고 멈춰서 `CONFUSION: <충돌 지점> → 선택지 A vs B`로 보고한다.

#### Phase 3. 마감 및 결과 보고 (Pre-Finish Gate): '판단의 포기(#938 ③)'를 막는 압축 증거 보고
1. **편향 제거 검증 & 에이전트 꼼수 감사 (`#939` `doubt-driven` + `Floor Guard`)**:
   - 마감(`issue_finish`) 직전, 작성 에이전트의 자기합리화(`CLAIM`)를 뺀 **`순수 git diff` + `Phase 1의 6줄 스펙 카드`**만 대조하여 비범위(`Out of Scope`) 침범 여부를 확인한다.
   - `git diff`에서 5대 꼼수(① 임계치 하향 ② 기존 테스트/assertion 삭제·`@skip` ③ 무단 `# noqa`/`# type: ignore` ④ 미완성 `TODO`/스텁 ⑤ 미승인 예외 추가)를 자동 스캔한다(`#908` 연계).
2. **인지 부채 제로(0) 요약 카드 제시 (`#938`)**:
   - 사람에게 긴 로그를 읽히지 않고, 첫 화면에 **① 목표 대비 변경 결과, ② `Proof Protocol` 실행 증거(성공 응답 / 검사 통과 / 실증 완료 구분 표기), ③ 남아 있는 `[판단 유보]` 및 미확인 한계** 딱 3가지만 분리해 보고한다.
