# ax-request — 일감을 등록한다 (요청자 측)

> 마스터가 생성해 배달한다. **손으로 고치지 말 것** — 다음 배달에 덮인다.

## 0. 🔴 이 머신의 자리

**여기는 사람이 쓰는 기계다.** 역할은 `requester` — **요청하고 확인한다.**

| | |
|---|---|
| 한다 | 일감 등록 · 매니페스트 확인 · 검색 · 시소러스 등록 |
| 🔴 **안 한다** | 큐에서 claim · `attempt/` 브랜치 생성 · 소스 파일 수정 · 빌드 |

**왜 안 하나**: 사람이 편집 중인 워킹트리에서 에이전트가 브랜치를 만들고 파일을 고치면,
그게 더티 체크가 막으려던 바로 그 사고다. `.uasset` 은 바이너리라 날리면 되살릴 수 없다.
실행은 `worker` 역할 머신이 한다 — 그쪽엔 `ax-work` 스킬이 있다.

설정은 항상 `./.ax/config.json` 에 있다. **없으면 추측하지 말고 마스터에 배달을 요청한다.**

## 1. 등록 전에 — 무엇을 부탁하는지 스스로 정리한다

사용자의 말을 그대로 큐에 넣지 않는다. 최소한 이 셋이 있어야 워커가 일할 수 있다:

| | 없으면 |
|---|---|
| **대상 클래스·파일** | 매니페스트 검색이 엉뚱한 걸 물어 온다 |
| **골조**(`[PSEUDO]` 본문만 비운 시그니처) | 🔴 워커가 시그니처를 지어낸다 |
| **동결 계약** (바꾸면 안 되는 선언) | 워커가 공개 API 를 바꿔 버린다 |

🔴 **골조는 지금 자동 생성되지 않는다.** `register_work_tool` 은 골조를 **인자로 받는다** —
사람(또는 네가 사용자와 합의해서) 써 주는 전제다. 없으면 **등록하지 말고 먼저 만든다.**

부족하면 **묻는다.** 반쯤 채운 일감은 워커가 반쯤 틀린 코드를 만들게 한다.

## 2. 검색은 입구가 하나다

    search_context_tool(query, limit)

🔴 **이것만 쓴다.** 대괄호 해석 → 시소러스 확장 → 검색을 한 번에 한다. 다른 경로로 돌면
시소러스가 안 걸려 한국어 질의가 조용히 나빠진다.

`[미션 시스템]` 처럼 **대괄호로 개념을 감싸면** 그게 시소러스 조회 신호다.

## 3. 등록

    register_work_tool(title, target_repo, specs_json, original_request, target_branch, project)

- `title` — 한국어 그대로 좋다. 내부에서 slug 로 바뀌고 한글도 안전하다
- `specs_json` — 태스크 목록. 태스크마다 대상 파일·골조·계약
- `original_request` — 🔴 **사용자 원문을 그대로** 넣는다. 나중에 "왜 이걸 시켰나" 의 유일한 근거다

등록되면 태스크마다 **매니페스트가 1회 수집**된다(컨텍스트 문서 + 도메인 규범 + 골조).

## 4. 등록 후 반드시 확인한다

    get_manifest(task_id, project)

🔴 **결손을 읽는다.** 매니페스트는 베스트에포트라 이런 문장이 들어 있을 수 있다:

- *"검색 결과가 없다"* → 대상 클래스명이 틀렸거나 아직 색인이 안 됐다
- *"규범 grounding 없이 진행된다"* → 도메인 규범이 안 붙었다. 그 상태로 보내면 워커가
  도메인 규칙을 모른 채 코드를 짠다

**결손이 있으면 워커에 보내기 전에 고친다.** 등록은 취소보다 싸다.

## 5. 어디로 갈 수 있나

    list_workshops_tool(name)        · 등록된 작업장과 역할
    check_workshops_clean_tool(name) · 지금 보낼 수 있는 곳 (dispatchable)

🔴 `dispatchable` 이 비어 있으면 **워커의 워킹트리가 더럽다는 뜻**이다. 사람이 편집 중일 수
있으니 **밀어붙이지 말고 알린다.** 자동화는 절대 `git clean` 을 부르지 않는다.

## 6. 🔴 언제든 멈출 수 있다 — 그게 대화식의 전제다

사용자가 *"방향이 이상한데"* 라고 하면 **바로 멈춘다.** 큐에 경로가 있다:

    POST /api/v1/tasks/<task_id>/cancel                 이 태스크를 취소
    POST /api/v1/admin/workers/<worker_id>/directive     그 워커에 지시(abort 등)

지시는 **화이트리스트 검증**을 거치고 **fire-once** 다 — 워커의 하트비트가 다음 박동에
가져간다. 그래서 **즉시가 아니라 다음 하트비트에 멈춘다**는 것을 사용자에게 말해 준다.

🔴 **멈춘 뒤에 브랜치를 지우지 않는다.** 실패한 attempt 도 조사 자산이다(§8.4 누적 모델).
정리는 사람이 판단한다.

## 7. 검증과 피드백 — 이 머신이 가장 빠르다

이 PC 에는 UE5 가 있다. **워커에 왕복하지 않고 여기서 바로 빌드해 컴파일 에러를 본다.**

🔴 **다만 메인 워킹트리에서 브랜치를 갈아타지 않는다.** 사람이 편집 중이던 것이 날아간다
(`.uasset` 은 복구 불가). 별도 워킹트리를 쓴다:

    git worktree add ../ModularStage-task-<id> task/<id>

반려할 때는 **코드 위치에 `[FEEDBACK]` 블록을 박아** commit·push 한다 — 골조의 `[PSEUDO]`
와 같은 자리, 같은 방식이다. 큐의 텍스트만으로는 워커가 **어디를** 고칠지 모른다.
🔴 **재구현이 아니라 수정**이다 — 그때까지의 구현은 누적된다.

## 8. 🔴 이 머신에서 하지 않는 것

    큐에서 claim · attempt/ 브랜치 · 소스 수정 · 빌드 · git clean · reset --hard · main push

사용자가 "여기서 그냥 고쳐줘" 라고 하면 — **할 수는 있다.** 다만 그건 **클러스터 작업이
아니라 사람의 로컬 편집**이고, 큐·매니페스트·검증 층을 타지 않는다는 것을 말해 준다.
둘을 섞으면 나중에 무엇이 검증된 코드인지 알 수 없다.
