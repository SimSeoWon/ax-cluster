| [실패] 안 되어 있던 것 | systemd 설치 · ufw 8103 · MCP 클라이언트 등록 · **커밋 0건** · 리포트 없음 |

즉 **만들고 테스트까지 끝냈는데 설치·개방·등록·커밋 직전에 멈춘** 상태였다.

### [중요] 내가 이 세션 초반에 어긴 규약

- **세션 시작 시 `reports/*.md` 정독** — 하지 않았다. 리포트 07 의 끝부분만 `tail` 로 잘라봤다.

- **`agy`·다른 머신 활용** — `agy_delegation` 메모리가 있는데 쓰지 않고 혼자 처리했다.
  사용자 지적을 받고 나서야 절 요약을 위임했다.

둘 다 "멈춘 지점 확인"을 가벼운 작업으로 판단한 데서 나왔다. 판단이 틀렸다.

## 2. `ax-projects` (8103) 가동

### 2.1 실행 전 기록 (인프라 변경)

```bash
install -o root -g root -m 644 \
  /home/sim/ax-cluster/master/systemd/ax-projects.service \
  /etc/systemd/system/ax-projects.service
systemctl daemon-reload
systemctl enable --now ax-projects.service
ufw allow from 192.168.0.0/24 to any port 8103 proto tcp \
    comment 'ax-projects MCP (LAN only)'
```

`pkexec` 로 실행(마스터는 화면에 polkit 대화상자가 뜬다 — `sudo_privilege_handling` 규약).
**exit 0**, `enabled` + `active`, ufw 규칙 등록 확인.

### 2.2 검증

| 확인 | 결과 |
|---|---|
| `ss -tln` | `0.0.0.0:8103` LISTEN |
| MCP `initialize` (LAN IP 로) | **200** — 세션 ID 발급, instructions 반환 |
| `journalctl -u ax-projects` | StreamableHTTP session manager started, 에러 없음 |
| `claude mcp add --scope user --transport http` | `ax-projects: ... -  Connected` |

이제 대화로 프로젝트 추가·전환이 된다. 노출 도구 4종:
`register_project` · `set_active` · `list_projects` · `check_registry`.

### 2.3 설계상 기록해 둘 것

- **설치본은 `mcp` 2.0.0 이라 `mcp.server.fastmcp` 가 없다.** 고수준 API 는 `mcp.server.MCPServer`.
  [중요] `task_queue/mcp_server.py` 도 옛 경로를 쓰고 있었다 → **§5 에서 수정 완료.**
- **DNS 리바인딩 보호를 켜 두었다.** 방화벽이 막는 것은 LAN 밖 접근이고, 이 보호가 막는 것은
  LAN 안 브라우저가 악성 페이지에 속아 이 포트를 찌르는 경로다. 서로 다른 위협이다.
- [주의] **SDK 의 `allowed_hosts` 는 와일드카드 `*` 를 지원하지 않는다** — 정확 일치 또는 `host:*` 뿐이고
  `["*"]` 를 넣으면 전부 거부된다 (2026-08-08 실측).
- `AX_PROJECTS_ROOT` 에 **폴백을 두지 않았다** (§5.5.3-④) — 루트를 역산하지 않는다.

## 5. [완료] `task_queue` stdio MCP 수정 (같은 세션, 사용자 지시)

§2.3 에서 발견한 것을 바로 고쳤다.

**증상:** `task_queue/mcp_server.py` 가 `mcp.server.fastmcp` 를 import 하는데 설치본은 `mcp` 2.0.0
이라 그 경로가 **없다.** stdio 모드가 import 단계에서 죽어 있었다.

**왜 아무도 몰랐나 — 이게 이 건의 핵심이다.**
① HTTP `--serve` 는 이 모듈을 **지연 import** 해서 가동 중인 서비스는 멀쩡했고,
② **어떤 테스트도 이 모듈을 import 하지 않았다.** 82건이 전부 통과하는데 stdio 는 죽어 있었다.

**수정:**

```diff
-from mcp.server.fastmcp import FastMCP
-mcp = FastMCP("task-queue")
-    mcp.run()
+from mcp.server import MCPServer
+mcp = MCPServer(name="task-queue", instructions=(...))
+    mcp.run(transport="stdio")
```

`master/projects/mcp_server.py` 와 같은 경로로 통일했다. API 는 FastMCP 와 거의 동형이라
`@mcp.tool()` 데코레이터와 도구 본문은 손대지 않았다.

**검증 — 모듈 import 로 그치지 않고 실제 stdio 핸드셰이크까지:**

| 단계 | 결과 |
|---|---|
| `initialize` | `serverInfo{name:"task-queue"}` |
| `tools/list` | 6종 전부 (`register_work`·`register_task`·`claim_task`·`list_tasks`·`list_works`·`status_summary`) |
| `tools/call status_summary_tool` | `{"tasks_by_status":{},"works":0,"tasks":0}` — **`ax-state` 실데이터** |

[주의] 2.0.0 API 함정 두 가지: `list_tools()` 는 **코루틴**이고, `Tool` 의 속성은 `inputSchema` 가
아니라 **`input_schema`** 다.

**회귀 테스트 신규 — `master/test_mcp_servers.py` (24건).**
버그가 살아남은 원인이 "테스트가 이 모듈을 안 건드림" 이므로, 로직이 아니라
**import 되는가 · 도구가 등록되는가 · 스키마가 생성되는가**를 검사한다.
`mcp.server.fastmcp` 가 **없다는 것**도 함께 단언해서 SDK 가 바뀌면 여기가 먼저 깨지게 했다.
두 MCP 서버(task_queue 6종 · projects 4종)를 같이 본다.

**테스트 82 → 106건 전부 통과.** 가동 중인 서비스 영향 없음
(`8101 /api/v1/health` 200 · `8102 /health` 200 · 셋 다 `active`).

커밋 `f78fef8`.

### 7.3 워크숍 스키마 구현 — `master/projects/` (커밋 `110a463`)

| 계층 | 추가 |
|---|---|
| `config.py` | `Workshop` 데이터클래스 + `ProjectConfig.workshops` |
| `logic.py` | `set_workshop` · `remove_workshop` · `list_workshops` (+`list_projects` 에도 포함) |
| `mcp_server.py` | 도구 3종 추가 — **4종 → 7종** |

`driven`(`ssh` | `interactive`)이 스키마의 핵심이다. 머신마다 구동 방식이 다른 것이
주석이 아니라 **필드**로 남고, `drivable_hosts` 로 "밀어넣을 수 있는 머신" 이 바로 뽑힌다.

설계 결정 2건:
- **fail-closed** — `driven=ssh` 인데 `path`/`user` 가 없으면 거부. 밀어넣겠다고 선언해 놓고
  대상을 특정 못 하면 그 선언이 거짓이 된다. 검증 전에 파일을 건드리지 않는다
- **재등록은 병합이 아니라 교체** — 부분 병합하면 "driven 을 interactive 로 바꿨는데 예전
  path 가 남은" 상태가 생기고, 파일만 봐서는 의도인지 사고인지 구분되지 않는다

[중요] **윈도우 경로 백슬래시 round-trip 을 테스트로 못박았다.** `E:\trunk\ModularStage` 가
YAML 에서 double-quote 에 갇히면 `\t` 가 **탭**으로 해석돼 경로가 조용히 깨진다.
원문 대조 + 탭 부재 + 파일 원문까지 3중 검사하고, `default_flow_style=False` 를 유지해야
하는 이유를 코드 주석에 남겼다.

실등록 후 **`.2` 에 그 경로가 실재하는지 SSH 로 대조**했다 — OK.

### 7.4 [중요] `project_id` 대소문자 확정 — 고를 문제가 아니었다 (커밋 `665fbe3`)

§5.5.4 초안은 "훅 배선 전에 정규값을 확정하고 **둘 중 하나를 고르라**"고 적었다.
Gitea DB(`repository` 테이블)를 `pkexec` 로 직접 읽어 보니 **고를 문제가 아니었다.**

| 컬럼 | 값 | 쓰임 |
|---|---|---|
| `owner_name`/`name` | **`Sim/ModularStage`** | 표시용 — **훅 페이로드가 싣는 `full_name`** |
| `lower_name` | **`modularstage`** | **디스크 경로 · 동일성 판정** |

소유자 `Sim` 아래 5개가 전부 CamelCase 다. §5.5.3 의 소문자 목록은 `lower_name` 을 본
것이었다 — **어느 한쪽이 틀린 게 아니라 용도가 다르고 둘 다 필요하다.**

하나로 통일했다면 어느 쪽을 골라도 깨졌다:

| 잘못된 통일 | 결과 |
|---|---|
| 전부 대문자 | `resolve_bare_path` 가 `gitea-repositories/Sim/ModularStage.git` 를 찾다 실패 — **그런 디렉토리는 없다** |
| 전부 소문자 | 훅이 대문자로 오는데 config 는 소문자 → 규약 ③ 의 **409 fail-closed 에 전부 걸려 색인이 조용히 안 돈다** |

**결정 — Gitea 자신의 모델을 따른다: 저장은 표시용 정규값, 비교는 casefold,
디스크 경로는 소문자.** `normalize_project_id()` · `project_id_disk_path()` ·
`Registry.find_by_project_id()` 3개로 구현했다.

[중요] **casefold 비교는 관용이 아니라 rename 방어다.** Gitea 에서 대소문자만 바꾸는 rename 은
`lower_name` 을 바꾸지 않는다. 표시값만 비교하면 그 한 번에 훅이 전부 409 로 거부되고
**아무 에러 없이 색인만 멈춘다.**

**조사 중 나온 운영 사실 2건** (§5.5.4-④-1 에 기록):
1. **Gitea DB 가 `/usr/local/bin/data/gitea.db` 다.** `app.ini` 의 `PATH` 가 상대경로라
   작업 디렉토리 기준으로 풀렸다. 표준 배치(`/var/lib/gitea/data/`)를 가정하면 엉뚱한 곳을 본다.
   `DB_TYPE=sqlite3` 인데 `HOST=127.0.0.1:3306` 이 남아 있는 것도 혼동 요인
2. **`sim` 이 `gitea` 그룹에 파일상으론 있는데 세션 자격증명엔 없다** — 그룹 추가 후
   재로그인을 안 했다. §5.5.3-a 의 조건이 **파일상 충족, 런타임 미충족** 상태다.
   재로그인하면 root 없이 읽힌다

### 7.5 [완료] loopback 프로세스 수명주기 — 세션 경계가 주인을 정한다 (커밋 `380e840`)

§5.5.4-① 이 "작업 단위로 SSH 로 띄우고 내린다"고만 적고 **누가 주인인가를 미뤄뒀다.**
실측해 보니 **하나의 답이 아니었다.**

```
SSH 로 들어온 프로세스의 SessionId = 0      ← 서비스 세션
query session → console janus 9 활성        ← 데스크톱은 세션 9
```

[중요] **윈도우 세션 0 은 데스크톱에 접근할 수 없다** — 설정으로 우회하는 게 아니라 OS 격리다.

| 프로세스 | 데스크톱 | 마스터 소유 | 주인 |
|---|---|---|---|
| **Unreal MCP** (GUI 에디터 내장) | 필요 | [실패] **구조적 불가** | 세션 9 의 사람 |
| **`gjc`** (CLI) | 불필요 | [완료] | 마스터 — 작업 단위 |
| **`UnrealEditor-Cmd`** | 불필요 | [완료] | 마스터 — 작업 단위 |

**① Unreal MCP 는 설계에서 뺐다.** §9.1 은 "loopback 이라 마스터가 *붙을* 수 없다"고 했는데,
세션 경계에서 한 번 더 막힌다 — **띄울 수조차 없다.** 절차를 만들 수 없으니 마스터는 이
프로세스에 수명주기 책임을 지지 않는다.

**② SSH 연결이 곧 수명이다.** 연결이 끊기면 자식도 죽는 것이 **버그가 아니라 설계다.**
감독자도 고아 프로세스도 없다 — **AgentTest 가 `watch.exe` 로 `.poll()` 감시해야 했던
이유가 여기서 사라진다**(그때는 소유 주체가 그 PC 안에밖에 없었다).
"SSH 보다 오래 살아야 한다"가 나오면 손으로 감독자를 짜지 말고 윈도우 서비스에 넘긴다 —
마스터에서 `process_lifecycle.py` 를 폐기하고 systemd 에 넘긴 것과 같은 판단(§5.4.3).

**③ 뜻밖의 소득 — 층3 경로가 열렸다.** `UnrealEditor-Cmd` 가 세션 0 에서 돈다는 것은
**빌드·`RunTests` 를 마스터가 SSH 로 몰 수 있다**는 뜻이다(`.2` 한정). [주의] 세션 배치만
확인했고 실제 구동은 안 해봤다 — 미결로 남겼다.

### 8.3 [중요] 판정 신호 함정 2건 — 이게 이 절의 진짜 소득이다

실검증의 값어치는 "된다" 가 아니라 **"어떻게 판정하면 틀리는가"** 를 알아낸 데 있다.

**① SSH 종료 코드를 믿으면 안 된다.**
두 실행 모두 에디터는 `EXIT CODE: 0` 인데 **`ssh` 는 1 을 반환했다.** 감싼 배치의
`echo [wrapper-exit] %ERRORLEVEL%` 도 **찍히지 않았다.** 같은 배치를 에디터 없이 돌리면
정상 기록되므로 **래퍼 문제가 아니다** — 원격 프로세스 종료와 SSH 채널 종료가 어긋난다.

**② `Error` 문자열로 판정하면 안 된다.**
**전부 통과한 실행에 `LogAutomationTest: Error` 가 15줄 있었다.** 실패를 일부러 유발해
보는 부정 경로 검사들이 그렇게 남긴다. `grep -i error` 로 게이트를 짜면
**통과한 빌드를 실패로 판정한다.**

**→ 올바른 신호는 둘뿐이다:**

```
LogAutomationController: Display: Test Completed. Result={Success|Fail} Name={..} Path={..}
LogAutomationCommandLine: Display: **** TEST COMPLETE. EXIT CODE: N ****
```

`Result={Fail}` == 0 **그리고** `EXIT CODE: 0` 일 때만 통과. 둘 중 하나라도 없으면
(로그가 잘렸거나 프로세스가 죽었거나) **fail-closed 로 실패 처리**한다.
§9.4.4 의 층2 VERDICT 계약이 "마지막 비어 있지 않은 줄" 을 못박은 것과 **같은 종류의
규약이고 같은 이유로 필요하다** — 파싱 규칙을 느슨하게 두면 게이트가 조용히 무의미해진다.

### 10.3 [중요] 이 절의 핵심 — `ssh` 종료 코드가 **실패를 숨긴다**

성공 경로만 봤으면 "빌드는 종료 코드가 멀쩡하네" 로 끝날 뻔했다. **실패 경로를 일부러

| `Build.bat` (**실패**) | `Failed (RulesError)` | **0** ← **거짓 성공** |

[중요] **마지막 줄이 치명적이다.** 종료 코드로 게이트했으면 **실패한 빌드를 통과시켰다.**
앞의 두 줄은 "거짓 실패" — 시끄럽지만 안전하다. 이건 반대다. **조용히 틀린다.**

감싼 배치의 `%ERRORLEVEL%` 는 빌드에서는 맞았지만(0 vs 8) **에디터 실행에서는 기록조차
되지 않았다**(§8.3). 즉 **래퍼로도 메울 수 없다** — 로그 파싱 외에 방법이 없다.

**§5.5.4-⑥-③-1 을 이 표로 교체했다.** 이전 서술은 "에디터가 1 을 낸다" 는 **한 방향만**
근거였다. 거짓 성공 사례가 생긴 지금이 훨씬 강한 근거다.

### 10.4 구현 — 빌드와 테스트는 계약이 다르다

## 11. [완료] 인증 계층 — 세 서비스 공유 베어러 토큰 (같은 세션, 사용자 지시)

이 리포트에서 **매 절마다 "계속 미뤄지는 중" 으로 적혀 있던 항목.** 닫았다.

### 11.1 무엇이 문제였나

`task_queue`(8101) · 브로커(8102) · `ax-projects`(8103) 세 서비스가 전부 인증 없이 떠 있었고
방어선이 `ufw` 하나뿐이었다. **방화벽은 LAN *밖*만 막는다** — LAN 안의 무엇이든
(감염된 기기, 브라우저가 연 악성 페이지, 잘못 설정된 컨테이너) 큐를 조작하고 추론을 태우고
프로젝트 마운트를 바꿀 수 있었다. 게다가 §7 에서 워크숍 경로까지 레지스트리에 넣었으므로
노출 시 드러나는 정보도 늘어난 참이었다.

### 11.2 왜 공유 베어러 토큰인가

mTLS 도 OAuth 도 아니다. 클라이언트가 **소수**(작업장 2대 + 마스터 자신)이고 전부 사람이
관리하는 LAN 장비다. 과한 장치는 운영이 안 되고, **운영 안 되는 보안은 없는 것과 같다.**
세분화가 필요해지면 서비스별 토큰으로 나눈다 — 구조는 그대로다.

`master/auth.py` 하나에 모았다. **순수 ASGI 미들웨어**라 FastAPI(브로커·task_queue)와
MCP(Starlette, ax-projects) 양쪽에 **같은 것**을 쓴다.

### 11.3 [중요] fail-closed 3중

| | |
|---|---|
| ① | **토큰이 없으면 서비스가 뜨지 않는다.** "인증 없이 계속" 은 선택지가 아니다 — **그게 바로 고치려던 상태다** |
| ② | 32자 미만이거나 **파일 권한이 열려 있으면(그룹·기타 비트) 거부.** 짧은 토큰은 없는 것보다 나쁘다 — 있다는 착각을 준다 |
| ③ | 헤더 없음·형식 오류·값 불일치 → **401**. 비교는 `hmac.compare_digest`, 실패 사유는 알려주지 않는다 |

스코프 처리도 명시했다: `lifespan` 은 **통과**(앱이 기동은 해야 한다), `websocket` 은
**거부**(쓰는 서비스가 없고, 인증 안 된 업그레이드 경로를 열어 둘 이유가 없다).

### 11.4 열린 것은 `/livez` 하나뿐

`{"ok": true}` 만 돌려주고 아무것도 노출하지 않는다.

[중요] **브로커의 `/health` 는 인증 뒤에 뒀다** — 노드 주소와 적재 모델을 드러내기 때문이다.

## 12. [완료] 이벤트 큐 설계·구현 (같은 세션, 사용자 지시)

Gitea 웹훅 전환의 **전제조건**. §7.4 에서 선결 조건(`project_id` 대소문자)이 해소돼
착수 가능해진 항목이다.

### 12.1 [중요] 원형을 그대로 쓰지 않았다 — append 방식은 이벤트를 잃는다

§5.4.5 는 `.claude/_regenerate_queue.jsonl` 을 "원형으로 쓸 것" 이라고 적어 뒀다.
**설계해 보니 그대로 쓰면 안 됐다.**

append-only 파일은 소비 시점에 경합이 생긴다:

```
소비자: events.jsonl 을 읽고 → rename 으로 가져감
생산자: 이미 열어 둔 fd 로 **rename 된 파일에 계속 append**
        → 소비자는 이미 읽은 뒤라 그 이벤트를 못 본다
```

창이 좁을 뿐 **유실**이고, §5.4.5 자신이 못박은 대로 **웹훅에서 유실은 영구다.**

→ **파일 하나 = 이벤트 하나.** 생산자는 임시 파일에 쓰고 `rename`(같은 FS 에서 원자적),
소비자는 디렉토리를 나열해 처리한다. **락도 offset 도 필요 없고 경합 창이 아예 없다.**

```
~/ax-spool/
    tmp/        rename 전 임시 파일
    incoming/   생산자(Gitea 훅)가 넣은 것
    claimed/    소비자가 처리 중인 배치
    rejected/   검증 실패 — [중요] 지우지 않는다(감사)
```

[중요] **`~/ax-state` 에 두지 않았다.** 그쪽은 상태 전이마다 **감사 커밋이 도는 git 저장소**다.
스풀은 **지워지는 것이 정상**인데 git 이력에는 영원히 남는다 — 성격이 정반대다.

### 12.2 [중요] 설계의 핵심 — 합치기가 안전한 근거

같은 `project_id` 의 이벤트 N 개에서 **최신 하나만 남기고 나머지를 버린다**(§5.5.3-⑤).
그래도 되는 이유가 이 설계에서 가장 중요한 연결이다:

> **워터마크가 커밋 해시이기 때문이다** (§5.5.3-c).
> 소비자는 "이 이벤트를 처리" 하는 게 아니라 **`last_indexed_commit` → 현재 HEAD 를
> 따라잡는다.** 중간 커밋을 개별로 알 필요가 없다.

**워터마크가 타임스탬프였다면 이 합치기는 안전하지 않다.** §5.5.3-c 의 결정과
§5.4.5 의 요구가 **서로를 떠받치고 있었다** — 따로 정해진 두 결정이 맞물린 것을
설계하면서 발견했다.

버린 개수는 센다(`coalesced_away`). 무거운 재색인을 몇 번 절약했는지가 이 큐의 존재
이유이므로, 그 수치가 안 보이면 효과를 알 수 없다.

### 12.3 나머지 결정

| | |
|---|---|
| **단일 소비자** | `flock` 으로 **강제**한다. 규약으로만 두면 언젠가 둘이 돈다. 획득 실패는 에러가 아니라 "이미 돌고 있다" — 프로세스가 죽으면 커널이 놓으므로 스테일 락이 없다 |
| **전달 보장** | **at-least-once.** 크래시하면 `claimed/` 가 남고 재기동 시 먼저 처리한다. exactly-once 를 안 만든 이유는 **색인이 멱등**이라서다(12.2 와 같은 근거) |
| **직렬화 단위** | `project_id` 별. 전역 락이면 프로젝트 A 의 재색인이 B 를 통째로 막는다 |
| **합치기 비교** | **casefold** (§5.5.4-④) — `Sim/ModularStage` 와 `sim/modularstage` 는 같은 것이다 |

[중요] **거부한 이벤트를 지우지 않는다** (`rejected/` + `.why` 사유 파일).
조용히 사라지면 **"훅이 안 오네" 와 "오는데 거부되네" 를 구분할 수 없다.**
이 세션의 §7.4(대소문자)가 바로 **모든 이벤트가 조용히 409 로 거부될 뻔한** 사례다 —
그때 rejected 가 없었다면 원인을 찾는 데 훨씬 오래 걸렸을 것이다.

[중요] **재귀 차단은 합치기 *전에* 한다** (§5.5.3-d). `[ax-index]` 트레일러가 붙은 커밋을
먼저 걸러야 한다 — 나중에 걸면 **색인 커밋이 더 최신일 때 사람 커밋을 잡아먹는다.**
테스트로 고정했다.

### 12.4 검증

테스트 **38건** (`test_events.py`):
유실 없음(claim 직후 도착분이 다음 배치에 온전히) · 크래시 후 재처리 · casefold 합치기 ·
`flock` 이중 기동 차단(실제 두 프로세스) · 거부 보존 + 사유 · 원자성(tmp 가 비는지) ·

## 14. [완료] 검색 코어 이식 — 1단계 (같은 세션, 사용자 지시)

> **"검색 코어 이식 시작해줘. 이것도 마운트 된 디렉토리 기준으로 처리하는게 맞는 거 같아."**
> **"기능은 공용이고, 어느 프로젝트를 바라보는가에 따라 어느 디렉토리에 저장된 데이터를 찾을지 분기를 타는거야"**

§5.2-E 에서 나눈 1단계(검색 코어 3,552줄)를 옮겼다. **원본 10파일 → 여기 7파일**로,
색인에 실제로 쓰이는 부분만 가져왔다.

### 14.1 이식의 핵심 변경점 — 경로가 상수에서 함수로

AgentTest 의 구조적 한계는 §5.5.1 에서 이미 실측해 뒀다:

```
AgentTest:  run_http_server(project_root, port)
              └─ register_*_routes(app, project_root, ...)   ← 전 라우트가 클로저에 캡처
                 → 요청 단위로 프로젝트를 고를 방법이 없다
```

사용자 지시가 이걸 정확히 뒤집는다. 그래서 **경로 해석을 상수가 아니라 함수로** 만들었다:

```python
def resolve(name="", *, registry=None) -> ProjectPaths:
    reg = registry or Registry.load()      # [중요] 매 호출 레지스트리를 다시 읽는다
    ...
```

캐시하지 않는 것이 요점이다. **마운트를 바꾸면 다음 호출이 바로 새 디렉토리를 본다 —
서비스 재기동이 필요 없다.** 두 번째 프로젝트를 동시에 열기로 결정하면
`resolve_mounted_only()` 만 안 쓰면 되고 아키텍처는 그대로다.

컬렉션 이름이 `context_a`/`context_b` 로 고정인데도 프로젝트가 안 섞이는 이유도 여기 있다 —
**`vector_db` 디렉토리가 프로젝트별로 갈린다.** §5.5.1 이 지적했던 "컬렉션명에 프로젝트
식별자가 없다" 는 문제가 경로 분기로 해소됐다.

| 파일 | 줄수 | 역할 |
|---|---|---|
| `paths.py` | 145 | 마운트 → 디렉토리 해석. **이식의 중심** |
| `documents.py` | 157 | 컨텍스트 MD 파싱·선별 (`cs_common.py` 717줄 중 필요분) |
| `index.py` | 181 | 벡터 색인, 더블 버퍼 (`double_buffered_index.py` 이식) |

### 14.2 [중요] 이식 중 발견한 누락 — 문서 149건을 조용히 버리고 있었다

첫 색인이 **1,055개 MD 중 888개**만 넣었다. 차이를 실측했다:

```
  전체 MD      1055
  _domains 제외  18   ← 정책 (원본과 동일)
  빈 본문 제외   149   ← [중요] 내가 넣은 규칙
  색인 대상     888
```

`Manager/ManagerBase.md`(273B)를 열어 보니 **프론트매터만 있고 본문이 없었다** —
`tags` · `category` · `related_classes: {UManagerBase: ...}` 는 있는데 산문이 없다.

원본을 확인했다. `double_buffered_index.py:108~121` 은 **읽기 실패와 `_domains/` 만**
거른다. 태그 캐시(`:215`)도 프론트매터가 **아예 없을 때만** 건너뛴다.
**원본은 본문 없는 문서를 버리지 않는다.** 내 `iter_documents()` 의 `if doc.is_empty: continue`
한 줄이 만든 이식 오류였다.

[주의] **이게 왜 나쁜가.** 그 스텁의 존재 이유가 바로 **클래스명**이다. 본문이 없다고 버리면
`UManagerBase` 로 검색해서 못 찾게 된다 — 찾으라고 만든 문서인데.

**고친 방식**은 원본과 다르다. 원본은 BM25 에 **원문 전체**를 넣지만, 여기서는 프론트매터를
**읽을 수 있는 문장으로 펼쳐** 임베딩한다(`search_text`). YAML 기호를 그대로 벡터에 넣으면
노이즈가 되기 때문이다. 의도적 편차라 코드에 근거를 남겼다.

결과 **888 → 961건**. 남은 76건도 확인했다 — 전부 `_archive/` 의 **20바이트 placeholder**
(`---\ntags: []\n---`)로 내용이 실제로 없다. 버리는 게 맞다.

**검증**: `UManagerBase` 로 검색하면 `Manager/ManagerBase.md` 가 **1위**다.

### 14.3 [중요] 원본에 없는 것을 둘 더했다 — 프로세스가 갈렸기 때문

**① 세대 포인터를 파일로 남긴다 (`generation.py`)**

색인을 961건 만들고 새 프로세스에서 열었더니 **`count()` 가 0** 이었다.

원인: 더블 버퍼의 Live 포인터가 **메모리에만** 있다. 원본도 부팅 때 무조건 `context_a` 를
Live 로 잡는다(`double_buffered_index.py:40~42`). **원본에서는 문제가 아니었다** —
상주 데몬이라 기동 직후 재색인하고 스왑하므로 포인터가 프로세스 수명 안에서만 의미가 있었다.

여기서는 **색인하는 쪽(이벤트 큐 소비자)과 검색하는 쪽이 다른 프로세스**다. 그대로 두면
재색인 직후 서비스가 재기동되는 순간 **빈 컬렉션을 보고 검색이 0건을 반환한다.**
에러도 안 난다 — 조용히 "결과 없음" 이 되는 종류다.

마커가 유실됐을 때는 **추측하지 않고 실제로 문서가 많은 세대를 고른다.** 자가 복구도 실측했다.

**② 두 채널을 함께 뒤집는 조정자 (`rebuild.py`)**

포인터를 채널마다 따로 두면 **벡터는 새 세대·BM25 는 옛 세대**인 순간이 생긴다.
검색은 둘을 RRF 로 섞으므로 그 순간의 결과는 **어느 세대도 아닌 것**이 된다.
그래서 순서를 고정했다:

```
① 벡터를 work 세대에 쌓는다   (swap 안 함)
② BM25 를 work 세대에 쌓는다  (swap 안 함)
③ 마커를 한 번 뒤집는다        ← 여기서만 Live 가 바뀐다
```

**①·② 중 어디서 죽어도 마커가 그대로라 옛 세대가 온전히 살아 있다.** 실패가 빈 색인을
노출하지 않는다 — §9.5.6 의 fail-closed 와 같은 방향이다.

## 15. [완료] 워크플로우 복구 착수 (같은 세션, 사용자 지시)

> **"워크 플로우를 먼저 하는 게 중요해! 기존에 에이전트 테스트 프로젝트을 참조해서
> 워크 플로우를 적합하게 복구하는 게 가장 먼저라고 생각해"**

검색 라우트·이벤트 소비자를 미루고 워크플로우로 전환했다. **맞는 판단이었다** —
검색은 워크플로우에 *공급*하는 부품이지 그 자체가 목적이 아니다.

### 15.1 먼저 대조부터 — 통째로 옮기면 안 된다

원본 워크플로우는 **9,690줄**이다(`worker/` 3,657 + `mcp/master_orchestrator/` 6,033).
그대로 복사하는 것은 "적합한 복구" 가 아니다. 실측 대조 결과:

**서버 쪽은 이미 살아 있었다.** `task_queue` 이식분(2,889줄)에 `job_kind` · `verify_capable` ·
`verify_epoch` fencing · durable/attempt · `reclaim` · lease · `depends_on` 이 **전부 들어 있다.**
빠진 것은 **루프를 도는 주체**다.

**이미 다르게 갖고 있어 이식하지 않는 것:**

| 원본 | 줄수 | 여기 |
|---|---|---|
| `ue_builder.py` + `ue_test_runner.py` | 541 | `master/layer3_verify.py` (§8·§10 에서 실측 완료) |
| `verifier.py` 판정부 | 일부 | `master/verdict.py` · `layer2_verify.py` |
| `cluster_context.py` 검색 채널 | 148 | `master/context_search/` (§14) |
| 배포 형태(exe 12종 zip) | — | 폐기 — §5.4 가 이미 기각 |

### 15.2 [중요] 가장 큰 차이 — durable merge 권위가 옮겨간다

| | AgentTest (C.3) | 여기 |

### 15.4 이번에 만든 것

**`master/work/branch_names.py`** — 2-tier 브랜치 규약

```
durable    task/<task_id>
ephemeral  attempt/<task_id>/<workshop>/<ts>
```

작업장 A 가 타임아웃돼 B 에 재배정돼도 **서로 다른 ref** 라 A 가 되살아나 push 해도
자기 죽은 브랜치로 간다. **공유 write 타깃이 없어 race 자체가 성립하지 않는다.**
§4.2 가 확정한 대로 작업장이 2곳이고 같은 프로젝트를 보므로 이건 **정확성 요건**이다.

원본의 `select_work_branch(distribution_mode, ...)`(pull 레거시 feature-flag)는 뺐다 —
호환할 레거시 브랜치 이력이 없다. 배포한 적 없는 모드를 위한 플래그는 검증할 수도 없다.
[주의] 브랜치의 그 자리에 오는 것은 `worker` 가 아니라 **`workshop`** 이다. 이 저장소에서
`worker/` 는 BC-250 추론 노드다(§4.1) — 이름을 섞으면 안 된다.

**`master/work/manifest.py`** — 컨텍스트 매니페스트

마스터가 등록 시 **1회 수집**하고 작업장은 **읽기만** 한다. 로컬 LLM 은 MCP 도구를 못 부르니
이게 없으면 grounding 이 아예 없고, 도구를 쓸 수 있는 상용 모델도 같은 검색을 N번 반복한다.

**`master/work/register.py`** — 등록 경로

원본 등록부에서 **저장소 조작부를 잘라냈다.** 원본 오케스트레이터는 윈도우 UE5 프로젝트
루트에 함께 배포돼 `create_branch_if_needed` · `commit_skeletons` 를 직접 했지만,
**우리 마스터는 파일을 소유하지 않고 push 도 못 한다.**

| 원본 등록부 | 여기 |
|---|---|
| 작업 브랜치 생성 · 골조 커밋 | [실패] **작업장** |
| 중복 검사 · work/task 큐 등록 | [완료] 마스터 |
| 컨텍스트 매니페스트 수집 | [완료] 마스터 |

[중요] **명세를 전부 검증한 뒤 등록한다.** 절반 등록하고 실패하면 큐에 반쪽 work 가 남고
그건 사람이 치워야 한다. 부분 실패와 매니페스트 결손은 **결과에 실어 숨기지 않는다.**

**분해(decomposition)는 넣지 않았다** — 요청 하나를 클래스 단위 N개로 쪼개는 것은 §4.5 주제이고
LLM 호출이 필요하다. 섞으면 등록을 테스트할 때마다 추론이 필요해진다.

**`ax-projects` MCP 창구 2종** — `register_work_tool` · `get_manifest`.
작업장(윈도우 Claude Code)이 부르는 진입점이다. 겸사겸사 그 모듈의
**"인증 계층이 없다"** 서술도 정정했다 — §11 에서 붙였는데 문서만 안 따라갔다.

### 15.5 [중요] 실측이 잡아낸 것 2건 — 둘 다 조용히 실패하는 종류였다

**① 골조가 작업장에 도달하지 못한다**

`task_data` 에 골조를 실어 보냈는데 claim 응답에도, `GET /tasks/{id}` 에도 없었다.
원인: 큐가 `task_data` 를 **태스크 마크다운 본문으로만 저장**하고 JSON API 로 노출하지
않는다(`task_queue/logic.py:202`). **원본에서는 문제가 아니었다** — 골조를 git 에 커밋해
보냈고 워커는 체크아웃 후 디스크에서 읽었으니까.

→ **골조를 매니페스트로 옮겼다.** 이미 만들어 둔 마스터→작업장 텍스트 채널이고,
골조·계약·RAG 히트가 한 문서에 모인다. `task_data` 는 감사 기록으로 남긴다.

**② 한글 제목이 전부 같은 slug 가 된다**

두 번째 일감 등록이 `duplicate` 로 거부됐다. 제목이 분명 다른데.

```
'워크플로우 복구 배선 확인' → 'work'
'골조 전달 확인'          → 'work'
'매니저 초기화'           → 'work'
```

`_slugify` 가 비-ASCII 를 버려 빈 문자열이 되고 폴백 `"work"` 로 떨어진다. 그리고
**slug 는 중복 검출 키**다(`find_active_duplicates`). 즉 **두 번째 한글 일감이 항상
첫 번째의 중복으로 거부된다** — 사용자가 한국어로 일하므로 워크플로우가 시작부터 막힌다.
팀이 영문 제목을 쓰던 환경에서는 드러나지 않았던 잠복 버그다.

**고친 방식**: 버려진 내용이 있으면 정규화 원문의 해시를 덧붙인다.

| 성질 | 결과 |
|---|---|
| 같은 제목 → 같은 slug | [완료] **중복 검출은 그대로** (이게 요점이다) |
| 다른 한글 제목 → 다른 slug | [완료] `work_d852a8dc` · `work_90c0f35b` |
| 순수 ASCII 제목 | [완료] 그대로 — 기존 work id 와 호환 |

### 15.6 배선 실측

```
등록   work=20260808_1809_work_90c0f35b  태스크 1/1
claim  job_kind=write  epoch=1  mode=push  requires=['ue5']
수령   get_manifest ok=True — 골조 도달 [완료]  계약 도달 [완료]  RAG 5건
```

프로브 태스크 3건은 **전부 cancel 로 정리**했다 — 큐에 남기면 나중에 작업장 러너가 집는다.
