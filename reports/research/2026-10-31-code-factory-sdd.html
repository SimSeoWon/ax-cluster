01 / 판단

확장은 가능하다. 먼저 ‘근거 있는 작업 단위’를 만든다.

SDD는 스펙을 계획·구현·검증까지 이어가는 개발 방식이고, 코드 팩토리는 그 과정을 반복 실행하는 운영 체계다. 이 보고서는 두 방향을 스펙 중심의 코드 팩토리로 연결하는 설계를 제안한다. 이는 AX가 이미 완성된 코드 팩토리라는 판정이 아니다.

재사용할 기반

RAG와 실행 자산

검색·별칭 확장·로그, 프로젝트 프로필, 작업 등재·검증·전진·마감, 초기화·배달 기능을 연결한다.

우선 보완

스펙에서 태스크까지

일감의 요구와 승인된 플랜 버전, 태스크 상태, 실제 실행·검증 근거 사이의 연결을 명시한다.

05 / 목표 구조 · 제안

Redmine은 요구·플랜·진행의 정본, RAG는 근거를 찾는 경로.

기존 자산 위에 연결할 흐름

01 / CONTROLRedmine 스펙·플랜요구·태스크·완료 조건·기록
02 / CONTEXTRAG + 현재 소스검색·문서 버전·실제 코드 대조
03 / EXECUTION단계 실행기프로필·선행 조건·정적 함수
04 / WORK코드 / 에디터 어댑터기존 분산 경로 / 신규 편집 연결
05 / EVIDENCE검증·실행 증거리비전·검사·변경·미확인
06 / CONTINUITY상태 반영·인수인계태스크 마킹·다음 작업·대화

실행기의 상세 계약과 에디터 어댑터는 제안입니다. 기존 큐·작업 브랜치·승인 함수를 재사용하는 방향이며 대체 구현을 새로 만든 상태가 아닙니다.

스펙과 플랜의 사람용 표시는 Redmine에 둡니다. 실행 증거는 기존 로그·Git 리비전·검사 결과를 가리키고, 태스크는 그 근거의 식별자를 보관합니다. RAG 색인은 검색용 파생물로 취급하여 일감 상태를 독립적으로 확정하는 정본으로 만들지 않습니다.

두 개의 정본을 만들지 않는다.Redmine 본문과 별도 JSON을 함께 쓴다면, 어느 쪽이 원본이고 어느 쪽이 투영인지 먼저 정해야 합니다. 사람 편집과 에이전트 상태 갱신이 충돌했을 때 오래된 플랜을 덮어쓰지 않는 계약이 필요합니다.
06 / 플랜·상태 계약 · 제안

체크박스에 실행 근거와 재개 조건을 연결한다.

  • 일감·스펙·플랜 버전과 프로젝트 유형
  • 태스크 ID·목표·대상 파일/어셋·선행 태스크
  • 기준 리비전·상태·시도 식별자
  • 요청·검색·실행·검증의 근거 ID

상황실행 계약 제안
스펙·플랜이 바뀜영향받는 미완료 태스크를 재검토한다. 과거 완료 결과는 당시 버전에 대한 결과로 남기고 현재 요구 충족 여부를 다시 판단한다.
동시 편집·중복 실행Redmine 갱신 충돌 검출과 실행 시도의 식별·중복 방지 수단을 기존 저장소/큐 구조에서 검토한다. 단순 체크박스를 잠금으로 간주하지 않는다.
리비전이 달라짐변경을 확인한 뒤 계획·대상 어셋·기존 승인 범위에 미치는 영향을 대조한다. 강제 초기화로 로컬 변경을 지우지 않는다.
작업 도중 세션 종료마지막 기록만 신뢰하지 않고 실제 리비전·어셋·실행 흔적과 대조한다. 중복 편집 위험이 있으면 재실행 전 상태를 조사한다.
검증이 없거나 실패완료를 확정하지 않고 미검증/실패와 재개 조건을 남긴다. 새 승인 절차를 무조건 추가하지 않고 기존 보고·승인 계약에 연결한다.
07 / 합의된 태스크 실행 순서

버전 동기화가 프리 에디터보다 먼저다.

#826에 정리된 사용자 요구입니다. 초기 6단계 구상에 프리 에디터와 소스 작업 위치를 반영한 순서를 기준으로 합니다. 언리얼에만 해당하는 단계와 실행 조건을 명시합니다.

1. 버전 동기화업데이트·기준 리비전·로컬 변경 확인
2. 프리 에디터소스 변경 전 필요한 어셋 조사·정리
3. 소스 작업태스크에 따른 추가·수정·제거
4. 제네레이트UE 클래스 추가·제거 등 필요시
5. 빌드UE 컴파일과 프로젝트별 검증
6. 에디터 작업MCP 확인 후 생성·편집·검증
7. 기록태스크 마킹·작업·근거·다음 단계

code 프로젝트 · 먼저 검증할 파일럿

스펙·플랜 확인 → 기준 리비전 확인 → 기존 작업 등재·코드 구현 → 등록 프로필의 정적/통합 검사 → 기존 전진·마감 절차 → 결과·근거 기록.

에디터·프로젝트 제네레이트 단계는 해당 없음으로 남깁니다. 프로젝트의 검증 계약을 읽고 적용하며 UE 규칙을 Python 태스크에 사용하지 않습니다.

신규 클래스 · 소스에서 어셋으로

업데이트·리비전 확인 → 클래스 소스 추가 → 프로젝트 제네레이트 → 빌드 → 에디터 작업이 필요하면 MCP 연결·도구 확인 → 새 클래스를 상속하는 어셋 생성 → 편집·컴파일·검증 → 태스크 기록.

상속 어셋 생성은 플랜상 필요할 때 수행합니다. 에디터가 새 클래스를 인식하는지와 재시작 필요 여부를 확인합니다.

클래스 제거 · 어셋이 먼저

업데이트·리비전 확인 → MCP 준비 → 최신 상태의 상속 어셋 조사 → 구체 대상에 대한 사용자 허락 → 어셋 먼저 제거 → 클래스 파일 제거 → 제네레이트 → 코드 컴파일 → 잔여 참조·상태 검증 → 기록.

의존/참조 조사 범위와 복구 방법은 상세 계획에서 정합니다. 클래스 파일을 먼저 지운 뒤 어셋을 조사하는 순서는 사용하지 않습니다.

08 / 에디터 지원과 배포 · #856

전체 툴을 복제하기보다 편집 어댑터를 좁게 만든다.

Epic 내장 MCP와 Monolith를 동시에 필수 설치로 요구하지 않습니다. 먼저 조회·생성·삭제 전 의존성 조사·컴파일·저장의 실제 지원 범위를 비교하고, 태스크별 필요한 기능에 맞춰 선택하거나 조합하는 방식이 적합합니다. 이는 #856을 구체화하기 위한 제안입니다.

마스터 · 요구·상태 관리

프로젝트·UE·플러그인 버전 계약, 태스크 계획, 승인 대상, 배달 상태와 실행 증거를 관리합니다. 작업 PC에서 확보한 결과를 Redmine에 연결합니다.

작업 PC · 실제 편집

로그인 사용자의 에디터와 로컬 MCP 연결을 사용합니다. 에디터별 직렬 실행과 재시작 후 연결 복구, 실제 어셋 저장·다시 읽기 검증을 설계합니다.

배포 옵션맞는 상황계약·검증할 것
프로젝트 플러그인 소스 고정프로젝트가 C++ 빌드 환경을 갖추고 특정 커밋으로 재현할 때라이선스·커밋·UE 호환성·빌드 환경·신규 PC 복원 경로
엔진에 맞춘 사전빌드 패키지지원 UE 버전용 신뢰할 산출물이 있고 빌드 부담을 줄일 때배포 출처·해시·대상 UE/플랫폼·누락 시 명시적 실패·복구
UE 내장 MCP + 필요한 Toolset현 설치본에서 필요한 기능이 제공되거나 작은 확장이 가능한 경우설치/활성화·실제 도구 목록·동작 버전·재시작·실험적 API 변화
배포 권고 · 아직 미확정프로젝트별 요구 버전을 고정하고 기존 AX 초기화·배달 과정에 필요한 항목만 추가하는 방향을 검토합니다. 자동 업데이트로 진행 중 태스크의 도구 계약이 바뀌지 않게 하며, 배달과 실제 편집 실증을 별도로 기록합니다.

실제 배포 전에는 에디터 연동부·MCP 실행부의 구성과 설정 병합 위치를 확인해야 합니다. 공식 문서의 네트워크·호환 제약도 포함해 로컬 연결/중계 방식을 결정하며, 특정 PC에서 만든 임시 바이너리를 신규 워커의 유일한 정본으로 삼지 않습니다.

공식 기능 근거: Monolith README, Epic 문서. AX 배달 재사용 후보: setup_host.py. 실제 설치·도구 호출 실증은 미수행.
