## 4. 실측이 드러낸 것

① **테스트가 실 Redmine 에 썼다.** T4 첫 구현의 노트 기본값이 실 Redmine 인데 기존 `test_review_range` 를 대역
없이 돌려 **#879 에 가짜 리뷰 노트 2건**(13:57:30Z, 임시 저장소 해시 · R1)이 샜다. 정정 노트를 남기고, 테스트에
대역을 넣고, **등록된 트윈 루트가 아니면 기본 noter 를 쓰지 않는 가드**(검사 ⑪)를 넣었다. 교훈: 「기본값 = 실
외부 쓰기」인 함수는 기존 테스트가 그 경로를 타는지 먼저 본다.

② **240초는 합친 diff 에 부족했다.** 커밋 리뷰는 24,000자에서 잘려 240초 안에 끝났지만, 상한 없는 범위 diff 는
약 3배다. range 만 480초(유닛 10분 안)로 올렸다. [주의] 같은 밤 **커밋 리뷰 `f72699b` 도 240초 시간 초과**했다 —
agy 응답이 느린 날이었을 수 있다(미조사).

③ **「미러 미도착」 일시적 실패가 몇 초 만에 포기됐다.** 의도는 「색인기 fetch 를 기다린다」였지만 `finish` 가
`pending` 으로 되돌린 항목을 **같은 회차의 `drain` 이 즉시 다시 꺼냈다** — LLM 0 실패라 3회가 수 초에 끝났다.
단위 검사 ⑦ 은 `run_once` 한 번만 봤다. → **#880**(버그 버전, 착수 전). 복구는 재등재로 했다.

④ (관찰) **`issue_finish` 뒤 `update` 가 「ax-projects 가 옛 코드」로 실패했다.** `switch main`·`merge --ff-only`
가 내용이 같은 `mcp_server.py` 의 수정 시각을 새로 써서 검사가 걸린 것으로 본다(내용 비교는 안 했다). 재기동으로
통과. `issue_finish` 마다 반복될 수 있다 — 일감 미등록.

## 11. #883 등록 — 일감 단위 작업 강제

사용자가 #883 을 「리뷰에 심각이 있으면 고지·확인·처리 강제」로 제안한 뒤 규칙 4개로 확정했다:

1. Redmine 번호로 시작하면 완료할 때까지 다른 작업을 할 수 없다 — 끝내거나 명시적으로 **멈추거나 취소**해야 한다
2. 모든 작업이 끝나면 자동으로 작업 내역 리뷰를 인프라 서버에 요청한다
3. 인프라 서버가 리뷰를 끝내면 Redmine 에 상태를 등록한다
4. 높음 지적이 있으면 검사한다 — 오탐·의도는 반려, 버그는 수정해야 일감을 완료할 수 있다

②③은 #879 로 이미 동작한다. 새로 만들 것은 ① 진행 중 일감 잠금·멈춤·취소 입구와 ④ 완료 처리 입구(미판정 높음·미완 범위
리뷰면 거절). [중요] **배치 전제**(사용자): AXCluster 는 작업 PC = 인프라 = `.57`, 언리얼 프로젝트는 작업 PC `.33` → 인프라
`.57`. 그래서 잠금·완료 판정은 인프라가 해야 하고(작업 PC 도구로 우회 불가), `.33` 은 사람의 트리라 시작이 브랜치 전환인지
worktree 인지를 정해야 한다. 기존 `redmine_note` 상태 변경으로 완료를 우회할 수 있다는 점도 열린 결정이다 — 오늘 #879~#881 도
그 도구로 닫았다. 착수 전, 플랜은 사용자와 짠다.
