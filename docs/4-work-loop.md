**[중요] `worker` 라는 단어가 세 군데서 서로 다른 것을 가리킨다.** 이 저장소의 `worker/` 는 BC-250

~~**[주의] 단 AgentTest `worker/` 의 실행 위치가 바뀐다 (2026-08-07).** … **마스터로 이전**한다~~
[중요] **폐기 (2026-08-08). §2.1 정정이 이 서술을 대체한다.**

- **작업장(윈도우)이 오케스트레이터다.** 파일을 소유하고, 적용·빌드·테스트·커밋을 한다.

`client/` 라는 이름은 그대로 둔다. AgentTest 의 `worker/`(윈도우 하네스)에 대응하는 자리이고,
거기서 도는 것은 **작업장 러너 + Claude Code 오케스트레이션**이다.

### 4.2 루프 (2026-08-07 개정)

```
윈도우 작업 PC 〈작업장 · 파일 소유〉
   │  ① 태스크 + 대상 코드 컨텍스트를 텍스트로 요청
   ▼
마스터 〈인프라〉 ── RAG·온톨로지로 컨텍스트 매니페스트 조립, 라우팅 판단
   │  ② stateless 추론 요청 (텍스트 in/out, 파일 접근 없음)
   ▼
BC-250 추론 노드 ── 로컬 LLM 이 코드 생성
   │  ③ 결과 텍스트(구현/diff) 반환
   ▼
마스터 ── ④ 층2 상용 모델 문법·API 검사(agy → Claude) 후 **적합한 코드 뭉치**를 전달
   ▼
윈도우 작업 PC ── ⑤ 파일 적용 · 층1 자기검증 · 층3 UE5 빌드 + RunTests
   │              ⑥ **통과 → 코드 등록(커밋)** / **실패 → ①로 재요청**
   ▼
git `task/<work_id>/<task_id>` 브랜치에 커밋으로 누적 → 다음 라운드가 읽어감
```

- **마스터는 코드 뭉치를 만들어 건네는 데서 끝난다.** 파일 적용·빌드·테스트·등록은 윈도우 몫이고,
  검증 실패 시 **재요청 루프**가 돈다. 마스터에 파일 I/O 가 생기면 §2.1 전제가 깨진다.
- **BC-250 은 파일을 만지지 않는다** — 텍스트만 왕복(§2.2-1).
- **추론 요청은 stateless**(Ollama `context` 필드 미재사용), **피드백 누적은 git**
  (plan v5.0 C.3 git-as-feedback-bus). 두 경로를 분리하는 이유는 토큰 비용 —
  라운드마다 누적 컨텍스트를 프롬프트로 재주입하면 인바운드 토큰이 폭증한다.
- **마스터 브로커 확정**: BC-250 을 호출하는 것은 마스터뿐이다. 노드 라우팅·헬스체크·페일오버가
  전부 마스터에 있고, BC-250 방화벽도 `192.168.0.57` 에서만 11434 를 허용하도록 잠겨 있다(리포트 24 §7).
  **오케스트레이션(무엇을 할지)과 브로커(추론 중계)는 다른 층이다.**
- [주의] **오케스트레이터가 셋이라 큐·git·RAG 에 동시 접근이 발생한다**(2026-08-08 정정).
  윈도우 UE5 PC **2대**가 각각 위 루프의 ①·⑤·⑥ 을 돌리므로, **두 작업장이 같은 `task/<work>/<task>`
  브랜치와 task_queue 를 두고 경쟁**한다. claim/lease/fencing 을 1인이라고 걷어내면
  안 된다(§2.2-5, §5.4.5).
  [완료] **확정 2026-08-08: 두 작업장은 같은 UE5 프로젝트를 본다.** 따라서 경쟁은 **가정이 아니라 실재**다 —
  두 PC 가 같은 저장소·같은 `task/<work>/<task>` 브랜치·같은 task_queue 를 동시에 만진다.
  **claim/lease/fencing 은 이 시스템의 정확성 요건이다**(성능 최적화가 아니다).
  ⬜ 남은 설계: 같은 파일을 두 작업장이 동시에 잡았을 때의 분해 단위(§4.5 클래스 단위 분할이
  충돌 방지 역할을 하는 근거가 여기 있다).
- **능력 기반 라우팅(`requires: ue5`)** — 빌드 게이트를 인프라에 박지 않고 큐 잡으로 돌리는
  CI 러너 패턴(§5.2-C) 때문에 필요했고, **2026-08-08 구현·실측 완료**다. 계약은 §5.2-C.

### 4.3 [중요] 환각 검증은 3층 — **컴파일만으로는 절반밖에 못 잡는다**

리포트 25 의 UE5 태스크 6종 실측에서, 오류 유형에 따라 잡히는 층이 갈렸다:

| 실측 오류 | 컴파일 | 실제로 잡는 층 |
|---|---|---|
| `FLifetimeProperty::AddRepNotifies` (35B, 없는 API) | [실패] 실패 | 층3 |
| `IsPendingKill()` on `TSoftObjectPtr` (14B) | [실패] 실패 | 층3 |
| `Cast<IInteractable>` 직접 호출 (**양쪽 모델**) | [완료] **통과** | 층2 또는 테스트 |
| `IsValid()` false → nullptr 로직 오류 (**양쪽 모델**) | [완료] **통과** | 테스트 |
| `FText::FromString` 지역화 우회 (35B) | [완료] **통과** | 층2 |

**절반이 컴파일을 통과한다.** `interface`·`softptr` 은 두 모델 모두 틀렸고 둘 다 "빌드는 되는데
런타임에 잘못 동작"하는 유형이다. 따라서:

```
층1  워커 자기검증 (무료·즉시·결정론적)
     동결 인터페이스 위반 · 펜스/[PSEUDO] 잔재
     기존 구현: AgentTest `worker/validator._frozen_interface_violation`

층2  상용 모델 문법·API 검사 (저비용)
     환각 API 를 컴파일 전에 선제 차단 → 층3 호출 횟수 절감
     기존 구현: plan v5.0 `worker/claude_spawn.syntax_check` (agy 우선, Claude 폴백)

층3  실제 UE5 빌드 + RunTests (고비용·최종 권위)
     기존 구현: Phase ζ.3c `FAutomationTest`
```

층2가 필요한 이유는 비용이다 — UE5 빌드는 분 단위라 모든 시도를 컴파일할 수 없다.
환각 API 는 상용 모델이 읽으면 대체로 잡히므로(“`DOREPLIFETIME` 이 맞다”) 층2에서 걸러낸다.

**모토 정합**: 층1 무료, 층2는 검증(고레버리지)에만 상용 토큰, 층3은 결정론적. 작성은 여전히 무료 로컬.

### 4.4 모델 배정 (리포트 25 결론)

| 역할 | 모델 | 근거 |
|---|---|---|
| **UE5 C++ 코드 생성** | `qwen2.5-coder:14b` (Q4_K_M, 8.9GB) | 도메인 관용구 정확, 환각 없음. 유일 결함(마크다운 펜스)은 파이프라인이 제거 |
| **컨텍스트 쿠킹**(요약·청크분류) | `35B-A3B IQ2_M` (13GB) | prefill 6.5× · 생성 3~4× 우위. 단 코드 생성에선 API 환각으로 부적합 |

- 두 모델 **동시 상주 불가**(8.9+13GB > 15.6GB, `MAX_LOADED_MODELS=1`). 전환 비용은 2026-08-08
  재측정 결과 **35B 66.9s / 14b 37.5s, 왕복 ≈100초**다(상주 시 각 2.7s/1.4s). 기존의 "36초"는 14b 방향만 본 값.
  → 보드 2대가 되면 **모델을 보드별로 고정 배정**: `#1 = 14B(생성)`, `#2 = 35B(쿠킹)`.
- 35B 호출 시 API 에 **`"think": false` 필수** — 없으면 사고 과정을 출력해 토큰을 낭비한다.
- **[주의] 코드 기본값이 아직 Gemma다 — 이식 시 반드시 교체할 것.** AgentTest 의 로컬 LLM 기본 모델이
  `gemma4:e4b` 로 하드코딩된 지점이 여럿이다: `watcher/config_init.py:65`(`"local_llm_model": "gemma4:e4b"`),
  `watcher/common.py:92`(`_local_llm_model` 초기값), `watcher/watch.py:141`(`config.get` 폴백).
  **지금 상태로 배선하면 위에서 확정한 코더 모델이 아니라 Gemma 가 호출된다.**
  다행히 `local_llm_model` 설정 키로 교체 가능하게 설계돼 있어 **코드 수정 없이 config 값만 바꾸면 된다**
  (다만 코드상 *기본값*은 여전히 Gemma 이므로, config 를 안 넣으면 조용히 Gemma 로 폴백한다).
  참고로 Gemma 가 나쁜 선택이었던 건 아니다 — 실측 57 t/s 로 14B 의 2배지만, 코딩 특화가 아니라
  UE5 도메인 정확도(=반려율)에서 밀린다(리포트 25).
- **로컬 LLM 공통 취약 영역**: `BlueprintNativeEvent` 의 `Execute_` 규약, `TSoftObjectPtr` 로드 패턴을
  두 모델 모두 틀렸다. 골조/매니페스트에 해당 패턴을 명시하거나, 이 유형은 상용 모델로 라우팅한다
  (κ.3 의 (b) regime).

### 4.5 대규모 모듈 작업 — 클래스 단위 분할 · 병렬 추론 · 순차 적용 (2026-08-07)

```
작업자(윈도우) ─ 거대한 모듈 작업 요청
   │
   ▼
마스터 ─ 골조 생성(인터페이스 동결) + 클래스 단위로 분할 + 각 조각에 컨텍스트 매니페스트 부착
   │        │            │            │
   ▼        ▼            ▼            ▼          ← 추론 노드 수만큼 **병렬**
 노드#1   노드#1(2번째)  노드#2       …            [주의] **현재 보드 1대 = 사실상 직렬**
                                              (#2 는 #1 완성 후 구성 — §3)
   │        │            │            │
   └────────┴─── 클래스 단위 텍스트 응답 ─┴──────┐
                                              ▼
작업자(윈도우) ─ **적용 풀(pool)에 쌓고 순차 적용** ─ 전부 적용 완료 후 ─▶ 검증 시작(층3)
```

**핵심**: 분할 단위가 **클래스**라서 응답끼리 파일이 겹치지 않는다. 생성은 병렬, **적용은 순차**다.

#### 이 가정이 성립하려면 — 인터페이스 동결이 선행돼야 한다

**클래스 단위 분할은 *파일* 충돌만 막는다. *인터페이스* 충돌은 못 막는다.**
A 를 만든 모델과 B 를 만든 모델이 서로의 시그니처를 다르게 가정하면 **컴파일에서야 드러난다.**

→ 그래서 **골조(skeleton)를 먼저 만들어 선언을 동결하고, 본문만 병렬로 채운다.**
리포트 02 의 품질 벤치가 쓴 방식이 정확히 이것이다 —
*"동결된 선언(시그니처·UE 매크로)은 그대로 두고 `[PSEUDO]` 본문만 채우기"*.
AgentTest 에 이미 구현돼 있다: `master_orchestrator` 의 골조 생성 +
`worker/validator._frozen_interface_violation`(제출 전 자기검증 = 층1).

**즉 순서는 골조 → 동결 → 병렬 본문 생성 → 순차 적용 → 검증이다.**

#### 검증은 일괄이되 층을 나눈다

**전부 적용한 뒤 빌드 한 번**은 비용상 맞지만, 실패 시 **어느 클래스가 원인인지 모른다.**
그래서 3층 게이트(§4.3)를 이렇게 배치한다:

| 시점 | 게이트 | 비용 |
|---|---|---|
| **조각마다(병렬)** | 층1 자기검증(동결 위반·펜스 잔재) + 층2 상용 모델 문법·API 검사 | 무료 / 저비용 |
| **전부 적용 후 1회** | 층3 UE5 빌드 + `RunTests` | 분 단위 — 그래서 일괄 |

**층1·층2 를 조각 단위로 먼저 돌리는 이유가 이것이다** — 환각 API 를 층3 전에 걸러
비싼 일괄 빌드의 실패율을 낮춘다(§4.3).

#### [중요] 분산의 값은 **처리량이 아니라 증분**이다 (사용자 재정의 2026-08-11)

> 사용자: *"분산 작업의 장점은 비용이나 시간이라고 생각했는데, 어찌보면 증분이 아닐까해"* /
> *"물론 클로드를 통한 검증은 필수겠지만 말이야"*

**실측이 처리량 쪽을 부정한다:**

    워커 2대 병렬     12% 빠르고 **90% 비쌌다**     캐시 생성이 워커별 고정비
    4파일 묶음        파일당 **3.2배 쌌다**         ← 묶음의 이득이지 병렬의 이득이 아니다
    층3               어차피 `.2` 한 대            검증은 원래 직렬이다

즉 **병렬로 얻은 것은 거의 없다.** 그런데 이 절이 요구하는 장치들은 전부 다른 것을 위한 것이다:

| 장치 | 실제로 무엇을 위한 것인가 |
|---|---|
| 인터페이스 **동결** | 조각들이 서로를 안 깨뜨린다 = **증분이 성립하는 조건** |
| 골조 **빌드 게이트** | base 가 서 있어야 그 위에 쌓인다 |
| **의존 순서** | 증분이 쌓이는 순서 |
| 통합자가 **통과분만 커밋** (§8.4) | [중요] durable 이 **항상 컴파일되는 상태**로 누적된다 |

[중요] **그래서 검증이 선택이 아니라 전제다.** 검증 없이 쌓으면 그건 증분이 아니라 부채다.
무료 로컬로 대량 생산하는 것이 성립하는 이유는 *"싸서"* 가 아니라 **"틀린 것이 안 쌓여서"** 다.
원전이 *"reject 는 폐기·재구현이 아니라 전진·수정"* 으로 뒤집은 것(2026-06-21)도 같은 이야기다
— 맞게 짠 코드를 버리면 증분이 아니게 된다.

[주의] **경계는 유지된다**: 실측상 골조를 로컬로 만들면 계약이 헐거워지지만(동결 30 vs 6, 리포트
12 §7) 그건 **골조=계약**이라 값을 쓸 자리라는 뜻이지 본문까지 상용으로 하라는 뜻이 아니다.

#### 미결 — [완료] **닫혔다** (중 1.2, 2026-08-11)

- ~~**적용 순서**~~ → [중요] **의존이 먼저**. `#include` 그래프 위상 정렬(`work/decompose.py`).
  *"동결돼 있으면 순서 무관"* 이라 적어 뒀던 예상은 채택하지 않았다 — 선언이 없으면 컴파일이
  깨지므로 순서는 실재한다. [주의] 순환은 **보고만 하고 막지 않는다**(역추적이 basename 근사라
  가짜 순환을 만들 수 있다).
- ~~**분할 입도**~~ → **파일 불가분 단위**(`batching.units`, 모듈+경로+stem). 원전의 *"8~20개
  파일"* 은 쓰지 않는다 — 개수가 아니라 **충돌 방지**가 기준이다. 묶음 크기 기본 4는 실측값.
- ~~**파일 하나가 너무 클 때**~~ → `[PSEUDO:N]` 뎁스로 **파일 *내* 순차 분할**. 뎁스는
  `depends_on` 으로 줄을 서므로 파일 불가분과 충돌하지 않는다.
- ⬜ **부분 실패 처리** — 조각 단위 재시도(소 1.3.3). [중요] 원전의 정정을 따른다: **전진·수정**.
- ⬜ **적용 풀의 위치** — [중요] **통합자 `.2`**(§8.4, 2026-08-11 토폴로지). 요청자도 마스터도 아니다.

#### ④ 매니페스트를 git 에 싣지 않는다 — 원본과 다른 점

원본은 서버가 골조를 push 하면서 `.claude/tasks/<id>/context.md` 를 함께 실었다.
**우리 마스터는 소스 저장소에 push 하지 못한다**(pushurl 비활성, §8). 그래서 매니페스트를
**디지털 트윈의 파생물**(`<Project>/manifests/<task_id>.md`)로 두고 마스터가 건넨다.

**잃는 것은 없다.** git-carried 였던 이유는 서버가 어차피 push 하고 있었기 때문이지 git 자체가
필요해서가 아니다. **"1회 수집 → 다회 소비"** 라는 성질은 그대로다 —
로컬 LLM 이 검색 없이 grounding 을 받는다는 목적도 그대로다.

[중요] **그래서 골조도 매니페스트로 간다** (2026-08-08 실측으로 확정). `task_data` 에 실어 보내려
했으나 **큐가 그것을 태스크 마크다운 본문으로만 저장하고 JSON API 로 노출하지 않는다**
(`task_queue/logic.py:202`) — 감사 기록이지 전송 수단이 아니다. 매니페스트가 마스터→작업장
텍스트 채널이므로 골조·계약·RAG 히트가 **한 문서에 모인다**. 작업장은 한 번 받아 읽으면 된다.

[주의] **한글 제목이 전부 같은 slug 가 되던 잠복 버그를 여기서 발견했다** (2026-08-08).
`_slugify` 가 비-ASCII 를 버려 `'워크플로우 복구'` · `'골조 전달'` 이 모두 `'work'` 가 됐고,
slug 가 **중복 검출 키**라 **두 번째 한글 일감이 항상 거부**됐다. 팀이 영문 제목을 쓰던
환경에서는 드러나지 않았던 것이다. 버려진 내용이 있으면 정규화 원문의 해시를 붙이도록 고쳤다 —
같은 제목은 여전히 충돌하고(중복 검출 유지), 순수 ASCII 제목은 그대로다(기존 work id 호환).

[주의] **지금 매니페스트는 RAG 채널뿐이다.** 원본은 `attach_norms=True` 로 온톨로지 도메인 규범을
함께 번들했다. 그것이 **마일스톤 2 의 소 2.3.1 — 목표 ②의 종점**이다. 매니페스트가
**"규범 미구현" 을 본문에 명시**한다 — 빈 섹션을 감추면 다음 세션이 버그로 오해한다.
