# 49 — 라운드 조각 브랜치가 영원히 안 지워진다 (정리가 이름을 못 찾는다)

**2026-09-05 17:53 실측** · NS 실증 3라운드 완주 후 마감에서 발견 · work `…2f005681` · 이슈 `#361`

---

## 1. 무슨 일이 있었나

마감(`finalize_work`)이 `main` 머지까지 정상으로 끝났는데 **조각 브랜치 7개가 그대로 남았다.**
레드마인 마감 노트가 스스로 그것을 말한다:

    - 통합: 작업 브랜치 `task/<work>/base` + 소스를 든 durable **7건** (no-ff)
    - 브랜치 정리: 삭제 **1건**

**같은 함수 안에서 머지는 7건을 찾고 정리는 1건만 찾았다.** 지워진 1건은 작업 브랜치(`base`)이고,
`r1/`·`r2/`·`r3/` 조각 7개는 **삭제 목록에도 보존 목록에도 안 올라갔다** — 아예 안 보였다.

## 2. 원인 — 라운드가 이름에 들어갔는데 정리만 안 따라갔다

`durable_branch(work_id, task_id, round)` 는 라운드를 받으면 `task/<work>/r<N>/<task>` 를 만들고,
안 받으면 옛 이름 `task/<work>/<task>` 를 만든다(스탬프 없는 것을 조용히 다른 데로 보내지 않으려는
설계였다). 그런데 **호출부 둘이 어긋나 있다**:

    review.py:185  머지   durable_branch(work_id, tid, int(t.get("round") or 0))   ← 라운드 넘긴다
    review.py:325  정리   durable_branch(work_id, tid)                             ← 안 넘긴다

실측(2026-09-05 17:5x, 같은 저장소):

    git ls-remote --heads origin "task/<work>/378da319"      → 0건   ← 정리가 찾는 이름
    git ls-remote --heads origin "task/<work>/r3/378da319"   → 1건   ← 실물

`ls-remote` 가 0건이면 그 브랜치는 `refs` 리스트에 **들어오지도 않는다.** 그래서
「도달 가능 → 삭제」도, 「미병합 → 보존」도 아닌 **제3의 상태(존재를 모름)** 가 됐고,
마감 노트는 아무 경고 없이 *"삭제 1건"* 만 적었다. **조용한 실패다.**

[주의] 폴백 경로(`work_id` 가 빈 경우)의 `refs/heads/task/*/{tid}` 도 같은 결함이다 —
`*` 하나는 라운드 계층을 못 넘는다.

**언제 들어왔나**: 어제(2026-09-04) `1da12bb` 「work 은 라운드를 여러 번 돈다 — 브랜치 이름의
라운드 번호」에서 이름에 `r<N>` 이 들어갔다. 머지 쪽은 같은 커밋에서 라운드를 넘기도록 고쳐졌고
정리 쪽은 안 고쳐졌다. **어제는 마감을 라이브로 안 돌려서 안 드러났다** — 오늘 처음 돌렸다.

## 3. 영향 — 「어느 브랜치를 써야 하나」를 찾는 데 시간이 든다

브랜치는 디스크로는 거의 공짜다(객체 공유 · ref 하나 수백 바이트). 비용은 **사람과 판정** 쪽이다:

    ① 목록이 죽은 것으로 덮인다   오늘 하루 한 work 에 7개. 실증 한 번에 라운드 2~3회면
                                 work 하나당 5~10개가 영구히 쌓인다. ⑺ 에서 「이번 라운드 것」을
                                 고르거나 디버깅으로 브랜치를 찾을 때, 목록의 대부분이 이미
                                 끝난 것이다 — 사람이 매번 걸러야 한다
    ② 🔴 증거가 묻힌다            이 저장소의 규칙은 *"미병합 브랜치는 증거다 — 사람이 본다"* 인데,
                                 **이미 머지된 잔재**가 그 목록을 덮는다. 실패해서 남은 진짜 증거
                                 하나가 죽은 브랜치 수십 개 사이에 숨으면 그 규칙은 무력해진다
    ③ 「깨끗한 상태」를 눈으로 못 판정  실증은 깨끗한 상태에서만 시작한다는 규약이 있는데,
                                 잔재가 쌓이면 전수 출력으로도 무엇이 살아 있는 것인지 안 갈린다
    ④ fetch 비용                 워커는 조각마다 fetch 하고 fetch 는 ref 전체를 나열한다.
                                 한 달 누적이면 수백 개 — 지금은 안 아프지만 단조 증가다

## 4. 지금 상태 (안전함)

남은 7개는 **전부 `origin/main` 에서 도달 가능**하다(대조 완료). 즉 데이터 손실 위험이 아니라
**청소 누락**이다. 지우려면 도달 가능 판정이 이미 참이므로 규칙 위반 없이 지울 수 있다.

    origin/task/<work>/r1/3a97940b · r1/d2f6ed39
    origin/task/<work>/r2/0c7e68b3 · r2/5140ba06 · r2/e8eea54f
    origin/task/<work>/r3/26f3974e · r3/378da319
