## 바뀐 것

| 자리 | 내용 |
|---|---|
| `master/issue_infra.py` `verify_span` | ① `end`·`base` 가 실제 커밋 ② `base` 가 `end` 의 조상 ③ `end` 가 `track.branch` 에서 도달 가능 ④ `base..end` 해시·제목을 git 에서 구한다. 보고된 `hashes` 는 대조만 한다 |
| `master/issue_infra.py` `infra_finish` | `end` 만 필수. `base` 생략 = 잠금의 시작 리비전, `hashes` 생략 = git 에서 구한 값. 검증 실패는 `step: verify`(`mismatch`/`lookup`)로 등록 전에 거절. `check_only` 는 쓰기 없이 도출 결과만 |
| `master/task_queue/server.py` | `IssueFinishReq` — `base`·`hashes` 선택, `check_only` 추가. 옛 클라이언트(전부 싣는 호출)도 그대로 받고 검증한다 |
| `client/runtime/client_mcp.py` | `issue_branch_end` 가 체크아웃 git 의 `issue/<N>` 끝을 읽는다. `issue_finish` 는 번호만 받고, 인자 `end` 가 git 과 다르면 서버로 보내기 전에 거절한다 |
| `master/client/skills/ax-issue/SKILL.md` | 마감 절차를 「번호만 넘긴다」로. 거절 응답(`verify`·`[git]`) 처리, 해시를 인자로 옮겨 적지 않는다는 규칙 |
| 모듈 머리말·주석 | 「git 을 보지 않는다」 계약을 「마감 범위만 Gitea 에서 읽어 검증한다」로 |

`base` 를 서버 잠금에서 가져오는 이유: 요청자 스킬은 push **뒤에** 마감을 부르는데, push 뒤에는
`merge-base origin/main issue/<N>` 이 끝 커밋 자체가 되어 범위를 다시 구할 수 없다. 시작 리비전은 서버가
시작 때 받아 잠금에 갖고 있다.

마스터 로컬 흐름(`issue_flow.finish`)은 원래 해시를 git 에서 구하므로 바꾸지 않았다.

## 남은 것 · 한계

- **게임 요청자 세션에서의 실제 마감 1회는 확인하지 못했다.** `.33` 이 꺼져 있었다. 도구의 git 읽기는 리눅스
  임시 저장소로만 돌렸다 — Windows 요청자 체크아웃에서의 첫 마감 때 `[git]` 오류 여부를 본다.
- **머지로 시작점이 달라진 경우**: 요청자가 `main` 을 `issue/<N>` 에 머지했으면 잠금의 시작 리비전부터의
  범위에 남의 커밋이 섞인다(rebase 는 조상 판정으로 거절된다). 스킬은 응답의 `commits` 를 승인받은 목록과
  대조하라고 적었지만 코드가 막지는 않는다.
- `base` 를 인자로 실을 때 그 값은 여전히 세션이 적는다. 없는 커밋·조상이 아닌 커밋은 거절되지만, 실재하는
  엉뚱한 조상은 범위가 넓어질 뿐 거절되지 않는다.
- 시작(`start_rev`)·보류(`end`)·취소(`commits`)의 해시 인자는 그대로다(사용자 결정으로 범위 밖).
- `#931`(AXCluster 의 `ax-client` 시작·마감 거절)·`#932`(등록 뒤 영영 없는 해시 감지)는 별도 일감이다.
