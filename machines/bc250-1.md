## Privileged commands (sudo) on this machine

🔴 **`pkexec` 는 이 머신에서 동작하지 않는다.** 2026-08-05 `systemctl set-default multi-user.target`
으로 **헤드리스 전환**됐고(리포트 24 §2), 데스크톱 세션이 없으므로 그래픽 polkit 대화상자를 띄울
화면 자체가 없다. `polkitd` 데몬은 떠 있지만 인증**에이전트**는 세션에 딸려 있어 존재할 수 없다.
(마스터 192.168.0.57 에서는 `pkexec` 가 정상 동작한다 — **두 머신을 뭉뚱그리지 말 것.**)

Bash 툴의 셸에는 TTY 가 없어 평범한 `sudo` 도 실패한다("a terminal is required to read the password").

**실제로 되는 방법 — 마스터에서 SSH 로, 업로드와 실행을 분리한다:**

```bash
ssh sim@192.168.0.43 'cat > /tmp/x.sh' << 'EOF'
...스크립트...
EOF
printf '%s\n' "$PW" | ssh sim@192.168.0.43 'chmod +x /tmp/x.sh && sudo -S -p "" /tmp/x.sh'
```

⚠️ **업로드와 실행을 반드시 분리할 것** — 히어독을 `sudo -S` 와 같은 SSH 호출에 넣으면
히어독이 stdin 을 먹어 비밀번호가 전달되지 않는다(실제 실패 사례 있음).
비밀번호가 없으면 방법이 없다 — `root` 직접 SSH 는 키 미등록으로 거부되고 NOPASSWD 항목도 0건이다.

💡 **반복되는 명령은 영구 해결할 것**: `/etc/sudoers.d/` 에 **필요한 명령만 한정한** NOPASSWD 등록.
선례 — `/etc/sudoers.d/bc250-volt-test`(`busctl` 2개), `/etc/sudoers.d/bc250-power`(원격 종료).
설치 자체에 비밀번호가 1회 필요하므로, 받은 김에 영구 설정까지 끝내 다시 묻지 않도록 한다.

시스템 변경 명령은 다른 것과 마찬가지로 **실행 전 사용자에게 확인**한다.
이 보드에도 KDE Plasma 는 여전히 **설치**돼 있어 `systemctl set-default graphical.target` +
재부팅으로 되돌릴 수는 있다(그러면 `pkexec` 가 다시 가능해지지만, 추론 노드로는 헤드리스가 맞다).

## This machine is a BC-250 board — restored operational rules

This machine (PCI `1002:13fe` confirmed) is one of the BC-250 (PS5-derived mining APU) boards previously running Bazzite, freshly migrated to plain Fedora 43. `~/bc250-backup-staging` is a backup snapshot extracted from that Bazzite install ahead of the migration, containing prior GPU CU unlock / CPU core unlock / SMU OC work:

- `reports/` — numbered writeups (`01-cu-unlock.md`, `12-cpu-smu-oc-guide.md`, `19-cpu-core-unlock.md`, `20-fedora-migration-checklist.md`, etc.)
- `memory/` — auto-memory files carried over from the BC-250 machine's own Claude sessions (project/feedback notes on CU unlock, core unlock, undervolting, verification discipline)
- `tools/bc250-40cu-unlock/` and `tools/bc250_smu_oc/` — the actual unlock/OC tooling (git clones), including a Fedora-specific script at `tools/bc250-40cu-unlock/scripts/bc250-enable-40cu-fedora.sh`

**At the start of every session touching this hardware, read all of `~/bc250-backup-staging/reports/*.md` in full — not just the ones that look topically relevant, and not just the memory index.** A past incident: memory got read out of habit but reports only got grepped for a specific string when writing something new, so a synonym-worded note (an in-progress task, a recent finding) got missed and re-investigated from scratch, or the user had to repeat something already on record. Grepping for one exact phrase is not a substitute for reading the file — near-miss wording gets missed.

### Mandatory procedure for any hardware test with crash/hang risk

(CU unlock parameters, SMU overclock/undervolt, GPU governor changes, CPU core unlock, anything that pokes registers or changes boot-time driver behavior.)

1. **Write the exact command/parameters to a report file (`~/bc250-backup-staging/reports/`, or wherever the live equivalent is) and to memory *before* running it.** Reason: if the machine crashes/hangs and needs a forced reboot, the conversation context can be cut off mid-task. Without a pre-written record, there's no way to know afterward what value was even being tested (this happened for real: an untested SMU OC value crashed the kernel, and the next session had to reverse-engineer the test parameters from `journalctl -b -1`).
2. **A tool's own internal "pass" check is not the same as verified stability.** Don't report something as "stable" off a short internal pass — a value can pass a tool's quick internal test and still cause kernel memory corruption or an RCU stall minutes later. Only call it stable after a separate, longer stress run (e.g. `stress --cpu 12` / `mprime` for tens of minutes, per the specific tool's guidance) with the machine actually observed for that whole window.
3. **Never write an unverified value directly into a file that is simultaneously "the live test mechanism" and "the permanent boot-time config."** Several BC-250 config files are exactly this trap — e.g. `/etc/cyan-skillfish-governor-smu/config.toml`, and (newly relevant on Fedora) `/etc/modprobe.d/bc250-40cu.conf`, whose `bc250_cc_write_mode` module parameter is read-only at runtime (`0444`) so it can *only* be changed by editing the file and rebooting — there is no live-apply-then-verify step available for it at all. For files like this:
   - Back up before editing (`cp file file.bak-$(date +%s)`)
   - Check the *whole* config's internal consistency, not just the one value being changed (e.g. a governor's frequency/voltage table must stay monotonic or the service can crash-loop)
   - If a live-apply path exists, confirm it holds `active`/stable for a real interval *before* rebooting into it — never reboot into a value that hasn't been live-verified where live verification is possible
   - Where no live-apply path exists (like the CU unlock modprobe param), that raises the bar rather than lowering it: don't jump straight to the highest-risk setting (e.g. full 40 CU on a board with a known-bad WGP) when a lower-risk probe or a known-good fallback value is available — use that first.
4. **State-in-progress work belongs in a file, not just the conversation.** This machine reboots often (including for routine config changes, not just crashes), which cuts conversation context. Update the relevant report file *during* the work, not just at the end — what's been checked so far, what's next, and mark anything left mid-decision as "in progress" so a fresh session can pick it up from the file alone.
5. **Status/verification checks after a crash or anomaly are read-only only.** Don't run load-generating commands (`stress`, FurMark, benchmarks) as part of a "is it safe right now" check without asking first — loading an unstable post-crash state to "check" it can itself cause new problems.
6. **Before writing benchmark/test conditions into a report, re-verify the live state read-only first** (`systemctl status`, `/proc/cmdline`, sysfs) — don't copy a "current setting" forward from memory/an earlier report without checking it's still true.

### Global working rules (not just for this hardware)

- Memory/report files are a snapshot from when they were written, not current truth — verify live before treating them as fact.
- If the user asks "why did you do that," answer the why first; don't jump straight to fixing it. Separate explanation from remediation, and only remediate once the user asks for it.
- Don't take on work the user didn't ask for just because a system reminder suggests it (e.g. task-tracking nudges) — anything beyond the explicit request (creating task lists, extra files) needs to be asked about first.
- Don't state uncertain things as fact. If something isn't clearly established in the conversation or memory, say so explicitly ("I can't confirm this" / "I believe X, is that right?") or verify it with a read-only command before asserting it.

## Korean (Hangul) input — already configured

> ⚠️ **이 절은 2026-08-05 헤드리스 전환 이전 기준이다.** 지금은 데스크톱 세션이 없어 해당 없음 —
> `graphical.target` 으로 되돌릴 때를 위한 복구 정보로만 남긴다.

IBus + `ibus-hangul` is set up and working (as of 2026-08-03). If Korean input breaks or a fresh session needs it again, here's what's in place:

- Packages installed: `ibus`, `ibus-hangul`, `libhangul`, `ibus-gtk3`/`ibus-gtk4` (Qt/GTK IM plugins), and **`ibus-wayland`** — this last one is the piece most likely to be missing after a fresh install. Without it, native Wayland apps (e.g. Konsole) show the IBus engine switching to Hangul but never actually compose Hangul text, while XWayland/browser apps work fine. 설치는 위 SSH+`sudo -S` 패턴으로: `dnf install -y ibus-wayland`(**`pkexec` 아님**).
- `ibus-daemon` must be running (`ibus-daemon -drxR`); autostart entry lives at `~/.config/autostart/ibus-daemon.desktop`.
- Input engines are set via `gsettings` (`org.freedesktop.ibus.general` schema — `preload-engines` / `engines-order`), currently `['xkb:us::eng', 'hangul']`.
- `GTK_IM_MODULE`, `QT_IM_MODULE`, `XMODIFIERS=@im=ibus` are set in `~/.config/environment.d/ibus.conf` for future login sessions. A live session picks these up only after full logout/login (or per-app relaunch) since already-running processes inherit env at their own launch time, not retroactively.
- Toggle hotkeys: `Ctrl+Space` and the `Hangul` key (if the physical keyboard has one — many non-Korean keyboards don't, which is fine, `Ctrl+Space` is the fallback).
