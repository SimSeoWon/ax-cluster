# ax-advance — 라운드를 끝내고 작업 브랜치를 전진시킨다 (요청자 측 · 정본 ⑺)

> 마스터가 생성해 배달한다. **손으로 고치지 말 것** — 다음 배달에 덮인다.

## 0. [중요] 먼저 — 이 스킬인지 `ax-review` 인지 가른다

**오늘(2026-09-04) 내가 그 둘을 섞어 오지시를 냈다.** 라운드가 끝났는데 공지가
*"`main` 에 올린다"* 를 권했고, 사용자가 *"리뷰 요청은 왜한건데? 전혀 다른 스킬을 요청한거
같은데"* 로 잡았다. 목적이 다르다:

| 발화 | 뜻 | 갈 곳 |
|---|---|---|
| `라운드 종결` · `전진시켜` · `서브 브랜치 머지해서 세워봐` | **작업 브랜치를 한 칸 전진** | [중요] **이 스킬** |
| `#N 리뷰` · `머지 검토` · `검수 요청 받았어` | 전진한 것을 **`main` 에 반영**할지 | `ax-review` |
| `이 파일 봐 줘` · `이 변경 검토해 줘` | 국소 코드 품질 | 일반 코드 리뷰 |

[중요] **`main` 은 이 스킬이 만지지 않는다.** 여기서 움직이는 것은 `task/<work_id>/base`
하나뿐이다.

## 1. 이 자리가 무엇인가 — 루프의 한 칸

사용자 확정 2026-09-04:

    라운드 N    base(N) ─┬─ 서브 브랜치들 → 워커가 각자 커밋
                          └─ **⑺ 여기**: 전부 base 에 머지 → 통합 빌드
                             → 「버그냐 구조 수정이냐」 사람에게 묻고
                             → 승인되면 base 에 커밋·push  =  base(N+1)

    라운드 N+1  base(N+1) 의 `.h`/`.cpp` 에 **개선·수정 내용을 주석으로** 남긴다
                → 분산 작업 재등재 (`target_branch` 에 **그 전진 브랜치**를 실어 재사용)
                → 서브태스크 브랜치가 **전진한 tip 에서** 또 갈라진다

사용자 서술: *"분산 작업 브랜치를 전진시킨게 재사용하기 위함이고. 전진한 메인 작업 브랜치를
기준으로 서브 작업이 있다면 해당 기점을 기준으로 서브 태스크용 브랜치를 추가할 생각이었어."*

[중요] **원전에 이 단계는 없다** (확인 2026-09-04, 원전 스킬 13종 전수). 원전은
「조각 검증 → 서버가 feature 에 머지 → 리더가 feature→main」로 **한 번** 끝난다. 이 루프는
사용자 설계이고, 그래서 **원전을 근거로 반박할 수 없다.**

## 2. 준비 — 이 PC 에 UE5 가 있으니 빌드는 여기서 돈다

    py -c "import sys; sys.path.insert(0,'.ax/lib'); from axmaster.work import review, build_local"

[중요] **`python` 이 아니라 `py` 다** — 이 PC 의 `python` 은 스토어 스텁이라 버전도 안 찍는다.

work·tasks 는 큐에서 읽어 넘긴다(이 모듈은 HTTP 를 모른다 — 그래야 테스트가 큐를 안 띄운다):

    from axmaster.clientside.client_mcp import queue_api
    api = queue_api()
    # list_works / get_work MCP 도구로 work_id 와 tasks 를 집는다

## 3. 세워 본다 — [중요] 사람의 트리를 건드리지 않는다

    res = review.advance_work(repo, work_id=..., work=..., tasks=...,
                              build_fn=bfn, api=api)   # confirm 생략 = False

하는 일: `<체크아웃 옆>/ax-advance-<work_id>` worktree 를 **`origin/<작업 브랜치>`** 에 세우고
(여기가 `ax-review` 와 다르다 — 그쪽은 `origin/main` 이다), 서브 브랜치를 **전부** 머지한 뒤
빌드한다. **`confirm` 없이는 어디에도 push 하지 않는다.**

[주의] **충돌하면 통째 중단**한다. 부분 머지를 남기지 않는다 — 그 상태로 빌드하면 무엇이
문제인지 알 수 없다.

빌드 함수는 이 PC 의 실측 엔진 경로에서 만든다. **경로를 손으로 적지 않는다** — 마스터가
프로브해 `config.json` 에 넣은 값이다:

    cfg = json.load(open(".ax/config.json", encoding="utf-8"))
    bfn = build_local.local_build_fn(project=cfg["project"],
                                     ue5_cmd=cfg["backends"]["ue5_cmd"])

[중요] **통합 빌드는 한 번이다.** 조각별로 나눠 세우지 않는다 — 교차 파일 정합성은 전부
모아 놓고 세워야 드러난다(사용자 지적: *"베리파이는 각자 미시적인 한 부분들인데 그거 검증해서
얼마나 잘나오겠냐"*).

## 4. [중요] 사람에게 묻는다 — 정본이 요구하는 그 물음

`res.question` 이 그 문장을 준다. 그대로 사람에게 낸다:

    빌드 통과   "코드에 버그가 없는가, 구조를 고쳐야 하지 않는가?"
    빌드 실패   "버그인가, 구조를 고쳐야 하는가?"
    빌드 미측정  "재지 못했다 — **확인 못 한 것은 통과가 아니다**"

세 갈래로 갈린다:

    이상 없음    → §5 승인 → 전진
    버그         → 그 트리에서 고쳐 커밋하거나, `.h`/`.cpp` 에 지시 주석을 남기고 다음 라운드
    구조 수정     → **전진을 보류**하고 주석을 남겨 다음 라운드를 등재한다

[중요] **묻지 않고 전진하지 않는다.** 잘못 전진하면 다음 라운드 조각이 그 위에서 갈라지고,
되돌리려면 사람이 브랜치를 되감아야 한다.

## 5. 전진 — 사용자의 승인 발화가 있고 나서

    review.advance_work(..., confirm=True, api=api,        # §2 의 queue_api()
                        decision_note="<사람이 방금 답한 것을 그대로>")

🔴 [중요] **`api=queue_api()` 를 반드시 넘긴다** (실측 2026-09-05: 안 넘겨서 전진은 됐는데
레드마인 기재가 조용히 실패했다). 이 기계에는 큐 토큰이 없어 기본 경로가 없다 — 자격은
MCP 모듈이 들고 있다. 없으면 `advance_work` 는 전진을 끝내고 *"[주의] 레드마인 기재 실패"*
를 로그로만 남긴다(전진을 되돌리지는 않는다).

`confirm=True` 여야 `HEAD:refs/heads/<작업 브랜치>` 로 push 한다. **빌드가 통과하지 않았으면
`confirm` 이 있어도 거절한다** — 미측정도 거절이다(fail-closed).

🔴 [중요] **`decision_note` 에 사람의 답을 그대로 싣는다.** 전진 직후 그것이 **레드마인 이슈에
노트로** 붙는다(이슈는 **등재 때** 이미 만들어져 있다 — 라운드마다 새로 만들지 않는다):

    라운드 2 전진 — `task/…/base` 35e72eb → 7991b38
    - 머지한 서브 브랜치: 2건 (…/r2/ab12, …/r2/cd34)
    - 통합 빌드: BUILD OK (4.02초)
    ## 이 자리에서 사람이 정한 것
    버그 아님 · 구조 유지 · 추가 개선: 입력 검증 보강 → 다음 라운드

[주의] **추측해서 채우지 않는다.** 비워 두면 노트에 *"사람의 판단이 기록되지 않았다"* 가
그대로 적힌다 — 그것이 빈 값보다 낫다. 사용자의 답을 못 받았으면 전진 자체를 하지 않는다.
[중요] **마감이면 여기가 아니다** — §7 의 `finalize_work` 가 `main` 머지 뒤 이슈를
**「완료」로 닫는다.**

[주의] push 가 거부되면 **force 하지 않는다.** 커밋은 트리에 남아 있고(잃지 않았다) 사람이
판단한다. push 한 뒤에는 트리를 지운다; 안 했으면 **남긴다** — 그 안에서 보고 고쳐야 하니까.

## 6. 다음 라운드 — 주석을 남기고 재등재

전진했고 더 할 일이 있으면, **그 시점 파일의 `.h`/`.cpp` 에 지시 주석을 남긴다** — 골조와
같은 기제다(`[DOC]` 로 「무엇을 왜」, `[PSEUDO]` 로 「여기를 채워라」).

🔴 [중요] **그다음은 「등재」가 아니라 「개선요청」이다 — 다른 도구다** (사용자 결정 2026-09-05:
*"분산작업 등록과 라운드 값을 받는 분산작업 개선 요청으로 말이야"*).

    ① 등록      `register_work(title, specs)`              **새** 분산 작업 · round = 1
    ② 개선요청   `improve_work(work_id, round=N, specs)`    이 자리 · N = **현재 + 1**
    ③ 마감      `ax-review` → `finalize`                   작업 전체가 끝났을 때만 (§7)

`get_work` 로 지금 라운드를 보고 **+1 을 실어라**. 그 값은 **확인용**이다 — 큐가 이미 알고
있고, 어긋나면 **거절**한다(맞추지 않는다). 너와 큐가 서로 다른 라운드를 보고 있다는 뜻이기
때문이다.

    round 맞음        라운드 +1 · 서브 브랜치 `task/<work>/r<N>/<조각>` ·
                      ⑺ 머지 대상은 그 라운드 것만 · 레드마인은 **그 이슈에 노트**
    round 어긋남      거절 — 큐가 아는 다음 라운드를 사유에 실어 돌려준다
    아직 도는 중       거절 — 조각이 전부 끝나 `ready_for_review` 여야 연다
    마감된 work       거절 — 되살리지 않는다

[주의] **`register_work` 에 `work_id` 를 실으면 거절된다.** 종전에는 그것이 재활성화였는데,
한 입구에 두 뜻이라 라운드를 **상태로 추론**했고 상태가 예상 밖이면 조용히 틀렸다.

[주의] `target_branch` 는 그 work 에 이미 저장돼 있으므로 다시 보내지 않아도 된다
(`work_base_branch` 가 *"저장된 값이 이긴다"*). 조각은 **전진한 tip** 에서 갈라진다.
[중요] **`[FEEDBACK]` 을 골조에 쓰지 않는다** — 층1 이 소스에 남은 `[FEEDBACK]` 을 위반으로
잡고(원전에서 그것으로 검증이 무한 실패했다), 사전 훑기는 `[PSEUDO]` 개수로만 「할 일 있음」을
판정한다. 기존 코드를 고치라는 지시도 **`[PSEUDO]` 로** 쓴다.

## 7. 작업 전체가 끝났으면 — 그때 `ax-review`

전진을 여러 번 해서 목표에 닿았으면, `main` 반영은 **다른 단계**다:

    review.review_work(...)     `origin/main` 기준 시뮬레이션 + 빌드
    review.finalize_work(..., confirm=True)   main 머지·push·기재·정리·**이슈 닫기(「완료」)**

[중요] 이 순서를 섞지 않는다. `main` 을 옮기는 것은 사람의 자리이고, 마스터의 `pre-push`
가드가 그렇게 거부한다.
