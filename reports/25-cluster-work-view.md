## §1 화면 — 주어를 task 에서 work 로

`/cluster` 실시간 층 **아래**에 「작업(work) — 등록 단위」 절 신설. 순서에 이유가 있다:
「지금 무엇이 도는가」(실시간 층)가 먼저고, 「내 작업이 어디까지 왔나」(work)가 그 다음이다.

    열   work · 제목 · 상태(merge_status) · 진행 · 태스크 · 등록 경과
    펼침 ① 「지금」 — #220 의 심박 note 가 work 로 올라온다
         ② 실패 근거 — 태스크별 사유+상세 (work 당 3건까지)
    범위 열린 work 전부 + 종료 work 최근 5건

[중요] **진행은 분수(종료/전체)이고 퍼센트를 만들지 않는다** — #221 에서 거부한 근거 그대로:
`claude -p` 한 번은 진행률을 모르므로 퍼센트는 거짓말이 된다. [주의] `work.total` 이 0 인
**등재 직후 순간**이 있어 그때는 태스크 실측 개수로 폴백한다(안 하면 진행이 `0/0` 으로 보인다).

[중요] **종료 work 에는 「지금」을 붙이지 않는다** — 끝난 일의 마지막 위상은 현재가 아니다.
[중요] **잘랐으면 잘랐다고 화면에 적는다**(「최근 5건만 표시」) — 조용한 절단은 「이게 전부」로 읽힌다.

제약은 #216 계승: 재료는 마스터 자신의 상태(큐 8101·브로커 8102)뿐, **SSH 무접촉**, 하드웨어는
스냅샷 유지. 실시간 층을 못 읽었으면 work 절도 그리지 않는다(재료가 없으므로).

## §2 [중요] 실패 근거가 API 에 닿지 않았다 — 화면을 만들려니 드러났다

`submit_fail` 은 사유를 **태스크 md 본문에만** 썼다(`## fail` 절). 그래서 `/api/v1/tasks` 는
「failed」까지만 알고 **「왜」를 몰랐다** — 화면에 근거를 실으려면 이 구멍을 먼저 막아야 했다.

    고친 것  submit_fail  → 레코드에도 fail_reason · fail_detail · failed_at
             verify_task  → 모든 판정에 verdict(+feedback), failed 면 fail_* 로도 승계
             rebuild      → 2026-08-19 이전 실패는 본문에만 있으므로 parse_fail_reason 으로 되읽는다

[주의] 본문은 **감사 기록으로 그대로 유지**한다 — 레코드는 표시용 사본이고 정본은 본문이다.
같은 태스크가 두 번 실패하면 **마지막** 것이 현재 상태다(파서가 마지막 절을 읽는다).
재기동 생존을 테스트로 박았다 — 리포트 18 의 교훈(등재 직후만 재면 메모리에만 있는 상태를
통과시킨다)과 같은 자리다.

## §4 #220 ③-B — 워커 로그를 마스터로 걷어와 화면에서 연다

사용자 지시로 소 A 다음에 바로 착수. 축적(#220 ①)은 있었지만 **열람이 없어서** 화면이 근거의
원문을 못 보여 줬다(리포트 24 §6 의 절반).

**회수 시점이 설계의 핵심**: `/cluster` 는 15초마다 자동 리로드하므로 서빙 순간에 원격을 읽으면
**BC-250 을 자주 두드리지 않는다**(#105·120초 가드)가 무너진다. 그래서 회수는 **이미 SSH 를
타는 순간에만** 한다 — `ax-status.timer`(5분)의 `master.status collect` 안. 화면은 회수된
**로컬 사본만** 읽고, 나이를 함께 적는다. 수동 회수는 `python -m master.work.logs collect`.

    걷는 것  태스크별  .ax/logs/claimer_debug/<task_id>/{heartbeat,llm_stdout,llm_stderr,build}.log
                      → 트윈 worker_logs/<task_id>/ (+ meta.json: host·회수 시각·원본 크기)
             머신별    .ax/logs/claimer_<날짜>.log → worker_logs/_hosts/<host>.log
    보는 곳  work 절의 실패·진행 태스크 행에 접힌 블록(꼬리 40줄) · 「워커 데몬 로그」 절

운송은 기존 `bundle._remote_read`(scp)를 **그대로** 쓴다 — 셸 경유 읽기가 조용히 빈 문자열을
돌려준 실측이 있어 이 자리에 새 경로를 만들지 않았다. 원격 디렉토리를 나열하지 않는다: 이름이
규약으로 고정돼 있으니 그대로 시도하고 없으면 scp 가 *No such file* 로 답한다.

**라이브가 잡은 것 셋** (이번에도 유닛이 아니라 실행이 잡았다):

1. [중요] **첫 회수가 「대상 4 · 파일 0」만 내놓고 이유를 한 줄도 안 적었다** — 내가 계속
   비판해 온 「조용한 빈칸」을 내가 만들었다. 대상별로 *"로그 없음(claimer_debug/… 가 아직
   없다)"* 을 적고 요약에 `대상·회수·로그 없음` 을 나눠 넣었다.
2. [중요] **오늘자 데몬 로그가 없는 것이 정상이었다** — 상주 claimer 는 **일이 있을 때만**
   기록하므로(폴링은 조용하다) 오늘만 보면 화면이 대부분 빈칸이 된다. 최근 3일까지 되짚고,
   **몇 일 전 파일인지 본문 머리에 적는다**(낡은 것을 최신인 척 보여 주지 않는다).
3. [중요] **화면이 켜지자마자 실제 문제를 드러냈다** — `.43` 의 5분 감시자가 남긴
   *"이미 상주 중"* 이 **하루 288줄**로 일별 로그를 뒤덮어 정작 볼 것(부팅·claim·실패)이
   묻혀 있었다. 정보가 없는 정상 메시지이므로 **콘솔만**으로 돌렸다(`_log(to_file=False)`).
   데몬이 죽으면 다음 틱이 진짜 `[boot]` 을 남기니 진단은 그대로 가능하다.
   **로그 열람을 만든 첫 소득이 로그 위생이었다.**

실측: 테스트 16건 신규(경로 규약·회수·실패 보고·상한·꼬리 절단·되짚기·요청자 제외·렌더),
전체 **3561/3561**. 라이브: `.43` 1089B · `.2` 305B(되짚기 작동) 회수 후 서빙 페이지에서
두 머신 로그 확인. [주의] **태스크별 로그는 아직 실물이 없다** — 대상 4건이 모두 claimer_debug
도입 전(2026-08-09) 태스크다. 다음 실 파견에서 자연 확인된다.
