## 1. 무엇이고 어디에 쓰나

이슈 본문은 **스펙**(무엇을·왜·어떻게 끝났다고 아는가)이고, 그 아래 `ax:plan` 영역은 **태스크**
(목표·대상·단계·선행·검증·근거)다. 이 문서는 앞쪽 — 스펙 — 의 항목을 정한다.

- 일감을 등록할 때(`ax-client:redmine_create_issue`) 본문을 이 항목으로 쓴다.
- `plan_start` 판정이 `no_spec` 이거나 응답의 `spec_missing` 이 비어 있지 않으면, 빠진 항목을
  사용자와 대화로 채운다 — 추측으로 채우지 않는다.
- 아이디어 버킷 항목은 이 형식을 요구하지 않는다. 마일스톤으로 옮겨 착수할 때 채운다.

## 2. 여섯 항목

각 항목은 **제목 줄**(`##` 등 `#` 로 시작하는 줄)로 쓴다. 판정은 제목에 아래 열쇠말 중 하나가
들어 있는지만 본다 — 제목 문구는 자유다. 플랜 영역(`ax:plan`) 안의 제목은 세지 않는다.

| 키 | 항목 | 제목 열쇠말 | 무엇을 쓰나 |
|---|---|---|---|
| `problem` | 문제·맥락 | 문제 · 배경 · 맥락 | 증상이 아니라 **현재 동작(how)** 과 **기존 의도·제약(why)**, 출발점 원천 자료(`파일:줄` · 리포트 · 로그) |
| `triage` | 초반 분류 | 분류 · 트리아지 | ① 기존 개선/버그인가 신기능인가 ② 참조할 외부·내부 레퍼런스 ③ 이식·재사용할 기존 소스(이 저장소·다른 트윈·원전) |
| `observe` | 관측 결과 | 관측 · You see · 사용 예 | 끝났을 때 호출자·운영자가 **실제로 치는 명령과 보게 되는 출력·화면·로그 줄** 1~3개 |
| `scope` | 범위·비범위 | 범위 · 비범위 · 파급 | 고칠 대상 경계 · **이번에 의도적으로 안 하는 것** · 영향받는 인접 모듈·상주 서비스(재기동 필요 여부) |
| `done` | 완료 조건 | 완료 조건 · 완료 기준 · 증명 | **반증 가능한 문장**으로: ① 변경 전 기준선 또는 실패 재현 ② 검사 명령과 기대 결과 ③ 실물 확인 `통과 조건: <관측>` |
| `open` | 열린 결정 | 열린 결정 · 열린 질문 · 미정 | 사람이 정할 갈림길을 **질문 형태**로 · 받아들인 트레이드오프(「X 를 받고 Y 를 얻는다」) |

[주의] 「구현 완료」 같은 자가 보고는 완료 조건이 아니다. 무엇을 실행해 무엇이 보이면 끝인지 적는다.
열린 결정이 없으면 항목을 두고 「없음」이라고 적는다 — 빠뜨린 것과 없는 것을 구분한다.

## 3. 판정은 경고만 한다

`master/plan_start.py` 의 `spec_missing()` 이 본문(플랜 영역 밖)의 제목 줄을 읽어 빠진 항목의
키를 돌려준다. `plan_start` 응답의 `spec_missing` 에 실리고 **판정(`verdict`·`ok`)은 바꾸지 않는다**
(사용자 결정 2026-11-14 — 「게이트를 다섯 번째로 만들지 않는다」, 열린 일감 대부분이 이 형식 이전이다).
`no_spec`(제목이 아닌 줄이 하나도 없음)은 종전대로다.

## 4. 착수 전 인터뷰 — 어떻게 묻나

`#939` (사용자 결정 2026-11-14). 원천: `addyosmani/agent-skills` `skills/interview-me/SKILL.md:14-169`
(커밋 `301b02b`) · 분석 `reports/research/2026-11-13-939-agent-skills-interview-analysis.md` §2.
2절이 **무엇을** 묻는지라면, 이 절은 **어떻게** 물어 스펙으로 수렴시키는지다.

**언제** — 사람이 대화창에 있는 지휘 세션에서, `plan_start` 가 `no_spec` 이거나 `spec_missing` 이 비어 있지
않을 때, 또는 `plan_needed` 에서 갈림길이 남았을 때. [중요] **사람이 없는 경로(워커 파견·자동 리뷰·훅)에서는
묻지 않는다** — 그 자리는 가정을 적고 진행하거나 실패로 보고한다(「워커는 묻지 않는다」).

| 단계 | 하는 일 | 형식 |
|---|---|---|
| ① 선조회 | 코드·문서·RAG·Redmine 으로 알 수 있는 것은 묻지 않는다 | — |
| ② 가설 | 첫 질문 전에 이해한 목표 한 문장과 확신도를 먼저 보인다. 확신도가 낮으면 무엇이 비었는지 한 줄 | `가설: …` / `확신도: 높음·중간·낮음 — 빈 것: …` |
| ③ 질문 | **한 턴에 하나**, 가장 갈리는 것부터. 백지 질문 대신 추정 답과 근거를 붙인다 | `질문: …` / `추정 답: … (근거: 파일:줄)` |
| ④ 요약 | 끝낼 때 2절 여섯 항목으로 요약한다 — 「범위·비범위」의 **비범위는 비워 둘 수 없다** | 아래 대응표 |
| ⑤ 승인 | 명시적 「예」를 받는다. 「알아서 해」는 승인이 아니라 위임이다 — 가장 갈리는 지점을 A/B 둘로 좁혀 다시 묻는다 | — |
| ⑥ 멈춤 | 승인한 턴에 바로 구현으로 넘어가지 않는다. 요약을 이슈 본문 스펙으로 쓰는 것까지가 이 단계다 | — |

끝내는 기준: 다음 질문 서너 개에 사용자가 뭐라 답할지 예측되면 멈춘다. 몇 번 물어도 확신도가 그대로면 남은
것을 「열린 결정」에 질문 형태로 적고 멈춘다. 사용자가 관성적인 답(「확장성 있게」·「깔끔하게」)을 하면
「지금 실제로 필요한 가장 단순한 동작」을 한 번 더 묻는다.

요약 대응표(`interview-me` 6줄 → 2절 항목):

| `interview-me` | 우리 항목 |
|---|---|
| Why now | 문제·맥락 |
| Outcome · User | 관측 결과 |
| Constraint · Out of scope | 범위·비범위 |
| Success | 완료 조건 |
| Open assumptions | 열린 결정 |
| — (우리 고유) | 초반 분류 3문 |

[주의] 사람의 답만 스펙으로 적는다. 모델의 추정 답은 사용자가 고르거나 고쳐야 답이 된다 — 골조 `questions`
가 이미 같은 원칙이다(`master/work/heuristics.py`).

## 5. 기능 분해 표와 3단 경계

`#939`. 원천: `skills/spec-driven-development/SKILL.md:22-175` (Phase 0 Capability Map · 3-Tier Boundaries).

**기능 분해 표** — 한 요청에 따로 검증할 수 있는 기능이 둘 이상 섞여 있으면, 스펙·플랜을 쓰기 **전에**
10줄 이내 표를 먼저 보이고 승인받는다. 승인된 행이 플랜 태스크나 자식 일감, `distribute` 조각의 단위가 된다.

| 기능 | 책임(한 줄) | 선행 | 검증 |
|---|---|---|---|
| 예: `spec_missing` 경고 | `set_plan` 응답에 누락 항목 | — | `test_plan_tools` rc0 |

행이 하나뿐이면 표를 생략한다. 행이 열을 넘으면 일감을 쪼갤지부터 묻는다.

**3단 경계** — 「범위·비범위」 항목에 셋으로 나눠 적을 수 있다. 구현 중 범위 이탈을 막는 기준이다.

- 항상 할 것 — 예: 공식 통합 검사, 커밋 제목 `종류(#N T#)`
- 먼저 물을 것 — 예: 대상 목록 밖 파일, 상주 서비스 설정, 자동 로드 문서
- 절대 안 할 것 — 예: 판정 거절로 바꾸기, 파괴적 git
