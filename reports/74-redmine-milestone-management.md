## 1. 사용자 지적

> *"NS 레드마인 봤는데 마일스톤 관리를 안하고 있더라구, 이에 .33 메인 작업 머신에서 레드마인
> 프로젝트에 마일스톤 생성을 요청하는 기능이 없다고 지적했어."*

지적은 **생성 기능 부재** 하나였다. 실측해 보니 셋이었고, 관리가 멈춘 원인은 지적받지 않은
둘이 더 컸다.

## 2. 실측 — 고장 셋

    ns           버전 1개 「마일스톤 1 — 입력·UI 토대 (게임패드)」(open)
                 이슈 24건 중 마일스톤 붙은 것 → 0건
    modularstage 버전 6개

**① 생성 경로가 어디에도 없다** (지적받은 것)

`master/redmine.py` 는 `resolve_version_id`(이름→id **조회**)만 있었다. `REQUESTER_SCOPE`
에도, `client_mcp` 로스터에도 생성이 없다. 요청자는 마일스톤을 이슈에 **붙일** 수는 있었는데
(`#303` 의 `fixed_version`) **만들** 수가 없었다 — 레드마인 키는 마스터의 컨테이너 DB 에만
있으니 유일한 길이 「사람이 웹 UI 를 연다」였다.

[중요] `redmine_create_issue` 의 도구 설명은 *"fixed_version(마일스톤)을 같이 줄 것"* 이라고
**지시하면서 그 값을 만들 방법을 안 줬다.** `#297` 부류다 — 절차서가 못 하는 것을 지시한다.

**② 🔴 `redmine_meta` 가 `modularstage` 하드코딩이었다** — 이게 더 아프다

`.33` 이 마일스톤 목록을 보는 **유일한 창**인데 `redmine.py:447` 이 `PROJECT_ID` 로 박혀
있었다. NS 작업장에서 물으면 **ModularStage 의 6개**가 오고 자기 것 1개는 안 보였다.

🔴 [중요] **클라이언트는 그때도 `project=` 를 보내고 있었다.** `queue_api` 가 모든 GET 에
쿼리로 붙인다(`client_mcp.py`). 고장은 **받는 쪽 한 줄**이었다 — `redmine_meta_ep()` 가
인자를 아예 안 받았다. 보내는 쪽만 보고 「배선돼 있다」고 읽으면 안 보이는 모양이다.

**③ 🔴 `[분산 작업]` 이슈는 구조적으로 무버전이었다**

`logic_cleanup._redmine_post_issue` 의 payload 에 `fixed_version` 이 없다. `#303` 이
`redmine.create_issue` 에 마일스톤을 열었지만 **이 경로는 그 함수를 안 쓴다**(stdio MCP 우회 ·
직접 REST). 한쪽만 고쳐졌고, 파이프라인이 만드는 이슈는 붙일 방법 **자체가** 없었다.

[중요] 그래서 ①만 고치면 *"만들어 놓고 여전히 안 보이고 안 붙는다."* 사용자에게 그 판단을
먼저 냈고, A~E 전부로 결정됐다.

## 3. 고친 것 (커밋 `e0b0e5c`)

    A  redmine.create_version() · list_versions() · meta(project=…)
    B  POST /api/v1/redmine/version — REQUESTER_SCOPE · tagging `TAG` · 폴백 없음
    C  client_mcp redmine_create_version (로스터 · 디스패치 · 허용목록)
    D  redmine_meta_ep(project) — 응답에 `versions_project` 를 실어 **무엇을 봤는지 말한다**
    E  register_work → work meta → 등재 이슈까지 `fixed_version` 배선

[중요] **동명은 만들지 않고 있는 id 를 돌려준다**(`existing: true`). 버전은 이름으로
참조되고 `resolve_version_id` 가 **부분 일치까지** 허용하므로, 동명이 둘이면 어디에 붙었는지
아무도 모른다. [주의] 충돌 판정만 **정확 일치**다 — 부분 일치를 쓰면 「마일스톤 1」을 만들려는데
「마일스톤 10」이 있다고 거절한다.

[주의] **여는 것은 생성뿐이다.** 잠그기·닫기는 사람의 결정이라 웹 UI 에 남겼다.

[주의] **`create_work` 는 마일스톤을 추론하지 않는다.** `worker_mode` 는 안 주면 전역값을
박지만 마일스톤에는 그런 「지금의 값」이 없다 — 지어내면 남의 마일스톤에 조용히 들어간다.

## 6. 실제로 써 봤다 — 그리고 결함이 하나 더 나왔다

[중요] **이 절이 리포트의 값이다.** ⑴~⑸ 는 기능을 만든 기록이고, 여기부터는 **그 기능으로
실제 일을 한** 기록이다. 만들어 놓고 안 쓰면 결함이 안 보인다 — 실제로 하나 나왔다.

### 6.1 🔴 `HTTP 422` 만 돌려주고 사유를 버렸다 (커밋 `89a6327`)

`[게임] 1` 마일스톤 생성이 이것만 돌려줬다:

    {"error":"HTTP 422"}

직접 쳐 보니 **레드마인은 사유를 정확히 주고 있었다**:

    {"errors":["설명 은 너무 깁니다 (최대 255자 까지)"]}

🔴 `create_version` 이 그 본문을 **읽지도 않고 버렸다.** 같은 함수의 독스트링이
*"깊은 곳의 HTTP 422 는 무엇이 틀렸는지 알려 주지 않는다"* 라고 적어 놓고 정작 그 자리가
그러고 있었다 — **규칙을 적은 자리와 어긴 자리가 같은 함수다.**

    A  _http_error_reasons()  오류 본문의 errors 배열을 사유로 싣는다
                              [주의] 읽기 실패가 원래 오류를 덮지 않는다
    B  DESCRIPTION_MAX = 255  due_date 형식 검사와 같은 관례로 **먼저** 말한다

[중요] **255 는 실측값이다** — 255 통과 · 256 거절을 라이브로 쟀다. 추측이 아니다.
[중요] **자르지 않고 거절한다.** 마일스톤 설명은 「여기 모이는 것은 무엇인가」라는 규약을
적는 자리라 조용히 잘리면 규약이 반쪽이 된다. 이름(60자)은 레드마인이 잘라서 받으므로 둔다.

### 6.2 이름 변경을 열었다 (커밋 `31e52da`, 사용자 요청)

생성만 열려 있어서 §6.3 의 이름 변경은 마스터에서 직접 PUT 을 쳤다 — `.33` 에는 길이 없었다.

    A  redmine.update_version()  이름·설명·마감일·상태
    B  PATCH /api/v1/redmine/version — REQUESTER_SCOPE · tagging TAG · 폴백 없음
    C  client_mcp redmine_update_version

🔴 [중요] **대상 해석에 `resolve_version_id` 를 쓰지 않는다 — 정확 일치다.** 그쪽은 부분
일치를 허용하는데(사람이 「마일스톤 6」만 친다) 그것은 **읽기·부착**의 편의다. 이름을
**바꾸는** 자리에서 부분 일치를 허용하면 「마일스톤 1」을 고치려다 「마일스톤 10」을 고친다.
잘못 붙은 마일스톤은 떼면 되지만 **잘못 바뀐 이름은 무엇이었는지 아무도 모른다** — 레드마인
버전에는 이슈 같은 변경 이력이 없다. 그래서 무엇을 바꿨는지 저널에 남긴다.

🔴 [중요] **`PATCH` 인 것이 의도다.** 스코프 판정이 `(METHOD, 접두어)` 라
`POST /api/v1/redmine/version/...` 같은 하위 경로를 만들면 **기존 POST 스코프가 조용히
딸려 온다.** 메서드를 나누면 `auth.py` 에 한 줄을 더해야만 열린다.

[주의] **`None` 이면 안 바꾸고 `""` 이면 비운다** — 빈 문자열을 「안 바꿈」으로 접으면
설명·마감일을 지울 방법이 없어진다.
[주의] `status` 는 받되 기본이 빈 값이다 — 잠그기·닫기는 사람의 결정이라 명시해야만 움직인다.
[중요] 게이트는 생성과 **같은 것**을 쓴다(마감일 형식·설명 255자). 두 벌이면 한쪽만 느슨해진다.

### 6.3 삭제를 열었다 (커밋 `4cadcfe`, 사용자 요청) — 🔴 **실측이 설계를 정했다**

앞 회차에 *"삭제는 열지 않았다 — 붙은 이슈가 있는 버전을 지우면 그 귀속이 말없이 사라진다"*
라고 적었다. **그 전제부터 쟀다.** 버려도 되는 버전에 이슈 하나를 붙이고 DELETE 를 쳤다:

    DELETE /versions/13.json  →  422, **본문이 비어 있다**
    버전 그대로 · 이슈의 마일스톤도 그대로
    이슈를 지운 뒤 다시 DELETE  →  204

🔴 **내 전제가 반쯤 틀렸다 — 레드마인은 이미 fail-closed 다.** 귀속이 말없이 사라지지
않는다. 진짜 문제는 **사유를 하나도 안 준다**는 것이었다(빈 422). 그래서 안전장치의 모양이
바뀌었다: 「막는다」가 아니라 **「먼저 세고 먼저 말한다」**.

    A  delete_version() + count_issues_in_version()
    B  DELETE /api/v1/redmine/version — REQUESTER_SCOPE · tagging TAG
    C  client_mcp redmine_delete_version

🔴 [중요] **`confirm=False` 가 기본이다** — 안 주면 무엇이 지워질지만 돌려주고 지우지
않는다. `finalize_work`·`advance_work` 와 같은 관례다(승인 발화가 곧 트리거). 버전에는
이슈 같은 변경 이력이 **없어서** 지우고 나면 무엇이었는지 남는 곳이 로그뿐이다.

🔴 [중요] **붙은 이슈가 있으면 승인했어도 거절한다.** 건수와 표본 번호를 실어서.
[주의] **대신 떼어 주지 않는다** — 어느 마일스톤으로 옮길지는 사람의 판단이고, 17건을
말없이 무버전으로 떨구는 것이 이 일에서 가장 비싼 실수다.

🔴 [중요] **못 센 것을 0 으로 접지 않는다** (`count_issues_in_version` 은 `-1` 을 돌려준다).
미확인을 0 으로 읽으면 「붙은 게 없다」가 되어 **지운다.** 미확인은 통과가 아니다.

[주의] 메서드를 `DELETE` 로 나눈 것은 `PATCH` 와 같은 이유다 — 스코프가 `(METHOD, 접두어)`
매칭이라 POST 하위 경로를 만들면 기존 스코프가 조용히 딸려 온다.

**라이브 판정**: 실제 17건이 붙은 「마일스톤 1 — 기본 전투 구조」를 `confirm=true` 로 쳐도
거절했다(건수 17 + 표본 10건 번호). 유닛이 아니라 **운영 데이터로** 재 봤다.

## 7. 마일스톤을 실제로 정리했다

### 7.1 NS — 사용자 판단이 이름을 정정했다

사용자: *"NS 마일스톤으로 아이디어가 추가되어야 하고 기존껀 기본 전투 구조를 잡는
마일스톤으로 보여."* 대조해 보니 맞았다 — **게임패드/입력 관련 이슈는 0건**이고 내용은
거의 전부 전투였다. 붙은 이슈가 0건이라 이름을 바꿔도 잃을 것이 없었다.

    마일스톤 1 — 입력·UI 토대 (게임패드)  →  마일스톤 1 — 기본 전투 구조   (id 7 유지)
    아이디어 — 추후 검토 수집                                              (신규, id 9)

19건을 스탬프했다(19/19). 전투 17건 = GAS 이전 `#641`~`#646` · Ver2.9 전투 `#620`·`#625` ·
패링 `#411`~`#413` · 상태/게이지 `#398`·`#400` · 상호작용 `#361`·`#397` · 계획 `#445`·`#446`.
아이디어 2건 = `#619`(타격감 연출 추가 검토) · `#444`(관우 기획).

[중요] **노이즈 5건에는 안 붙였다** — 마일스톤은 작업 단위인데 그것들은 작업이 아니다.
`#408`·`#409`·`#410`(buildjob 찌꺼기) · `#651`(실증) 은 사유 노트와 함께 닫았고,
`#386`(`[AX]` 지휘자 모드 실증)은 **ModularStage 로 옮겨** 부모 축 `#385` 와 같은
「마일스톤 6」에 맞췄다.

### 7.2 🔴 ModularStage — 게임 코드가 갈 마일스톤이 아예 없었다

열린 78건 중 16건이 무버전이었다. 전수로 세어 보니 원인이 나왔다:

    ModularStage 415건 — 마일스톤이 붙은 388건이 **전부 AX 클러스터 축**이다
      마일스톤 2·3·4·5·6   [AX] 379 · 게임 0
      아이디어 버킷         9건 (7건이 [아이디어] 접두어의 AX 건)

**게임 코드용 마일스톤이 하나도 없었다.** 이 레드마인 프로젝트는 게임과 AX 인프라를 같이
쓰는데(사용자 결정 2026-08-09) 마일스톤 축은 AX 것만 있었다. 그래서 리뷰·플랜이 낸 지적이
**갈 데가 없어서** 무버전으로 쌓인 것이지 누가 빠뜨린 것이 아니었다.

    [게임] 1 — 리뷰 지적 반영 (미션·UI·에디터)   신규 · 5건
       #2 #3 #6   MissionRuntime   MissionTaskExecutor 버그 ([High]×2 · [Mid]×1)
       #9         UiManagement     UI Subsystem + CommonUI (머지 미결)
       #209       MissionEditor    반복 패턴 — 네이밍

[중요] **`[게임]` 접두어를 쓴 것은 번호 충돌 때문이다** — 이미 AX 축의 「마일스톤 1~6」이
있다. 이슈 제목의 `[AX]` 규약을 마일스톤에 뒤집어 적용했다.

### 8.1 🔴 백틱이 셸 명령 치환으로 먹혔다 — **리포트 73 과 같은 사고다**

`#13`~`#20` 의 종결 노트에서 `` `cluster-selftest` `` 가 `()` 로 사라졌다. 셸이
백틱을 명령으로 실행했다(`cluster-selftest: 명령어를 찾을 수 없음`). 리포트 73 이

    복구   PUT /journals/{id} 로 8건 전부 원문으로 교체 (레드마인은 노트 수정을 지원한다)
    예방   이후 모든 노트는 **파일에 써서** 실행했다 — 셸 인용을 아예 거치지 않는다

[중요] **문서에 적는 것으로는 안 막혔다.** 같은 함정을 두 번 밟았고, 두 번 다 「조심한다」가

### 8.3 🔴 테스트가 부정 인덱스로 짚어 **공허하게 통과하고 있었다**

`test_client_mcp` 가 호출을 `calls[-3]` 처럼 뒤에서 세어 짚었다. 삭제 도구를 목록에
끼우자 그 인덱스가 다른 호출을 가리켰는데 — **없는 키를 보는 검사**(`"project" not in …`)는
엉뚱한 호출에서도 통과한다. 「이슈 생성은 프로젝트를 안 받는다」가 실제로는 **PATCH 본문을
보고 있었다.** 드러난 것은 순전히 **바로 옆 칸**(`status == "open"`)이 값을 보는 검사라
같이 밀려서 깨졌기 때문이다.

[중요] **없는 것을 확인하는 검사는 대상이 틀려도 안 깨진다.** 위치가 아니라 **경로+메서드로
찾도록** 바꿨다.

### 8.5 로그를 `tail` 로 봤다가 「안 찍혔다」고 읽을 뻔했다

`.33` 실물 확인(§9) 뒤 저널을 `grep -r … | tail -3` 으로 봤는데 이번 실행분이 없었다.
`grep -r` 은 **파일 단위로** 쏟아 내므로 `tail` 은 **가장 최근**이 아니라 **마지막 파일의 끝**이다.
`sort` 로 다시 보니 세 줄 다 있었다 — **안 찍힌 게 아니라 내가 잘못 본 것**이다.

[중요] 하마터면 **멀쩡한 로그 배선을 고장으로 보고**할 뻔했다. 여러 파일을 훑을 때는
`tail` 앞에 `sort` 를 두거나, 시각을 직접 본다.
