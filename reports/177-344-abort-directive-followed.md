# 177 — #344 워커 지시(abort)를 읽고 따르게 했다

2026-11-13 · 지휘 Claude · 이 세션이 직접 구현(사용자 선택) · 작성 계열 claude.

## 무엇이 문제였나

워커 지시(`POST /api/v1/admin/workers/<worker_id>/directive`)를 보내면 큐에서 빠지기만 하고 아무 일도 일어나지 않았다. 하트비트가 지시를 큐에서 꺼내는데(fire-once) 파견 루프는 그 응답을 버렸다. 보낸 사람은 멈췄다고 믿고 워커는 계속 돌았다.

## 본문(09-01)과 달라져 있던 것

일감 본문과 10-05 결정(ⓐ 하트비트가 읽고 따른다)은 「이미 파견된 실행은 못 끊는다」를 전제로 했다. 현재 소스를 대조하니 그 뒤 `#796`(10-11, `7f70309`)이 **태스크 취소 → Windows 세션 1 실행 중단**(`cancel.flag`)을 이미 만들어 두었다. 남아 있던 것은 셋이었다.

- 지시 abort 는 여전히 읽히지 않고 버려진다.
- 리눅스 직접 SSH(`.43`)는 취소로도 못 끊는다 — `bundle._ssh` 한 번이 끝날 때까지 막고 있다.
- 배달되는 `ax-request` 스킬 §6 이 「지시는 아무 일도 안 한다 · 파견된 추론은 끝까지 돈다」고 적고 있다(Windows 에서는 이미 틀린 말).

원격 종료가 세션 단위인 근거: sshd 는 tty 없는 exec 의 셸을 세션 리더로 띄운다. `.43` 실측에서 셸의 pid = pgid = sid 였고 자식도 같은 sid 였다. 그래서 셸이 자기 pid 를 `/tmp/ax-run-<id>.sid` 에 적고, 종료는 `pkill -s <sid>`(TERM, 5초 뒤 KILL)로 그 세션만 겨눈다. 로컬 ssh 만 죽이면 tty 가 없어 원격은 죽지 않는다.

로그 줄: 큐 `[directive] push|refuse|take …`, 파견 `[dispatch] [directive] … abort 수신 / 큐 취소 완료 / 큐 취소 실패`, `[dispatch] [ssh] … 원격 종료 시도 / 원격 종료 확인 / 원격 종료 미확인 / 원격 실행 흔적 없음`.

## 사고 — 단위 검사가 `.43` 에 실제 지휘자를 띄웠다

`c7a9835` 를 만들던 중, 기존 `test_runner.py` 가 `bundle._ssh` 만 가린 채 `run_worker` 를 부르는 검사 넷이 새 `_ssh_stoppable` 을 타고 **`.43` 에 실제 SSH 를 열었다.** 23:33 에 `~/trunk/ModularStage` 에서 codex 세션 1개(약 6초, 15줄)와 claude 세션 1개(8줄, 도구 사용 0)가 생겼다.

- 확인한 것: `.43` 의 세 체크아웃 모두 `main`·작업 트리 깨끗·새 reflog 없음·task 브랜치 0·stash 0, 남은 codex/claude 프로세스 0, sid 파일 0.
- 비용: 상용 CLI 호출 2회분(짧게 끊김)이 내 실수로 쓰였다.
- 원인: 전송 함수를 바꾸면서 「그 함수를 가려서 실물을 막던 검사」를 먼저 찾지 않았다.
- 막은 방법: 프로세스 생성을 `runner._POPEN` 한 자리로 모으고 `test_runner.py` 가 그것을 거절 함수로 바꾼다(실제 ssh 를 띄우려 하면 AssertionError). 해당 검사 넷은 `_ssh_stoppable` 을 가리도록 고쳤다. 이후 재실행에서 `.43` 세션 수 불변을 확인했다.
- 공식 통합 검사는 `ssh` 를 가짜 실행 파일로 가린 채 돌려, 워커로 가는 `codex exec`·`claude -p` 호출이 0건임을 로그로 확인했다(다른 검사의 ssh 시도 13건은 종전부터 있던 것).

## 한계 — 확인하지 않은 것

- **실제 codex·claude 조각의 중단은 실증하지 않았다.** 대역은 `sleep` 두 개다. 지휘자가 자식을 다른 세션으로 띄우면(`setsid`) 세션 종료로 못 잡는다 — 그 경우 로그는 `원격 종료 확인`이라고 답할 수 있다(그 세션만 본다).
- **Windows 세션 1 에서의 abort 는 단위 검사까지다.** 취소 → `cancel.flag` 는 `#796` 이 만든 경로이고, 이번에 그 앞에 지시 읽기를 붙였다.
- **운영 큐 서비스로는 확인하지 않았다** — 재기동 뒤 실물 확인은 `issue_wrapup` 단계 몫이고, 운영 큐에 가짜 작업을 등재하지 않았다.
- `lane` 모드의 본문 생성과 층2 검증 구간은 못 끊는다. 그동안 취소된 조각이 워커에 무엇을 남기는지(서브 브랜치 커밋 여부)는 확인하지 않았다.
- `infer._default_runner`(`ax-infer` 경로)는 종전 `bundle._ssh` 그대로다 — 이번 범위 밖.
- abort 로 멈춘 조각은 「취소」 종결이라 그 work 의 집계가 취소 쪽으로 간다(기존 태스크 취소와 같은 동작).
