### 1.7 인프라 변경의 RAG·위임 — 사용자 결정 2026-10-03 (#716)

`.57` 인프라 정비도 `.33` NS 요청 흐름을 참조한다(리포트 `85`). 변경 전 **RAG 검색 후
현재 소스와 대조**하고, 근거·대상·분해안을 제시해 **단독(로컬 서브 에이전트) / AX 워커 분산**을
사용자에게 묻는다. 이미 같은 작업의 방식을 정했으면 다시 묻지 않는다. 결정에 맞춰 서브
에이전트를 구성하고, 회수한 실물·검사·기록까지 메인 지휘자가 책임진다. 작은 수정이라는
이유로 선택을 대신 정하지 않는다. 읽기·분석은 준비 단계이며 구현·파견과 구분한다.

분산 준비가 부족하면 문제·선행 정비를 밝혀 사용자의 결정을 따른다. 환경 마찰로 분산
선택지를 영구히 지우거나 준비 전 즉시 가능하다고 제시하지 않는다. `index_only`의 파견
제외는 등록 타입의 계약이다. **골조·소스 경계·검사·빌드는 등록 `kind`로 분기**하며
`.uproject` 유무·프롬프트 단어·테스트 설정으로 타입을 추정하지 않는다. `code`는 현재
프로필의 `work_exts`·소스 경계·테스트 계약을 읽는다. UE 규칙을 Python 작업에 적용하지 않는다.

구체 호출·도구별 위임·준비 검사: [`../master/skills/distribute/SKILL.md`](../master/skills/distribute/SKILL.md).
커밋·푸시, ⑺ 전진·finalize 승인은 기존 §1.1대로 별개다.

### 1.8 등록된 스킬 우회 금지 — 사용자 결정 2026-10-04

- 등록된 스킬이 있는 작업은 해당 스킬의 기존 도구·모듈·명령으로 실행한다.
- 실행 전에 사용할 스킬 경로와 실제 호출 명령을 사용자에게 밝힌다.
- **스킬의 절차나 호출 방법이 불명확하면 사용자에게 먼저 묻는다.** 답변 전에는 임시
  스크립트 작성·대체 경로 실행·처리 방식 변경을 하지 않는다.
- 기존 기능을 대신하는 임시 스크립트나 별도 실행 경로를 임의로 만들지 않는다. 기존 절차로
  처리할 수 없다면 실제 확인한 호출·제약과 부족한 기능을 제시하고 사용자 결정을 기다린다.
- 기억 속 파일의 부재를 시스템 기능의 부재로 판단하지 않는다. 사용자가 선택한 분산 방식을
  직접 처리로 바꾸거나, 요청 범위를 기존 분산 실행 코드·파견 계약 정비로 임의 확대하지 않는다.
- 권한 승인을 위한 좁은 스크립트도 기존 호출 방법을 확인한 뒤 승인받아 실행한다.
  권한 문제 규칙을 스킬 대체 경로를 만드는 근거로 사용하지 않는다.

## 2. 교대 절차 (요약)

전문은 `docs/15-orchestrator-handoff.md` §15.4. 여기서는 어기면 손해가 나는 것만.

1. **체크포인트는 작업 중에 쓴다.** 한도 소진 직전에만 쓰면 갑작스러운 종료를 복구할 수 없다.
2. **넘길 때 강제 종료·커밋·푸시·브랜치 삭제를 자동 수행하지 않는다.** 미커밋 변경과
   진행 중인 테스트를 보존하고, 실행 중인 것은 **담당 파일·프로세스·로그 위치**를 적는다.
3. **같은 작업을 지휘하는 세션은 한 번에 하나.** 양쪽이 열려 있어도 이전 세션은 재개하지
   않는다. **문서 기록은 잠금이 아니다** — 실행을 차단하지 않는다.
4. **받는 쪽은 대조부터 한다.** HEAD·dirty diff·관련 이슈·프로세스/로그를 기록과 맞춰 본다.
   🔴 **기록의 「완료」 주장을 그대로 믿지 않는다.** 이것은 상대 도구를 못 믿어서가 아니라
   **기록 일반의 성질**이다 — 실측 근거는 §5.
5. **승인은 대상·범위·근거와 함께 전달한다.** 도구 교대만으로 승인을 넓히지도, 이미 받은
   승인을 다시 요구하지도 않는다. 미승인인 ⑺ 전진·finalize, `awaiting_resume` 의 사람 재개
   조건은 그대로 유지된다.
6. **대화가 멈춘 것이 작업이 멈춘 것은 아니다.** systemd 서비스·`ax-dispatch.path` 의 보류
   (`~/.cache/ax-dispatch/hold.json`, 재부팅을 넘는다)·원격 작업은 세션과 무관하게 남는다.

## 5. 기록을 믿지 않는 이유 — 실측

§2 ④의 근거. 2026-09-07 조사에서 **Claude 자신의 기억 안에 모순이 있었다**:

    ns_pipeline_first_run_state.md 본문   "등재 완료 … 다음은 .33 이 골조 push"
    같은 기억의 색인 줄                    "2026-08-30 NS 를 전부 지웠다 · 되살리지 말 것"

본문이 지워지기 **전** 상태로 굳어 있었다. `pipeline_redesign_axis.md` 도 `description` 이
*"실증은 아직 시작 전"* 인 채 남아 있다(본문은 축이 닫혔다고 적는다).

→ **어느 도구의 기록이든 오래되면 틀린다.** 인계에서 정본은 **레드마인과 저장소의 실제
상태**이고, 인수인계 파일은 그리로 가는 포인터다. 그래서 §15.3 이 *"전체 기억을 반복해서
싣지 않고 관련 이슈·설계·로그를 가리킨다"* 고 적는다.

[주의] **인증 키·토큰·비밀번호는 어디에도 적지 않는다.** 접근 방법과 **자격 정보의 위치**만.
