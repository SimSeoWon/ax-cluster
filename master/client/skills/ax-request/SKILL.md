# ax-request — 일감을 등록한다 (요청자 측)

> 마스터가 생성해 배달한다. **손으로 고치지 말 것** — 다음 배달에 덮인다.

## 0. [중요] 이 머신의 자리

**여기는 사람이 쓰는 기계다.** 역할은 `requester` — **요청하고 확인한다.**

| | |
|---|---|
| 한다 | 일감 등록 · [중요] **작업 브랜치 생성 + 골조 커밋**(§3.5) · 매니페스트 확인 · 검색 · 시소러스 등록 · **검증 빌드**(§7) · 피드백 · **단일 클래스·미세 수정은 직접**(§0.1) |
| [중요] **안 한다** | 큐에서 claim · **분산 조각 구현**(조각 브랜치 `task/<work_id>/<task_id>`) · 로컬 큐 등재 |

구현 중 **분산으로 도는 것**은 `worker` 역할 머신이 한다 — 그쪽엔 `ax-work` 스킬이 있다.

## 0.05 [중요] **게임 소스는 고치기 전에 계획을 말하고 동의를 받는다** (BLOCKING)

원전 `.agents/AGENTS.md` 1조 이식 (`docs/11-agent-conduct.md`). **아래 분기보다 먼저 적용된다.**

    대상   `Source/**` · `*.uproject` · `Config/*.ini` · `Content/**` ·
           그리고 **빌드·에디터 실행**(산출물을 바꾼다)
    절차   ① 무엇을 왜 고칠지 말한다 ② 사용자 동의를 받는다 ③ 그 다음에 고친다

[중요] **「미세 수정」은 *어디서* 처리할지의 기준이고 *동의가 필요한지*의 기준이 아니다.**
두 축을 섞으면 안 된다 — 아래 표에서 「여기서 직접 처리」로 갈렸다고 해서 동의가 면제되지
않는다. 실측 2026-08-24: 플러그인 활성화 요청에서 `.uproject` 를 고치고 **빌드까지 간 뒤**
사용자가 세션을 중단했다. 분기 판단은 맞았고 **빠진 것은 이 절차**였다(`#298`).

[주의] 읽기·검색·매니페스트 확인·계획 제시는 동의 없이 한다 — **막는 것은 「쓰기」다.**

## 0.1 [중요] 분기 — 직접 처리 vs 분해·분배 (원전 규칙 그대로 · 결정은 사용자)

원전 `.claude/CLAUDE.md` 의 `code-writer` vs 분산 분기를 그대로 옮긴 것이다
([주의] 원전의 그 스킬은 **마스터에 있다** — 이 기계는 `ax-request` 로 등재만 한다, `#297`).
**시스템 규모는 자동 트리거가 아니다 — 애매하면 묻는다.**

| 요청 | 어디서 |
|---|---|
| 「X 기능 구현해줘」·「이 코드 리팩터링」 — **단일 클래스·기존 클래스 미세 수정** | **여기서 직접 처리한다.** 요청한 기계가 하는 것이 빠르다 (사용자 2026-08-20). [중요] **§0.05 동의가 먼저다** |
| 「X 시스템 추가」·「Y 기능 만들어줘」 — **신규 파일 3개 이상 + 클래스 간 상속/포함/import 관계**, 또는 **여러 클래스가 묶이는 신규 시스템** | 마스터에 등재해 분해·분배 (§1 이하) |

애매하면 **a/b/c 를 모두 제시하고 사용자가 고른다**:

> - a) 마스터 등재로 분산 (골조 + 게이트 + 조각별 UE5 빌드)
> - b) 여기서 직접 작성 (브랜치 격리 없이 즉시, `main` 또는 사용자 지정 브랜치)
> - c) 작은 단위로 쪼개 직접 처리

[중요] **옵션을 환경 상태로 자동 거르지 말 것** (원전 BLOCKING). 마스터 큐가 죽어 있어도,
`_stale` 이 붙어 있어도 **a 를 빼지 않는다** — MCP 미연결은 환경 마찰이지 영구 제약이 아니다.
복구는 마스터에서 한다(`systemctl status ax-task-queue ax-projects`, [주의] 성공 판정은 종료코드가
아니라 `ExecMainStartTimestamp`). ❌ *"큐가 안 돌아서 분산 불가"* 는 금지된 응답이다.

이유(원전): 다중 클래스를 한 번에 직접 쓰면 **의사코드 단계 없이 본문까지 써버려 분산이
무의미해지고**, 반대로 모든 다중 클래스 작업을 큐에 박으면 **빠른 일회성 작업까지 오버헤드**다.

[주의] **등재는 마스터 큐 한 곳으로만.** 원전의 이유 그대로 — 워커 PC 가 work 를 등재하면
동일 큐가 여러 곳에 생겨 진실의 원천이 깨진다. 그래서 로컬 `task_queue` MCP 등록은 2026-08-20
제거됐다.

[주의] 직접 처리해도 **사람이 편집 중인 트리다** — `git clean`·`reset --hard`·`main` 강제 push
금지. 미커밋 `.uasset` 은 바이너리라 날리면 되살릴 수 없다. 브랜치는 사용자가 지정한 것을 쓴다.

### 0.2 [중요] 직접 처리할 때도 **너 혼자 다 하지 않는다** (원전 규약)

원전의 클라이언트 흐름은 네 걸음이다 — ① 인프라 서버에서 **컨텍스트 문서를 받고**(§2 검색)
② 스스로 할지 분산할지 **대화형으로 묻고**(§0.1) ③ 분산이면 **서버에 태스크 등록**(§1 이하)
④ **아니면 스스로 작업하는데, 거기서 `agy`·로컬 LLM 을 쓴다.** ④ 가 이 절이다.

| 무엇에 | 누구에게 |
|---|---|
| 반복적 본문 채우기 · 대량 변환 | **로컬 LLM** — [주의] 이 머신은 실측이 안 맞는다(아래) |
| 큰 파일 조사·정리 · 토큰 절감 | **`agy`**(Antigravity CLI). [중요] **`--add-dir` 로 파일을 쥐여줄 것** — 웹에서 찾으라고 시키면 **출처를 지어낸다**(실측). `-p` 는 **프롬프트 직전**에 둔다 |
| 오케스트레이션 · 소스 대조 · 최종 검증 | **너(Claude)** — 이건 위임하지 않는다 |

[중요] **위임 결과의 "완료" 를 믿지 말고 산출물을 본다.** `agy` 가 `status:"SUCCESS"` 를
반환하면서 파일을 안 쓴 사건이 있다(원전 실측). 파일이 생겼는지·내용이 맞는지 **네가 확인한다.**

[주의] **이 머신의 로컬 LLM 은 실측상 큰 모델을 못 돌린다** (2026-08-20): 여유 VRAM
**7.7GB** 인데 설치된 모델은 `qwen2.5-coder:14b` **9.0GB** · `gemma4:e4b` **9.6GB** 이고,
**UE5 를 열면 더 줄어든다.** 그래서 이 머신의 기본 위임 대상은 **`agy`** 다(실측 1.0.16 설치됨).
대량 반복 작업이 로컬 LLM 을 정말 필요로 하면 그것은 **분산으로 보낼 신호**다 — 워커
(`.43`·`.2`)가 상주 모델을 갖고 있다.

[중요] **결정적 게이트가 LLM 판단보다 우선한다** — 컴파일·테스트·린트가 있으면 그것이 최종
판정이고, *"모델이 괜찮다고 했다"* 는 근거가 아니다.

[주의] **빌드는 예외다.** 이 PC 에는 UE5 가 있어 **검증 빌드가 여기서 가장 빠르다**(§7).
다만 **메인 워킹트리가 아니라 별도 워킹트리에서** 돈다 — 사람의 트리는 건드리지 않는다.

설정은 항상 `./.ax/config.json` 에 있다. **없으면 추측하지 말고 마스터에 배달을 요청한다.**

### 0.3 🔴 [중요] 직접 처리를 끝냈으면 **기재한다** (`#310`)

분산 경로에는 자동 기재가 있다 — work 이 종결될 때 큐가 history 를 쓰고 `finalize_work` 가
레드마인에 남긴다. **직접 처리는 큐를 지나지 않으므로 기재 주체가 너뿐이다.** 안 하면 아무도
안 한다. 실측(`ns#302`, 2026-08-24): 직접 처리한 작업이 **노트 0건 · 상태 신규**로 남았고,
본문은 마스터가 대신 적어야 했다.

**셋을 한 묶음으로 부른다 — 하나만 하면 반쪽이다:**

| 부를 것 | 무엇을 | 빠뜨리면 |
|---|---|---|
| `log_history` | **왜 그렇게 했나** (결정·대안·사용자 발화) | 다음 세션이 같은 결정을 처음부터 다시 한다 |
| `redmine_note` | **무엇을 했나** (일감에 이력) | 일감이 「신규」로 남아 사람이 진행을 못 읽는다 |
| `redmine_link_commit` | 커밋했다면 **어느 커밋인가** | 이력과 코드가 이어지지 않는다 |

[중요] **상태는 「해결」까지만.** 「완료」로 닫는 것은 사람의 판단이다 — 파이프라인의
`finalize_work` 도 같은 자리에서 멈춘다. 되돌릴지 유지할지 같은 **사용자 결정이 남아 있으면
상태를 올리지 말고** 무엇을 기다리는지 노트에 적는다.

[주의] **커밋은 별개의 승인이다.** 기재했다고 커밋이 된 것이 아니고, 이 트리는 사람이 편집 중이다
(§0.1 끝). 미커밋으로 남겨 두는 것도 선택이지만 그렇다면 **노트에 「미커밋」이라고 적는다** —
적지 않으면 다음 사람이 코드에 들어갔다고 읽는다.

[주의] `log_history` 는 **trivial 에는 쓰지 않는다**(오탈자·단순 리네이밍). `redmine_note` 는
일감 번호가 있으면 언제나 쓴다 — 그쪽은 진행 기록이고 판단이 아니다.

## 1. 등록 전에 — 무엇을 부탁하는지 스스로 정리한다

사용자의 말을 그대로 큐에 넣지 않는다. 최소한 이 셋이 있어야 워커가 일할 수 있다:

| | 없으면 |
|---|---|
| **대상 클래스·파일** | 매니페스트 검색이 엉뚱한 걸 물어 온다 |
| **골조**(`[PSEUDO]` 본문만 비운 시그니처) | [중요] 워커가 시그니처를 지어낸다 |
| **동결 계약** (바꾸면 안 되는 선언) | 워커가 공개 API 를 바꿔 버린다 |

[중요] **골조는 요청자가 작업 브랜치에 실물로 커밋한다** (`#317` 미결 ① ⓐ · `#319`, 2026-08-27).
매니페스트에는 골조 텍스트가 실리지 않는다 — 조각은 `task/<work_id>/base` 의 tip 에서 갈라지고
**그 tip 이 곧 인터페이스 동결**이다. 절차는 §3.5.

[주의] 마스터가 골조 *텍스트*를 만드는 경로는 남아 있다 — `instruction` 이 있고 골조가 없으면
`claude:opus` 로 만들고 `.2` 에서 게이트를 통과시킨 뒤 등재한다(소 1.1.4). 그때 게이트는
**경량 UHT** 다(`#317` 미결 ②, `.2` 실측 9.7초 대 풀 빌드 75~122초).
[중요] **사람이 쓴 골조를 마스터가 덮지 않는다.**

부족하면 **묻는다.** 반쯤 채운 일감은 워커가 반쯤 틀린 코드를 만들게 한다.

## 2. 검색은 입구가 하나다

이 머신(요청자)에서는 **ax-client MCP 의 `search_context(query, tags?, n)`** 를 쓴다 —
마스터 RAG 에 위임하고, 마스터 미연결이면 마지막 정상 응답을 **`_stale` 표기**로 준다.
[중요] `_stale: true` 가 보이면 낡은 값이다 — 그 값으로 등재하지 말고 마스터부터 확인한다.
`list_domains` / `get_domain(name)` 으로 온톨로지도 읽을 수 있다 (전부 읽기 전용).

**세밀 조회도 같은 입구다** (2026-08-20 — 원전 로컬 exe 의 자리를 인수했다):

    get_domain_layer(domain, layer?)   층 서술 + 그 층의 objects·actions·invariants 이름
                                       (layer 생략/0 = 전체 층. 원전의 list_actions 도 이것)
    get_object_spec(domain, name)      클래스 1건 상세 (부모·파일·불변식 근거)
    get_action_spec(domain, name)      행위 1건 상세 (트리거·흐름·영향 객체)

[중요] **로컬 `context-search` 로 부르지 않는다.** 온톨로지가 마스터로 옮겨진 뒤 그 인덱스는
정본이 아니고, **비었다고 말하지 않고 0 으로 답한다** — 실측 2026-08-20: 로컬 240항목은 전부
서버에 있었고 서버가 54항목 앞섰는데도 로컬 exe 는 objects/actions 를 0/0 으로 답했다.
없는 이름을 물으면 이 입구는 **404 로 시끄럽게** 답한다 — 그게 맞는 실패다.

[중요] 다른 경로로 돌면 시소러스가 안 걸려 한국어 질의가 조용히 나빠진다.

`[미션 시스템]` 처럼 **대괄호로 개념을 감싸면** 그게 시소러스 조회 신호다.

### 2-1. 사용자가 답해 준 것을 기억시킨다 (2026-08-20)

    add_object_alias(class_name, term)   확인된 별칭 등록
    mark_not_a_class(term)               "그건 클래스가 아니다" 기록 — 다음부터 안 묻는다

[중요] **사용자가 명시로 확인한 것만 부른다.** 별칭은 검색 질의에 클래스명을 덧붙여 확장하므로
추측으로 등록하면 검색이 조용히 오염된다(원전 규약: silently auto-add 금지).

[주의] **거부는 오류가 아니다** — 마스터의 범용어 가드가 `status: rejected_short`(공백 제거 4자
미만) · `rejected_generic`(정확 구 DF 가 코퍼스의 2.5% 초과)로 **사유를 돌려준다.** 그대로
사용자에게 보여 주고 더 판별력 있는 표현을 받는다. 오타 클래스는 `not_found` 로 막힌다.
문턱값을 여기서 흉내내지 말 것 — 판정은 마스터 한 곳이다.

## 3. 등록

    register_work(title, specs, original_request)          ← `ax-client` 도구 (`#336` ④)

[중요] **`register_work_tool` 이 아니다.** 그 이름은 마스터 MCP 의 도구이고 이 기계 로스터에
없다 — 오래 그렇게 적혀 있었고 실제로 막혔다(`#297` 부류). 지금은 요청자가 직접 등재한다:
`.ax/token` 으로 8103 의 `/work/register` 를 탄다.

- `title` — 한국어 그대로 좋다. 내부에서 slug 로 바뀌고 한글도 안전하다
- `specs` — 태스크 목록(**배열**). 필드와 형은 **도구 스키마가 정본이다** — 거기 없는 이름을
  넣으면 거절된다(실측: `summary` 를 지어내 거절됨)

[중요] **조각은 클래스 단위이고 서로 독립이다 — `depends_on` 을 붙이지 마라.** 골조가 모든
클래스의 선언(함수·변수)을 **미리 다 만들어 비운 채로** 올라가므로, 조각들은 서로의 결과를
기다릴 이유가 없다. 그것이 인터페이스 동결의 존재 이유다(`skeleton.py`: *"클래스 관계·
인터페이스는 골조에서 1회 확정, 워커는 본문만 채우고 변경 불가"*).

    묶음 (동시)   서로 **다른 파일** → 병렬 파견            ← 클래스 단위 조각이 여기다
    뎁스 (순차)   **같은 파일**을 `[PSEUDO:N]` 로 쪼갬 → `depends_on` 으로 줄을 선다

[주의] 실측 2026-08-30: 서로 다른 파일 넷에 `depends_on` 을 붙여 **병렬로 갈 수 있는 것을
직렬로 묶었다.** 첫 조각이 끝나도 나머지가 안 풀렸다 — 제출은 통합자 몫이라 앞 조각이
`verified` 가 되지 않기 때문이다.

[주의] `requires` 도 마찬가지로 **보통 비운다.** 그것은 능력 라우팅이고, **추론에는 UE5 가
필요 없다** — `~/CLAUDE.md`: *"UE5 only decides who can run the layer-3 verdict"*. `ue5` 를
넣으면 UE5 없는 워커(`.43`)가 후보에서 빠진다.
- `original_request` — [중요] **사용자 원문을 그대로** 넣는다. 나중에 "왜 이걸 시켰나" 의 유일한 근거다

[중요] **`target_branch` 를 보내지 마라.** 비우면 마스터가 `task/<work_id>/base` 로 잡는다.
`main` 을 넣으면 조각들이 `main` 에서 갈라져 골조 동결이 약속으로만 남는다(실측 2026-08-30).

[중요] **골조는 마스터가 만들지 않는다.** 등재가 하는 것은 큐 등록과 매니페스트 수집이다.
`instruction` 은 골조를 마스터가 만들던 **옛 경로의 재료**라 보통 넣지 않는다 — 넣을 것은
`contracts`(**한 문자열**, 워커가 읽는 동결 계약)다.

[주의] **동기 호출이라 시간이 걸릴 수 있다.** 타임아웃은 **실패가 아니다** — 서버는 계속 돈다.
먼저 `list_works` 로 들어갔는지 보고, 있으면 **재시도하지 마라**(중복 등재가 된다).

[주의] 거절은 200 + `ok:false` 다 — `reason`·`hint`·`valid_fields` 를 읽고 고친다.
실패해도 반쪽 work 는 남지 않는다(`#336` ③ — 자동 종결).

등록되면 태스크마다 **매니페스트가 1회 수집**된다(컨텍스트 문서 + 도메인 규범).

## 3.5 [중요] 등재 다음은 작업 브랜치다 — 골조를 실물로 올린다 (`#319`)

    등재 → work_id 수령 → task/<work_id>/base 생성 → 골조 .h + 주석 작업지시서 커밋
         → UHT 게이트 → push → **여기까지가 이 기계의 몫이다**
         ↓
    [마스터 .57] 골조 push 이벤트 → ax-dispatch.service → 워커에 추론 파견

[중요] **push 뒤에 이 기계가 할 일은 없다 — 그러나 「저절로 된다」고 사용자에게 말하지 마라.**
파견은 마스터의 `ax-dispatch.service`(`#340`)가 골조 push 를 보고 건다. 그것이 **안 걸린 채로
조용히 멈추는 사고가 실제로 있었다**(2026-08-29~31, 이틀. 트리거 배선이 없어서 4조각이
`pending` 으로 방치됐고, 이 스킬의 옛 문장이 *"그 다음이 분해·파견"* 이라 요청자 세션이
「기다리면 된다」고 읽었다). 그래서 **확인이 절차의 일부다**:

    list_works(project) → 그 work 의 태스크가 pending 에서 움직이는가 (수 분 안)

**5분이 지나도 전부 `pending` 이면 기다리지 말고 사용자에게 보고한다.** 마스터에서 확인·수동
파견하는 명령은 이것이고, 이 기계에서 실행하는 것이 아니다:

    ssh sim@192.168.0.57 journalctl -u ax-dispatch -u ax-dispatch-catchup -n 50 --no-pager
    ssh sim@192.168.0.57 'cd ~/ax-cluster && AX_PROJECTS_ROOT=$PWD \
        .venv/bin/python -m master.work.autodispatch <프로젝트> <work_id>'

[주의] **`[dispatch]` 로그가 한 줄도 없으면 그것이 「안 걸렸다」의 증거다** — 파견은 걸었는지와
왜 안 걸었는지를 **둘 다** 찍게 되어 있다. 침묵은 정상이 아니다.

[중요] **이름을 여기서 지어내지 않는다.** `get_manifest(task_id, project)` 의 「작업 브랜치」 절이
브랜치 이름 · 기준 커밋 · **없으면 실행할 명령**까지 준다. 그 절이 *"[중요] 그 브랜치가 원격에
아직 없다"* 로 끝나면 바로 아래 줄에 적힌 명령을 그대로 쓴다.

[중요] **브랜치만 따면 안 된다.** 골조 없는 base 에서 조각이 갈라지면 인터페이스 동결이 다시
약속으로만 남는다 — 워커 N명이 같은 헤더를 본다는 보장이 git 에서 사라진다(`#319` 가 고친 자리).

[중요] **골조 커밋은 `Source/**` 를 만진다 → §0.05 가 먼저 적용된다.** 계획을 말하고 동의를 받는다.

[주의] 없는 채로 파견되면 **시끄럽게 실패한다** — `twin_base.resolve()` 가 `exists=False` 로 두고
기준 커밋을 비운다. 조용히 `main` 으로 접지 않는다. 그 실패는 고치는 자리가 아니라 보고하는 자리다.

[주의] 게이트는 **경량 UHT** 다 — 풀 빌드는 이 단계에 성립하지 않는다(`.h` 만으로 LNK2019).
UHT 가 못 보는 것: include 누락·순환 · 타입 불일치 · 실재하지 않는 부모. 그것은 조각별 빌드와
마지막 `.33` 머지가 잡는다.

## 4. 등록 후 반드시 확인한다

    get_manifest(task_id, project)

[중요] **결손을 읽는다.** 매니페스트는 베스트에포트라 이런 문장이 들어 있을 수 있다:

- *"검색 결과가 없다"* → 대상 클래스명이 틀렸거나 아직 색인이 안 됐다
- *"규범 grounding 없이 진행된다"* → 도메인 규범이 안 붙었다. 그 상태로 보내면 워커가
  도메인 규칙을 모른 채 코드를 짠다

**결손이 있으면 워커에 보내기 전에 고친다.** 등록은 취소보다 싸다.

## 5. 어디로 갈 수 있나

    list_workshops_tool(name)        · 등록된 작업장과 역할
    check_workshops_clean_tool(name) · 지금 보낼 수 있는 곳 (dispatchable)

있으니 **밀어붙이지 말고 알린다.** 자동화는 절대 `git clean` 을 부르지 않는다.

## 6. [중요] 언제든 멈출 수 있다 — 그게 대화식의 전제다

사용자가 *"방향이 이상한데"* 라고 하면 **바로 멈춘다.** 큐에 경로가 있다:

    POST /api/v1/tasks/<task_id>/cancel                 이 태스크를 취소
    POST /api/v1/admin/workers/<worker_id>/directive     그 워커에 지시(abort 등)

지시는 **화이트리스트 검증**을 거치고 **fire-once** 다.

🔴 [중요] **「다음 하트비트에 멈춘다」는 틀렸다 — `directive` 는 지금 아무 일도 안 한다.**
`#320`(2026-08-27)이 상주 claimer 를 걷어서, 큐를 폴링하며 지시를 읽고 **따르던** 주체가
사라졌다. 지금 하트비트를 보내는 것은 마스터의 파견 루프 하나뿐인데(`infer.py:554`
→ `runner.py:308`), 그 루프의 목적은 **리스 연장**이라 하트비트 **응답을 읽지 않는다.**
`directive` 는 하트비트로만 큐에서 빠지고(fire-once) 그대로 버려진다 —
**보낸 사람은 「멈추라고 했다」고 믿고, 워커는 계속 돈다.**
[주의] 그러니 `directive` 로 멈추려 하지 말고 아래 둘을 쓴다. (마스터 미결 항목이다)

지금 실제로 멈추는 방법은 둘이고, 무엇을 멈추는지가 다르다:

    태스크 취소   POST /api/v1/tasks/<task_id>/cancel   큐에서 뺀다. 이미 파견된 추론은
                                                        끝까지 돌고 결과가 버려진다
    파견 자체     마스터에서 사람이 멈춘다               ax-dispatch.service 는 oneshot 이다:
                  `systemctl stop ax-dispatch`           돌고 있는 것을 끊고, .path/.timer 를
                  + `.path`·`.timer` 정지                안 막으면 다음 신호에 또 뜬다

[주의] **사용자에게 「즉시 멈췄다」고 말하지 마라.** 조각 하나가 이미 워커에 나가 있으면
그 추론은 끝까지 돈다(실측 조각 1건 162.7초 · $0.74). 취소가 막는 것은 **다음 조각**이다.

[중요] **멈춘 뒤에 브랜치를 지우지 않는다.** 실패한 attempt 도 조사 자산이다(§8.4 누적 모델).
정리는 사람이 판단한다.

## 7. 검증과 피드백 — 이 머신이 가장 빠르다

이 PC 에는 UE5 가 있다. **워커에 왕복하지 않고 여기서 바로 빌드해 컴파일 에러를 본다.**

[중요] **다만 메인 워킹트리에서 브랜치를 갈아타지 않는다.** 사람이 편집 중이던 것이 날아간다
(`.uasset` 은 복구 불가). 별도 워킹트리를 쓴다:

    git worktree add ../ModularStage-task-<id> task/<id>

반려할 때는 **코드 위치에 `[FEEDBACK]` 블록을 박아** commit·push 한다 — 골조의 `[PSEUDO]`
와 같은 자리, 같은 방식이다. 큐의 텍스트만으로는 워커가 **어디를** 고칠지 모른다.
[중요] **재구현이 아니라 수정**이다 — 그때까지의 구현은 누적된다.

## 8. [중요] 이 머신에서 하지 않는 것

    큐에서 claim · attempt/ 브랜치 · 태스크 소스 수정 ·
    [중요] 메인 워킹트리에서 브랜치 전환 · git clean · reset --hard · main 직접 push

(검증 빌드는 한다 — 단 §7 의 별도 워킹트리에서다.)

사용자가 "여기서 그냥 고쳐줘" 라고 하면 — **할 수는 있다.** 다만 그건 **클러스터 작업이
아니라 사람의 로컬 편집**이고, 큐·매니페스트·검증 층을 타지 않는다는 것을 말해 준다.
둘을 섞으면 나중에 무엇이 검증된 코드인지 알 수 없다.
