# distribute — 큰 작업을 분산한다 (마스터 측 입구)

> [중요] 이 파일의 **정본은 저장소**(`~/ax-cluster/master/skills/distribute/SKILL.md`)다.
> `~/.claude/skills/distribute` 는 그리로 가는 **심볼릭 링크**다 — 링크를 실제 파일로 덮지 말 것.

## 0. [중요] 원샷이 아니다 — 단계마다 멈춘다

    ① plan      분해 계획을 세워 보여준다        → [중요] **사람이 파일을 편집해 자른다**
    ② register  골조 생성 + 골조 빌드 게이트     → [중요] 통과해야 큐에 등재된다
    ③ dispatch  추론 파견 (기본 직렬)            → 응답이 스풀에 쌓이고 인계 묶음이 나온다
    ④ integrate 적용 → 조각마다 UE5 빌드 → [중요] 통과분만 커밋·push (ff-only)

단계를 합치지 않는 이유가 각각 있다:

- **분해가 틀리면 N개 조각이 전부 헛일**이다. 골조가 틀린 것 다음으로 비싸다
- **골조는 모든 병렬 조각의 계약**이다. 틀린 골조는 조각 전부를 오염시킨다
- **파견은 돈이다.** 실측: 4파일 묶음 파일당 $0.042 vs 단일 $0.133

[중요] **다음 단계로 네가 알아서 넘어가지 않는다.** 각 단계 출력의 마지막 줄이 *"다음은 사람이
한다"* 로 끝나면 거기서 멈추고 사용자에게 보여준다.

## 1. 시작 전 — 대상을 먼저 정한다

`plan` 은 *"어떤 클래스·파일을 고칠 것인가"* 를 **입력으로 받는다.** 그것을 정하는 것이 먼저다:

```bash
# 트윈에서 관련 코드를 찾는다 (MCP: search_context_tool 도 같은 일을 한다)
.venv/bin/python -m master.context_search "미션 스냅샷 저장"
.venv/bin/python -m master.graph find <클래스>          # 부모·자식·include
```

[중요] **사용자와 대상을 합의한 뒤에** 계획으로 넘어간다. 매니페스트 검색은 대상이 엉뚱하면
엉뚱한 것을 물어 온다.

## 2. ① plan — 계획을 세우고 **파일로** 낸다

```bash
.venv/bin/python -m master.work.distribute plan ModularStage <슬러그> \
    UMissionSnapshot:Source/ModularStage/Mission/MSMissionSnapshot.h \
    UMissionSnapshot:Source/ModularStage/Mission/MSMissionSnapshot.cpp
```

무엇을 보여주나 — **물결**(동시에 파견 가능한 묶음)·**적용 순서**(의존이 먼저)·위험:

- [완료] 같은 물결 안에 파일 겹침 없음 ← 없으면 **파견하면 안 된다**
- [주의] 순환 의존 — 막지는 않는다(include 역추적이 근사라 가짜일 수 있다)
- [주의] 그래프에 없는 파일 — 신규 파일이면 정상

[중요] **그 다음은 사람이 한다.** 계획 파일(`<프로젝트>/plans/<슬러그>.json`)을 열어 **필요 없는
조각을 지우거나 순서를 고친다.** 파일이 있는 이유가 그것이다 — 눈으로 보는 것만으로는 자를 수
없다. 사용자에게 계획을 보여주고 **자를 것이 있는지 물어본다.**

## 3. ② register — 골조를 세워 보고 등재한다

```bash
.venv/bin/python -m master.work.distribute register ModularStage <슬러그> "<제목>" <저장소>
```

- 골조가 없는 조각은 **`claude:opus` 로 생성**된다(작업당 1회 · 모든 조각의 계약이라 값을 쓴다.
  A/B 실측: opus 동결 30 vs 로컬 14b 6 — **5배**)
- [중요] **골조 빌드 게이트**(소 1.1.5)가 `.2` 에서 골조를 세운다. 통과해야 등재된다.
  [주의] **게이트를 안 돌린 것은 통과가 아니라 미확인이다** — 출력이 그렇게 말한다
- 골조가 *"여기서 추측했다"* 를 질문으로 내놓으면 [중요] **사람에게 그대로 물어본다.** 모델의
  제안을 답으로 적립하지 않는다. 답에는 **범위**(`project`/`domain:<D>`/`once`)가 붙는다
  - 물음은 **등록 결과에 실려 온다** — `Registered.questions` · `question_lines()`,
    요약이 *"골조가 물음 N건을 냈다 — 답해야 적립된다"* 로 크게 말한다 (`#328`)
  - 사람의 답은 **다음 등록 호출에 실어 보낸다**:
    `register_work(..., heuristics=[{"topic": …, "decision": …, "why": …, "scope": …}])`
    [중요] **적립이 골조 생성보다 먼저** 돈다 — 이번에 답한 것이 이번 프롬프트에 실린다
  - [중요] **`scope=once` 는 적립하지 않는다** — 그 골조에만 실리고 버려진다. 적립하면
    *"이번 스냅샷은 컴포넌트로"* 가 관계없는 다음 작업을 오염시킨다(사용자 지적 2026-08-11)
  - [주의] **방향이 반대다**: 물음(모델)은 결과로 **나가고**, 답(사람)은 요청으로 **들어온다.**
    타입이 갈라져 있어(`Question` vs `Heuristic`) 모델의 물음은 구조적으로 적립될 수 없다

[중요] **durable `task/<id>` 브랜치는 요청자(`.33`)가 만든다** — 마스터는 소스 저장소에 push 할 수
없다. 그 PC 가 꺼져 있으면 매니페스트의 기준 절이 *"원격에 아직 없다"* 로 남고, 워커는 (옳게)
`BLOCKED` 을 낸다. **파견 전에 브랜치가 있는지 확인한다.**

## 4. ③ dispatch — 추론 파견

```bash
.venv/bin/python -m master.work.infer probe ModularStage        # 누가 받을 수 있나 (큐 무접촉)
.venv/bin/python -m master.work.distribute dispatch ModularStage <work_id> 4
```

[중요] **워커는 커밋하지 않는다.** 읽고 추론해서 파일 본문을 **텍스트로** 답하고(`ax-infer` 스킬),
마스터가 그 응답을 스풀에 쌓는다. 적용·빌드·커밋은 통합자 한 대의 일이다.

[주의] **병렬은 기본값이 아니다** — 실측 2026-08-09: 워커 2대는 **12% 빠르고 90% 비쌌다**(캐시
생성이 워커별 고정비). 조각이 클 때만 `run-p` 로 켠다. 분산의 값은 **처리량이 아니라 증분**이다.

스풀 확인:

```bash
.venv/bin/python -m master.work.infer spool ModularStage <work_id>
```

## 4.5 ④ integrate — [중요] 여기가 **유일하게 쓰는** 단계다

```bash
.venv/bin/python -m master.work.integrate plan ModularStage <work_id>          # [중요] 먼저 본다
.venv/bin/python -m master.work.integrate run  ModularStage <work_id> task/<id>
```

**조각마다** 층1(무료·결정적) → 적용 → **UE5 빌드** → 통과하면 커밋, 실패하면 [중요] **되돌리고
커밋하지 않는다.** 첫 실패에서 멈춘다 — 적용 순서가 의존 순서라 앞이 깨지면 뒤는 헛일이다.

- [완료] **증분이 남는다**: 조각 3이 깨져도 1·2 는 이미 커밋됐고 그 상태는 컴파일된다
- [중요] **durable 브랜치를 주지 않으면 로컬 커밋까지만** 한다(그렇게 말한다). 요청자가 만든다
- [중요] push 는 **ff-only**. 거부되면 커밋은 격리 트리에 남아 있으니 **force 하지 말고** 사람에게
  보고한다
- 실측: 격리 트리 + 콜드 빌드 + 커밋 **159초**(빌드 142초). 두 번째부터는 증분이라 훨씬 빠르다

## 5. [중요] 판정을 사람에게 어떻게 보고하나

**"통과했다" 가 아니라 무엇으로 통과했는지**를 적는다. 이 파이프라인이 fail-closed 인 지점:

| | 통과 조건 |
|---|---|
| 골조 게이트 | `.2` 의 UE5 빌드가 `BUILD OK` |
| 추론 응답 | 마커 두 줄 + **대상 파일 전부** + 목록 밖 없음 + 펜스 없음 |
| 층1 (적용 직전) | 동결 위반 없음 + `[PSEUDO]`/펜스 잔재 없음. [주의] 기준 원본이 없으면 **동결 미검사** |
| 조각별 빌드 | `.2` 의 격리 트리에서 UE5 가 `Result: Succeeded` |
| (층2·층3 RunTests) | [대기] 아직 없다 — 중 2.2·2.3 |

[주의] **"빌드 통과" 는 "코드가 맞다" 가 아니다.** 실측상 **환각의 절반이 컴파일을 통과한다**(§4.3):
`Cast<IInteractable>` 직접 호출 · `IsValid()` 로직 오류 · `FText::FromString` 지역화 우회.
그것을 잡는 층2·층3(RunTests)은 **아직 없다** — 그때까지는 **사람이 본다.**

## 6. 막혔을 때

- **워커가 없다** → `probe` 가 사유를 말한다. `.43` 은 스마트플러그로 꺼져 있을 수 있고,
  `.33` 은 [중요] **요청자라 파견 대상이 아니다**(역할이지 도달성 문제가 아니다)
- **계획이 파일 겹침으로 막혔다** → 분해 대상을 다시 고른다. 같은 파일을 두 조각이 고치면
  두 워커가 같은 곳을 쓴다
- **응답이 BLOCKED** → 사유를 그대로 사용자에게 보인다. 스풀에 실패도 남아 있다
- **리스가 만료돼 태스크가 다시 집혔다** → 정상이다(제출은 통합자가 한다). [중요] 스풀에 같은
  기준 커밋의 응답이 있으면 **다시 사지 않고 재사용**한다
