# 31. 두 번째 프로젝트가 실제로 붙었다

## 1. 무엇을 했나

사용자가 Gitea 빈 저장소 신설을 승인하고 **NS**(Non-self · UE 5.8.1 · 쿼터뷰 TPS 패드 조작 ·
프로젝트 접두사 `NS`)를 만들어 push 했다. `#259` 의 **첫 실증**이고, 이 저장소에서 **두 번째
프로젝트가 처음으로 존재하게 된 순간**이다.

    서버 절   bare(Gitea API 신설) · register · clone(dcf315c) · graph(classes=61 files=87)  [완료]
              synth · index                                                                  [보류]
    클라 절   작업장 등재 3 · 클론 3 · 배달 3(rc=0) · 태그 3 · 클로드 3 · 이그노어 3          [완료]

[중요] **마운트는 옮기지 않았다.** `register_project` 는 「첫 프로젝트일 때만」 자동 마운트하고,
전환은 §12.5-b 의 되묻기 계약을 타야 한다. NS 는 등재만 됐고 활성은 ModularStage 그대로다.

## 2. [중요] 실증된 것 — 한 기계에 두 프로젝트가 공존한다

같은 `.2` 에서:

    NS 체크아웃            태그 NS            · 출처 마스터 HEAD 와 같다      OK
    ModularStage 체크아웃  태그 ModularStage  · 3 커밋 뒤 (재배달 필요)       FAIL

`.ax/config.json` 이 **체크아웃 안**에 있어 NS 배달이 ModularStage 설정을 덮지 않았다. 즉
`#229`(기계당 다중 프로젝트 경로 없음)의 걱정은 **config 축이 아니라 claimer 상주·홈 스킬 축**
이라는 것이 실측으로 갈렸다. 그리고 `check` 가 프로젝트별로 **다른 답**을 낸다 — ModularStage 가
뒤처짐으로 잡힌 것은 NS 만 재배달했으니 참이다.

[중요] **claimer 상주는 NS 에 켜지 않았다.** claim 에 프로젝트 축이 없어(`ClaimReq` 에 필드 없음 ·
`claimer.py:93` 이 값을 읽고도 `:119` 본문에 안 넣는다) 두 프로젝트의 claimer 가 동시에 돌면
**남의 태스크를 집는다.** 사용자 승인 순서 A→B 의 A 에서 지켜야 하는 조건이고, 그것을 지켰다.

## 3. 라이브 런이 잡은 함정 셋 — 유닛으로는 절대 안 나온다

### ⓐ Git LFS — 클론이 아예 실패한다

NS 의 `.gitattributes` 가 `*.uasset filter=lfs` 다. **로컬 bare 경로에서 클론하면 LFS 엔드포인트가
없어** `Smudge error: Error downloading …` 로 죽는다.

[중요] 그런데 **마스터는 그 바이트가 필요 없다** — `Content/**` 는 색인 제외이고 트윈의 범위는
source-only 다. `GIT_LFS_SKIP_SMUDGE=1` 로 포인터만 받아 트윈이 **11MB**(게임 저장소 137MB)로
끝났다. 파일 내용으로 포인터임을 확인했다.

[중요] **LFS 처리는 역할별로 갈린다** (이것이 이 함정의 진짜 내용이다):

    마스터        포인터   색인은 Source/ 뿐이다
    .2  worker    실물     UE5 빌드·에디터 자동화를 한다 → 134MB 받았다 (git-lfs 3.3.0)
    .43 worker    포인터   git-lfs **미설치** · UE5 없음 · 소스 판단만 한다 → 4MB
    .33 requester 실물     사람이 UE 로 작업한다 (사용자가 직접 만든 체크아웃)

[주의] ModularStage 는 LFS 를 쓰지 않아(매칭 0건) 이 함정이 여태 안 드러났다 — 그 클론은
`cp -a` 로 만들어졌다(§5.5.3-a). **첫 LFS 프로젝트가 첫 사고 지점이었다.**

### ⓑ 윈도우 소유권 — 사용자가 먼저 맞았다

사용자 보고: *"git status 에러 코드 128로 실패함 : fatal: detected dubious ownership"*.

원인을 **정상 저장소와 대조**해 확정했다:

    ModularStage\.git   DESKTOP-FU2GNGL\USER      ← 사람이 만들어서 정상
    NS\.git (클론 직후)  BUILTIN\Administrators    ← 마스터가 만들어서 깨짐

마스터의 SSH 세션이 관리자 권한이라 `git clone` 이 만든 `.git` 소유자가 `Administrators` 가 된다.
`.33`·`.2` **두 대에서 재현**했다. [중요] `safe.directory` 로 덮지 않고 `icacls /setowner` 로
**맞췄다** — 정상 저장소와 구분되지 않아야 한다. 덮으면 그 기계만 특례가 되고 다음 도구가 또 걸린다.

같은 자리에 함정이 하나 더 있다: **빈 저장소 클론은 로컬 브랜치가 `master` 로 잡힌다**(로컬 git
기본값). Gitea 기본과 우리 `config.yaml` 은 `main` 이라, 그대로 커밋하면 `master` 가 올라가
**설정과 실물이 어긋난다.** `git symbolic-ref HEAD refs/heads/main` 으로 교정했다.

→ 셋 다 `#254`(체크아웃 부트스트랩)에 옮겨 적었다.

### ⓒ 사실 게이트 오탐 — 새 UE 프로젝트마다 반복된다

최초 합성 4그룹 표본: **작성 1 · 사실게이트 거부 3**(통과 25%). ModularStage 기준선은 3/3 이다.
사유를 파일·행으로 확인하니 셋 중 **둘이 오탐**이었다:

    "All"       NS.h:1  `// Copyright Epic Games, Inc. All Rights Reserved.`   ← 저작권 헤더
    "GameMode"  NSGameMode.h:10  `*  Simple GameMode for a third person game`  ← 설명 주석
    "StateTree" CombatAIController.h:12 `* … capable of running StateTree`     ← 설명 주석

모델이 한국어 산문에서 쓴 **평범한 영어 낱말**을 *"주석에만 있는 식별자를 살아 있는 것처럼
서술"* 로 판정했다. 원인 위치는 `verify.py:31 _IDENT_RE`(3자 이상 영단어 전부를 식별자 후보로
본다) + `_NOISE` 에 저작권 헤더 낱말이 없는 것이다.

[주의] **셋 중 하나는 진짜 결함이다** — `CombatAIController` 는 *"실측 선언 클래스를 하나도
언급하지 않았다: ACombatAIController"*. 게이트 자체는 값이 있다. 문제는 **식별자와 서술어를
구분하지 못하는 것**이다. → `#270` 신설. 느슨하게 고치면 §4.3 의 「컴파일되는 환각」 방어가
약해지므로, 완료 조건에 *"2026-08-12 의 없는 enum 멤버 사례가 계속 거부돼야 한다"* 를 넣었다.

## 4. 합성을 보류한 이유 (사용자 결정)

지금 NS 소스는 **UE 5.8 기본 템플릿**이다 — 84파일 42그룹이 전부
`Variant_Combat`·`Variant_Platforming`·`Variant_SideScrolling` 이고, 사용자가 실제 게임 코드로
바꿀 것이다. **템플릿 문서는 곧 폐기되므로 지금 합성하지 않는다.** `#270` 을 고치고 실 코드가
들어온 뒤 돈다.

[주의] 합성 모델은 `gemma4:e4b`(BC-250 로컬)라 **돈이 들지 않는다** — 세션 중 내가 「LLM 비용」
이라고 말한 것을 정정했다. 드는 것은 시간(42그룹 ≈ 8~22분)과 보드 GPU 다.

## 5. 여기서 배운 것

1. [중요] **「첫 프로젝트에서 안 드러난 것」이 두 번째에서 전부 나온다.** LFS·소유권·브랜치 기본값·
   게이트 오탐 넷 중 **하나도** ModularStage 에서는 보이지 않았다. ModularStage 는 `cp -a` +
   원전 export 라는 **일회성 경로**로 채워졌기 때문이다 — 재현 가능한 절차가 없으면 함정도 안 보인다.
2. [중요] **함정은 도구가 아니라 환경에서 온다.** 셋 다 우리 코드의 논리 오류가 아니라
   *LFS 설정 · 윈도우 ACL · git 기본 브랜치* 였다. 유닛 3,900건이 이것을 잡을 방법은 없다.
3. [중요] **사용자가 먼저 맞은 오류를 그대로 재현해 원인을 갈랐다** — 「정상 저장소와 대조」가
   그 방법이었다. 추측(`safe.directory` 로 덮자)으로 갔으면 근본은 남았다.
4. [주의] **오탐을 고치는 일감에는 「기존 방어가 살아 있음」을 완료 조건으로 넣어야 한다.**
   게이트를 무디게 해서 오탐을 없애는 것은 고친 것이 아니다.
5. [주의] **역할별로 갈리는 것을 하나로 처리하려 하지 말 것.** LFS 를 「받는다/안 받는다」로
   정하려 했으나 실측은 셋으로 갈렸다(빌드 기계·판단 기계·마스터).
