## 8. git 조작 권한 — 사람 세션과 파이프라인을 분리한다 (2026-08-07)

**AgentTest 는 "Claude 는 절대 커밋하지 않는다(사용자가 시켜도 금지)"는 절대 규칙을 갖고 있다.**
계기는 2026-07-12 사고 — 사용자의 **"중간 커밋하고 올게"**(본인이 하겠다는 **1인칭 서술**)를
지시로 **오독**해 임의로 `git commit` 을 실행했고, 사용자가 "다 지워진 줄 알고 깜짝 놀랐다"고 항의했다.
결론은 "의도를 더 잘 판별하자"가 **아니라 판별을 포기하고 금지를 절대화**하는 것이었다.
`build.bat`/배포/데몬 재기동도 같은 형태로 묶여 있다("빌드할까요?" 같은 질문 형태조차 금지).

**⚠️ 그 규칙을 이 프로젝트에 그대로 복사하면 안 된다.** AgentTest 규칙이 막은 것은
**"개발 저장소에서 Claude 가 사람 대신 커밋하는 것"** 이지, **파이프라인이 설계대로 하는 git 조작**
(워커가 `task/<id>` 브랜치에 커밋, durable merge CAS)이 아니다. 후자는 plan v5.0 C.3 의 정상 동작이다.
**AX 클러스터는 마스터가 자율 오케스트레이션을 하므로 이 둘이 섞이기 쉽다** — 권한을 명시적으로 나눈다.

### 8.1 사람 세션 (Claude Code — 윈도우 오케스트레이터 ① / 마스터 작업 세션)

| 구분 | 규칙 |
|---|---|
| ✅ 요청 시 실행 | `add` · `commit` · `push`(일반) · `fetch`/`pull --ff-only` · 조회 계열 전부 |
| ❌ **실행 금지 — 되돌리기 어려움** | `push --force` · `reset --hard` · 브랜치/태그 **삭제** · `rebase` · 히스토리 재작성 · `clean -fdx` |
| 원칙 | 금지 항목은 **명령형 지시를 받아도 실행하지 않고**, 실행할 명령을 안내한다 |

- 이 저장소(`ax-cluster`)에 적용한다. **AgentTest 저장소는 참조용이라 애초에 커밋하지 않는다**
  — 그쪽 `CLAUDE.md` 의 절대 금지 규칙과도 일치한다.
- 1인칭 서술("~하고 올게", "~할게")을 지시로 읽지 말 것. 애매하면 되묻는다.

### 8.2 파이프라인 (윈도우 작업자 하네스 · 마스터 자동화 — 자율 실행)

**사람 세션 규칙의 적용 대상이 아니다.** 설계상 자율로 해야 하는 일이 있다.

| 구분 | 규칙 |
|---|---|
| ✅ 자율 허용 | `task/<task_id>` 및 attempt 브랜치 생성·커밋·push, `[FEEDBACK]` 커밋, durable merge(**CAS**) |
| ❌ **금지** | `main` 직접 push · `push --force` · 히스토리 재작성 · 사람이 만든 브랜치 삭제 |
| 필수 | **CAS(compare-and-swap)로만 durable 전진** — 좀비 워커 방어(plan v5.0 C.2). 모든 조작은 로그로 추적 가능해야 한다 |

- 작업 브랜치는 워커의 것이고, `main` 은 사람의 것이다. **이 경계가 두 규칙을 가르는 기준이다.**
- 오케스트레이터가 둘이므로 **같은 브랜치에 동시 접근이 실재한다**(§2.2-5) — fencing 을 걷어내지 말 것.

### 8.3 🔴 완료 신호를 믿지 말 것 — 산출물을 검증한다

**실측 사고 (2026-08-07, 마스터 리포트 04):** `agy` 에 "파일을 작성하라"고 지시했더니
`status:"SUCCESS"` + `response:"DONE"` 을 반환했는데 **파일이 어디에도 생성되지 않았다.**
원인은 print 모드가 기본적으로 편집 비활성이라 `--mode accept-edits` 가 필요했던 것 —
**작업은 무시되고 완료 신호만 온 것이다.**

AgentTest 가 이미 같은 계열 문제를 다루고 있다: `**TASK_COMPLETE**` 센티넬의 관대 인식,
`worker/validator.py` 의 제출 전 자기검증(`_frozen_decls`), `claude_spawn.syntax_check`.
**존재 이유가 이것이다 — 위임한 백엔드의 "완료" 주장을 그대로 믿으면 안 된다.**

**규칙: 위임 결과는 반드시 두 가지를 모두 확인한다.**
1. 반환된 상태(`status` / 종료코드 / 센티넬)
2. **산출물의 실제 존재와 내용** (파일 생성 여부, diff 적용 여부, 컴파일 통과 여부)

이 검증이 없으면 자동화에 **조용히 빈 결과가 흘러간다.** §4.3 의 3층 게이트가 층1 부터
결정론적 검사로 시작하는 것도 같은 이유다.

**⚠️ 산출물이 존재해도 부족하다 (2026-08-07 2차 실증, 리포트 05).** `agy` 에 Unreal MCP 리서치를
위임했더니 파일도 생겼고 내용도 80% 정확했는데, **설계 결정을 좌우하는 절이 틀렸다** —
"Bind Address 를 `0.0.0.0` 으로 바꾸면 LAN 접속 가능"이라며 4단계 절차까지 서술했으나
실제로는 서버가 non-loopback `Origin` 을 거부하고, 함께 제시한 `Require Capability Token`
설정은 **존재하지 않는 기능이었다.** 그대로 믿었으면 아키텍처가 틀어졌다.
또 "실제 참조 URL"을 명시 요구했는데 **도메인 루트만 반환**했다(검색을 안 한 신호).
**→ 위임은 초안 생성용으로 쓰고, 사실 확정은 1차 출처로 한다. 출처를 요구하고 그 출처를 열어볼 것.**

## 8.4 작업 브랜치 수명주기 — 1인 + N워커 (사용자 확정 2026-08-09)

> 사용자: *"기존 AgentTest 는 여러 명이 하나의 프로젝트를 관리하다 보니 git 버전 관리가
> 고민이었는데, 이제 단일 1명의 작업자이고 여러 대 워커가 도와주는 것"* /
> *"실패 처리를 위해 메인 작업 PC에서 시작할 때 원격 브랜치를 만들어야 할 듯"* /
> *"성공하던 실패하던 작업용 원격 브랜치에 커밋하고, 검증 요청이나 메인 작업 컴퓨터가 검증"*

### 누가 무엇을 만드나

| 주체 | 하는 일 | 왜 그 주체인가 |
|---|---|---|
| **요청자** (`.33`, 사람의 PC) | ① `main` 최신화 ② **durable `task/<id>` 를 만들어 원격에 push** ③ 등록 | 🔴 **마스터는 소스 저장소에 push 할 수 없다**(§2.1). push 권한이 있는 것은 사람의 체크아웃뿐이다 |
| **마스터** | 큐·매니페스트·라우팅 | 파일을 소유하지 않는다 |
| **워커** | `attempt/<id>/<workshop>/<ts>` 를 durable 에서 따서 작업 → **성공·실패 무관하게 push** | 파일을 소유한다 |
| **검증** | 층2(마스터) → 층3(`ue5` 워커) → 사람 승인 | 층3 이 최종 권위 |

### 🔴 실패도 커밋한다

**성공한 것만 push 하면 실패가 조사 불가능해진다.** 무엇을 시도했고 어디서 막혔는지가
사라지고, 피드백을 줄 근거도 없어진다. 그래서:

    성공 → attempt push → 검증 → 통과분만 durable 로
    실패 → attempt push → 사유와 함께 제출 → 피드백 → 같은 durable 에서 재시도

큐가 이미 그 형태를 받는다 — `submit(feedback=…, new_base_commit=…)` 의 주석이
*"revise 시 워커 브랜치에 feedback 주석 박은 새 HEAD — 다음 claim 이 이 commit 에서 체크아웃"*.

### 1인 체제라 덜어내는 것 / 그대로 두는 것

| | 팀 전제였던 이유 | 지금 |
|---|---|---|
| 작성자별 분리 (`reviews/<작성자>/`) | 팀원마다 리뷰가 섞임 | 🔴 **덜어낸다** |
| durable merge CAS | 팀원 둘이 동시에 머지 | **단순화** — 사람이 최종 승인, 층3 이 게이트 |
| **attempt 브랜치 격리** | 팀원 PC 가 여럿 | 🔴 **그대로** — 워커 머신이 2대라 충돌은 실재(리포트 06 §4.6) |
| **lease · epoch fencing** | 워커가 죽고 되살아남 | 🔴 **그대로** — 기계도 죽는다 |

⚠️ **`attempt` 를 "머지 후 폐기" 로만 보지 않는다.** 실패한 attempt 는 조사 자산이라
**즉시 지우지 않는다.** 정리는 사람이 판단한다 — 자동화가 브랜치를 지우는 것은 §8 금지 목록이다.

### 지금 없는 것

- 요청자 측 브랜치 생성·push (스킬 `ax-request` 에 절차는 적었으나 **자동 실행은 없다**)
- `register_work_tool(target_branch=…)` 이 값을 **저장만 하고 쓰지 않는다**
- durable ← attempt 승격 경로 (사람 승인 + 층3 통과 후)

### 🔴 피드백은 텍스트가 아니라 **코드 위치에 박는다** (사용자 확정 2026-08-09)

> 사용자: *"피드백을 골조처럼 코드 위치에 추가하고, 작업 워커를 할당해 해당 원격 브랜치
> 최신화 시도"*

골조가 `[PSEUDO]` 로 *"여기를 채워라"* 를 말하듯, 피드백은 `[FEEDBACK]` 으로 *"여기가
틀렸다"* 를 **같은 자리에** 말한다. 큐의 텍스트 필드만으로는 워커가 **어디를** 고칠지 모른다.

    ① 검증이 반려          → 대상 파일에 [FEEDBACK] 블록을 박아 commit + push
    ② 큐에 new_base_commit → 그 커밋을 다음 base 로 기록
    ③ 다음 claim           → 워커가 그 커밋에서 체크아웃 → 피드백이 **코드 안에 보인다**
    ④ 워커는 **수정**한다    → 재구현이 아니다

**원본이 검증한 형태 그대로다** — `mcp/master_orchestrator/verifier.py:85`
(*"worker 브랜치에 feedback 주석을 target_file 상단에 박아 commit + push"*),
`worker/verify_worker.py:9~11` (*"reject → durable 을 attempt 로 fast-forward(구현 누적)한 뒤
[FEEDBACK] 블록 commit … [FEEDBACK] 기준으로 **수정**(재구현 아님 — 누적 모델,
사용자 2026-06-21)"*).

🔴 **누적 모델이라는 점이 핵심이다.** 반려돼도 그때까지의 구현을 버리지 않고, 그 위에서
고친다. 그래서 실패한 attempt 도 push 되어야 한다 — 버리면 누적할 것이 없다.

**이식 상태:**

| | |
|---|---|
| ✅ **게이트** | `layer2_verify.py:46` 이 *"leftover `[PSEUDO]/[FEEDBACK]` placeholders"* 를 이미 검사한다 — 마커가 남은 코드는 통과하지 못한다 |
| ✅ **큐** | `submit(feedback=…, new_base_commit=…)` · `base_commit` 필드 |
| ❌ **박는 쪽** | `_embed_feedback_in_worker_branch` 상당이 없다 — 반려 시 `[FEEDBACK]` 을 파일에 써서 commit·push 하는 주체 |
| ❌ **durable ff** | 반려 시 durable 을 attempt 로 전진시켜 구현을 누적하는 경로 |

⚠️ **누가 박나는 아직 미정이다.** 마스터는 push 를 못 하므로(§2.1) 후보는 둘 —
**요청자(사람의 PC)** 또는 **검증을 수행한 `ue5` 워커**. 층3 을 돌린 쪽이 결과를 아는
주체이므로 후자가 자연스럽지만, 사람의 승인 전에 워커가 durable 을 움직이게 할지는
별도 결정이다.

### 🔴 durable 은 "빨리 머지할 것" 이 아니라 **오래 사는 작업 공간**이다 (사용자 확정 2026-08-09)

> 사용자: *"기존 AgentTest 와 달리 작업 요청자가 있으니 머지 단계가 나중이라 문제가 생길 일이
> 없이, 계속 작업용 원격 브랜치에서 모두 작업이 될 때까지 요청자와 대화식으로 피드백 요청이
> 가능할 듯"*

**이것이 AgentTest 를 복잡하게 만들던 압력을 없앤다.** 거기서는 팀원 여럿이 각자 결과를
`main` 쪽으로 밀어 넣으려 했기 때문에 **durable merge 를 빨리·안전하게** 하는 장치
(CAS·경합 방어·상용 모델 verdict 가 머지 권한을 가짐)가 필요했다.

우리는 다르다:

    task/<id>  ──▶ 워커들이 attempt 를 얹으며 **오래 산다**
                   요청자가 대화식으로 [FEEDBACK] 을 박고 재작업을 돌린다 (몇 번이든)
                   ▼
    main       ──▶ 🔴 **다 됐을 때, 사람이, 한 번** 머지한다

| | AgentTest (팀) | 여기 (1인 + N워커) |
|---|---|---|
| 머지 시점 | 태스크마다 즉시 durable 로 | **끝에 한 번**, `main` 으로 |
| 머지 권한 | 상용 모델 verdict → CAS | **사람** (층3 이 게이트) |
| 경합 | 팀원 간 실재 | 🔴 **없다** — 미는 주체가 하나다 |
| 피드백 | 워커↔검증자 자동 왕복 | **요청자와 대화식**, 횟수 제한 없음 |

**그래서 `verify_worker.py`(314줄)의 CAS·durable merge 권한 이전은 이식하지 않는다.**
리포트 08 §15.2 가 이미 *"이식 대상이 아니라 재설계 대상"* 으로 분류했는데, 재설계의 답이
여기서 나왔다 — **그 장치 자체가 필요 없어진다.**

#### ✅ 미정이던 것이 풀린다 — `[FEEDBACK]` 은 **요청자가 박는다**

앞 절에서 *"요청자냐 층3 을 돌린 워커냐"* 를 미정으로 남겼는데, 요청자가 루프 안에 상주하며
대화식으로 판단하므로 **요청자가 박는 것이 맞다.** 워커가 사람 승인 전에 브랜치를 움직이는
경로를 만들 이유가 없어진다.

    검증 결과 → 요청자에게 보고 → 사람이 판단 → 요청자가 [FEEDBACK] 을 박고 재작업 요청

⚠️ **여전히 남는 경합 하나**: 워커 2대가 **같은 파일**을 만지는 태스크를 동시에 받으면
durable 로 얹을 때 충돌한다. 클래스 단위 분해가 파일을 가르므로 보통은 안 겹치지만,
**분해가 파일 경계를 지키는지는 분해기(§4.5)의 책임**이다 — 거기서 보장해야 한다.

### 층3(컴파일) 을 어디서 도나 — **요청자가 가장 빠르다** (사용자 확정 2026-08-09)

> 사용자: *"컴파일 에러는 작업 요청한 클로드쪽에서 바로 알 수 있을 것 같아."*

맞다. `.33` 은 **UE5 가 설치된 사람의 메인 작업 PC** 다. 워커에게 왕복하지 않고 **요청자가
바로 빌드해 에러를 본다** — 대화식 피드백 루프에서 가장 짧은 경로다.

| 위치 | 층3 가능 | 성격 |
|---|---|---|
| **`.33` 요청자** | ✅ | **사람이 직접·즉시.** 피드백 루프가 가장 짧다 |
| **`.2` 워커** | ✅ | 마스터가 SSH 로 몰 수 있다(실측 완료 — 리포트 08 §8.2·§10). 무인 배치용 |
| **BC-250 워커** | ❌ | 툴체인 없음 |

즉 **빠른 반복은 요청자가, 무인 검증은 `.2` 가** 맡는다. 둘은 배타가 아니다.

#### ⚠️ 함정 — 요청자의 워킹트리는 **사람이 쓰던 트리다**

durable 브랜치를 빌드하려면 그 브랜치를 체크아웃해야 하는데, **거기엔 사람이 편집 중이던
것이 있을 수 있다.** 브랜치를 갈아타면 그게 날아가거나 섞인다 — 더티 체크가 막으려던 바로
그 사고이고, `.uasset` 은 되살릴 수 없다.

🔴 **그래서 요청자는 자기 메인 트리에서 브랜치를 갈아타지 않는다.** 대신:

    git worktree add ../ModularStage-task-<id> task/<id>

**별도 워킹트리**를 만들어 거기서 빌드한다. 사람의 트리는 손대지 않고, DDC·Binaries 는
재생성 비용이 있지만 **사람의 미커밋 작업을 날리는 것보다 훨씬 싸다.**

⚠️ 미측정: UE5 프로젝트에서 worktree 를 쓸 때 DDC/Binaries 재생성이 실제로 얼마나 드는지.
`.2` 에서 기존 체크아웃 재사용을 택한 이유가 그 비용이었다(§5.5.4-⑥, 콜드 빌드 수십 분 예상).
**요청자에게 이 방식을 강제하기 전에 한 번 재 볼 것.**

### 8.5 워커 git 인증 — Gitea SSH 키 (2026-08-09 확보)

🔴 **이것이 §8.4 루프 전체의 선결이었다.** 워커가 durable 브랜치를 fetch 하고 attempt 를
push 해야 하는데, **두 대 모두 Gitea 에 접근하지 못했다**(실측):

    .2  (janus)  Git Credential Manager 가 대화형 프롬프트 → SSH 세션에서 실패
    .43 (BC-250) ksshaskpass 사망 — 자격증명 없음

Gitea 가 `REQUIRE_SIGNIN_VIEW = true` 라 **public 저장소인데도** 익명 클론이 안 된다.

**선택: HTTP 토큰이 아니라 Gitea SSH 키.** 셸을 주지 않고 **git 만** 주며, 워커에 새 비밀
파일을 심지 않는다(이미 있는 SSH 키를 쓴다). `docs/2-architecture.md` §2.2-a 가 걱정한
*"노드에 자격증명을 심으면 재구축이 어려워진다"* 도 덜하다.

    gitea@192.168.0.57:Sim/ModularStage.git

#### 🔴 함정 — Gitea 의 `HOME` 과 sshd 가 보는 홈이 다르다

키를 API 로 등록하면(`POST /api/v1/user/keys`, 201) Gitea 가 `authorized_keys` 를 쓰는데,
**systemd 유닛이 `HOME=/var/lib/gitea`** 라 거기에 쓴다. 반면 **sshd 는 `gitea` 계정의
passwd 홈인 `/home/gitea`** 를 본다. 두 경로가 어긋나 **키는 등록됐는데 인증은 계속 거부**된다.

    Environment=USER=gitea HOME=/var/lib/gitea     ← 유닛
    getent passwd gitea → /home/gitea              ← sshd 가 보는 곳

**조치(가장 덜 침습적):** 심볼릭 링크. `usermod` 도 `sshd` 재시작도 하지 않는다.

    ln -sfn /var/lib/gitea/.ssh /home/gitea/.ssh && chown -h gitea:gitea /home/gitea/.ssh

`StrictModes`(기본 yes)를 통과한다 — 경로상 디렉토리가 전부 `drwxr-x--- gitea:gitea` 이고
키 파일은 `-rw-------` 다. 되돌리기: `rm /home/gitea/.ssh`.

**검증(실측):**

| | |
|---|---|
| `ssh -T gitea@192.168.0.57` (양쪽) | *"successfully authenticated with the key named ax-worker-N, but Gitea does not provide shell access"* — 원하던 상태 그대로 |
| `git ls-remote origin HEAD` | `.2`·`.43` 둘 다 `bc4b38f` |
| `git push --dry-run origin HEAD:refs/heads/…` | `.2` **`[new branch]`** ✅ |

⚠️ **Gitea API 토큰은 해시로만 저장되어 DB 에서 복구할 수 없다.** 새로 발급한다:
`gitea admin user generate-access-token --username Sim --scopes write:user,write:repository`.
발급본은 `~/.config/ax-cluster/gitea-token`(0600) — 🔴 **저장소에 넣지 않는다.**
