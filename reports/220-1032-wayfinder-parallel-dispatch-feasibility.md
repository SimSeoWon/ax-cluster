# 220 — Redmine 티켓 발주·의존 없는 노드 병렬 진행은 가능한가 (#1032, #1008 첫 노드)

> 2026-11-27 · Redmine `#1032`(#1008 맵의 프리필 노드) · 마일스톤 8 — 개선·확장 · 분류 검증 · 작업 브랜치 `issue/1032` · 시작 `de79cdc`

## 1. 무엇을 쟀나

#1008 목적지(사용자 정정 2026-11-27): **Redmine 노드 일감(스펙·플랜 영역과 노트)이 작업 지시서가 되어, 웨이파인더 의존 그래프에서
기다릴 필요 없는 노드(서로 선행 없는 Frontier)를 등록된 워커들에 발주해 병렬로 진행한다.** 브랜치·main 적용은 안개다.

사용자의 발상: 지금 분산 작업은 마스터·`.33` 이 실제 파일을 만들고 주석(`[DOC]`/`[PSEUDO]`)으로 설계도를 적어 워커에 준다.
Redmine 이 「명세서를 적을 완벽한 자리」가 됐으니 티켓으로 발주하면 다른 컴퓨터들이 분산작업 하기에 더 맞지 않을까(1번),
의존 그래프상 대기할 일이 아니면 등록된 워커로 병렬 진행이 가능할까(핵심). 순서는 웨이파인더 1차 → 그 결과로 분산작업 개선.

이 노드는 그 전제 일곱(Q1~Q7)을 코드 검사·웹 리서치·임시 저장소 실험·더미 프로토타입으로 재서 「가능 / 조건부 / 막힘」으로
판정했다. 판정 기준은 재기 전에 명세 노트로 적었다. 운영 코드는 고치지 않았다.

[주의] 처음에는 목적지를 「기존 분산 작업 경로(골조 파일)로 보낸다」로 잡았다가 사용자에게 정정받았다 — 조사·명세·파급을
다시 기록했다(인터뷰 노트).

**요약 — 가능성은 보인다.** 병렬 실행 자체(Q6)와 지시서 내용(Q2)은 된다. 막는 것은 둘이고 둘 다 **우리가 일부러 정한 경계**다:
워커는 Redmine 을 못 읽는다(Q1 · κ.0) · 한 번에 한 일감(Q4 · #883). 나머지(Q3·Q5·Q7)는 이미 있는 표면에 자리를 더하는 일이다.

## 3. 웹 리서치 (README 기준 — 독립 검증 안 함)

- 같은 모양의 도구가 여럿 있다 — 티켓 하나 ↔ worktree·브랜치 하나, 의존 그래프에서 병렬 가능한 것을 골라 발주, 끝나면 머지:
  [git-parsec](https://docs.rs/git-parsec/) · [ticks](https://pkg.go.dev/github.com/pengelbrecht/ticks@v0.8.0) ·
  [Retasc](https://mcpservers.org/servers/retasc-com) · [tasq](https://dev.to/version1/introducing-tasq-an-ai-native-task-orchestrator-for-coding-agents-506c).
- 병렬 발주의 공통 모양: 준비된 집합을 한꺼번에 발주 → 끝날 때마다 새로 풀린 것을 더함 + **작업별 claim** + **워커별 동시 상한**
  ([task-graph-mcp](https://docs.rs/crate/task-graph-mcp/0.1.2/source/README.md) · [arXiv 2604.22446](https://arxiv.org/pdf/2604.22446) ·
  [open-multi-agent](https://raw.githubusercontent.com/JackChen-me/open-multi-agent/master/docs/task-scheduling.md)).
- 쌓인 브랜치는 의존 순서대로 머지하고, 부모가 바뀌면 자식을 재정렬해야 한다
  ([GitHub stacked PRs](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs) ·
  [Graphite](https://graphite.com/guides/understanding-and-managing-stacked-branches-in-git)).
