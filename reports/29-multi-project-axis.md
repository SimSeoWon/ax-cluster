# 29. 「새 프로젝트를 어떻게 붙이나」 — 축을 열고 자리를 만들었다

## 1. 출발 — 잃었다가 되찾은 질문

사용자(2026-08-21, 재확인 08-22): *"새로운 프로젝트를 서버에서 관리할 때 각 워커랑 메인 작업 PC
를 어떻게 설정할지 레포에 저장되어있어? **하나의 프로젝트에 디펜던시 되지 않는 형태로.**"* 그리고
더 좁게: *"지금까지 SSH 로 단일 프로젝트 기준으로 대충 작업해서, 다른 프로젝트를 추가할 때
**워커와 메인 작업 컴퓨터에 프로젝트의 레포를 설치하고 인프라 컴퓨터와 작업할 수 있도록 설정하는
부분**에 대한 처리가 전혀 관리가 안 되어 있고 프로젝트에 종속된 형태로 의심되어서 일감 정리한 거야."*

[중요] **첫 착수 순서가 그 출발점을 맨 뒤(11번)에 뒀다.** 근거는 *"막을 수 있는 것을 먼저
막는다"* 였는데, 사람 결정이 선결인 것은 `#230` **전체가 아니라 mcp.json 갈래뿐**이었다. 그것이
오독이고, 사용자가 두 번 바로잡아 줬다. **막을 것을 먼저 막는 것과 본론을 미루는 것은 다르다.**

## 3. 확정 다섯 — 전부 사용자 결정 (`docs/12` §12.5-a~e)

    a  설치는 여럿, 작업은 마운트된 하나 — [중요] **거절 주체는 마스터**다. 워커가 무엇을 들고
       있는지로 판정하지 않으므로 강제가 **한 곳**에 산다
    b  전환은 **되묻는다** — 정리 대상을 이름으로 돌려주고 승인을 받는다.
       [중요] 자동 정리(금지) · 단순 거절(지금 = 절반) · 되묻기(확정) 셋을 구분했다.
       선례를 따랐다: `finalize_work(confirm=False)` 가 「멈추고 명령을 돌려준다」다
    c  요청은 태그를 담고 마스터가 **대조한다** — 빈 태그도 거절(fail-closed) ·
       형태는 **200 + ok:false + 사유**
    d  초기화는 **이 저장소의 코드 + SSH 배포** — 런북은 대체물이 아니라 그 코드의 설명서
    e  `client/` 를 실물로 — 기준은 **어디서 도는가**. `master/` 는 이 인프라 서버다

[중요] **c 에서 방향이 반대였다는 것이 드러났다.** `context_search/paths.py:150 resolve(name)` 은
`name` 이 있으면 **`reg.active` 를 아예 보지 않는다.** 그래서 지금 태그를 담아 보내면 마스터는
그것을 **검사하지 않고 따른다** — `task_queue/server.py:430` 별칭 등록이 `resolve(req.project or "")`
라서 **비마운트 프로젝트의 트윈에 그대로 써진다.** 거절 함수(`resolve_mounted_only`)는 호출자 0
이고 그 함수조차 `active` 가 비면 통과한다. **태그가 강제가 아니라 우회의 열쇠였다.**

[주의] **거절 형태를 409 로 하지 않은 이유는 실측이다** — `ax-client` 는 [미연결] 시 지난
스냅샷으로 폴백하도록 되어 있어 **거절을 장애로 오인해 낡은 결과를 돌려준다.** 그리고 이
저장소에 이미 관례가 있다: *"거부도 200 + ok:false 로 말한다. 조용히 무시하면 사용자는 등록된 줄
안다"*(`server.py:426`).

## 5. `#262` — 한 값이 두 뜻을 겸하고 있었다 (커밋 `30d5ed0`)

`PAYLOAD_BY_ROLE` 의 항목 하나가 *저장소에서 읽을 위치*와 *클라에 놓일 위치*를 동시에 뜻해,
**저장소에서 파일을 옮기면 배달 위치가 따라 움직였다.** 배달 위치는 함부로 못 바꾼다 — `.33` 의
`.mcp.json` args 가 그 값이고, `.2` schtasks·`.43` cron 이 `axmaster.work.claimer` 로 상주를 부른다
(`work/claimer.py:27-28`).

`(배달, 저장소)` 쌍으로 갈랐고 순서는 **`workshop_files()` 관례에 맞췄다** — 한 파일에 관례가
둘이면 다음에 갈린다. 동작 불변을 **기준선 파일 `diff`** 로 확인했다(배달 위치·`payload_dirs`·
`.mcp.json` args 글자까지 동일).

[주의] 자체 검토에서 둘을 고쳤다 — 블록 주석이 순서를 **반대로** 적고 있었고, 경로 목록을
`_MIRROR` 로 **한 벌 더** 두려 했다(오타는 `payload_text` 와 테스트가 이미 잡으므로 막아 주는
게 없고, `#232` 의 하드코딩 드리프트와 같은 모양이었다).

## 6. `#263` — 이동이 **조용한 실패**를 드러냈다 (커밋 `9959c88`)

사용자 결정 ⓒ: **claimer 사슬은 `master/work/` 에 남긴다.** 근거는 실측이다 — `claimer` →
`build_local` → `layer3_verify` 인데 그 `layer3_verify` 를 **마스터도 쓴다**
(`integrate.py:423,486` 의 `__import__("master.layer3_verify")` — **정적 grep 에 안 걸린다**).

옮긴 것은 `client_mcp.py`·`ontology_cache.py` 둘. `payload_text()` 의 기준을 `master/` →
**저장소 루트**로 바꿨다.

[중요] **그리고 이 세션이 결함 하나를 넣었다.** `vector_fallback.py` 가
`from ..context_search import embedding` 으로 마스터의 임베더를 올려다보는데, `client/runtime/` 으로
옮기자 `client.context_search` 를 찾다 실패했다. 그 실패를 `except Exception` 이 삼켜
`available=False` 가 되고 — **테스트가 검사 9개를 건너뛰고 「통과」로 보고했다.** 분모가 33→24 로
줄어서야 보였다.

원인: 앞서 상대 import 를 잰 셋(`client_mcp`·`ontology_cache`·`claimer`)에 **이 파일이 없었다** —
배달 목록에 없어서 대상에서 빠졌다. **배달 여부와 의존은 다른 축인데 하나로 봤다.**

    · vector_fallback.py → master/context_search/   배달 안 되고 호출자 0, 마스터 임베더를 쓴다
    · 건너뜀 두 자리를 시끄럽게                     chromadb 부재만 용인, 그 밖의 사유는 실패
    · master/README.md:46 의 「client/vector_fallback.py」는 리포트 28 이 적발한 **없는 경로**였다

테스트 **3737/3737 · 실패 0**. 그리고 [중요] **전 파일 분모를 HEAD 와 1:1 대조**(형식 A·B 모두)해서
감소 0 을 확인했다 — 합계만 보면 이 부류를 놓친다.

## 7. 여기서 배운 것

1. [중요] **출발점을 잃지 않는 것이 순서의 첫 조건이다.** 「막을 수 있는 것을 먼저 막는다」는
   옳은 원칙이었지만, 그것으로 본론을 뒤로 보냈다. 사람 결정이 선결인 것이 **축 전체인지 갈래
   하나인지**를 봐야 했다.
2. [중요] **한 값이 두 뜻을 겸하면 재배치가 계약을 끌고 간다.** 배달 위치는 다른 기계의 설정
   파일과 상주 등록이 가리키는 값이라 **저장소 사정으로 움직여선 안 된다.** 가르는 것이
   이동의 선결이었고, 그 순서를 지켰기에 `.2`·`.43` 이 안 죽었다.
3. [중요] **배달 여부와 의존은 다른 축이다.** 목록(`PAYLOAD_BY_ROLE`)을 대상 집합으로 쓰면
   목록 밖 파일이 조용히 깨진다. **디렉토리 전수로 재야 한다** — `#264` 에도 같은 함정이 있다.
4. [중요] **`except Exception` + `available=False` 는 테스트를 침묵시킨다.** 실패가 「기능 없음」
   으로 번역되면 검사가 사라지고 「통과」가 보고된다. **분모를 대조하지 않으면 안 보인다.**
5. [주의] **관례는 세기 전에 찾는다.** `(배달, 저장소)` 순서를 `workshop_files()` 가 이미
   정해 두었고, 나는 반대로 쓴 뒤 고쳤다. 200+ok:false 도 이미 있던 관례였다.
