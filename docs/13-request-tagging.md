# 13. 요청 태그 — 어느 프로젝트의 요청인가

> [중요] **이 문서는 기능 하나의 정본이다.** 결정의 경위는 [`12-multi-project.md`](12-multi-project.md)
> §12.5-c, 격리 규약은 [`5_5-project-isolation.md`](5_5-project-isolation.md) §5.5.3-③,
> 진행·항목은 **레드마인만**. 여기엔 **계약과 배선**만 적는다.
>
> 코드 정본: [`master/task_queue/tagging.py`](../master/task_queue/tagging.py) ·
> 테스트: `master/test_tagging.py`

## 13.1 왜 표 하나인가

사용자 요구(2026-08-22): *"기존에 서버랑 통신하는 부분들 모두 태그 추가해. 그래서 무슨
프로젝트의 요청인지 알 수 있잖아"*.

[중요] **엔드포인트마다 `if` 를 뿌리면 다음에 추가되는 엔드포인트는 태그가 없다.** 실측이
그랬다 — `#243` 이 시소러스 둘만 배선하고 `signals`·`history`·`claim` 을 남겼다. 같은 병이
유닛에도 있었다: `ax-task-queue.service` 에 **프로젝트 이름이 박혀** 있어 표면을 늘릴 때마다
손으로 경로를 추가해야 했고, 그래서 `ontology/` 가 빠져 시소러스 대행이 **처음부터 500**
이었다(`#276`).

그래서 선언은 한곳(`tagging.py`)이고, **선언 없는 라우트가 생기면 테스트가 깨진다.**

## 13.2 네 정책

    OPEN    프로젝트 축이 없다 (건강·상태·관리자)        태그를 받지도 않는다
    TAG     귀속·필터만 — 트윈에 쓰지 않는다             거절하지 않는다
    MOUNT   요청자가 태그를 고른다 → **마운트와 대조**    다르거나 **없으면** 거절
    STAMP   큐가 등재 시 스탬프한 값으로 푼다 (`#210`)   태그는 **대조만** 한다

[중요] **`MOUNT` 와 `STAMP` 를 가르는 것이 이 표의 핵심이다.** `#210` 이 *"활성이 아니라 work 의
스탬프로 푼다"* 를 정한 이유는 **미종결 work 를 둔 채 활성을 바꿨을 때 산출물이 원래
프로젝트로** 가야 하기 때문이다. `STAMP` 표면에서 마운트를 강제하면 `#210` 을 깨뜨린다 —
거기서는 태그가 **스탬프와 어긋났는지**만 본다.

같은 이유로 **마스터 쪽 발신자는 필수 표면에만** 태그를 붙인다(`tagging.requires_tag`).
전부에 붙이면 다른 프로젝트의 미종결 work 를 만지는 흐름이 `project_mismatch` 로 막힌다.

## 13.3 태그가 **필수**인 표면 — 사유에서 도출됐다

사용자 결정(2026-08-22): *"태그 없으면 동일하게 마운트 다름으로 처리해야지 그러다가 엉뚱한
데이터로 오염되는거잖아"*.

[중요] 그 **사유**(오염)에서 범위가 스스로 정해진다 — 오염 경로는 **태그가 없어 마운트로
「가정」하는 자리**다:

    쓰고 · 마운트로 푼다   → **필수**   태그가 없으면 가정이 된다 (여기가 오염 경로다)
    쓰고 · 스탬프로 푼다   → 선택      스탬프가 판정한다 — 가정이 아니다 (`#210`)
    읽는다                 → 선택      오염이 없다. 태그는 필터로만 쓴다

필수 목록(`tagging.REQUIRE_TAG`): `POST /works` · `POST /tasks/claim` ·
`POST /workers/{id}/poll` · `POST /thesaurus/alias` · `POST /thesaurus/not-a-class`.

[주의] `POST /history`·`/signals` 는 목록에 **없다** — `work_id` 가 있으면 스탬프로 풀리고,
없으면 서버가 조건부로 필수를 건다.

## 13.4 거절 — 형태 하나, 사유 셋

    no_project_tag     태그를 안 보냈다            → 고칠 곳: **발신자 배선**
    not_mounted        다른 프로젝트다              → 고칠 곳: **마운트 전환**
    project_mismatch   이 work 의 스탬프와 다르다    → 고칠 곳: **요청자의 착각**

[중요] **사유를 가른 이유는 고칠 곳이 다르기 때문이다.** 하나로 뭉치면 배선 버그와 운영
상황을 구분할 수 없다.

[중요] **형태는 전부 `200 + ok:false + 사유`** 다 — 4xx/5xx 가 아니다(§12.5-c 확정).
`ax-client` 는 [미연결] 시 지난 스냅샷으로 폴백하므로 **거절을 장애로 오인하면 낡은 결과를
정답처럼 돌려준다.** `500` 은 더 나쁘다: 사유가 없다.

[주의] **계약은 양쪽이 지켜야 성립한다.** 서버가 옳게 말해도 받는 쪽이 상태 코드만 보면
거절을 성공으로 읽는다 — 실측: `claimer.claim()` 이 `st == 200` 만 봐서 거절 응답을 태스크로
착각했고, 그것이 §13.6 사고의 실행자였다.

## 13.5 보내는 쪽 — 관문마다 한 번

    master/work/runner.py     `_tag()` → `_api` (review 가 이것을 재사용한다)
    master/work/selftest.py   `_q` 안에서
    master/work/buildjob.py   `enqueue(project=…)` — [중요] **인자로 받는다**
    master/work/register.py   work·task 양쪽에 `paths.name`
    master/work/claimer.py    `_call` 에서 (배달되는 코드 — 체크아웃은 단일 프로젝트다)
    client/runtime/client_mcp.py  `queue_api` — POST 본문 + **GET 은 쿼리로**

[중요] **도구마다 넣게 하면 다음 도구는 또 빠진다.** 그래서 관문에서 붙인다.

[주의] `buildjob` 은 안에서 환경(`AX_PROJECTS_ROOT`)을 읽게 만들었더니 `api=` **주입 이음을
우회**했고 유닛 하나가 그것을 잡았다. 프로젝트를 인자로 받는 것이 옳다 — 이 함수는 어느
프로젝트의 빌드인지 알아야 한다.

## 13.6 [중요] 순서가 계약이다 — 어겨서 사고가 났다 (2026-08-22)

§12.5-c 가 이미 이렇게 적어 뒀다: *"판단이 클라이언트보다 앞서면 태그 없는 요청이 전부
거절되고, 클라이언트가 서버보다 앞서면 서버가 모르는 인자를 받는다."*

    22:38  서버를 조였다
    22:40  .43 상주가 시작 — **옛 코드**(태그 안 보냄) → 거절 → 거절을 태스크로 읽음
           → 빈 task_id 로 submit-fail 무한 반복. 로그 4.4MB · 큐 저널 44,343줄
    22:55  배달
    23:01  상주 재기동(cron 감시자) — 정상. 최근 120초 거절 0건 · 204 12건

큐 상태·감사 파일 피해는 없었다(빈 `task_id` 는 상태에 닿기 전 거부).

[중요] **`.2` 는 우연히 살았다** — 그 상주가 배달 뒤에 떠서 새 코드였다. 우연이 방어였다.
→ `#277`(배달이 상주 프로세스를 갱신하지 않는다). 확인은 **파일 해시가 아니라 도는
프로세스**로 한다 — 이번에 파일은 이미 맞았는데 사고가 났다.

**규칙: 발신자 배달이 서버 조임보다 먼저다. 그리고 배달 뒤에는 상주를 다시 띄운다.**

## 13.7 숨은 선결 — 스탬프 백필 21건

`work_id` 만 있는 요청은 스탬프가 없으면 결국 마운트로 떨어진다. 태그를 필수로 만들어도 남는
오염 경로다. 21건 전부 `target_repo` 가 ModularStage 를 가리키고 최후 생성이 2026-08-19
(NS 는 08-22 신설)라 근거가 확실했다. 그중 3건은 `project: null` 이었고, 원인은 `buildjob` 이
`target_repo` 를 **하드코딩**하고 `project` 를 안 보낸 것이었다. **지금 25/25.**

[주의] 백필 도중 「디스크 7건 vs API 4건」 불일치를 「저장했는데 안 읽는 값」으로 의심했으나,
`project: null` 을 내 정규식이 스탬프로 센 것이었다 — **불일치를 발견하면 계측기를 먼저
의심할 것.**

## 13.8 claim 의 프로젝트 축 (`#248`)

큐가 후보를 **work 스탬프**로 거른다. 스탬프가 **있고 다를 때만** 건너뛴다(스탬프 없는 옛
work 는 계속 후보 — `_paths_for` 와 같은 호환 규칙). 걸른 건수는 로그로 **읽는다**(세고 안
읽는 값을 만들지 않는다).

[중요] **이로써 한 기계에 두 프로젝트의 claimer 상주를 켤 수 있다** — `#251`·`#255` 가 걸어
둔 전제 조건이 풀렸다. 잠금은 체크아웃 단위이고 큐는 공유이지만, 이제 큐가 프로젝트로 거른다.
