# 12. 다중 프로젝트 운영 — 무엇이 갈려 있고 무엇이 안 갈려 있나

> [중요] **항목과 진행은 레드마인만 쓴다** (사용자 2026-08-22). 이 문서는 **설계와 결정**만 든다 —
> 개수·진행률·「몇 개 중 몇 개」를 여기 적지 않고, `docs/milestones/` 도 쓰지 않는다.
> 그 수치는 M2 에서 두 번 어긋났고, 어긋난 수치는 읽는 사람의 판단을 바꾼다.

## 12.1 출발 — 질문 하나

사용자 2026-08-21: *"새로운 프로젝트를 서버에서 관리할 때 각 워커랑 메인 작업 PC 를 어떻게
설정할지 레포에 저장되어있어? **하나의 프로젝트에 디펜던시 되지 않는 형태로.**"*

§5.5 가 프로젝트 격리를 설계했고 그 결정(*"런타임은 1개, 레이아웃은 N개"*)은 지금도 옳다.
§5.5.5 는 **요청 단위 라우팅과 프로젝트별 분리를 「두 번째 프로젝트가 실제로 생길 때」로
미뤘고**, 그 판단도 옳았다 — 디스크에 쌓이는 것만 먼저 정하고 순수 코드는 나중에 쓴다.

**그 「두 번째 프로젝트」가 지금이다.** 이 문서는 그때 할 일의 지도다.

## 12.2 실측 — 갈린 것과 안 갈린 것 (2026-08-21~22)

| 축 | 상태 | 근거 |
|---|---|---|
| 트윈 데이터 (디렉토리·색인·온톨로지) | [완료] **갈렸다** | `context_search/paths.py:150` `resolve()` 가 **매 호출 레지스트리를 읽는다** — 마운트가 바뀌면 다음 호출이 새 경로를 본다 |
| 검색 | [완료] **갈렸다** | `search_context_tool(query, limit)` 에 **프로젝트 인자가 없다** — 늘 활성만 본다. 다른 프로젝트를 뒤질 방법이 도구에 없다 |
| 등록·전환 도구 | [완료] **있다** | `register_project_tool` · `set_active_tool`(+미종결 work 거부 가드) |
| 큐의 귀속 스탬프 | [완료] **있다** | `WorkRegisterReq.project` → `server.py:140-142` 가 그 값으로 트윈을 푼다 |
| **마운트 강제** | [실패] **없다** | `resolve_mounted_only()` 프로덕션 호출자 **0** — §12.4 |
| **색인기의 마운트 인식** | [실패] **없다** | 등록만으로 대상이 된다. `process_event` 가 `active` 를 안 보고, 빈 스풀 폴링이 `reg.names` 전부를 돈다 |
| **claim 의 프로젝트 축** | [실패] **없다** | `claimer.py:115-119` 본문이 `{worker_id, types}` 뿐. 워커는 값을 갖고도 신고하지 않는다 |
| **기계당 다중 프로젝트** | [실패] **경로가 없다** | `.ax/config.json` 은 프로젝트 단일값 · claimer 상주는 기계당 하나 |
| **클라이언트 설치물** | [실패] **프로젝트·기계에 묶여 있다** | `workshop/` 은 `.33` 디스크 스냅샷(그 README §3 이 *"정본이 아니다"* 라고 적었다) · `mcp.json` 11종 중 `ax-client` 하나만 안 묶였다 · `mcp.json` 은 **배달되지 않는다** |

[중요] **요약하면 마스터의 「읽는 쪽」은 갈렸고, 「시키는 쪽」과 「설치하는 쪽」이 안 갈렸다.**

## 12.3 네 축과 순서 — 항목은 레드마인

    #231  전환이 성립하는가        마운트 강제 · 색인기 · 워터마크 · 워커 재배달 고지
    #228  워커 매칭               claim 에 프로젝트를 실어 큐가 거른다
    #229  기계당 다중 프로젝트    [중요] 허용 여부 결정이 본체다 — 워커 쪽 규약의 빈칸
    #230  클라이언트 설치물        mcp.json 생성 · 원전 exe 처분 · 템플릿화

각 부모의 소분류와 완료 조건은 레드마인에 있다. **여기에 옮겨 적지 않는다** — 두 벌이 되면 갈린다.

**순서 논점**: 처음에 `#231 → #228 → #229 → #230` 으로 잡았다(전환이 성립하지 않는 상태에서
워커 매칭을 만들면 마스터가 가리키는 것과 워커가 든 것이 어긋난 채 판단 로직만 는다).
그런데 §12.2 마지막 행을 보면 **#230 이 「신규 프로젝트 등록」의 입구**다 — 클라이언트에 설치할
것이 정해지지 않으면 전환이 성립해도 그 프로젝트로 일할 기계가 준비되지 않는다.
**순서는 사람이 정한다** (`CLAUDE.md`: *"Do not pick the next task yourself"*).

## 12.4 [중요] 이 문서가 정정하는 거짓 서술 — 같은 거짓말이 네 곳에 있었다

§5.5.2 는 마운트 정책을 정했지만 **강제하는 코드는 쓰이지 않았다.** 그런데 네 곳이 그것을
**이미 된 것처럼** 적었다:

| 자리 | 적힌 것 | 실제 |
|---|---|---|
| `docs/5_5-project-isolation.md` §5.5.2 | *"마운트되지 않은 프로젝트 요청은 ③ 에 따라 409 로 거부된다"* | 거부하는 코드가 없다 |
| `PLAN.md` 5.5 행 | *"mismatched requests get 409, fail-closed"* | 같다 (2026-08-22 정정) |
| `paths.py:167` 독스트링 | *"§5.5.2 의 단일 마운트 정책을 **강제한다**"* | 프로덕션 호출자 0 |
| `logic.set_active` 반환 | *"가리키는 프로젝트가 다른 동안에는 이 프로젝트의 문서 갱신이 **멈춰 있었다**"* | 안 멈췄다 |

[중요] **왜 이게 최악인가.** 그 문서들은 매 세션 읽힌다. 2026-08-21 세션이 그것을 믿고 그 위에
구현을 얹었고, 그 구현은 전량 되돌려졌다(리포트 28). **덜 된 것을 됐다고 적으면, 읽은 사람이
없는 것을 있다고 믿고 결정한다** — 코드가 덜 된 것보다 이것이 비싸다.

[주의] **미룬 것 자체는 잘못이 아니다.** §5.5.5 의 미룸은 근거가 있었다. 잘못은 **미룬 사실을
적지 않은 것**이다. 미룸은 결정이고, 결정은 기록되어야 한다.

## 12.5 미결 — 사람이 정할 것

1. **강제의 경계** — 「자동으로 도는 것(타이머·검색)은 활성만 / 사람이 이름을 대고 부르는 것
   (`rebuild <이름>`·`client … <프로젝트>`·`integrate`)은 그 프로젝트」를 규약으로 확정할지.
   [주의] 2026-08-21 의 신규 프로젝트 온보딩은 **후자에 전적으로 의존했다.**
2. **한 기계가 여러 프로젝트를 맡는 것을 허용할지** — §5.5.2 는 마스터 규약이고 워커 쪽은
   빈칸이다. 불허로 정하면 #229 가 훨씬 작아진다.
3. **`mcp.json` 을 마스터가 생성할지** — `.ax/config.json` 과 같은 방식(probe 실측 → 생성 →
   되읽어 대조)이면 프로젝트 귀속과 기계 귀속이 한 번에 풀린다. 사람이 손으로 넣은 항목
   보존 계약은 `merge_mcp_json` 이 이미 갖고 있다.
4. **원전 exe 6종** — 이식 / 로컬 유지 + **설치 절차** / 폐기. 「로컬 유지」로 정해도 새 기계에
   놓는 절차가 필요하다.
5. **claim 의 빈 `project` 값** — fail-closed 인가 활성 폴백인가.

## 12.6 여기서 배운 것 — 완료 조건을 쓰는 법

레드마인 소분류의 완료 조건을 **「무엇이 없으면 미완인가」**로 적는다.

    나쁨   "mcp.json 을 생성한다"
    좋음   "`plan` 출력에 `.mcp.json` 이 배달 항목으로 나타나고 `check` 가 해시로 잰다.
            `plan` 에 안 보이면 미완이다"

근거는 이 저장소의 실측이다 — 유닛 3,720건이 통과하는 동안 결함 10건이 살아 있었고
(*"Injection tests contracts, not reality"*), 「완료」 표시와 실물이 어긋난 사례가
원전 σ 감사가 만들어진 계기였다. **검증 가능한 사실 하나로 적으면 거짓 보고가 구조적으로
불가능해진다.**
