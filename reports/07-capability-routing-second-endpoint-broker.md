# 1. 능력 기반 라우팅 (`requires` / `capabilities`) — `d2beae2`

리포트 06 의 "다음 세션에서 바로 집을 것" 1순위. 큐가 `job_kind`(write/verify) 로만 갈라져
**마스터 워커가 UE5 잡을 집어갈 수 있던** 구멍을 막았다. §5.2-C 의 CI 러너 패턴 선결 항목.

## 1.1 계약

| 축 | 값 |
|---|---|
| task 쪽 | `POST /api/v1/tasks` 의 `requires: ["ue5"]` (빈값 = 아무나) |
| 워커 쪽 | `POST /api/v1/tasks/claim` 의 `capabilities: ["ue5"]` — **미신고 = 능력 없음** |
| 매칭 | `requires ⊆ capabilities`, **fail-closed** |
| 허용 태그 | `ue5`(에디터+빌드 툴체인) · `windows`. 화이트리스트 |
| 적용 범위 | write 잡 + **verify 잡 양쪽** |

## 1.2 설계 판단 3가지

**(가) 미지 태그를 등록 시점에 거부한다.** claim 이 fail-closed 라서, 오타 하나(`ue-5`)면
**아무 워커도 만족시킬 수 없는 task** 가 조용히 pending 에 굶는다. 조용한 기아보다 등록 실패(400)가 낫다.
`_VALID_DIRECTIVES` 화이트리스트가 이미 있던 패턴이라 거기 맞췄다.

**(나) verify 잡도 능력으로 거른다.** 검증 워커는 판정하려면 그 task 의 브랜치·diff 를 쥐어야
하고, 그건 파일을 소유한 작업장뿐이다(§2.1). 안 거르면 마스터가 UE5 task 의 verify lease 를
점유한 채 아무것도 못 하고 lease 만 태운다. 걸러서 검증자가 없으면 **backlog 카나리가 시끄럽게
알린다** — 조용한 오배정보다 낫다.

**(다) 능력 미달은 skip 이지 중단이 아니다.** 큐 앞을 막으면 안 된다. quota 차단과 달리
**시간이 지나도 안 풀린다** — 능력은 기계의 속성이기 때문이다.

## 1.3 실서비스 실측

| 단계 | 결과 |
|---|---|
| `requires:["ue-5"]` 등록 | ✅ `400 unknown requires: ue-5 (allowed: ue5,windows)` |
| 마스터 워커(능력 미신고) claim | ✅ **우선순위 10 인 `ue5` 잡을 건너뛰고 우선순위 1 인 일반잡**을 집음 |
| 마스터 워커 재시도 | ✅ `204` — 남은 `ue5` 잡을 못 집음 |
| `capabilities:["ue5"]` 워커 | ✅ 그 잡을 집음 |
| `/admin/workers` | ✅ `capabilities` 노출 |
| 로그 | ✅ `[claim] master-worker 능력 미달로 1건 skip (보유=-)` |

테스트 16건 신규. 테스트용 work 는 `admin/reset` 으로 아카이브 처리해 큐를 원상 복구했다.

# 2. 🔴 2번째 추론 엔드포인트 확보 — **보드가 아니라 RTX 3060 이었다**

## 2.1 발단

사용자 질문: *"윈도우 PC도 클러스터링 노드에 추가할 수 있을까?"*
그때까지 §9.4.2(35B=드라이버 / 14b=코드생성기)는 **왕복 전환 ~100초** 때문에 보류였고,
해제 조건이 "BC-250 #2 를 추론 노드로 전환" = **게임 머신을 내주는 자원 배분 결정**이었다.

## 2.2 장비 확정 (사용자만 아는 사실 — 물어서 얻었다)

| PC | GPU | 용도 |
|---|---|---|
| 메인 작업 PC | **RTX 3080 10GB** (Galax EX Gamer, LHR) | 에디터 포함 주력 UE5 작업 |
| 보조 PC | **RTX 3060 12GB** (Colorful iGame Ultra OC) | 리눅스 원격 확인 + **UE5 빌드 멀티 테스트(에디터는 거의 안 띄움)** |

> ⚠️ 사용자가 처음에 "3070"이라 했다가 실제 확인 후 3080 으로 정정됐다. 리포트 06 의 교훈
> ("장비 현황은 계획서에 추론으로 채우지 말고 먼저 물어라")이 또 적용됐다.
> **"마스터"라는 말도 두 번 엇갈렸다** — 사용자는 *메인 작업 PC* 라는 뜻으로 썼고,
> 문서상 마스터는 리눅스 박스다. 이후로는 **"리눅스 마스터" / "메인 작업 PC"** 로 항상 구분해 쓰기로 했다.

## 2.3 용량이 배치를 결정한다 — 속도가 아니라

실측 모델 크기: `qwen2.5-coder:14b` **8.37 GiB** · `35B-A3B IQ2_M` **12.91 GiB**

| | 가용 | 14b | 35B |
|---|---|---|---|
| BC-250 | ~15.6 GiB (통합 메모리) | ✅ | ✅ **유일하게 담을 수 있다** |
| RTX 3060 | 12 GB − 데스크톱 ~2GB = **~10GB** | ✅ | ❌ |
| RTX 3080 | 10 GB − 데스크톱 ~2GB = **~8GB** | ❌ | ❌ |

**→ 35B 를 담을 수 있는 기계가 BC-250 뿐이라 역할이 저절로 갈린다.**
BC-250 = 에이전틱 드라이버(tool-calling 4/4 통과 유일) / 3060 = 코드 본문 생성기.

## 2.4 접속 확보

윈도우 PC 쪽 Claude Code 세션이 OpenSSH Server 설치 + `administrators_authorized_keys` +
ACL 잠금 + 방화벽 규칙을 처리했고, 마스터의 기존 공개키(BC-250 과 같은 키)를 등록했다.
**Ollama 11434 는 `192.168.0.57` 출발지 한정** — BC-250 firewalld 와 같은 형태다.

접속 후 마스터에서 직접 `ollama pull qwen2.5-coder:14b` 실행. `nvidia-smi` 로
**RTX 3060 12288 MiB 확정**(12GB 변형 여부가 전체 판단을 뒤집는 유일한 변수였다).

## 2.5 성능 실측 — 동일 프롬프트 · `temperature:0` · `num_ctx:8192`

| | 냉시작(wall) | 적재 | **상주 생성** | 오프로드 |
|---|---|---|---|---|
| BC-250 `14b` | 47.1s | 37.9s | **25.2 t/s** | 100% |
| RTX 3060 `14b` | 33.8s | 12.8s | **31.1~33.0 t/s** | 100% |

**3060 이 같은 모델을 ~23% 빠르게 돌린다.**

# 5. 마스터 브로커 — `c20034d` · `b7e1ae7`

엔드포인트가 둘이 되면서 §4 의 "마스터 브로커"가 실제로 필요해졌다.
작업자에게 **클러스터가 Ollama 하나로** 보이게 한다. gjc 가 부르는 표면은 3종뿐이라 작다.

| 파일 | 역할 |
|---|---|
| `routing.py` | 결정 로직(순수) — **상주 > prefer > 폴백** |
| `health.py` | `/api/tags`·`/api/ps` 갱신 + **상주 재확립** |
| `server.py` | 프록시(스트리밍 통과) + fail-closed 라우팅 |
| `config.py` | 실측 확정 배치. `AX_BROKER_CONFIG` 로 교체(없으면 즉시 실패 — 폴백 없음) |

결정 로직을 HTTP 에서 **분리한 이유**: 노드 없이 테스트되어야 하기 때문이다.
`/api/tags` 는 합집합, 보유하지 않은 모델은 **추측해서 보내지 않는다**(그쪽에서 pull 이 터진다).

## 5.1 🔴 실측으로 잡은 버그 2건 — 둘 다 브로커가 원인이었다

**(1) 브로커를 거치면 상주가 풀렸다.** 프록시 요청에 `keep_alive` 가 없으면 Ollama 가
**노드 기본값으로 덮어쓴다.** BC-250 유닛이 `KEEP_ALIVE=30m` 이라, 요청 하나 흘려보낸 것만으로
영구 상주(2318년)가 **시한부(11:43 만료)로 풀렸다.**
→ 그 노드의 pin 모델이면 `-1` 을 주입한다. **호출자가 명시했으면 존중한다**(일시 사용은 그쪽 의도).

**(2) `num_ctx` 가 요청마다 다르면 모델을 통째로 다시 올린다** — 같은 35B 인데 `num_ctx` 만
바뀌어 **61.6초** 재적재가 걸렸다. → 미지정 시 `AX_BROKER_NUM_CTX`(8192) 주입.

| 왕복 2회 | |
|---|---|
| 수정 전 | **74.1s** |
| 수정 후 | **7.0s** |
| 직접 호출 | 7.2s |

**브로커 오버헤드가 사실상 0이다.**

## 5.2 상주 재확립의 안전장치

**in-flight 요청이 있으면 재확립하지 않는다.** `MAX_LOADED_MODELS=1` 이라 다른 모델을 올리는
것은 **지금 쓰이는 모델을 쫓아내는 것**이고, 폴백으로 14b 를 쓰는 중에 35B 를 복구하려 들면
그 요청이 죽는다. 실패 시 5분 백오프(적재가 비싸다).
`/api/show` 는 추론 호출이 아니라 메타 조회라 주입 대상에서 제외했다.

## 5.3 가동 실측

`enabled`/`active` · 샌드박스(`ProtectSystem=strict`, **`ReadWritePaths` 없음** — 브로커는
파일을 안 쓴다) 하에서 정상 · **BC-250 에서 LAN 도달 200** · `kill -9` 후 `Restart=always`
재기동(`NRestarts=1`) 확인. `ufw` 8102 는 `192.168.0.0/24` 한정 —
🔴 **task_queue 와 마찬가지로 인증 계층이 없다. 방화벽이 유일한 방어선이다.**

# 7. RAG 이식(2단계) 사전 조사 — **계획서 판정이 틀렸다**

리포트 06 은 *"`sys.platform` 분기 0건이라 1단계보다 가볍다"* 고 적었다. 분기가 0건인 건
맞지만 **그게 작업량 근거가 못 된다.**

| | task_queue (1단계) | context_search (2단계) |
|---|---|---|
| 규모 | 2,717줄 / 9파일 | **14,401줄 / 40파일 (5.3배)** |

1단계에서 배운 것이 *"진짜 작업은 플랫폼이 아니라 전제를 바꾸는 데 있다"* 였는데,
2단계 판정을 **다시 플랫폼 분기 수로 내렸다.** 같은 실수다.

**확정된 사실 4가지:**

1. **인덱스 이관은 논점이 아니다.** 이 클론의 `.claude/vector_db` 는 188K, 색인 대상
   `.claude/context/` 는 **파일 0개**다. 실물은 윈도우의 UE5 프로젝트 안에 있고,
   마스터는 **새로 색인**하는 것이 맞다.
2. **임베딩에 BC-250 이 필요 없다.** `get_or_create_collection` 에 `embedding_function` 이
   없어 ChromaDB **기본 임베딩(CPU/ONNX)** 을 쓴다.
3. **같은 "전제" 문제 재발** — `_get_chroma_client()` 가 `project_root/.claude/vector_db` 로
   역산한다. task_queue 2번 문제와 동일 → `AX_*_ROOT` 명시 방식으로 통일하면 된다.
4. `llm_chat.py` 가 `%LOCALAPPDATA%\agy\bin\agy.exe` 를 프로브 — 리눅스 경로 분기 필요.

⬜ **미결: 이식 범위.** 40파일에 RAG 검색·온톨로지·웹 UI 가 섞여 있고, 명백한 웹 UI 3파일만
1,614줄이다. §5.2-D 가 *"착수 전 개별 판단, 일괄 폐기 금지"* 라 **범위를 정하기 전엔 코드를
건드리지 않는다.** 제안은 **검색 코어 먼저**(`search_*`+`*_index*`), 온톨로지는 별건 설계.
