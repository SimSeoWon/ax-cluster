## 6. 추론 노드 장애 감지·페일오버 (2026-08-06)

### 6.1 기존 하트비트로는 안 덮인다

AgentTest 에 이미 하트비트/lease 회수가 있다 — `worker/heartbeat.py`(directive `pause`/`resume`/
`drain`/`abort` 수신, `lease_lost` 시 진행 중 LLM kill) + `task_queue/reclaim.py`(`_reclaim_loop` 가
lease cutoff 로 회수, `_verify_loop` 가 stuck alert). **단 이건 작업자(윈도우) 계층이다.**

BC-250 은 task_queue 에 claim 하지 않는 **HTTP 추론 엔드포인트**라 하트비트를 보낼 주체가 아니다.
노드가 행 걸리면:

1. 마스터의 HTTP 요청이 응답 없이 매달림
2. 작업자는 **멀쩡히 살아서** 마스터 응답 대기 → **하트비트는 계속 정상 전송**
3. 따라서 lease 가 만료되지 않아 **회수 로직이 안 뜬다**
4. 태스크는 조용히 멈추고, `_verify_loop` 의 stuck alert 가 임계 시간 뒤에나 알림

즉 기존 메커니즘은 "작업자 죽음"을 잡지 **"추론 노드 죽음"을 못 잡는다.**

### 6.2 설계 — 스트리밍이 곧 하트비트

```
마스터 ──assign──▶ 노드 #1
                    │ stream:true 로 토큰 청크가 계속 흘러나옴 = 살아있다는 신호
                    ▼
마스터 ── 청크 간격 감시 ── 임계 초과 ──▶ 연결 끊고 노드 #N 으로 재할당
```

**별도 통신 인프라를 만들지 않는다.** Ollama `"stream": true` 의 토큰 청크가 그대로 생존 신호가 된다
— **작업 산출물 자체가 하트비트**다. 노드에 에이전트 코드를 심을 필요가 없어
"노드는 상태도 코드도 갖지 않는다"는 원칙과 [[feedback_no_communication_infra_creep]] 을 함께 지킨다.

### 6.3 임계값 — 실측 기반 (2026-08-06, `qwen2.5-coder:14b`)

`~/claude-workspace/bench_stream_gap.py` 로 측정. **두 구간을 반드시 분리해야 한다.**

| 구간 | 실측 | 임계값 제안 |
|---|---|---|
| 생성 중 청크 간격 | p50 **38.7ms** / p95 47.2ms / p99 51.0ms / 최대 51.1ms | **2s** (관측 최대의 ~40배) |
| 첫 청크까지 (웜, 모델 적재됨) | **1.07s** | — |
| 첫 청크까지 (콜드 로드) | **36.4s** (14B 최초 적재) | **120s 이상** |
| 첫 청크까지 (긴 프롬프트 prefill) | **38.1s** (2.5k 토큰 상당) | (위에 합산) |

**[주의] 임계값 하나로 뭉뚱그리면 정상 동작을 죽음으로 오판한다.** 콜드 로드(36s) + 긴 prefill(38s) 가
겹치면 첫 청크까지 **70초 이상**이 정상이다. 반면 일단 생성이 시작되면 간격이 40ms 수준으로
매우 규칙적이라, 생성 중 2초 무응답은 명백한 이상이다.

### 6.4 Python 추론 클라이언트 래퍼 — `master/` 에 둔다

Ollama 를 그대로 호출하지 않고 **얇은 Python 래퍼를 거친다.** 감시·검증·재시도를 걸 지점이 필요하다.

**위치는 마스터 측**이다(노드 측 아님). 근거: ① 노드를 일회용으로 유지해야 재구축이 쉽다
② 검증에 필요한 태스크 컨텍스트(동결 선언·매니페스트)가 마스터에 있다 ③ 노드 간 페일오버는
본질적으로 마스터의 책임이다.

**책임**

| 구분 | 내용 |
|---|---|
| 생존 감시 | 스트리밍 청크 간격 감시(§6.3 2구간 임계), 초과 시 연결 종료 + 재할당 |
| 노드 상태 | 주기적 헬스 프로브(`/api/tags`) → 죽은 노드로 라우팅 중단. `watcher/common_utils.py` 의 `local_llm_health_check_one_shot`(`ollama_down` 판별) 재사용 |
| 요청 정규화 | `"think": false` 주입(35B 필수), `num_predict`·`temperature` 정책, 타임아웃 |
| 응답 후처리 | 마크다운 펜스 제거, `[PSEUDO]` 잔재 검사 |
| 사전 검증 | 동결 인터페이스 위반 검사 — 실 파이프라인의 `worker/validator._frozen_interface_violation` 과 동일 규칙을 여기서도 1차 적용해 왕복 낭비 차단 |
| 라우팅 | 모델↔노드 고정 배정(§4.4) 반영, 모델 전환 비용(왕복 ≈100초) 회피 |
| 계측 | 토큰 수·tok/s·첫 청크 지연 기록 → 임계값 재조정 근거 |

### 6.5 한계 — 이것으로 해결되지 않는 것

- **재할당할 곳이 있어야 한다.** BC-250 #2 가 없으면 감지는 되지만 페일오버는 불가능하다.
- ~~**노드는 스스로 회복하지 못한다.**~~ → **해결됨 2026-08-07** (§6.6). GPU 크래시 = 호스트 하드 행이라는
  사실은 그대로지만, 스마트 콘센트로 **원격 전원 재투입 경로가 확보**됐다.
- **좀비 응답**: 늦게 살아난 노드가 응답을 보내도 마스터가 이미 재할당했으면 무시하면 된다.
  stateless HTTP 라 git push 하는 좀비 워커(C.2)만큼 위험하지 않아 epoch fencing 까지는 불필요하다.
- **빈도는 여전히 미지수.** 장시간 안정성 검증(§3) 이 선행되어야 한다. 주 1회면 스마트 플러그로 충분하고,
  하루 여러 번이면 이 보드를 무인 루프에 넣는 것 자체를 재고해야 한다.

### 6.6 원격 전원 제어 — 확보 완료 (2026-08-07)

**양방향 모두 원격으로 가능해졌다.** §6.5 가 남긴 최대 공백이 메워졌다.

| 방향 | 수단 | 실증 |
|---|---|---|
| **끄기 (정상)** | `ssh sim@192.168.0.43 'sudo -n systemctl poweroff'` | [완료] 비밀번호 없이 동작 |
| **끄기 (행 걸렸을 때)** | 스마트 콘센트 차단 | [완료] (더티 종료이나 크래시 상황엔 불가피) |
| **켜기** | 스마트 콘센트 재공급 → **자동 부팅** | [완료] BIOS `Restore on AC Power Loss`=`Power On` |

**비밀번호 없는 종료가 되는 이유** — `/etc/sudoers.d/bc250-power` 에 전원·ollama 명령 6개만
NOPASSWD 등록(2026-08-07). 헤드리스라 polkit 인증 에이전트가 존재할 수 없어 `systemctl poweroff` 가
`Access denied`, `sudo` 는 비밀번호를 요구해 원격 자동화가 원천 차단돼 있던 것을 푼 것이다.
설치·검증 절차와 마스터(`pkexec` 가능)와의 차이는 마스터 리포트 03 참조.

**콜드 부팅 후 자동 복구 확인 (실측)**

| 항목 | 결과 |
|---|---|
| SSH 응답까지 | 전원 재공급 후 **약 30초** |
| TTM `pages_limit` | 3959290 유지 — `systemd-tmpfiles` 되돌림 함정 **3회 연속 미발생** |
| 시스템 RAM | 15,198 MB |
| `ollama` · `governor` · `cu-live-manager` · `cpu-core-unlock` | 전부 active |
| `bc250-smu-oc` | `inactive` 이나 **정상** — 부팅 시 `3500 MHz @ Scale -31` 적용 후 종료하는 유닛 |
| Ollama 모델 3종 | 마스터에서 `/api/tags` 정상 응답 |
| 커널 오류 | amdgpu hpd 24건 — **직전 2회 부팅과 동일 건수**, 디스플레이 없는 보드의 핫플러그 감지 오류로 무해 |

**즉 전원만 넣으면 사람 개입 없이 추론 노드로 복귀한다.** 무인 루프의 전제 하나가 충족됐다.

**남은 것**: 크래시 자동 감지 → 자동 전원 재투입까지의 배선. 지금은 사람이 콘센트를 조작해야 한다.
마스터의 추론 래퍼(§6.4)가 노드 사망을 판정하므로, 그 지점에서 스마트 콘센트 API 를 호출하면 닫힌다.
[주의] **자동 전원 차단은 신중할 것** — 살아 있는 노드를 오판해 끊으면 더티 종료가 된다.
§6.3 의 임계값(첫 청크 120s+)이 콜드 로드·긴 prefill 을 정상으로 인정하도록 되어 있는지 먼저 확인해야 한다.

### 6.7 [중요] 실제 사망 1건 — 감지는 됐고, **브로커가 회복을 시도하다 악화시켰다** (2026-08-15)

§6.5 의 *"빈도는 미지수"* 에 첫 데이터가 생겼다. 온톨로지 배치 중 BC-250 이 죽었다:

    03:04  OOM 킬러 · 03:11 저널 정지 · 03:22 **보드 자체 재부팅** · 이후 SSH 배너 정지 ~10분
    감지    [완료] 브로커가 unhealthy 로 내리고 그 모델 요청을 503 으로 거절했다 (설계대로)
    페일오버 [실패] 불가 — 35B 는 그 보드에만 있다. **모델 이름이 노드를 고르는 구조의 대가**다

**두 가지가 회복을 방해했다** (둘 다 2026-08-15 에 고쳤다 — `master/broker/health.py`):

| | 있던 일 | 고친 것 |
|---|---|---|
| 워밍업 `num_ctx` 누락 | repin 이 **4096** 으로 올리고 우리 요청은 8192 → **매번 전체 재적재 59.6초** | 프록시와 **같은 값**을 싣는다 |
| 「상주 없음」 ↔ 「못 읽었다」 혼동 | `/api/ps` 실패도 `resident=None` → 힘들어하는 노드에 **35B 적재**를 걸었다 | `resident_known` — [중요] **판정 불가는 보존** |

[주의] **자동 전원 차단(§6.6)을 붙일 때 이 사례를 기준으로 삼을 것** — 이 보드는 **핑도 TCP accept 도
정상인데 유저스페이스만 멈춘** 상태로 10분 이상 있었다. 「무응답」 판정을 핑·포트로 하면 못 잡고,
반대로 성급히 끊으면 이번처럼 **스스로 재부팅해 살아나는** 경우를 죽인다.

[중요] **그리고 §6.5 의 마지막 줄이 실제 질문이 됐다** — 원인이 특별한 사고가 아니라 **평소 부하가
한계선**(여유 138~300MB)이라, *"이 보드를 무인 루프에 넣을 것인가"* 는 이제 미룰 수 없다.
